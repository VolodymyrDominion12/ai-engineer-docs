## 5. OpenAI API та сумісні провайдери

OpenAI API — другий за важливістю SDK після Anthropic (розділ 4), і єдина екосистема, чий **формат
запиту став міжгалузевим стандартом**: Gemini, Mistral і DeepSeek приймають той самий JSON, що й
`/v1/chat/completions`. Тому рішення про інтеграцію тут має подвійну ціну: ви обираєте не лише
провайдера, а й формат, до якого прив'яжете весь код.

Центральний факт розділу: generation-ендпоінтів **три**, і підтримка в них різна. `/v1/completions`
отримав останнє оновлення в липні 2023 року; `/v1/chat/completions` досі підтримується, але
документація прямо радить Responses для всіх нових проєктів; `/v1/responses` — новий примітив,
навколо якого будуються агентні можливості. Решта розділу — наслідки цього вибору: чому `messages`
відрізняється від `items`, чому `429` буває шести видів і лише два з них лікуються ретраєм, і як
той самий JSON-формат працює проти вас, коли провайдер приймає його частково.

Ліміти, коди помилок і ціни взяті з документації OpenAI, Google, Mistral і DeepSeek; там, де
наведено вивід, код реально виконано. Назви моделей у прикладах узяті зі сторінки цін і changelog
на 26.09.2026.

### 5.1 Екосистема OpenAI: chat/completions vs responses

**Що це.** Два способи попросити модель щось згенерувати, з різними одиницями контенту:

| | Chat Completions | Responses |
|---|---|---|
| Ендпоінт | `POST /v1/chat/completions` | `POST /v1/responses` |
| Одиниця входу | `messages` — масив повідомлень із `role`/`content` | `input` — рядок **або** масив *items* |
| Системна інструкція | `messages[0]` з `role: "system"` | окреме поле `instructions` |
| Межа виходу | `max_tokens` | `max_output_tokens` |
| Читання тексту | `completion.choices[0].message.content` | `response.output_text` |
| Кілька генерацій | `n` → `choices[]` | прибрано, одна генерація |
| Стан між ходами | лише вручну, надсилаючи всю історію | `store: true` + `previous_response_id` |
| Вбудовані інструменти | немає | web search, file search, computer use, code interpreter, remote MCP |
| Статус | підтримується | рекомендовано для нових проєктів |

`items` — не перейменовані `messages`. Це ширший тип: об'єднання повідомлень, викликів функцій
(`function_call`), їхніх результатів (`function_call_output`) та інших дій моделі. У Chat Completions
усе це склеєно в один об'єкт `message`; у Responses кожна дія — окремий елемент масиву.

**Навіщо це знати.** Три практичні наслідки.

Перший: **формат визначає архітектуру стану**. Chat Completions stateless за побудовою — сервер не
пам'ятає нічого, ви щохода надсилаєте всю розмову. Responses може бути stateful: `store: true`
зберігає хід на боці OpenAI, і наступний запит посилається на нього через `previous_response_id`.
Це не косметика — це різні профілі витрат. У stateful-режимі ви не платите за повторне надсилання
історії, але втрачаєте контроль над тим, де вона лежить.

Другий: **деякі можливості існують лише в Responses**. Вбудовані інструменти (web search, code
interpreter, remote MCP) і збереження зашифрованих reasoning-блоків між ходами доступні тільки там.
Якщо ваш продукт — агент, а не чат, Chat Completions змусить вас відтворювати ці цикли вручну
(розділ 12).

Третій: **сумісні провайдери реалізують саме Chat Completions**. Gemini, Mistral і DeepSeek надають
OpenAI-сумісний `/chat/completions`; Responses-формат підтримується нерівномірно (DeepSeek заявляє
підтримку Responses API, Gemini — ні). Вибір Responses звужує множину провайдерів, до яких ви
зможете перемкнутися без переписування коду.

**Як працює під капотом.**

#### Чому Responses дає інший результат на тих самих промптах

Документація міграції наводить три конкретні твердження, які варто читати як гіпотези для перевірки
на своїй задачі, а не як гарантії:

| Твердження документації | Заявлена величина |
|---|---|
| Кращий результат reasoning-моделей на Responses проти Chat Completions | +3% на SWE-bench за того самого промпту й setup |
| Дешевше за рахунок кращого використання кешу | покращення 40–80% у внутрішніх тестах |
| Responses — «агентний за замовчуванням» | кілька викликів інструментів у межах **одного** запиту |

Механізм другої лінійки — у порядку контенту. Кеш працює за префіксом (розділ 9), а Responses
формує стабільніший префікс: `instructions` відокремлені від діалогу, а items не перепаковуються
щохода. У Chat Completions додавання системного повідомлення в `messages[0]` з подальшою правкою
будь-якого поля зсуває префікс і скидає кеш.

#### Стан розмови: три режими

| Режим | Як виглядає код | Що зберігається | Ціна |
|---|---|---|---|
| Stateless (як у Chat Completions) | щохода надсилаєте весь масив `input` | нічого на сервері | повний вхід щохода |
| `previous_response_id` | `store: true` + посилання на попередній `id` | хід на боці OpenAI | менший вхід, потрібен `store` |
| Conversations API | `client.conversations.create()` — довготривалий об'єкт | items у контейнері розмови | як `previous_response_id`, плюс явний ID |

`previous_response_id` несумісний із параметром `conversation` — документація це зазначає прямо.
Вибір один із двох.

#### Стрімінг: семантичні події проти дельт

У Chat Completions стрім — це повторюваний об'єкт `chat.completion.chunk`, де кожен чанк має
`choices[]` із `delta`. У Responses — **типізовані події**: кожна має поле `type`, і SDK віддає
різні класи.

| Подія Responses | Коли приходить |
|---|---|
| `response.created` | один раз, на старті |
| `response.output_text.delta` | багато разів, шматки тексту |
| `response.function_call_arguments.delta` | багато разів, аргументи виклику інструмента |
| `response.completed` | один раз, успішне завершення |
| `error` | збій посеред потоку |

Практична різниця: у Responses ви фільтруєте за `event.type`, а не збираєте `choices[0].delta.content`
із кожного чанка. Це прибирає цілий клас помилок, коли чанк приходить порожній (наприклад,
останній чанк при `stream_options: {"include_usage": true}` у Chat Completions має порожній `choices`).

#### Що робить strict mode з вашою схемою

Це стосується обох API, але типово різниться. У Responses запит **намагається нормалізувати** вашу
схему в strict-режим, а якщо не вдається — тихо відкочується до best-effort, і в об'єкті tool
з'явиться `strict: false`. У Chat Completions strict вимкнений за замовчуванням. Наслідок: та сама
схема інструмента може бути жорсткою в одному API й м'якою в іншому. Щоб дізнатися, що сталося,
перевіряйте `strict` у відповіді, а не припускайте.

**Приклад.** Форма запиту й те, що змінюється між API. Це побудова словників, а не виклик мережі —
вивід відтворюється локально:

```python
import json

chat_payload = {
    "model": "gpt-6-astra",
    "messages": [
        {"role": "system", "content": "Ти помічник."},
        {"role": "user", "content": "Столиця України?"},
    ],
    "max_tokens": 64,
}
resp_payload = {
    "model": "gpt-6-astra",
    "instructions": "Ти помічник.",
    "input": "Столиця України?",
    "max_output_tokens": 64,
}

print("CHAT KEYS :", sorted(chat_payload))
print("RESP KEYS :", sorted(resp_payload))
print("лише в chat:", sorted(set(chat_payload) - set(resp_payload)))
print("лише в resp:", sorted(set(resp_payload) - set(chat_payload)))

chat_followup = {"model": "gpt-6-astra",
                 "messages": [{"role": "user", "content": "А населення?"}]}
resp_followup = {"model": "gpt-6-astra",
                 "previous_response_id": "resp_abc123",
                 "input": "А населення?"}
print()
print("chat, 2-й хід:", json.dumps(chat_followup, ensure_ascii=False))
print("resp, 2-й хід:", json.dumps(resp_followup, ensure_ascii=False))
```

Фактичний вивід:

```
CHAT KEYS : ['max_tokens', 'messages', 'model']
RESP KEYS : ['input', 'instructions', 'max_output_tokens', 'model']
лише в chat: ['max_tokens', 'messages']
лише в resp: ['input', 'instructions', 'max_output_tokens']

chat, 2-й хід: {"model": "gpt-6-astra", "messages": [{"role": "user", "content": "А населення?"}]}
resp, 2-й хід: {"model": "gpt-6-astra", "previous_response_id": "resp_abc123", "input": "А населення?"}
```

Різниця у другому рядку й показує суть: chat-версія не знає про перший хід узагалі — щоб модель
пам'ятала, ви мусите дописати в `messages` і свій промпт, і відповідь асистента. Responses-версія
посилається на збережений хід одним рядком.

Реальні виклики обох API (потрібен `OPENAI_API_KEY`) виглядають так; блок позначено як такий, що
без ключа не виконується:

```python
from openai import OpenAI  # схема: потрібен OPENAI_API_KEY

client = OpenAI()

# Chat Completions — вручну керуємо історією
chat = client.chat.completions.create(
    model="gpt-6-astra",
    messages=[{"role": "user", "content": "Столиця України?"}],
)
print(chat.choices[0].message.content)

# Responses — сервер тримає хід, ми лише посилаємось на нього
first = client.responses.create(model="gpt-6-astra", input="Столиця України?", store=True)
second = client.responses.create(
    model="gpt-6-astra",
    previous_response_id=first.id,
    input="А населення?",
)
print(second.output_text)
```

**Типові помилки**

- Переносити `messages` у Responses і передавати `role: "system"` усередині `input`. Системні
  інструкції там живуть в окремому полі `instructions`; при використанні разом із
  `previous_response_id` інструкції з попереднього запиту **не переносяться** автоматично.
- Чекати `choices` від Responses. Читання `response.choices[0]` дає `AttributeError`; текст —
  це `output_text`, а повний структурований результат — `output`.
- Вважати, що `store: true` — безкоштовне зручність. Це змінює модель даних: хід лежить на сервері,
  і політика зберігання стає частиною вашого комплаєнсу, а не деталлю реалізації.
- Ставити `strict: true` на схему, яка не відповідає вимогам (див. 5.4 про `anyOf` у корені й
  `additionalProperties`). У Responses такий запит може не впасти, а тихо перейти в best-effort — і
  ви шукатимете причину невалідного JSON не там.
- Будувати стрімінг на `choices[0].delta.content` для Responses. Там `delta` живе в події
  `response.output_text.delta`.

**Альтернативи**

| Ситуація | Що вибрати | Чому |
|---|---|---|
| Новий проєкт, агент, вбудовані інструменти | Responses | Єдиний API з web search, code interpreter, MCP |
| Потрібна сумісність із Gemini/Mistral/локальними серверами | Chat Completions | Це формат, який вони реалізують |
| Довга розмова, контроль над історією | Chat Completions або Responses без `store` | Ви самі вирішуєте, що надсилати |
| Довга розмова, економія на вході | Responses + `previous_response_id` | Не платите за пересилання історії |
| Потрібен один формат для кількох провайдерів | Власна абстракція над Chat Completions | Розділ 25 про сервінг і шари абстракції |
| Інша екосистема повністю | Anthropic Messages | Розділ 4: інша модель стану, інші типи помилок |

### 5.2 Читання changelog як робочий процес

**Що це.** Changelog OpenAI — це Markdown-файл за адресою
`https://developers.openai.com/api/docs/changelog.md`, який веде список змін API з жовтня 2023 року.
Він не є ні пресрелізом, ні довідником: це **структурований журнал із машинно-читабельним каркасом**,
і саме тому його варто не читати оком, а парсити.

**Навіщо це знати.** Три причини, кожна з конкретною ціною помилки.

Перша: **changelog — єдиний документ, який попереджає про ламальні зміни завчасно**. Сторінка
deprecations дає строки виведення, але анонс з'являється саме тут. Пропустити анонс означає
дізнатися про виведення моделі з `404 model_not_found` у продакшні.

Друга: **теги `API:` показують, куди рухається платформа**. Порахувавши згадки ендпоінтів у
changelog, ви бачите розподіл інвестицій без жодного пресрелізу: `v1/responses` згадується
47 разів, `v1/chat/completions` — 32, `v1/realtime` — 13. Це і є відповідь на питання «що обрати»
з 5.1, отримана з первинного джерела, а не з думки в блозі.

Третя: **оновлення SDK і оновлення API — різні події**. Changelog описує API; версію Python-бібліотеки
треба брати окремо (див. приклад із PyPI нижче). Плутанина між ними дає класичну помилку: оновити
`pip install openai` і вирішити, що ви дізналися про зміни API.

**Як працює під капотом.**

#### Каркас документа

Формат жорсткий і повторюваний, що й робить парсинг тривіальним:

| Рівень | Шаблон | Приклад |
|---|---|---|
| Місяць | `## <Month>, <YYYY>` | `## September, 2026` |
| День | `### <Mon> <D>` | `### Sep 15` |
| Тип події | `Feature` / `Update` / `Announcement` | `Feature` |
| Теги (опційно) | ` · Model: <id> · API: <path>` | `Feature · API: v1/responses` |
| Тіло | абзац Markdown, часто з посиланнями | текст із посиланням на guide |

Теги розділені символом `·` (U+00B7) — не дефісом і не комою. Це важливо, бо від нього залежить
регулярка.

#### Строки повідомлення про виведення

Строки взяті зі сторінки deprecations і визначають, скільки часу у вас є:

| Тип моделі | Мінімальний строк попередження | Приклади з документації |
|---|---|---|
| Загальнодоступна (GA) | не менше **6 місяців** | — |
| Спеціалізований варіант GA-моделі | не менше **3 місяців** | `gpt-5.1-chat-latest`, `gpt-5.3-codex`, `o3-deep-research` |
| Preview (`preview` у назві) | може бути **2 тижні** | `computer-use-preview`, `gpt-4o-audio-preview` |

Документація формулює наслідок прямо: preview-моделі не рекомендовані для бізнес-критичних
навантажень, якщо ви не можете мігрувати за короткий строк. Це не застереження заради обережності —
це різниця в 6 місяців і 2 тижні, і вона має бути в архітектурному рішенні, а не в голові
розробника.

#### Термінологія: deprecation проти legacy

Документація розрізняє три стани, і плутати їх дорого:

| Стан | Що означає | Чи працює |
|---|---|---|
| **Legacy** | більше не оновлюється, але й не виведено | Так. Сигнал, що модель виведуть у майбутньому |
| **Deprecated** | анонсовано виведення, є дата | Так, до дати |
| **Sunset / shut down** | виведено | Ні, ендпоінт недоступний |

Практичний висновок: `legacy` — це не «можна ігнорувати», це «порахуйте бюджет часу на міграцію».

**Приклад.** Парсер changelog. Він будує ту саму статистику, яку неможливо отримати оком за
170 записів: розподіл за типами подій, найактивніші ендпоінти та приклад реального запису
з тегами.

```python
import collections
import pathlib
import re

CHANGELOG = pathlib.Path("research/11/openai_changelog.md")

MONTH_RE = re.compile(r"^## ([A-Z][a-z]+), (\d{4})$")
DAY_RE = re.compile(r"^### ([A-Z][a-z]{2}) (\d{1,2})$")
TAG_RE = re.compile(
    r"^(Feature|Update|Announcement|Changed|Bug fix|Deprecation)(?:\s+·\s+(.*))?$"
)


def parse_changelog(text):
    """Повертає список записів: місяць, день, тип, теги Model/API, тіло."""
    entries, month, current = [], None, None
    for line in text.splitlines():
        m = MONTH_RE.match(line)
        if m:
            month = f"{m.group(1)}, {m.group(2)}"
            continue
        d = DAY_RE.match(line)
        if d:
            current = {
                "month": month,
                "day": int(d.group(2)),
                "kind": None,
                "models": [],
                "apis": [],
                "body": [],
            }
            entries.append(current)
            continue
        if current is None:
            continue
        t = TAG_RE.match(line.strip())
        if t and current["kind"] is None:
            current["kind"] = t.group(1)
            for part in (t.group(2) or "").split(" · "):
                if part.startswith("Model: "):
                    current["models"].append(part[7:].strip())
                elif part.startswith("API: "):
                    current["apis"].append(part[5:].strip())
            continue
        current["body"].append(line)
    return entries


entries = parse_changelog(CHANGELOG.read_text(encoding="utf-8"))

print("усього записів:", len(entries), "| місяців:", len({e["month"] for e in entries}))
print("найновіший :", entries[0]["month"], entries[0]["day"])
print("найстаріший:", entries[-1]["month"], entries[-1]["day"])

kinds = collections.Counter(e["kind"] or "(без мітки)" for e in entries)
print("\nрозподіл за типом:")
for kind, n in kinds.most_common():
    print(f"  {kind:14} {n}")

apis = collections.Counter(a for e in entries for a in e["apis"])
print("\nнайчастіші API-теги:")
for api, n in apis.most_common(6):
    print(f"  {api:26} {n}")
```

```
  v1/images/generations      4
```

Два записи без мітки — не дефект парсера, а реальна особливість документа: у двох випадках після
заголовка дня одразу йде текст. Це саме та причина, чому наївна регулярка на кшталт
`^(Feature|Update)` без запасного варіанта мовчки пропускає дані.

`v1/responses` переважає `v1/chat/completions` приблизно 3:2 — але це показник напрямку інвестицій, а
не кількості функцій: changelog веде **нові** можливості, тож Chat Completions згадується там
переважно як «друга адреса» тієї самої функції.

#### Оновлення SDK — окремий трек

Версію Python-бібліотеки беруть із PyPI. Формат відповіді — JSON, у якому є поля `info` і `releases`:

```python
import json
import pathlib

raw = pathlib.Path("research/11/openai_sdk_pypi.json").read_text(encoding="utf-8")
# fetch.py додає рядок-заголовок "### SOURCE: ..." і порожній рядок перед тілом.
body = raw.split("\n\n", 1)[1]
meta = json.loads(body)

print("версія         :", meta["info"]["version"])
print("вимога Python  :", meta["info"]["requires_python"])
print("усього релізів :", len(meta["releases"]))

releases = meta["releases"]


def uploaded(version):
    files = releases[version]
    return files[0]["upload_time"] if files else ""


latest = sorted(releases, key=uploaded)[-4:]
for version in latest:
    print(f"  {version:8} {uploaded(version)}")
```

Фактичний вивід:

```
версія         : 3.19.2
вимога Python  : >=3.10
усього релізів : 432
  3.18.0   2026-09-22T18:26:29
  3.19.0   2026-09-23T00:08:45
  3.19.1   2026-09-23T19:16:36
  3.19.2   2026-09-24T00:06:05
```

Швидкість релізів SDK — частина робочого процесу: три мінорні версії за три дні означають, що
пінінг версії (а не `>=`) є вимогою відтворюваності, а не педантизмом.

#### Що робити з цією інформацією

| Крок | Дія | Інструмент |
|---|---|---|
| 1. Виявити | Раз на тиждень витягнути записи з тегами `Model:` і `API:`, які вас стосуються | Парсер вище, фільтр за своїм списком моделей |
| 2. Перевірити | Звірити свій список ID моделей зі сторінкою deprecations | Розділ 6 про пінінг версій |
| 3. Оцінити | Для кожного ламального — знайти заміну й оцінити її на своїй задачі | Розділ 24 про евалюацію |
| 4. Зафіксувати | Завести дату виведення в календар із запасом | — |
| 5. Автоматизувати | Тест у CI, який викликає кожну використовувану модель і падає при `404` | Розділ 23 про observability |

**Типові помилки**

- Читати changelog очима раз на квартал. Обсяг — 170 записів за 35 місяців; на квартал припадає
  приблизно 15 записів, і оком вони не запам'ятовуються.
- Ігнорувати теги `Model:` і `API:`, читаючи лише текст. Саме теги дозволяють фільтрувати
  релевантне без семантичного аналізу.
- Плутати `legacy` і `deprecated`. Legacy-модель працює й не має дати виведення — але й не
  оновлюється, тож багфікс у неї не приїде.
- Вважати строк 6 місяців гарантією для всіх моделей. Він не поширюється на preview (2 тижні) і на
  випадки, коли виведення вимагають safety або compliance-міркування.
- Орієнтуватися лише на дату виведення, ігноруючи дату **анонсу**. Між ними і є ваш бюджет часу.
- Будувати парсер на `·`-роздільнику, не перевіривши його код. Заміна символу на дефіс ламає
  розбір тегів без жодної помилки — просто порожні списки.

**Альтернативи**

| Потреба | Джерело | Що дає, чого не дає changelog |
|---|---|---|
| Дати виведення й заміни | Сторінка deprecations | Точні дати shutdown і рекомендовані заміни в таблицях |

| Повний індекс документації | `https://developers.openai.com/llms.txt` | Перелік усіх сторінок із `.md`-двійниками |
| Один файл з усією документацією | `https://developers.openai.com/api/docs/llms-full.txt` | Не треба обходити дерево сторінок |
| Зміни в поведінці моделі | Сторінки моделей і blog | Changelog фіксує API, не зміни якості на ваших промптах |
| Автоматичний моніторинг | CI-тест на свої моделі | Changelog не знає, які моделі використовуєте ви |

### 5.3 Коди помилок і що робити з кожним

**Що це.** Помилки OpenAI приходять у двох шарах. Перший — HTTP-статус і тіло відповіді з полями
`error.type`, `error.code`, `error.param`. Другий — клас винятку в Python-бібліотеці, який SDK
виводить із статусу. Обидва шари важливі, бо **той самий статус `429` покриває шість різних
ситуацій**, і лише дві з них лікуються повторною спробою.

**Навіщо це знати.** Пастка тут одна й дорога: ретраїти все, що схоже на тимчасову помилку.
Документація формулює прямо — «повторні спроби при помилках білінгу, лімітів витрат або квоти не
відновлять доступ до API». Ретрай цикл на `credit_balance_exhausted` не просто марний: кожна невдала
спроба **зараховується у ваш ліміт за хвилину**, тож цикл сам погіршує ситуацію.

Другий наслідок: `429` з `slow_down` виникає **навіть коли ви в межах RPM і TPM** — він відображає
швидкість зростання трафіку, а не вичерпання ліміту. Логіка «нас 429, отже треба підняти ліміти» тут
хибна за визначенням.

**Як працює під капотом.**

#### Повна таблиця кодів з документації

| HTTP | `error.type` | `error.code` | Причина | Дія |
|---|---|---|---|---|
| 400 | `invalid_request_error` | — (`error.param: service_tier`) | Обраний або розв'язаний service tier не дозволений для проєкту | Змінити `service_tier` або налаштування проєкту |
| 401 | `invalid_request_error` | — | Невірна автентифікація | Перевірити ключ і організацію |
| 401 | `invalid_request_error` | — | Невірний API-ключ | Перевірити ключ, очистити кеш, створити новий |
| 401 | `invalid_request_error` | — | Акаунт не входить до організації | Приєднатися до організації |
| 401 | `invalid_request_error` | — | IP не авторизований | Надіслати з правильного IP або оновити allowlist |
| 403 | `invalid_request_error` | — | Країна, регіон або територія не підтримуються | Перевірити список підтримуваних країн |
| 429 | `insufficient_quota` | `credit_balance_exhausted` | Скінчилися передплачені креди | **Поповнити баланс** — ретрай не допоможе |
| 429 | `rate_limit_error` | — | Перевищено ліміт запитів | Дотримуватись `Retry-After`, вирівняти темп |
| 429 | `rate_limit_error` | `slow_down` | Швидкість зростання трафіку завелика | **Ретрай** з `Retry-After` або відкат; знизити темп і нарощувати поступово |
| 429 | `insufficient_quota` | `organization_spend_limit_exceeded` | Досягнуто ліміту витрат організації | Підняти ліміт — ретрай не допоможе |
| 429 | `insufficient_quota` | `project_spend_limit_exceeded` | Досягнуто ліміту витрат проєкту | Підняти ліміт проєкту — ретрай не допоможе |
| 429 | `insufficient_quota` | `organization_usage_limit_exceeded` | Досягнуто призначеного OpenAI ліміту використання | Запросити вищий ліміт або звернутися в підтримку |
| 500 | — | — | Збій на боці сервера | **Ретрай** після короткої паузи |
| 503 | `service_unavailable_error` | `server_is_overloaded` | Модель тимчасово перевантажена | **Ретрай** з `Retry-After`, збільшувати затримку |

Два рядки з `429` виглядають як «тимчасово», але ними не є: `organization_spend_limit_exceeded` і
`project_spend_limit_exceeded` знімаються лише зміною ліміту або скиданням місячного періоду.

#### Розрізнення `429` від `503`

Документація окремо описує зміну контракту, яка ламає старі обробники:

| Умова | Було | Стало |
|---|---|---|
| Різке зростання трафіку | `503` з кодом `slow_down` | **`429`** з `rate_limit_error` і `slow_down` |
| Перевантаження моделі | `503` з кодом `slow_down` | `503` з `service_unavailable_error` і `server_is_overloaded` |

Причина зміни — раніше два різні стани були нерозрізненні. Наслідок для коду: обробляти треба
**обидва** статуси, а вирішувати — за `error.code`. У Python статус `429` дає `RateLimitError`,
`503` — `InternalServerError`; якщо ваш обробник ловив лише один клас, частина ситуацій проходила
повз нього.

#### Заголовки відповіді

Ліміти видно в заголовках — це дешевший спосіб зрозуміти стан, ніж чекати на `429`:

| Заголовок | Приклад | Значення |
|---|---|---|
| `Retry-After` | `56` | Мінімум секунд до повтору; присутній на тимчасових `429` і на `503` |
| `x-ratelimit-limit-requests` | `60` | Максимум запитів до вичерпання ліміту |
| `x-ratelimit-limit-tokens` | `150000` | Максимум токенів |
| `x-ratelimit-remaining-requests` | `59` | Залишок запитів |
| `x-ratelimit-remaining-tokens` | `149984` | Залишок токенів |
| `x-ratelimit-reset-requests` / `-reset-tokens` | `1s` / `6m0s` | Час до скидання відповідного лічильника |
| `x-ratelimit-limit-project-tokens` | `60000` | Ліміт токенів проєкту (коли застосовний) |
| `x-ratelimit-remaining-project-tokens` / `-reset-project-tokens` | `57000` / `3s` | Залишок і час скидання для проєктного ліміту |

`Retry-After` трактується як **мінімум**, не як точна затримка: документація радить додати невелику
випадкову затримку, щоб кілька клієнтів не повторили запит одночасно. І окремо застерігає: якщо
серверний `Retry-After` перевищує максимум, який підтримує ваш SDK, SDK поверне початкову HTTP-помилку
замість того, щоб чекати менше. Тоді запит треба **відкласти**, а не ретраїти раніше.

#### Класи винятків у Python

| Виняток | Причина | Дія |
|---|---|---|
| `APIConnectionError` / `APITimeoutError` | Мережа, проксі, SSL; запит перевищив час | Перевірити оточення; повторити після паузи |
| `AuthenticationError` | Ключ невірний, прострочений або відкликаний | Згенерувати новий |
| `BadRequestError` | Запит невалідний (раніше `InvalidRequestError`) | Читати `error.param` |
| `NotFoundError` / `PermissionDeniedError` | Ресурс не існує; немає доступу | Перевірити ID, ключ, організацію |
| `ConflictError` | Ресурс оновлено іншим запитом | Повторити оновлення |
| `InternalServerError` | Збій на боці OpenAI (у т.ч. `503`) | Повторити після паузи |
| `RateLimitError` | Ліміт або занадто швидке зростання | Дотримуватись `Retry-After` |
| `UnprocessableEntityError` | Формат вірний, але обробити не вдалося | Спробувати ще раз |

**Приклад.** Вирішувач «ретраїти чи ні», побудований на таблиці вище. Логіка навмисно відокремлює
класифікацію від дії, щоб рішення було видимим у коді, а не розсипаним по `except`-гілках.

```python
# Таблиця кодів -> рішення. Джерело: research/11/openai_error_codes.md,
# research/11/openai_rate_limits.md (розділ "Error mitigation").

RETRYABLE_TYPES = {"rate_limit_error", "server_error", "service_unavailable_error"}

ERRORS = [
    (400, "invalid_request_error", "invalid_service_tier"),
    (401, "invalid_request_error", "invalid_api_key"),
    (401, "invalid_request_error", "ip_not_authorized"),
    (403, "invalid_request_error", "unsupported_country"),
    (429, "rate_limit_error", "rate_limit_exceeded"),
    (429, "rate_limit_error", "slow_down"),
    (429, "insufficient_quota", "credit_balance_exhausted"),
    (429, "insufficient_quota", "organization_spend_limit_exceeded"),
    (429, "insufficient_quota", "project_spend_limit_exceeded"),
    (429, "insufficient_quota", "organization_usage_limit_exceeded"),
    (500, "server_error", "server_error"),
    (503, "service_unavailable_error", "server_is_overloaded"),
]


def decide(status, error_type, error_code, retry_after=None):
    """Повертає (рішення, обґрунтування).

    STOP    — ретрай не допоможе, потрібна дія на боці користувача
    WAIT    — сервер назвав точну затримку
    BACKOFF — затримки немає, будуємо її самі
    """
    if error_type not in RETRYABLE_TYPES:
        return "STOP", f"потрібна дія користувача: {error_code}"
    if retry_after is not None:
        return "WAIT", f"чекати щонайменше {retry_after} с (Retry-After)"
    return "BACKOFF", "експоненційний відкат із джиттером"


print(f"{'HTTP':>4} {'error.type':26} {'error.code':34} {'рішення':8} підстава")
for status, etype, ecode in ERRORS:
    hint = 5 if (status, ecode) == (429, "rate_limit_exceeded") else None
    decision, why = decide(status, etype, ecode, hint)
    print(f"{status:>4} {etype:26} {ecode:34} {decision:8} {why}")

safe = sum(1 for _, t, _ in ERRORS if t in RETRYABLE_TYPES)
print()
print(f"з {len(ERRORS)} кодів ретраїти можна {safe}, "
      f"решта {len(ERRORS) - safe} — ні (ретрай не допоможе)")
```

#### Ліміти: як їх планувати

Лічильники, які застосовує OpenAI:

| Лічильник | Розшифрування | Особливість |
|---|---|---|
| RPM / RPD | запити за хвилину / за добу | RPM спрацьовує першим при дрібних запитах |
| TPM / TPD | токени за хвилину / за добу | — |
| IPM | зображення за хвилину | Для зображень |
| Хвилини аудіо | хвилини за хвилину | Для потокових аудіомоделей |

Чотири властивості, які змінюють планування:

| Властивість | Наслідок |
|---|---|
| Ліміти на рівні **організації та проєкту**, не користувача | Кілька сервісів з одним ключем ділять пул; сплеск в одному б'є по іншому |
| Ліміт спрацьовує за **тим, що вичерпається першим** | 20 запитів по 100 токенів вичерпують RPM=20, навіть якщо TPM далеко не вибраний |
| Ліміт рахується як **максимум із `max_tokens` і оцінки за симводами** | Завищений `max_tokens` з'їдає TPM, навіть якщо вихід короткий |
| Для довгого контексту — **окремий ліміт** | Довгі запити не конкурують із короткими за той самий лічильник |

Останнє — практична порада документації: ставте `max_tokens` якомога ближче до очікуваного виходу.

#### Ramp-rate: правило, яке не видно в лічильниках

Документація наводить емпіричне правило: **після 1 млн вхідних токенів за хвилину нарощуйте трафік
не більше ніж на 50% кожні 15 хвилин**. Точка, з якої діє обмеження швидкості зростання, залежить від
моделі й стану трафіку, тож план запуску мусить містити графік нарощування, а не «увімкнути на повну».

**Типові помилки**

- Ретраїти `insufficient_quota`. Це дві третини всіх `429` у реальних логах — і саме ті, де ретрай
  гарантовано не працює, а кожна спроба з'їдає ліміт за хвилину.
- Ловити лише `RateLimitError`. `503` приходить як `InternalServerError`, а перевантаження моделі —
  це найчастіший стан у пікові години.
- Чекати **менше** за `Retry-After`, бо SDK «не підтримує таку довгу затримку». Правильна реакція —
  відкласти запит, а не скоротити паузу.
- Будувати власний цикл ретраїв, не вимкнувши вбудовані в SDK. Вкладені цикли перемножують кількість
  запитів: 3 спроби SDK × 5 ваших = 15 фактичних викликів.
- Ретраїти стрім після початку потоку. Помилка після старту стріму приходить **подією в потоці**;
  автоматичний повтор змусить користувача побачити текст двічі.
- Не розділяти прод і staging на різні проєкти. Ліміти на рівні організації означають, що тестовий
  сплеск з'їдає ліміт продакшну.

**Альтернативи**

| Проблема | Що робити | Джерело |
|---|---|---|
| Не влізаєте в RPM | Об'єднувати кілька задач в один запит | Документація радить це прямо, коли TPM має запас |
| Не влізаєте в TPM | Знизити `max_tokens`, скоротити вихід, кешувати префікс | Розділ 9 про кешування |
| Не потрібна синхронна відповідь | Batch API з окремими лімітами черги | Розділ 10 про батчі |
| Знизити ціну за рахунок швидкості | `service_tier: "flex"` — ціна рівня Batch | Ціна Batch-тарифу, але очікуйте на `429 Resource Unavailable` |
| Пікові сплески в продакшні | Черга з обмеженням паралелізму + відкат | Розділ 25 про сервінг |
| Потрібна передбачувана ємність | Scale Tier / Reserved Tier | Документація згадує як опцію для тих, хто регулярно впирається в ramp-rate |
| Треба менше витрат на неважливих задачах | Flex processing із `service_tier: "flex"` | Нижча ціна, але ймовірні відмови ресурсу |

### 5.4 OpenAI-сумісні ендпоінти

**Що це.** Механізм, за якого сторонній провайдер приймає **той самий HTTP-запит**, що й
`POST /v1/chat/completions` у OpenAI, і повертає відповідь тієї самої форми. У коді це виглядає як
три змінені рядки: `api_key`, `base_url`, `model`. Офіційний Python SDK OpenAI при цьому
використовується без змін — його не замінюють, а лише перенаправляють.

**Навіщо це знати.** Це найдешевший важіль стійкості, який у вас є, і водночас найчастіше джерело тихих збоїв.

З одного боку, сумісний `base_url` означає, що зміна провайдера не вимагає переписування шару
інтеграції: для проєкту з жорстким бюджетом це різниця між «переписати за тиждень» і «змінити
конфіг». Формат став стандартом де-факто: Gemini, Mistral і DeepSeek приймають його як основний, а
документація сторонніх інструментів описує **self-hosted OpenAI-сумісні** сервери (vLLM, LocalAI,
llamafile) як окремий клас бекендів. Точний перелік локальних серверів із підтвердженою сумісністю
перевіряйте в їхній документації: у межах цього дослідження вдалося підтвердити саме ці три.

З іншого боку: **«сумісний» не означає «еквівалентний»**. Кожен провайдер реалізує підмножину, і
невідомі параметри поводяться по-різному: одні ігноруються мовчки, інші повертають помилку,
треті працюють, але з іншою семантикою. Найнебезпечніший випадок — **мовчазне ігнорування**:
ви передали `response_format` з JSON-схемою, провайдер його не підтримує, не скаржиться, а модель
повертає вільний текст. Помилка проявиться не в логах API, а в парсері через кілька хвилин.

**Як працює під капотом.**

#### Адреси та формати

| Провайдер | `base_url` (OpenAI-формат) | Інший формат | Джерело |
|---|---|---|---|
| OpenAI | `https://api.openai.com/v1` | — | Документація SDK |
| Gemini | `https://generativelanguage.googleapis.com/v1beta/openai/` | власний Gemini API | Сторінка OpenAI compatibility |
| Mistral | `https://api.mistral.ai/v1` | SDK `mistralai` | Migration guides |
| DeepSeek | `https://api.deepseek.com` | `https://api.deepseek.com/anthropic` | Сторінка першого виклику |

DeepSeek цікавий тим, що надає **обидва** формати одночасно: `https://api.deepseek.com` для
OpenAI SDK і `https://api.deepseek.com/anthropic` для Anthropic SDK. Один постачальник, два SDK, ті
самі моделі — найзручніший кандидат для перевірки гіпотези «а чи справді мій код не залежить від
провайдера».

Форма URL теж має значення: у Gemini він закінчується на `/openai/` — це окремий шар сумісності, а
не власний API Google, тож текст помилок формулює саме він.

#### Що підтверджено, а що ні

Найкорисніша таблиця цього підрозділу — не «що підтримується», а **що вдалося підтвердити в
документації**. Порожня клітинка означає не «ні», а «не знайдено підтвердження»; перш ніж
покладатися на функцію, перевірте її самостійно.

| Можливість | Gemini | Mistral | DeepSeek |
|---|---|---|---|
| `chat/completions` | так | так | так |
| Стрімінг | так | не підтв. | так |
| Function calling | так | не підтв. | так |
| Structured outputs | так | не підтв. | так |
| Embeddings | так | не підтв. | не підтв. |
| Batch API | так | не підтв. | не підтв. |
| `models.list` / `models.retrieve` | так | не підтв. | не підтв. |
| `service_tier` | так | не підтв. | не підтв. |
| `/v1/responses` | не підтв. | не підтв. | **так** |
| Anthropic-формат | не підтв. | не підтв. | **так** |

Найтонше місце — останні два рядки. Якщо ваш код побудований на Responses (5.1), множина
провайдерів, до яких ви можете перемкнутися, звужується до тих, хто підтвердив Responses-формат.
Це прямий зв'язок між рішенням із 5.1 і свободою маневру тут.

#### Деталі, які ламають сумісність

**1. Розбіжність у назвах моделей.** Формат запиту однаковий, назви — ні. Mistral наводить таблицю
відповідності, яка показує масштаб:

| Модель OpenAI | Еквівалент Mistral |
|---|---|
| `gpt-4o` | `mistral-large-latest` |
| `gpt-4o-mini` | `mistral-small-latest` |
| `text-embedding-3-small` | `mistral-embed` |

Це не «перейменування», а твердження про схожість призначення. Перевіряти треба на своїй задачі
(розділ 24).

**2. `extra_body` — єдиний спосіб дістати нативні функції.** Gemini передає так можливості, яких
немає в OpenAI. Підтверджений перелік із документації:

| Параметр | Тип | Ендпоінт | Що робить |
|---|---|---|---|
| `cached_content` | Text | Chat | Відповідає загальному кешу контенту Gemini |
| `thinking_config` | Object | Chat | Відповідає `ThinkingConfig` |
| `safety_settings` | List | Images | Власні пороги фільтрів безпеки |
| `resolution` / `seed` | Text / Integer | Video | Роздільність виходу та детермінованість |

Ключовий наслідок для архітектури: щойно ви використали `extra_body`, код більше не портативний —
`extra_body` не існує в OpenAI і буде проігнорований або відкинутий. Це усвідомлений компроміс, але
його треба фіксувати явно, наприклад окремим адаптером на провайдера.

**3. Мапінг `reasoning_effort`.** Gemini наводить таблицю відповідності між рівнями OpenAI і своїми
`thinking_level` / `thinking_budget`. Вона не тотожна:

| `reasoning_effort` (OpenAI) | `thinking_level` (Gemini 3.1 Pro) | `thinking_budget` (Gemini 2.5) |
|---|---|---|
| `minimal` | `low` | 1,024 |
| `low` | `low` | 1,024 |
| `medium` | `medium` | 8,192 |
| `high` | `high` | 24,576 |

`minimal` і `low` відображаються в **однаковий** рівень Gemini. Отже, перемикання значення з
`low` на `minimal` для економії на Gemini не дасть нічого. Документація також зазначає, що
`reasoning_effort` і `thinking_level`/`thinking_budget` перекриваються функціонально й **не можуть
використовуватися одночасно**, а вимкнути мислення можна лише для 2.5-моделей
(`reasoning_effort: "none"`) — для Gemini 2.5 Pro і моделей 3 це неможливо.

**4. Структуровані вихідні дані через той самий SDK.** Gemini підтримує `client.beta.chat.completions.parse`
з Pydantic-моделлю як `response_format` — той самий код, що й для OpenAI. Найкраща демонстрація, що
сумісність реальна, а не декларативна.

Вимоги до самої схеми при цьому не змінюються, і вони специфічні:

| Обмеження Structured Outputs | Наслідок |
|---|---|
| Кореневий об'єкт має бути `object`, не `anyOf` | Патерн Zod `discriminatedUnion` дає `anyOf` у корені й не працює |
| Усі поля мусять бути в `required` | Необов'язкових полів немає; позначайте їх через `type: ["string", "null"]` |
| `additionalProperties: false` обов'язкове | Без нього запит відхиляється або втрачає strict |
| Композиція `allOf`, `not`, `if`/`then`/`else` не підтримується | Переписуйте схему пласко |
| До 5000 властивостей, до 10 рівнів вкладеності, до 1000 значень `enum` | Глибокі структури сплощуйте, довгі переліки виносьте в окремий виклик |

Перевірка `strict` у відповіді — єдиний спосіб дізнатися, у якому режимі схема справді працювала:
у Responses невдала нормалізація не падає, а повертає `strict: false`.

**5. Batch без завантаження файлів.** Gemini підтримує OpenAI-сумісний Batch для **створення**,
моніторингу та перегляду результатів, але сумісність для upload і download — **не підтримується**:
файли завантажують нативним клієнтом `genai`, а batch створюють через `openai_client.batches.create`.
Приклад «часткової сумісності» в чистому вигляді — ендпоінт є, а половина циклу навколо нього ні.

**6. `service_tier` іменується так само, але типовий tier інший.** Gemini підтримує Flex і Priority,
але коли параметр не задано, типовим є `standard`, що для OpenAI еквівалентно `default`. Код, який
покладається на типове значення, поводиться по-різному на різних провайдерах.

**7. Промпт-формат.** Це вже не про OpenAI-сумісність, а про перехід із self-hosted моделей, але
попередження з документації Mistral варте цитування: моделі Mistral **не** використовують формат
`[INST]`/`[/INST]` з Llama 2, і передача таких рядків дає деградований вихід. Тобто «сумісність» —
це завжди про дві сторони: і про API, і про токенізацію з форматуванням.

**Приклад.** Фабрика клієнтів плюс перевірка, які поля запиту є спільними, а які —
провайдер-специфічними. Мережа не потрібна:

```python
import json

# base_url із документації провайдерів. Джерела: research/11/gemini_openai_compatibility.md,
# research/11/mistral_openai_migration.md, research/11/deepseek_first_api_call.md
PROVIDERS = {
    "openai":   {"base_url": "https://api.openai.com/v1", "env": "OPENAI_API_KEY"},
    "gemini":   {"base_url": "https://generativelanguage.googleapis.com/v1beta/openai/",
                 "env": "GEMINI_API_KEY"},
    "mistral":  {"base_url": "https://api.mistral.ai/v1", "env": "MISTRAL_API_KEY"},
    "deepseek": {"base_url": "https://api.deepseek.com", "env": "DEEPSEEK_API_KEY"},
}

# Те, що змінюється при перемиканні. Рівно три значення — це і є вся обіцянка сумісності.
for name, cfg in PROVIDERS.items():
    print(f"{name:9} {cfg['base_url']:56} ключ із ${cfg['env']}")

# Спільне ядро Chat Completions: поля, які приймає кожен із чотирьох.
common_core = ["model", "messages", "stream", "tools", "tool_choice",
               "response_format", "max_tokens", "temperature", "top_p",
               "n", "stop", "seed"]

# Те, що додає лише Gemini.
gemini_only = ["reasoning_effort", "extra_body", "service_tier"]

print()
print(f"спільне ядро ({len(common_core)} полів):")
print("  " + ", ".join(common_core))
print(f"лише Gemini: {', '.join(gemini_only)}")

portable = sorted(set(common_core) - set(gemini_only))
print()
print(f"портативних полів: {len(portable)} з {len(common_core) + len(gemini_only)}")
print("непортативні:", ", ".join(sorted(set(gemini_only) - set(common_core))) or "немає")

print()
print("запит, ідентичний для всіх чотирьох провайдерів:")
print(json.dumps({"model": "<id провайдера>", "messages": [
    {"role": "user", "content": "Hello"}]}, ensure_ascii=False))
```

Фактичний вивід:

```
openai    https://api.openai.com/v1                                ключ із $OPENAI_API_KEY
gemini    https://generativelanguage.googleapis.com/v1beta/openai/  ключ із $GEMINI_API_KEY
mistral   https://api.mistral.ai/v1                                ключ із $MISTRAL_API_KEY
deepseek  https://api.deepseek.com                                 ключ із $DEEPSEEK_API_KEY

спільне ядро (12 полів):
  model, messages, stream, tools, tool_choice, response_format, max_tokens, temperature, top_p, n, stop, seed
лише Gemini: reasoning_effort, extra_body, service_tier

портативних полів: 12 з 15
непортативні: extra_body, reasoning_effort, service_tier

запит, ідентичний для всіх чотирьох провайдерів:
{"model": "<id провайдера>", "messages": [{"role": "user", "content": "Hello"}]}
```

Останній рядок — і є вся суть: тіло запиту не залежить від провайдера. Залежать три речі навколо
нього: адреса, ключ і **назва моделі**.

Реальний виклик до сумісного ендпоінта (потрібен ключ відповідного провайдера):

```python
import os

from openai import OpenAI  # схема: потрібен ключ провайдера

client = OpenAI(
    api_key=os.environ["GEMINI_API_KEY"],
    base_url="https://generativelanguage.googleapis.com/v1beta/openai/",
)

response = client.chat.completions.create(
    model="gemini-3.8-flash",
    messages=[
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "Explain to me how AI works"},
    ],
)
print(response.choices[0].message.content)
```

Той самий код із `base_url="https://api.mistral.ai/v1"` і `model="mistral-large-latest"`
працюватиме проти Mistral — за умови, що ви не використовуєте нічого з `extra_body`.

**Типові помилки**

- Вважати сумісність повною. Кожен підрозділ вище — приклад часткової сумісності: Batch без
  upload/download, `service_tier` з іншим типовим значенням, `minimal` і `low`, що зливаються
  в один рівень.
- Передавати `response_format` із JSON-схемою у провайдера, який її не підтвердив, і не перевіряти
  результат. Найгірший сценарій — мовчазне ігнорування й вільний текст замість JSON.
- Використовувати `extra_body` у коді, який має працювати з кількома провайдерами. Поле
  провайдер-специфічне за визначенням.
- Ставити `service_tier` одночасно з `reasoning_effort` і `thinking_level` у Gemini. Документація
  зазначає, що `reasoning_effort` та `thinking_level`/`thinking_budget` перекриваються й не можуть
  використовуватися разом.
- Переносити `base_url` разом із `model`, забувши, що назви моделей різні. `gpt-4o` у Mistral не
  існує — треба `mistral-large-latest`.
- Покладатися на текст помилки. Шар сумісності формулює повідомлення сам, тож код, який парсить
  рядок помилки, ламається при зміні провайдера. Класифікуйте за HTTP-статусом і `error.code`.
- Вважати, що сумісний `base_url` прибирає потребу в евалюації. Формат однаковий — якість ні
  (розділ 24).

**Альтернативи**

| Потреба | Варіант | Ціна рішення |
|---|---|---|
| Мінімум коду, зміна провайдера за конфігом | `base_url` + `api_key` + `model` | Втрачаєте провайдер-специфічні можливості |
| Нативні функції важливіші за портативність | Нативний SDK провайдера (`mistralai`, `google-genai`) | Два шари інтеграції замість одного |
| Один формат, багато провайдерів | Шар абстракції над Chat Completions | Своя робота, але контроль над відмінностями |
| Обидві екосистеми одночасно | Провайдер із обома форматами (DeepSeek) | Перевірка гіпотези портативності на реальному коді |
| Повна незалежність | Свій інференс (vLLM, Ollama) | Інша модель витрат — розділ 25 |
| Антропічна екосистема | Anthropic Messages | Розділ 4: інший формат, інший стан, інші помилки |
| Responses-можливості (вбудовані інструменти) | Лишатися на OpenAI | Див. таблицю підтверджених можливостей вище |

### 5.5 Огляд інших провайдерів і цінові профілі

**Що це.** Ціновий профіль — це не одне число за мільйон токенів, а **набір тарифних режимів**:
стандартний, батчовий, гнучкий, прискорений, кешований, піковий і позапіковий, короткий і довгий
контекст. Той самий запит коштує по-різному залежно від того, у який режим ви його поклали.

**Навіщо це знати.** Розділ 6 порівнює провайдерів за осями; тут — той самий матеріал, але з погляду
**конкретної цифри для конкретного навантаження**. Причина: розкид між крайніми конфігураціями на
одному й тому самому сценарії сягає двох порядків. Це не різниця між «дешевше й дорожче», це
різниця між «проєкт окупається» і «проєкт не окупається».

Тому ціни нижче подані не як прайс-лист, а як **сценарій**: одне фіксоване навантаження, порахуйте
самі під своє.

#### OpenAI: чотири тарифні режими на одну модель

Та сама модель `gpt-6-astra` (ціни за 1M токенів, короткий контекст):

| Режим | Вхід | Кешований вхід | Запис кешу | Вихід | Як увімкнути |
|---|---|---|---|---|---|
| Standard | $10.00 | $1.00 | $12.50 | $50.00 | за замовчуванням |
| Batch | $5.00 | $0.50 | $6.25 | $25.00 | Batch API |
| Flex | $5.00 | $0.50 | $6.25 | $25.00 | `service_tier: "flex"` |
| Fast | $20.00 | $2.00 | $25.00 | $100.00 | `service_tier: "fast"` або `"priority"` |

Три висновки з таблиці:

1. **Batch і Flex мають однакову ціну.** Документація Flex це підтверджує прямо: токени
   тарифікуються за ставками Batch API, плюс знижки від кешування. Різниця не в ціні, а в
   **механізмі**: Batch — асинхронний файловий цикл, Flex — синхронний виклик, який може повернути
   `429 Resource Unavailable` (за нього не стягується плата).
2. **Fast — рівно вдвічі дорожче за Standard.** «Priority processing» перейменовано на «Fast mode»
   30 липня 2026; працюють обидва значення `service_tier`.
3. **Довгий контекст має окремий тариф — удвічі дорожчий.** Для `gpt-6-astra`: вхід $20.00 і вихід
   $75.00 замість $10.00 і $50.00. Межа для `gpt-5.5` позначена як `<272K context length`;
   перевищення порогу подвоює ціну **всього** запиту, не лише надлишку.

Кешований вхід тут — 10% ціни входу ($1.00 проти $10.00), а запис у кеш дорожчий за звичайний вхід
($12.50 проти $10.00). Це та сама логіка, що в Anthropic (розділ 9): ви платите надбавку за запис,
щоб потім читати зі знижкою.

Окремо тарифікуються інструменти — їх не можна порахувати за токенами:

| Інструмент | Ціна |
|---|---|
| Web search (усі моделі) | $10.00 / 1k викликів + токени вмісту за ставками моделі |
| Web search preview (reasoning-моделі) | $10.00 / 1k викликів |
| Web search preview (не-reasoning моделі) | $25.00 / 1k викликів, токени вмісту безкоштовні |
| File search — зберігання / виклик | $0.10 / GB за добу (1 GB безкоштовно) / $2.50 за 1k викликів |
| Hosted Shell і Code Interpreter | 1 GB $0.03, 4 GB $0.12, 16 GB $0.48, 64 GB $1.92 за 20-хвилинну сесію |

Агент із web search може витратити більше на виклики інструмента, ніж на токени моделі, — тому

#### Mistral: правила важливіші за цифри

Сторінка цін Mistral не дає надійно вилученої таблиці за моделями, але формулює **правила**, які
переносяться на будь-яку модель:

| Правило | Величина |
|---|---|
| Базова тарифікація | За 1M токенів, вхід і вихід окремо |
| Батч | Знижка **50%** |
| Кешований вхід | Знижка до **90%** на повторюваних промптах |
| OCR | За 1,000 сторінок |
| Мовні моделі | За хвилину |
| Tool API | За виклик |

Документація наводить ілюстративний приклад: Mistral Large коштує $0.5 /M токенів на вході та
$1.5 /M на виході. Це приклад із FAQ, не повна таблиця; перевіряйте перед бюджетуванням.

**Приклад.** Той самий сценарій на всіх чотирьох провайдерах. Навантаження фіксоване: 20,000
викликів, 6,000 токенів входу й 400 токенів виходу на виклик.

```python
# Сценарій: 20 000 викликів, 6 000 вхідних і 400 вихідних токенів на виклик.
# Ціни за 1M токенів узяті з research/econ/openai_pricing.md,
# research/11/gemini_pricing.md, research/11/deepseek_pricing.md,
# research/econ/mistral_pricing.txt.
CALLS, TOKENS_IN, TOKENS_OUT = 20_000, 6_000, 400

SCENARIOS = [
    ("OpenAI gpt-6-astra (standard)",     10.00,  50.00),
    ("OpenAI gpt-5.6-terra (standard)",    2.00,  12.00),
    ("OpenAI gpt-5.6-luna (standard)",     0.20,   1.20),
    ("OpenAI gpt-5.6-luna (batch/flex)",   0.10,   0.60),
    ("OpenAI gpt-6-astra (fast)",         20.00, 100.00),
    ("Gemini 3.8 Flash (до 31.12.2026)",   0.75,   3.75),
    ("Gemini 3.8 Flash (з 01.01.2027)",    1.50,   7.50),
    ("Gemini 3.8 Flash (batch)",           0.375,  1.875),
    ("DeepSeek V4-Flash (peak)",           0.30,   1.20),
    ("DeepSeek V4-Flash (off-peak)",       0.15,   0.60),
    ("DeepSeek V4-Pro (peak)",             1.32,   3.96),
    ("Mistral Large (приклад із FAQ)",     0.50,   1.50),
]


def cost(pin, pout):
    return (TOKENS_IN / 1e6 * pin + TOKENS_OUT / 1e6 * pout) * CALLS


print(f"Сценарій: {CALLS} викликів × ({TOKENS_IN} вх / {TOKENS_OUT} вих)")
print(f"{'конфігурація':36} {'ціна виклику':>13} {'усього':>10}")
for name, pin, pout in SCENARIOS:
    per_call = TOKENS_IN / 1e6 * pin + TOKENS_OUT / 1e6 * pout
    print(f"{name:36} ${per_call:>12.5f} ${cost(pin, pout):>9.2f}")

totals = [cost(p, o) for _, p, o in SCENARIOS]
print()
print(f"розкид між крайніми конфігураціями: "
      f"${min(totals):.2f} ... ${max(totals):.2f} (×{max(totals) / min(totals):.0f})")
```

Читати цю таблицю треба не як рейтинг провайдерів, а як **рейтинг рішень**. Найбільший множник дає не
вибір провайдера, а вибір режиму й моделі всередині одного провайдера: `gpt-6-astra` і `gpt-5.6-luna`
— це один постачальник, той самий формат API і той самий SDK, а різниця в 190 разів.

Другий висновок: міжпродавча різниця на **порівнянних** рівнях значно менша за внутрішню. У дешевому
сегменті Gemini $60–$120, DeepSeek $22.80–$45.60, Mistral $72 — розкид приблизно 3×, і він залежить
від співвідношення входу й виходу. Обґрунтовувати зміну провайдера цією різницею без урахування
якості (розділ 24) — типова помилка.

Третій висновок видно лише в динаміці: ціна Gemini зростає вдвічі з 1 січня 2027, а `Batch` і `Flex`
в OpenAI коштують однаково. Бюджет на рік неможливо скласти за поточним прайсом — потрібні
оголошені зміни.

**Типові помилки**

- Ігнорувати поріг довгого контексту. Для `gpt-6-astra` перехід із 200K на 300K токенів подвоює
  ціну всього запиту, а не надлишку.
- Забувати, що вихід Gemini включає thinking-токени. Порівняння з моделлю, де reasoning тарифікується
  окремо, дає неправильний висновок.
- Планувати бюджет за поточним прайсом без оголошених змін. Gemini здешевлення не обіцяє — з
  1 січня 2027 ціна подвоюється.
- Вважати кеш безкоштовним сховищем. У Gemini це $0.50 за 1M токенів на **годину**; добове зберігання
  1M токенів — $12.
- Не враховувати платні інструменти. Web search — $10 за 1,000 викликів понад токени, а агентський
  цикл може робити десятки викликів на одну відповідь.
- Будувати розклад пакетної обробки без урахування часових тарифів. DeepSeek дає двократну знижку
  за перенесення в позапікове вікно, і це найдешевший важіль із наявних.

**Альтернативи**

| Ситуація | Що вибрати | Що отримаєте |
|---|---|---|
| Асинхронна обробка без вимог до часу | Batch API (усі провайдери з ним) | 50% знижки, окремі ліміти черги |
| Синхронно, але не критично до швидкості | `service_tier: "flex"` в OpenAI | Ціна Batch без файлового циклу; ризик `429` |
| Потрібна мінімальна латентність за будь-яку ціну | `service_tier: "fast"` | ×2 до ціни Standard |
| Повторюваний префікс у кожному запиті | Кеш промптів | 10% ціни входу в OpenAI, до 90% знижки в Mistral |
| Обсяг у неробочі години | Позапікові ставки DeepSeek | 50% знижки за розкладом |
| Дуже довгий контекст | Модель із 1M контексту | Увага на поріг довгого контексту в OpenAI |
| Треба зафіксувати ціну на рік | Передплачена ємність | Scale Tier / Reserved Tier в OpenAI |
| Бюджет жорстко обмежений | Співвідношення ціни й якості на своїй задачі | Розділ 6 і розділ 24: без власних евалюацій цифри не працюють |

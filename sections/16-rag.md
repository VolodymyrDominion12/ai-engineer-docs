## 16. RAG: chunking, гібридний пошук, Postgres і Qdrant

RAG (Retrieval-Augmented Generation) — це конвеєр із шести кроків, і кожен крок має власний режим
відмови. Документ ріжуть на чанки (chunking), чанки кодують у вектори, вектори кладуть в індекс,
запит шукають одночасно лексичним і семантичним пошуком, списки зливають в один, найкращі
переранжовують (reranking), і лише потім формують контекст — із посиланнями на джерела.

Найбільше якість втрачається не на виборі моделі, а на першому кроці. Техзвіт Chroma виміряв це
прямо: вибір стратегії chunking змінює recall до 9 відсотків, а усталені налаштування популярних
бібліотек дають відносно погані результати
([Evaluating Chunking Strategies for Retrieval](https://research.trychroma.com/evaluating-chunking)).
Anthropic називає ту саму проблему інакше — «традиційний RAG знищує контекст» — і пропонує додавати
до кожного чанка короткий опис його місця в документі перед індексацією
([Introducing Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)).

| Термін | Значення |
|---|---|
| Чанк (chunk) | Фрагмент документа — одиниця індексації й пошуку |
| Bi-encoder | Модель, що кодує текст у вектор **окремо**; швидка, але груба |
| Cross-encoder | Модель, що читає **пару** (запит, документ) разом; точна, але повільна |
| Розріджений вектор (sparse vector) | Вектор розмірності словника, майже всі координати нульові |
| Щільний вектор (dense vector) | Вектор фіксованої розмірності (384–3072) з навченої моделі |
| Константа рангу (rank constant) | Параметр `k` у RRF, що згладжує внесок позицій |
| Гілка (branch) | Один список результатів, що входить у злиття |

### 16.1 Стратегії chunking і чому це головне джерело проблем

**Що це.** Chunking — розбиття документа на фрагменти, кожен з яких індексується окремо. Чанк — це
одночасно одиниця зберігання, одиниця пошуку й одиниця контексту, яку модель побачить у промпті.

**Навіщо це знати.** Причин три:

1. **Recall.** Техзвіт Chroma показав розкид recall від 85.4 до 89.5 відсотка на тому самому
   корпусі й тій самій моделі embeddings — різниця тільки в стратегії та розмірі чанка.
2. **Вартість.** Перекриття — прямий множник на обсяг індексу: воно дублює текст, і ви платите за
   дублікати і під час індексації, і під час кожного запиту.
3. **Діагностика.** Коли RAG «не знаходить» відповідь, причина зазвичай у тому, що відповідь
   розірвана між чанками. Рeranker це не виправить — він переранжовує те, що вже знайдено.

**Як працює під капотом.**

Механіку рекурсивного розділювача описано в джерелі `langchain-text-splitters`. Клас `TextSplitter`
має такі усталені параметри
([base.py](https://github.com/langchain-ai/langchain/blob/master/libs/text-splitters/langchain_text_splitters/base.py)):

```python
# Фрагмент джерела (langchain_text_splitters/base.py), не самостійна програма.
chunk_size: int = 4000,
chunk_overlap: int = 200,
length_function: Callable[[str], int] = len,
keep_separator: bool | Literal["start", "end"] = False,
add_start_index: bool = False,
strip_whitespace: bool = True,
```

`length_function` за замовчуванням — `len`, тобто **символи, а не токени**. `chunk_size=4000` — це
4000 символів; для українського тексту приблизно 800–1200 токенів. Плутанина символів і токенів —
найпоширеніша помилка в налаштуваннях.

`RecursiveCharacterTextSplitter` використовує **список** роздільників, а не один. Усталений список —
`["\n\n", "\n", " ", ""]`
([character.py](https://github.com/langchain-ai/langchain/blob/master/libs/text-splitters/langchain_text_splitters/character.py)):
алгоритм бере перший роздільник, присутній у тексті, ріже за ним, а залишки, більші за `chunk_size`,
рекурсивно ріже наступними. Порожній рядок `""` — останній рубіж (поріз на символи). Межі речення в
усталеному списку **немає**. Техзвіт Chroma прямо пише, що їм довелося змінити роздільники на
`["\n\n", "\n", ".", "?", "!", " ", ""]`, бо усталені «зазвичай давали дуже короткі чанки, які
показували погані результати».

Найважливіше: **перекриття працює в одиницях фрагментів, а не символів**. `_merge_splits` скидає
переповнений чанк і відкидає **цілі фрагменти** з початку, доки сумарна довжина не впаде до
`chunk_overlap`:

```python
# Фрагмент джерела (langchain_text_splitters/base.py), не самостійна програма.
while total > self._chunk_overlap or (
    total + len_ + (separator_len if len(current_doc) > 0 else 0)
    > self._chunk_size
    and total > 0
):
    total -= self._length_function(current_doc[0]) + (
        separator_len if len(current_doc) > 1 else 0
    )
    current_doc = current_doc[1:]
```

Наслідок практичний: якщо ви додали в роздільники межу речення (`. `), фрагменти стають завдовжки з
речення, і `chunk_overlap`, менший за речення, **не дає перекриття взагалі**. Ви ставите 200
символів перекриття, а на виході отримуєте нуль.

Перевірка на реальному коді. Спрощена модель розділювача повторює логіку `_merge_splits`; документ
містить відповідь на запит «як часто надсилати heartbeat?», рознесену на два факти: «десять хвилин»
і `keep_alive_interval`.

```python
import re


class RecursiveChunker:
    """Спрощена модель RecursiveCharacterTextSplitter із langchain-text-splitters:
    рекурсія за списком роздільників + склеювання з перекриттям (_merge_splits)."""

    def __init__(self, chunk_size, chunk_overlap, separators):
        if chunk_overlap >= chunk_size:
            raise ValueError("chunk_overlap має бути меншим за chunk_size")
        self.size, self.overlap, self.separators = chunk_size, chunk_overlap, list(separators)

    def split(self, text):
        return self._merge(self._split(text, self.separators), " ")

    def _split(self, text, separators):
        sep, rest = separators[-1], []
        for i, s in enumerate(separators):
            if s == "" or re.search(re.escape(s), text):
                sep, rest = s, separators[i + 1:]
                break
        parts = list(text) if sep == "" else [p for p in text.split(sep) if p]
        out = []
        for p in parts:
            if len(p) <= self.size:
                out.append(p)
            elif rest:
                out.extend(self._split(p, rest))
            else:
                out.append(p)
        return out

    def _merge(self, splits, separator):
        """Точна копія логіки _merge_splits: перекриття відміряється ЦІЛИМИ фрагментами."""
        sep_len = len(separator)
        docs, current, total = [], [], 0
        for piece in splits:
            n = len(piece)
            if total + n + (sep_len if current else 0) > self.size and current:
                docs.append(separator.join(current))
                while total > self.overlap or (
                    total + n + (sep_len if current else 0) > self.size and total > 0
                ):
                    total -= len(current[0]) + (sep_len if len(current) > 1 else 0)
                    current = current[1:]
            current.append(piece)
            total += n + (sep_len if len(current) > 1 else 0)
        if current:
            docs.append(separator.join(current))
        return docs


DOC = ("Брокер відкидає неактивні з'єднання через тридцять хвилин простою. "
       "Щоб цього уникнути, надсилайте heartbeat кожні десять хвилин. "
       "Інтервал heartbeat задається параметром keep_alive_interval у конфігурації клієнта.")
ANCHORS = ("десять хвилин", "keep_alive_interval")
DEFAULT_SEPS = ("\n\n", "\n", " ", "")          # як у langchain за замовчуванням
SENTENCE_SEPS = ("\n\n", "\n", ". ", " ", "")   # як радить техзвіт Chroma

for label, seps in (("усталені", DEFAULT_SEPS), ("з межею речення", SENTENCE_SEPS)):
    print(f"--- роздільники: {label} ---")
    for size, overlap in [(85, 0), (85, 20), (85, 40)]:
        chunks = RecursiveChunker(size, overlap, seps).split(DOC)
        full = [i for i, c in enumerate(chunks) if all(a in c for a in ANCHORS)]
        print(f"  size={size}, overlap={overlap}: чанків {len(chunks)}, "
              f"повна відповідь: {full if full else 'ЖОДЕН'}")
```

**Фактичний вивід:**

```text
--- роздільники: усталені ---
  size=85, overlap=0: чанків 3, повна відповідь: ЖОДЕН
  size=85, overlap=20: чанків 4, повна відповідь: ЖОДЕН
  size=85, overlap=40: чанків 4, повна відповідь: ЖОДЕН
--- роздільники: з межею речення ---
  size=85, overlap=0: чанків 3, повна відповідь: ЖОДЕН
  size=85, overlap=20: чанків 3, повна відповідь: ЖОДЕН
  size=85, overlap=40: чанків 3, повна відповідь: ЖОДЕН
```

Другий рядок кожної групи ілюструє описаний ефект: з усталеними роздільниками `overlap=20` дає
**чотири** чанки замість трьох (текст фізично дублюється, бо перекриття відміряється цілими
словами), а з межею речення — **три**, стільки ж, скільки `overlap=0`. Перекриття не спрацювало:
щоб досягти 20 символів, алгоритм мусив би відкинути ціле речення.

Чому жодна з шести конфігурацій не дала повної відповіді? Виміряймо відстань між фактами:

```python
a = DOC.index(ANCHORS[0]) + len(ANCHORS[0])
b = DOC.index(ANCHORS[1])
print(f"від кінця {ANCHORS[0]!r} до початку {ANCHORS[1]!r}: {b - a} символів")
```

**Фактичний вивід:**

```text
від кінця 'десять хвилин' до початку 'keep_alive_interval': 42 символів
```

Два факти, які мусять опитися в одному чанку, розділяє 42 символи. Жодне з перекриттів 0, 20, 40
не дотягується. Щойно перекриття перевищує 42, чанк із повною відповіддю з'являється:

```python
for size, overlap in [(85, 60), (160, 60)]:
    chunks = RecursiveChunker(size, overlap, DEFAULT_SEPS).split(DOC)
    full = [i for i, c in enumerate(chunks) if all(x in c for x in ANCHORS)]
    print(f"size={size}, overlap={overlap}: чанків {len(chunks)}, "
          f"повна відповідь: {full if full else 'ЖОДЕН'}")
```

**Фактичний вивід:**

```text
size=85, overlap=60: чанків 7, повна відповідь: [5]
size=160, overlap=60: чанків 2, повна відповідь: [1]
```

Робоче правило: **перекриття має бути не меншим за типову відстань між фактами, які мусять
відповісти разом.** Цю відстань вимірюють на своїх даних. Ціна видна в першому рядку: `size=85` із
перекриттям 60 дає сім чанків із 212 символів документа — майже втричі більше за текст.

**Що показав вимірювальний звіт Chroma.** Метрика там не звична: замість nDCG@K автори рахують
**IoU на рівні токенів** — перетин множини токенів релевантних уривків із множиною повернутих
токенів, поділений на об'єднання. Логіка: у RAG порядок документів майже не важливий, важливо,
скільки потрібних токенів потрапило в контекст і скільки зайвих приїхало разом із ними.

| Chunking | Size | Overlap | Recall | Precision | Precision$_\Omega$ | IoU |
|---|---|---|---|---|---|---|
| Recursive | 800 (~661) | 400 | 85.4 ± 34.9 | 1.5 ± 1.3 | 6.7 ± 5.2 | 1.5 ± 1.3 |
| TokenText | 800 | 400 | 87.9 ± 31.7 | 1.4 ± 1.1 | 4.7 ± 3.1 | 1.4 ± 1.1 |
| Recursive | 400 (~312) | 200 | 88.1 ± 31.6 | 3.3 ± 2.7 | 13.9 ± 10.4 | 3.3 ± 2.7 |
| TokenText | 400 | 200 | 88.6 ± 29.7 | 2.7 ± 2.2 | 8.4 ± 5.1 | 2.7 ± 2.2 |
| Recursive | 400 (~276) | 0 | **89.5 ± 29.7** | **3.6 ± 3.2** | **17.7 ± 14.0** | **3.6 ± 3.2** |
| TokenText | 400 | 0 | 89.2 ± 29.2 | 2.7 ± 2.2 | 12.5 ± 8.1 | 2.7 ± 2.2 |

Три висновки (n=5 чанків, модель `text-embedding-3-large`):

1. **Менший чанк виграв за recall** — 400 токенів дало 89.5 проти 85.4 у 800.
2. **Перекриття не допомогло, а зашкодило.** Найкращий рядок — `Overlap = 0`, бо IoU карає за
   дублювання: релевантний токен у чисельнику рахується один раз, а всі повернуті токени в
   знаменнику — усі.
3. **Recursive стабільно кращий за TokenText** за однакових розмірів: він поважає межі абзаців і
   слів, тоді як TokenText ріже рівно по N токенів.

Корпус синтетичний, тож цифри не переносять на свій проєкт без перевірки. Але напрямок однозначний:
**розмір чанка впливає сильніше, ніж перекриття.**

**Передіндексаційне збагачення контекстом.** Чанк «The company's revenue grew by 3% over the
previous quarter» не містить ні назви компанії, ні кварталу — знайти його за запитом «який був ріст
виручки ACME Corp у Q2 2023?» практично неможливо. Anthropic пропонує дописати до чанка короткий
опис його місця в документі:

```text
<document>
{{WHOLE_DOCUMENT}}
</document>
Here is the chunk we want to situate within the whole document
<chunk>
{{CHUNK_CONTENT}}
</chunk>
Please give a short succinct context to situate this chunk within the overall document
for the purposes of improving search retrieval of the chunk. Answer only with the
succinct context and nothing else.
```

Результат — «зазвичай 50–100 токенів» — дописується до чанка **і перед обчисленням embeddings, і
перед побудовою індексу BM25**. Виміряний ефект: contextual embeddings знизили частку невдач у
top-20 з 5.7% до 3.7% (на 35%), разом із contextual BM25 — до 2.9% (на 49%), а в комбінації з
переранжуванням — на 67%. Вартість за припущень 800-токенних чанків і 8k-токенних документів —
$1.02 на мільйон токенів документа, одноразово, завдяки кешуванню промпту.

**Типові помилки**

- **Плутати символи й токени.** `chunk_size=4000` — це 4000 символів, бо `length_function=len`.
- **Ставити `chunk_overlap` більшим або рівним `chunk_size`.** Логіка фрагментів цього не витримує;
  перевіряйте конфігурацію на старті, а не на 100-тисячному документі.
- **Вважати, що `chunk_overlap` гарантує перекриття.** З межею речення в роздільниках воно часто
  дорівнює нулю. Перевірка: узяти еталонну пару «запит → фрагмент відповіді», порахувати відстань
  між фактами й порівняти з `chunk_overlap`.
- **Різати структуровані формати наївно.** Markdown, HTML і код мають власну структуру; у LangChain
  для цього є `MarkdownHeaderTextSplitter` і `RecursiveCharacterTextSplitter.from_language`.
- **Індексувати чанк без метаданих.** Без `document_id`, `chunk_index` і зсуву неможливо ні показати
  посилання, ні дедуплікувати результати, ні прибрати чанки видаленого документа.
- **Оптимізувати chunking без оцінного набору.** Мінімум — 30–50 пар «запит → уривок, який мусить
  бути знайдений» і recall@k на них.

**Альтернативи**

| Стратегія | Ідея | Коли доречна | Ціна |
|---|---|---|---|
| Фіксований розмір | Різати рівно по N токенів | Однорідні тексти, швидкий старт | Розриває речення й слова |
| Recursive character | Рекурсія за списком роздільників | Універсальний усталений вибір | Не бачить змісту |
| Структурний | За заголовками, тегами, функціями | Markdown, HTML, код | Потрібен парсер формату |
| Семантичний (Kamradt) | Розриви в косинусних відстанях сусідніх вікон | Тексти без розмітки | Дорого, розмір непередбачуваний |
| Cluster semantic | Максимум сумарної схожості в чанку | Коли якість критична | Переобчислення при додаванні даних |
| LLM chunking | Модель розставляє межі | Складні документи | Найдорожчий, ризик галюцинацій |

Семантичний chunking виглядає привабливіше, ніж працює. Алгоритм Kamradt рахує embeddings ковзного
вікна й шукає розриви в косинусних відстанях між сусідніми вікнами; поріг за замовчуванням — будь-яка
відстань вище 95-го перцентиля всіх послідовних відстаней. Це **відносна** метрика: на більшому
корпусі поріг дасть більші чанки, і розмір перестає бути контрольованим. Техзвіт Chroma змушений був
дописати бінарний пошук порогу, щоб найбільший чанк вкладався в ліміт моделі. Дорожчі варіанти:
`ClusterSemanticChunker` ріже документ на шматки по 50 токенів і динамічним програмуванням максимізує
сумарну попарну схожість усередині чанка (обмеження — глобальна оптимізація залежить від статистики
всього корпусу); `LLMSemanticChunker` подає документ із тегами `<start_chunk_N>` і просить повернути
індекси у вигляді `split_after: 3, 5`.

### 16.2 Гібридний пошук: BM25 + вектори

**Що це.** Гібридний пошук — коли той самий запит виконується двома незалежними способами: лексичним
(за збігом слів, зазвичай BM25) і семантичним (за близькістю векторів), після чого два списки
зливаються в один. Це не «покращений BM25» і не «покращений вектор» — це дві окремі гілки, кожна зі
своїм індексом.

**Навіщо це знати.** Лексичний і семантичний пошук провалюються **по-різному**, і саме тому
комбінація працює. Anthropic описує розрив прикладом: користувач шукає «Error code TS-999» у базі
техпідтримки. Модель embeddings знайде текст про коди помилок як клас явищ, але може не знайти саме
`TS-999`, бо цей рядок семантично порожній — у ньому немає значення, яке можна закодувати вектором.
BM25 знайде його точно. Зворотний випадок так само частий: BM25 не знайде «як скинути пароль» у
документі з заголовком «Відновлення доступу до облікового запису», бо спільних слів немає.

**Як працює під капотом.**

**BM25.** Точний вигляд формули найпростіше взяти з реалізації. У пакеті `rank_bm25` (версія 0.2.2)
клас `BM25Okapi` має такі усталені параметри й таку формулу оцінки
([rank_bm25.py](https://github.com/dorianbrown/rank_bm25/blob/master/rank_bm25.py)):

```python
# Фрагмент джерела (rank_bm25/rank_bm25.py), не самостійна програма.
def __init__(self, corpus, tokenizer=None, k1=1.5, b=0.75, epsilon=0.25):
    ...

# idf обчислюється так:
idf = math.log(self.corpus_size - freq + 0.5) - math.log(freq + 0.5)

# оцінка документа для одного терміна запиту:
score += (self.idf.get(q) or 0) * (q_freq * (self.k1 + 1) /
        (q_freq + self.k1 * (1 - self.b + self.b * doc_len / self.avgdl)))
```

Три компоненти:

- **IDF** (`log(N - f + 0.5) - log(f + 0.5)`) — вага терміна: що рідше термін у корпусі, то він
  важливіший. Якщо термін є в понад половині документів, IDF стає **від'ємним**; `rank_bm25`
  підставляє підлогу `epsilon * average_idf` (типово `0.25` від середнього IDF).
- **Насичення частоти (`k1`)** — множник зростає з частотою, але **асимптотично**: десяте входження
  слова додає набагато менше, ніж друге. Саме це відрізняє BM25 від сирого TF.
- **Нормалізація довжини (`b`)** — доданок `b * doc_len / avgdl`. `b=0` вимикає нормалізацію, `b=1`
  застосовує повністю.

Параметри **відрізняються між реалізаціями**. ParadeDB для `pg_search` документує `k1 = 1.2` і
`b = 0.75` (діапазони: `k1` від 0 до 100, `b` від 0 до 1). Тобто `1.5` у Python-бібліотеці проти
`1.2` у ParadeDB — не помилка жодної з них, а різні усталені значення.

Нижче — повна реалізація BM25 на стандартній бібліотеці, поруч із косинусною схожістю на TF-IDF.
Обидві реалізації лексичні; косинус грає роль «другої гілки» лише для демонстрації розбіжностей.

```python
import math
import re
from collections import Counter

CORPUS = [

    "Error code TS-999 indicates a failed TLS handshake in the transport layer.",    # d1
    "A failed TLS handshake usually means an expired or mismatched certificate.",    # d2
    "How to rotate API keys without downtime.",                                      # d3
    "Handshake timeouts on the transport gateway after a certificate renewal.",      # d4
    "Billing FAQ: invoices, refunds and the quarterly revenue report.",              # d5
    "Rate limits are counted per organisation, not per API key.",                    # d6
    "The broker drops idle connections after thirty minutes of inactivity.",         # d7
    "Certificate chain validation fails when the intermediate CA is missing.",       # d8
    "Streaming responses use server-sent events and cannot be resumed mid-stream.",  # d9
    "Audit logs retain ninety days of request metadata for compliance review.",      # d10
    "Retry with exponential backoff when you receive HTTP 429 or 529.",              # d11
]


def tokenize(t):
    return re.findall(r"\w+", t.lower())


class BM25:
    """BM25Okapi: формула й усталені параметри з rank_bm25."""

    def __init__(self, corpus, k1=1.5, b=0.75, epsilon=0.25):
        self.corpus = [tokenize(d) for d in corpus]
        self.k1, self.b = k1, b
        self.n = len(self.corpus)
        self.avgdl = sum(map(len, self.corpus)) / self.n
        self.freqs = [Counter(d) for d in self.corpus]
        df = Counter()
        for d in self.corpus:
            df.update(set(d))
        self.idf = {t: math.log(self.n - f + 0.5) - math.log(f + 0.5)
                    for t, f in df.items()}
        eps = epsilon * (sum(self.idf.values()) / len(self.idf))
        for t, v in list(self.idf.items()):
            if v < 0:
                self.idf[t] = eps

    def score(self, query, i):
        dl, s = len(self.corpus[i]), 0.0
        for t in tokenize(query):
            f = self.freqs[i].get(t, 0)
            if f:
                s += self.idf[t] * (f * (self.k1 + 1)) / (
                    f + self.k1 * (1 - self.b + self.b * dl / self.avgdl))
        return s


def cosine_tfidf(corpus, query, i):
    """Косинусна схожість на TF-IDF — лексична метрика, не семантична."""
    docs = [tokenize(d) for d in corpus]
    df = Counter()
    for d in docs:
        df.update(set(d))
    n = len(docs)
    vec = lambda tokens: {t: (1 + math.log(c)) * math.log((n + 1) / (df[t] + 1))
                          for t, c in Counter(tokens).items()}
    a, b = vec(docs[i]), vec(tokenize(query))
    dot = sum(a[t] * b.get(t, 0.0) for t in a)
    na = math.sqrt(sum(v * v for v in a.values()))
    nb = math.sqrt(sum(v * v for v in b.values()))
    return dot / (na * nb) if na and nb else 0.0


bm = BM25(CORPUS)
query = "TS-999 TLS handshake"
print(f"Корпус: {len(CORPUS)} документів, avgdl = {bm.avgdl:.1f} токенів")
print(f"idf('tls') = {bm.idf['tls']:.4f}, idf('999') = {bm.idf['999']:.4f}\n")
for rank, i in enumerate(sorted(range(len(CORPUS)), key=lambda j: -bm.score(query, j))[:4], 1):
    print(f"{rank:>2}. d{i:<2} BM25={bm.score(query, i):7.4f} "
          f"cosine={cosine_tfidf(CORPUS, query, i):6.4f}  {CORPUS[i][:52]}")
```

Документ d7 «The broker drops idle connections after thirty minutes of inactivity» — очевидна
правильна відповідь — отримав **нуль**. BM25 порівнює рядки, а не слова: запит містить `connection`
і `dropping`, документ — `connections` і `drops`. Без стемера або лематизатора це різні терміни.
Класичний BM25 у пошукових системах завжди йде разом з аналізатором, і без нього цифри вище не мають
сенсу.

**Де живе BM25 у Postgres.** Дві різні речі, які легко переплутати.

Вбудований повнотекстовий пошук Postgres — це **не BM25**. `ts_rank` «ранжує вектори за частотою
збігу лексем», а `ts_rank_cd` рахує cover density за статтею Clarke, Cormack і Tudhope 1999 року —
тобто враховує близькість лексем. Документація застерігає: «концепція релевантності розпливчаста й
дуже залежить від застосунку… вбудовані функції ранжування — лише приклади»
([Ranking Search Results](https://www.postgresql.org/docs/current/textsearch-controls.html)). Ваги
задаються через `setweight` з мітками `A`–`D`, масив ваг за замовчуванням — `{0.1, 0.2, 0.4, 1.0}`
(порядок `{D, C, B, A}`):

```sql
UPDATE documents SET tsv =
    setweight(to_tsvector(coalesce(title, '')),    'A') ||
    setweight(to_tsvector(coalesce(keywords, '')), 'B') ||
    setweight(to_tsvector(coalesce(body, '')),     'D');
```

Нормалізація довжини задається бітовою маскою: `0` ігнорує довжину, `2` ділить на довжину документа,
`1` — на `1 + логарифм довжини`, `32` — на `rank + 1` (єдиний варіант, що приводить оцінки до
діапазону 0–1). Кілька бітів комбінуються через `|`. Ці функції **не використовують глобальної
статистики корпусу**, тому IDF у них немає взагалі.

| Функція | Що робить із введенням | Коли використовувати |
|---|---|---|
| `to_tsquery` | Повний синтаксис `&`, `\|`, `!`, `<->` | Тільки для власних перевірених запитів |
| `plainto_tsquery` | Вставляє `&` між словами, оператори не розпізнає | Прості запити з довіреного джерела |
| `phraseto_tsquery` | Вставляє `<->` (FOLLOWED BY) замість `&` | Пошук точної фрази з урахуванням порядку |
| `websearch_to_tsquery` | Розуміє лапки й мінус, **ніколи не кидає помилку синтаксису** | Сирий ввід користувача |

Останній рядок критичний: `websearch_to_tsquery` «ніколи не породить помилок синтаксису, що дозволяє
використовувати необроблений ввід користувача для пошуку». Якщо підставити ввід користувача в
`to_tsquery`, будь-яка дужка чи двокрапка перетвориться на помилку SQL.

Друга річ — розширення, які додають справжній BM25. `pg_search` від ParadeDB описується як
розширення, що дає «швидкий повнотекстовий, фасетний і гібридний пошук по таблицях Postgres за
алгоритмом BM25», побудоване на Tantivy (Rust-аналог Apache Lucene) через `pgrx`:

```sql
CREATE INDEX search_idx ON articles
USING paradedb (id, title, body, embedding vector_cosine_ops)
WITH (key_field = 'id');

SELECT id, pdb.score(id) AS score
FROM articles
WHERE body ||| 'heartbeat'
ORDER BY score DESC
LIMIT 5;
```

Один такий індекс обслуговує і текст, і вектори, і фільтри — принципово інша архітектура, ніж
«pgvector + окремий `tsvector`-стовпець із GIN-індексом», де це два індекси й два запити, які ви
зливаєте в застосунку.

**Розріджені вектори як міст між світами.** У Qdrant лексична гілка — це не окремий рушій, а вектор
особливого типу (пари «індекс терміна → вага»), і пошук за ним виконується тим самим `query_points`.
Дві деталі з документації: функція відстані для розріджених векторів **завжди `Dot`** і не
задається; IDF не можна попередньо обчислити, тому його вмикають модифікатором
`models.SparseVectorParams(modifier=models.Modifier.IDF)`, після чого запит модифікується
статистикою IDF автоматично.

| Властивість | Лексична (BM25 / sparse) | Семантична (dense) |
|---|---|---|
| Що кодує | Точні терми й їхню вагу | Узагальнений зміст |
| Розмірність | Розмір словника, майже все нулі | 384–3072, усе заповнене |
| Рідкісні рядки (`TS-999`, артикули, UUID) | Знаходить точно | Часто пропускає |
| Перефразування | Не знаходить | Знаходить |
| Морфологія | Потрібен стемер/лематизатор | Не потрібен |
| Оновлення індексу | Дешеве (інвертований індекс) | Дорожче (граф HNSW) |
| Пояснюваність | Видно, які терми збіглися | Не видно |
| Стійкість до набивання ключовими словами | Низька | Вища |

**Типові помилки**

- **Використовувати `to_tsquery` для вводу користувача.** Будь-який `&`, `|`, `!`, `:` або дужка
  дасть помилку SQL. Для сирого вводу існує `websearch_to_tsquery`.
- **Порівнювати оцінки BM25 і косинусної схожості напряму.** BM25 необмежений зверху й залежить від
  довжини корпусу, косинус лежить у межах від -1 до 1. Документація Qdrant попереджає: «поширений
  запит — альфа-зважена лінійна комбінація оцінок dense і sparse… це ненадійно без попередньої
  нормалізації».
- **Забути про аналізатор.** BM25 без стемера дає нуль на запиті «dropping» до документа зі словом
  «drops». Для української мови ситуація гостріша, ніж для англійської.
- **Будувати гібрид на двох індексах, які розсинхронізуються.** Один транзакційний запис на чанк,
  або один індекс, як у ParadeDB.
- **Ставити `b=0` «щоб довгі документи не каралися».** У корпусі з різною довжиною документів це
  означає, що найдовший документ виграє за рахунок того, що містить більше слів.
- **Індексувати текст без збереження початкового вигляду.** BM25 працює з нормалізованими лексемами,
  а користувачеві треба показати оригінал. Зберігайте і вихідний текст, і нормалізовану форму.

**Альтернативи**

| Підхід | Ідея | Ціна |
|---|---|---|
| BM25 (класичний) | Інвертований індекс, статистика корпусу | Слабка морфологія, немає семантики |
| BM25 + стемер/лематизатор | Нормалізація словоформ | Потрібен аналізатор на кожну мову |
| SPLADE та навчені розріджені вектори | Модель сама розширює запит синонімами | Дорожча індексація |
| BM25F | Окремі ваги для полів | Потрібна розмітка полів |
| BM25+ | Нижня межа для нормалізації за довжиною | Ще один параметр `δ` |
| Dense-only | Тільки вектори | Втрачає точні збіги рядків |
| Sparse-only | Тільки BM25 | Втрачає перефразування |

Про `BM25+` варто знати точну мотивацію. Компонент нормалізації за довжиною не має належної нижньої
межі: довгі документи, які **справді** містять термін запиту, отримують несправедливо низьку оцінку —
приблизно таку саму, як короткі документи, що не містять його взагалі. `BM25+` додає один вільний
параметр `δ` зі значенням за замовчуванням `1.0`, який задає цю нижню межу.

### 16.3 Злиття результатів: RRF і зважені оцінки

**Що це.** Злиття (fusion) — крок, на якому два відсортовані списки перетворюються на один. Є два
принципово різні підходи: зливати **за позиціями** (rank fusion) або **за оцінками** (score fusion)
після їх нормалізації. Reciprocal Rank Fusion (RRF) — перший підхід і практичний стандарт.

**Навіщо це знати.** Спокуслива ідея — просто скласти оцінку BM25 і косинусну схожість із вагами. Це
найпоширеніша помилка в саморобних конвеєрах, і документація Qdrant описує її прямо: «поширений
запит — альфа-зважена лінійна комбінація оцінок dense і sparse… це ненадійно без попередньої
нормалізації: щільні (косинус, обмежений) і розріджені (BM25, необмежений) оцінки живуть у різних
масштабах, які до того ж зсуваються від запиту до запиту». RRF обходить проблему тим, що **відкидає
оцінки взагалі**.

**Як працює під капотом.** Формула RRF — один рядок:

```text
score = 0.0
for q in queries:
    if d in result(q):
        score += 1.0 / ( k + rank( result(q), d ) )
return score
# де k — константа рангу,
# rank(result(q), d) — позиція d у списку result(q), починаючи з 1
```

Документ отримує внесок від кожної гілки, у якій він з'явився, і внесок тим більший, чим вища позиція.
Документ, що є в обох списках, отримує **дві** добавки й майже завжди виграє — у цьому сенс гібридного
пошуку.

```python
from collections import defaultdict


def rrf(result_lists, k=60):
    """result_lists — списки ідентифікаторів, кожен відсортований за спаданням релевантності.
    Ранг нумерується з 1, як в Elasticsearch."""
    scores = defaultdict(float)
    for results in result_lists:
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] += 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda kv: (-kv[1], kv[0]))


query_a = [1, 2, 3, 4]          # лексична гілка
query_b = [5, 4, 3, 1, 2]       # семантична гілка

print("Приклад із документації Elasticsearch, k=1 (rank_constant=1):")
for doc, score in rrf([query_a, query_b], k=1):
    print(f"  _id: {doc} = {score:.3f}")
print("\nТі самі списки, k=60 (усталене значення Elasticsearch):")
for doc, score in rrf([query_a, query_b], k=60):
    print(f"  _id: {doc} = {score:.6f}")
```

**Фактичний вивід:**

```text

  _id: 4 = 0.533
  _id: 2 = 0.500
  _id: 3 = 0.500
  _id: 5 = 0.500

Ті самі списки, k=60 (усталене значення Elasticsearch):
  _id: 1 = 0.032018

  _id: 2 = 0.031514
```

Перший блок точно відтворює числа з документації Elasticsearch: `_id: 1 = 1.0/(1+1) + 1.0/(1+4) = 0.7`,
і підсумковий порядок `[1, 4, 2, 3, 5]`. Це хороша перевірка правильності вашої реалізації RRF:
візьміть опублікований приклад і відтворіть його до останньої цифри.

**Константа рангу `k` вирішує більше, ніж здається:**


Документація Elasticsearch формулює це так: вище значення означає, що нижчі позиції мають більший
вплив. `k=60` вибирають, коли хочуть, щоб документ, знайдений **обома** гілками навіть невисоко,
переміг документ, знайдений однією гілкою на першому місці.

**Усталені значення `k` різняться між системами:**

| Система | Параметр | Усталене | Нумерація рангів |
|---|---|---|---|
| Elasticsearch | `rank_constant` | 60 | з 1 |
| ParadeDB (`pg_search`) | `k` | 60 («загальноприйняте») | з 1 |
| Qdrant | `k` в `Rrf` | **2** | **з 0** |
| Власна реалізація | `k` | — | вибираєте самі |

Qdrant відрізняється двічі: і константа інша, і нумерація з нуля — «Qdrant використовує позиції з
нуля; найкращий результат має $r_d = 0$». Формула при цьому така:

$$ score(d\in D) = \sum_{r_d\in R(d)} \frac{1}{k + \frac{r_d + 1}{w_r} - 1} $$

де $k$ — константа (усталено 2), $w_r$ — вага гілки (усталено 1), $D$ — множина точок з усіх
результатів, $R(d)$ — множина рангів документа. Оскільки $w_r$ усталено дорівнює 1, формула
спрощується до класичної $\sum 1/(k + r_d)$.

**Зважений RRF.** Документація Qdrant формулює інтуїцію так: «якщо у вас два префетчі й ви
призначаєте вагу 3.0 першому та 1.0 другому, документ, що стоїть третім у першому запиті, отримує
стільки ж, скільки документ на першому місці в другому». Перевірмо це на обох формах запису:

```python
def rrf_weighted(ranks, weights, k):
    """Усталена форма: сума w/(k+rank), rank з 1."""
    return sum(w / (k + r) for r, w in zip(ranks, weights))


def rrf_qdrant(ranks0, weights, k):
    """Формула з документації Qdrant: w_r / (k + (r_d + 1)/w_r - 1),
    де r_d — позиція з нуля."""
    return sum(w / (k + (r + 1) / w - 1) for r, w in zip(ranks0, weights))


print("Твердження з документації Qdrant: «документ, що стоїть третім у першому запиті "
      "з вагою 3.0,\nотримує стільки ж, скільки документ на першому місці в другому з вагою 1.0».\n")
for k in (0, 1, 2, 60):
    a = rrf_weighted([3], [3.0], k)
    b = rrf_weighted([1], [1.0], k)

          f"рівні: {abs(a - b) < 1e-12}")

print()
```

Рівність виконується **лише** для усталеної форми при `k=0`. Для опублікованої формули Qdrant вона не
виконується за жодного з перевірених `k`, включно з усталеним `k=2`. Це розбіжність між прозовим
поясненням і формулою в документації, а не помилка в реалізації. Практичний висновок: **не переносьте
ваги між системами наосліп** — ваговий коефіцієнт має сенс лише разом із конкретною формулою й
конкретним `k`.

Приклад із документації ParadeDB відтворюється точно: документ на 5-й позиції в текстовій гілці з
вагою 1.0 дає `1.0 / (60 + 5) = 0.0154`, на 10-й у векторній із вагою 0.7 — `0.7 / (60 + 10) =
0.0100`, разом `0.0254`. Зверніть увагу на масштаб: підсумкова оцінка
RRF порядку 0.025. **Це не ймовірність і не відсоток релевантності.** Порівнювати оцінки RRF між
запитами безглуздо: вони залежать від кількості гілок і від `k`, а не від якості пошуку. Єдине, для
чого вони придатні, — сортування всередині одного запиту.

**DBSF — альтернатива, коли ви довіряєте сирим оцінкам.** Distribution-Based Score Fusion (Qdrant
v1.11.0) не відкидає оцінки, а нормалізує їхні розподіли. Для кожної гілки обчислюються середнє $\mu$ і
вибіркове стандартне відхилення $\sigma$, після чого межі три-сигма стають кінцями відрізка:

$$ \hat{s} = \frac{s - (\mu - 3\sigma)}{6\sigma} $$

```python
def dbsf_norm(values):
    """Формула з документації Qdrant: s_hat = (s - (mu - 3*sigma)) / (6*sigma)."""
    n = len(values)
    mu = sum(values) / n
    sigma = (sum((v - mu) ** 2 for v in values) / (n - 1)) ** 0.5 if n > 1 else 0.0
    if sigma == 0:
        return [0.5] * n
    return [(v - (mu - 3 * sigma)) / (6 * sigma) for v in values]


bm25_raw = [12.4, 9.1, 7.8]        # шкала BM25 необмежена
cosine_raw = [0.87, 0.84, 0.61]    # шкала косинуса 0..1
print(f"BM25   сирі        : {bm25_raw}")
print(f"BM25   нормалізовані: {[round(v, 4) for v in dbsf_norm(bm25_raw)]}")
print(f"cosine сирі        : {cosine_raw}")
print(f"cosine нормалізовані: {[round(v, 4) for v in dbsf_norm(cosine_raw)]}")
print(f"усі оцінки однакові -> {dbsf_norm([5.0, 5.0, 5.0])}, один документ -> {dbsf_norm([5.0])}")
```

**Фактичний вивід:**

```text
BM25   сирі        : [12.4, 9.1, 7.8]
BM25   нормалізовані: [0.6851, 0.4531, 0.3618]
cosine сирі        : [0.87, 0.84, 0.61]
cosine нормалізовані: [0.6133, 0.5781, 0.3086]
усі оцінки однакові -> [0.5, 0.5, 0.5], один документ -> [0.5]
```

Різниця між «без нормалізації» і «з DBSF» виглядає косметичною — порядок у цьому прикладі однаковий.
Але зверніть увагу на масштаб: сира комбінація дає 6.6350, нормалізована — 0.6492. Якщо ви додаєте
третю ознаку (свіжість, популярність) із вагою 0.3, то в першому випадку вона потоне в шумі BM25, а в
другому реально вплине на результат. Нормалізація потрібна саме тоді, коли ви додаєте до RRF власні
сигнали. Останній рядок виводу відтворює задокументовану поведінку: «якщо всі повернуті оцінки
однакові (або повернуто лише одну точку), DBSF видає `0.5`, а не ділить на нуль».

Документація Qdrant застерігає щодо статистичної слабкості DBSF: статистика береться з top-k
префетчу, тобто з малої вибірки, а один домінантний викид може перекосити нормалізацію для всього
запиту. Порада там же — збільшувати `limit` префетчу, якщо ранжування нестабільне.

| Якщо у вас є… | Використовуйте |
|---|---|
| Оцінний набір (запити з відомими релевантними документами) | Зважений RRF, ваги підібрані на train/val-розбитті |
| Довіра до сирих оцінок ретриверів і немає оцінного набору | DBSF |
| Ні оцінного набору, ні впевненості в оцінках | RRF (безпечне усталене) |

Там же прямо сказано, що жоден із методів не домінує: «на добре відкаліброваних ретриверах DBSF може
перевершити налаштований зважений RRF; на інших перемагає зважений RRF».

**Типові помилки**

- **Складати оцінки різних гілок без нормалізації.** У прикладі вище BM25 дає 12.4, косинус — 0.87;
  за ваги 0.5 гілки номінально рівноправні, а фактично домінує BM25 у понад чотирнадцять разів.
- **Не знати, з якого числа починається ранг.** Elasticsearch і ParadeDB рахують з 1, Qdrant — з 0.
- **Переносити `k` з однієї системи в іншу.** `k=60` і `k=2` — різні компроміси між довірою до
  верхівки списку й глибиною.
- **Забути про `rank_window_size`.** Документація Elasticsearch описує це прямо: якщо
  `rank_window_size` змінюється між сторінками, порядок результатів теж змінюється. Гарантія «жоден
  документ не пропущено й не продубльовано» діє тільки за незмінного `rank_window_size`, і він мусить
  бути не меншим за `size`.
- **Ставити `limit` префетчу рівним `limit` головного запиту.** У Qdrant `offset` впливає тільки на
  головний запит, тому префетчі мусять мати `limit` щонайменше `limit + offset`, інакше можна
  отримати порожній результат.
- **Вважати оцінку RRF мірою якості.** 0.0254 не означає «2.5% релевантності».
- **Не дедуплікувати за ідентифікатором чанка.** Якщо один чанк прийшов як два різні записи індексу,
  RRF нарахує йому два внески, і він виграє не через релевантність.

**Альтернативи**

| Метод | Принцип | Перевага | Недолік |
|---|---|---|---|
| RRF | Обернені ранги, оцінки відкидаються | Не потребує налаштування | Втрачає величину оцінок |
| Зважений RRF | Те саме з вагами на гілку | Підсилює сильнішу гілку | Ваги треба підбирати |
| DBSF | Нормалізація розподілів за 3-сигма | Зберігає величину оцінок | Статистика з малої вибірки |
| Лінійна комбінація після нормалізації | `alpha * a + (1 - alpha) * b` | Найзрозуміліша | Потрібна нормалізація під кожен запит |
| CombSUM / CombMNZ | Сума нормалізованих оцінок | Класика IR | Чутлива до викидів |
| Переранжування замість злиття | Об'єднати, потім переранжувати | Найвища якість | Дорожче за латентністю |

### 16.4 Переранжування

**Що це.** Переранжування (reranking) — друга стадія пошуку. Перша швидко дістає з індексу великий
список кандидатів (типово 50–200), друга — повільно, але точно перевпорядковує їх і залишає найкращі
(типово 3–20). Друга стадія не додає до списку нічого — вона працює тільки з тим, що дала перша.

**Навіщо це знати.** Перша стадія змушена бути дешевою: вона порівнює запит із мільйонами документів,
і дешевизна досягається тим, що запит і документ кодуються **незалежно** (bi-encoder). Друга стадія
може дозволити собі читати пару разом. Документація Sentence Transformers формулює це в трьох
пунктах: cross-encoder «обчислює оцінку схожості для пар входів», «зазвичай дає вищу якість порівняно
з Sentence Transformer (bi-encoder)» і «часто повільніший, бо потребує обчислень для кожної пари».

Anthropic описує той самий розподіл ролей як послідовність кроків: «виконати початковий пошук, щоб
отримати top потенційно релевантних чанків (ми використали top-150); пропустити top-N чанків разом із
запитом користувача через модель переранжування; дати кожному чанку оцінку релевантності й вибрати
top-K (ми використали top-20); передати top-K у модель як контекст». Друга стадія відкидає 87
відсотків кандидатів — саме на цьому економляться гроші й латентність генерації.

**Як працює під капотом.** Різниця між стадіями — не в розмірі моделі, а в тому, **що саме** модель
бачить на вході.

| | Bi-encoder (перша стадія) | Cross-encoder (друга стадія) |
|---|---|---|
| Вхід | Документ окремо, запит окремо | Пара `(запит, документ)` разом |
| Вихід | Один вектор на текст | Одне число на пару |
| Коли рахується | Під час індексації — документів | Під час запиту — по разу на кандидата |
| Порівняння | Косинус/скалярний добуток векторів | Немає: оцінка вже готова |
| Складність на запит | O(1) після кодування запиту + пошук в ANN | O(N) прогонів моделі для N кандидатів |
| Що бачить | Узагальнений зміст документа | Взаємодію кожного терміна запиту з кожним терміном документа |

Останній рядок — суть: cross-encoder бачить **увагу між токенами запиту й токенами документа**, тому
вловлює те, що BM25 і навіть косинус пропускають — чи стоять потрібні слова поруч, у правильному
порядку, у правильному контексті.

```python
import math
import re
from collections import Counter


def tokenize(t):
    return re.findall(r"\w+", t.lower())


POOL = {
    0: "Щоб уникнути розриву, надсилайте heartbeat кожні десять хвилин.",
    1: "heartbeat десять heartbeat хвилин heartbeat десять heartbeat хвилин",
    2: "Інтервал heartbeat задається параметром keep_alive_interval у конфігурації клієнта.",
    3: "Брокер відкидає неактивні з'єднання через тридцять хвилин простою.",
}
QUERY = "heartbeat десять хвилин"


def bm25_scores(query, corpus, k1=1.5, b=0.75, epsilon=0.25):
    docs = [tokenize(d) for d in corpus]
    n, avgdl = len(docs), sum(map(len, docs)) / len(docs)
    freqs = [Counter(d) for d in docs]
    df = Counter()
    for d in docs:
        df.update(set(d))
    idf = {t: math.log(n - f + 0.5) - math.log(f + 0.5) for t, f in df.items()}
    eps = epsilon * (sum(idf.values()) / len(idf))
    for t, v in list(idf.items()):
        if v < 0:
            idf[t] = eps
    out = []
    for i, doc in enumerate(docs):
        s = 0.0
        for t in tokenize(query):
            f = freqs[i].get(t, 0)
            if f:
                s += idf.get(t, 0.0) * (f * (k1 + 1)) / (
                    f + k1 * (1 - b + b * len(doc) / avgdl))
        out.append((i, s))
    return out


def proximity_score(query, text):
    """Заміна cross-encoder: покриття термінів плюс те, наскільки тісно вони стоять.
    Справжній cross-encoder — натренована модель; тут відтворена лише та властивість,
    якої BM25 не має: він читає пару разом і бачить близькість термінів."""
    q = set(tokenize(query))
    d = tokenize(text)
    pos = {}
    for p, t in enumerate(d):
        pos.setdefault(t, []).append(p)
    matched = [t for t in q if t in pos]
    if not matched:
        return 0.0, 0.0, 0.0
    coverage = len(matched) / len(q)
    if len(matched) > 1:
        span = max(pos[t][-1] for t in matched) - min(pos[t][0] for t in matched) + 1
        proximity = (len(matched) - 1) / (span - 1)
    else:
        proximity = 0.5
    return coverage, proximity, coverage + 0.5 * proximity


bm = dict(bm25_scores(QUERY, [POOL[i] for i in sorted(POOL)]))
print(f"Запит: {QUERY!r}\n")
print(f"{'чанк':>5} {'BM25':>8} {'покриття':>9} {'тісність':>9} {'разом':>8}  текст")
for i in sorted(POOL):
    cov, prox, total = proximity_score(QUERY, POOL[i])
    print(f"{i:>5} {bm[i]:8.4f} {cov:9.2f} {prox:9.2f} {total:8.2f}"
          f"  {POOL[i][:44].rstrip()}")

order_bm25 = sorted(POOL, key=lambda i: -bm[i])
order_rerank = sorted(order_bm25, key=lambda i: -proximity_score(QUERY, POOL[i])[2])
print(f"\nПорядок BM25          : {order_bm25}")
print(f"Порядок після rerank  : {order_rerank}")
```

**Фактичний вивід:**

```text
Запит: 'heartbeat десять хвилин'

 чанк     BM25  покриття  тісність    разом  текст
    0   0.3361      1.00      0.67     1.33  Щоб уникнути розриву, надсилайте heartbeat к
    1   0.5424      1.00      0.29     1.14  heartbeat десять heartbeat хвилин heartbeat
    2   0.1681      0.33      0.50     0.58  Інтервал heartbeat задається параметром keep
    3   0.1593      0.33      0.50     0.58  Брокер відкидає неактивні з'єднання через тр

Порядок BM25          : [1, 0, 2, 3]
Порядок після rerank  : [0, 1, 2, 3]
```

BM25 поставив набитий повтореннями чанк 1 на перше місце (0.5424 проти 0.3361) — він бачить лише
частоти термінів. Друга стадія підняла чанк 0, бо в ньому потрібні терміни стоять у межах трьох слів
(тісність 0.67 проти 0.29). Це і є те, що дає читання пари разом.

**Що переранжування НЕ робить.** Воно не піднімає recall. Якщо правильної відповіді немає серед
кандидатів першої стадії, друга стадія її не вигадає. Документація Qdrant формулює той самий принцип
для багатостадійних запитів: «спочатку використайте менше й дешевше подання, щоб отримати великий
список кандидатів; потім переоцініть кандидатів, використовуючи більше й точніше подання».

**Обмеження готових API.** Для Cohere документація фіксує конкретні межі, і вони впливають на
архітектуру:

| Обмеження | Мінімум | Максимум | Усталено |
|---|---|---|---|
| Кількість документів | 1 | 10 000 | — |
| `max_chunks_per_doc` | 1 | — | 1 |
| Токенів на запит | 1 | 2048 | — |

Ключове правило — не «10 000 документів», а нерівність: `кількість_документів * max_chunks_per_doc`
не може перевищувати 10 000, інакше ендпоінт повертає помилку. Оскільки `max_chunks_per_doc` усталено
дорівнює 1, «документ» для reranker'а — це рівно один ваш чанк. Якщо передавати цілі документи, сервіс
ріже їх сам: для `rerank-v4.0` — на шматки по 32 764 токени (контекст 32 768 мінус чотири службові
токени), а фінальна оцінка документа береться як **максимум** оцінок його шматків. Для `rerank-v3.5`
і `rerank-v3.0` шматки по 4093 токени. Запит теж обрізається: у `rerank-v4.0` запит довший за 16 384
токени обрізається до перших 16 384; у `rerank-v3.5` відповідно 4096 і 2048. Документація дає пораду:
«якщо ви хочете більше контролю над тим, як робиться chunking, радимо різати документи самостійно».

**Локальний варіант.** Двофазний виклик із документації Sentence Transformers — `predict` приймає
список пар, `rank` приймає запит і список документів:

```python
from sentence_transformers import CrossEncoder

model = CrossEncoder("cross-encoder/ms-marco-MiniLM-L6-v2")
scores = model.predict([
    ("How many people live in Berlin?",
     "Berlin had a population of 3,520,031 registered inhabitants in an area of 891.82 square kilometers."),
    ("How many people live in Berlin?", "Berlin is well known for its museums."),
])
print(scores)
# => array([ 8.607138 , -4.3200774], dtype=float32)
```

Зверніть увагу на числа: 8.607 і -4.320. Це **логіти, а не оцінки від 0 до 1**, і документація це
застерігає: «моделі MS Marco повертають логіти… Завантажте `CrossEncoder` з
`activation_fn=torch.nn.Sigmoid()`, щоб отримати оцінки між 0 і 1. Це не впливає на ранжування».
Практично це означає, що **абсолютні значення оцінок reranker'а не можна використовувати як поріг
релевантності** без активації й калібрації на своїх даних; порівнювати оцінки між запитами не можна
взагалі.

Пакет `rerankers` збирає різні підходи під один інтерфейс і показує, наскільки вони різні.
Встановлюється частинами: `rerankers[transformers]` для cross-encoder'ів, `rerankers[api]` для Cohere,
Jina, MixedBread, Pinecone, `rerankers[flashrank]` для ONNX-моделей під CPU, `rerankers[rankllm]` для
RankGPT, `rerankers[monovlm]` для мультимодальних. У версії 0.10.0 додано підтримку
ColBERT/late-interaction, у 0.9.0 — MXBai V2 reranker.

**Типові помилки**

- **Чекати від переранжування зростання recall.** Якщо `recall@100` першої стадії дорівнює 0.6, то
  `recall@5` після переранжування не перевищить 0.6 ніколи. Перша стадія мусить мати добрий recall@N
  на глибині N, а не precision@5.
- **Брати занадто малий пул кандидатів.** Пул у 10 чанків — типова помилка. Anthropic використовує
  150, Qdrant у прикладі багатостадійного запиту — 1000.
- **Використовувати логіти як поріг.** `8.607` і `-4.320` — не «86% і 0%».
- **Ставити малу модель і чекати якості великої.** Родина `cross-encoder/ms-marco-*` відрізняється
  кількістю шарів (`TinyBERT-L2`, `MiniLM-L2`, `L4`, `L6`, `L12`, `electra-base`) — це прямо різні
  компроміси між швидкістю й якістю.
- **Ігнорувати обрізання в хмарному API.** Для довгих документів оцінка береться як максимум по
  шматках, тож релевантний фрагмент у хвості може витягнути оцінку всього документа вгору.
- **Переранжовувати тим, що вже використали на першій стадії.** Порядок не зміниться, а латентність
  подвоїться. Друга стадія має бути **іншою моделлю**, яка бачить пару.
- **Ставити переранжування перед фільтрацією за правами доступу.** Модель не знає про ACL: ви
  витратите обчислення на недоступні документи й отримаєте менше ніж top-K результатів.

**Альтернативи**

| Підхід | Що це | Латентність | Якість |
|---|---|---|---|
| Cross-encoder (BERT-подібний) | Натренована модель на парі | Середня (N прогонів) | Висока |
| Late interaction (ColBERT) | Кілька векторів на документ, взаємодія на етапі пошуку | Низька | Висока |
| LLM as reranker (RankGPT) | Модель перевпорядковує список у промпті | Висока | Дуже висока |
| Хмарний rerank API | Готовий сервіс | Залежить від мережі | Висока |
| Квантизований ONNX-reranker | Модель на CPU | Низька | Середня |
| Друга стадія на повних векторах | Переоцінка тими самими embeddings | Дуже низька | Помірна |
| Reciprocal Rank Fusion | Злиття списків замість переранжування | Мінімальна | Помірна |

Передостанній рядок плутають зі справжнім переранжуванням. Qdrant описує це як «багатостадійний
запит»: перша стадія бере квантизовані вектори й дістає 1000 кандидатів, друга переоцінює їх
повнорозмірними векторами й повертає top-10. Це дешевше за cross-encoder і не потребує окремої моделі,
але це **не** переранжування парою: друга стадія використовує ті самі embeddings і бачить рівно те
саме. Окрема порада з документації: «вимкніть індекс HNSW для векторів, які використовуються лише для
переоцінки, встановивши `m=0` у конфігурації HNSW цього вектора. Переоцінка не використовує індекс
HNSW, тому вимкнення звільнить пам'ять».

### 16.5 Postgres як векторна БД

**Що це.** `pgvector` — розширення Postgres, що додає тип `vector`, оператори відстані та індекси
HNSW і IVFFlat. `README` описує його як «векторний пошук схожості з відкритим кодом для Postgres» із
підтримкою точної та наближеної найближчої сусідської вибірки, одинарної, половинної, бінарної та
розрідженої точності й шести метрик відстані, «плюс ACID-сумісність, відновлення на точку в часі,
JOIN-и та всі інші чудові можливості Postgres».

Актуальна версія розширення за станом на момент написання — **v0.8.6**: саме цей тег фігурує в
інструкції встановлення, і він же є найновішим у переліку тегів репозиторію. Підтримуються Postgres
13 і новіші.

**Навіщо це знати.** Окрема векторна БД — це окремий сервіс, окреме резервне копіювання й, головне,
окреме джерело розсинхронізації: чанк у Postgres і вектор у векторній БД можуть розійтися. Якщо у вас
уже є Postgres і десятки мільйонів векторів, а не мільярди, окрема векторна БД частіше додає
складності, ніж користі.

**Як працює під капотом.**

| Оператор | Метрика | Що повертає |
|---|---|---|
| `<->` | L2 (евклідова) | Відстань |
| `<#>` | Inner product | **Від'ємний** скалярний добуток |
| `<=>` | Cosine | Косинусну **відстань** (1 - схожість) |
| `<+>` | L1 (манхеттенська) | Відстань |
| `<~>` | Hamming (для `bit`) | Відстань |
| `<%>` | Jaccard (для `bit`) | Відстань |

Дві пастки задокументовані прямо. `<#>` повертає від'ємний скалярний добуток, «бо Postgres підтримує
лише сканування індексу в порядку `ASC`». `<=>` — це **відстань**, а не схожість: щоб отримати
схожість, треба порахувати `1 - (embedding <=> ...)`. Перевірмо обидві конверсії та один неприємний
наслідок вибору метрики:

```python
import math


def normalize(v):
    n = math.sqrt(sum(x * x for x in v))
    return [x / n for x in v]


def l2(a, b):
    return math.sqrt(sum((x - y) ** 2 for x, y in zip(a, b)))


def inner(a, b):
    return sum(x * y for x, y in zip(a, b))


def cosine_distance(a, b):
    return 1 - inner(normalize(a), normalize(b))


query = [3.0, 1.0, 2.0]
rows = {"a": [1.0, 2.0, 3.0], "b": [4.0, 5.0, 6.0], "c": [3.0, 1.0, 2.0]}

print(f"{'рядок':>6} {'<-> L2':>10} {'<#> (відʼємн. IP)':>18} {'<=> cosine dist':>17} {'1 - <=>':>9}")
for name, v in rows.items():
    print(f"{name:>6} {l2(v, query):10.4f} {-inner(v, query):18.4f} "
          f"{cosine_distance(v, query):17.4f} {1 - cosine_distance(v, query):9.4f}")

print("\nНенормалізовані вектори — порядок за L2 і за inner product відрізняється:")
by_l2 = sorted(rows, key=lambda n: l2(rows[n], query))
by_ip = sorted(rows, key=lambda n: -inner(rows[n], query))
print(f"  за L2            : {by_l2}")
print(f"  за inner product : {by_ip}")

print("\nТі самі вектори після нормалізації до довжини 1:")
norm_rows = {n: normalize(v) for n, v in rows.items()}
nq = normalize(query)
by_l2 = sorted(norm_rows, key=lambda n: l2(norm_rows[n], nq))
by_ip = sorted(norm_rows, key=lambda n: -inner(norm_rows[n], nq))
print(f"  за L2            : {by_l2}")
print(f"  за inner product : {by_ip}")
print(f"  порядки збігаються: {by_l2 == by_ip}")
```

**Фактичний вивід:**

```text
 рядок     <-> L2  <#> (відʼємн. IP)   <=> cosine dist   1 - <=>
     a     2.4495           -11.0000            0.2143    0.7857
     b     5.7446           -29.0000            0.1167    0.8833
     c     0.0000           -14.0000            0.0000    1.0000

Ненормалізовані вектори — порядок за L2 і за inner product відрізняється:
  за L2            : ['c', 'a', 'b']
  за inner product : ['b', 'c', 'a']

Ті самі вектори після нормалізації до довжини 1:
  за L2            : ['c', 'b', 'a']
  за inner product : ['c', 'b', 'a']
  порядки збігаються: True
```

Найголовніше тут — третій блок. Для **ненормалізованих** векторів L2 і скалярний добуток дають
**різні порядки**: за L2 рядок `c` абсолютно точний збіг, а за скалярним добутком першим іде `b`, бо
він просто довший. Документація радить: «якщо вектори нормалізовані до довжини 1 (як embeddings
OpenAI), використовуйте скалярний добуток для найкращої швидкості» — і саме тому, що після
нормалізації порядки збігаються. Практичний висновок: **метрика мусить відповідати тому, як
навчалася модель**. Модель нормалізує вихід, а ви будуєте індекс із `vector_l2_ops` — ви отримаєте
інший порядок і не побачите жодної помилки.

**Два типи індексів.** За замовчуванням pgvector виконує **точний** пошук, який дає ідеальний recall.
Індекс додають, щоб отримати наближений пошук: «на відміну від типових індексів, ви побачите різні
результати для запитів після додавання наближеного індексу».

| | HNSW | IVFFlat |
|---|---|---|
| Структура | Багаторівневий граф | Вектори діляться на списки |
| Побудова | Повільніша | Швидша |
| Пам'ять | Більше | Менше |
| Швидкість запиту | Кращий компроміс швидкість/recall | Гірший компроміс |
| Потрібні дані перед створенням | Ні (немає кроку навчання) | **Так** (є крок k-means) |
| Ключовий параметр побудови | `m` (16), `ef_construction` (64) | `lists` |
| Ключовий параметр запиту | `hnsw.ef_search` (40) | `ivfflat.probes` (1) |

Правила для IVFFlat: «створіть індекс **після** того, як у таблиці з'явилися дані; виберіть
відповідну кількість списків — гарний старт це `rows / 1000` для до 1M рядків і `sqrt(rows)` для
понад 1M; під час запиту вкажіть відповідну кількість проб — гарний старт це `sqrt(lists)`». Симптом
«після додавання IVFFlat-індексу запит повертає менше результатів» документація діагностує прямо:
«індекс, найімовірніше, було створено з замалою кількістю даних для такої кількості списків».

Створювати треба **окремий індекс на кожну функцію відстані**:

```sql
CREATE INDEX ON items USING hnsw (embedding vector_l2_ops);
CREATE INDEX ON items USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON items USING hnsw (embedding vector_ip_ops);
```

Допустимі розмірності обмежені типом: `vector` — до 2 000 вимірів, `halfvec` — до 4 000, `bit` — до
64 000, `sparsevec` — до 1 000 ненульових елементів. Якщо модель видає більше ніж 2 000 вимірів,
документація пропонує `halfvec`, індексацію підвекторів або зниження розмірності.

**Фільтрація — головна пастка.** З наближеними індексами «фільтрація застосовується **після** того, як
проскановано індекс». Документація дає арифметику: «якщо умова відбирає 10% рядків, то з HNSW і
усталеним `hnsw.ef_search = 40` у середньому збігатиметься лише 4 рядки». Запит поверне 4 результати
замість 5 і ви не побачите помилки. Виправлення — ітеративні сканування, додані у версії 0.8.0:

```sql
SET hnsw.iterative_scan = strict_order;   -- результати строго за відстанню
SET hnsw.iterative_scan = relaxed_order;  -- трохи розмитий порядок, кращий recall
```

Обмежувачі сканування: `hnsw.max_scan_tuples` (20 000 за замовчуванням), `hnsw.scan_mem_multiplier`
(множник до `work_mem`, за замовчуванням 1), `ivfflat.max_probes`. Окреме зауваження: якщо
`ivfflat.max_probes` менше за `ivfflat.probes`, використано буде `ivfflat.probes`.

**Пастка з індексом і `ORDER BY`.** Найчастіша причина «індекс не використовується»: запит мусить мати
`ORDER BY` і `LIMIT`, і `ORDER BY` мусить бути **результатом оператора відстані**, а не виразом.
`ORDER BY embedding <=> '...' LIMIT 5` використає індекс;
`ORDER BY 1 - (embedding <=> '...') DESC LIMIT 5` — ні.

**Робота з Python.** Пакет `pgvector-python` (версія 0.5.0) дає реєстрацію типів для драйверів; без
неї ви будете передавати рядки замість векторів:

```python
import psycopg
from pgvector.psycopg import register_vector

with psycopg.connect("dbname=test") as conn:
    register_vector(conn)
    with conn.cursor() as cur:
        cur.execute("SELECT * FROM items ORDER BY embedding <-> %s LIMIT 5", (query_vector,))
```

Для SQLAlchemy є тип `vector` із `pgvector.sqlalchemy` і реєстрація через подію `connect`; для
асинхронного psycopg — окрема функція `register_vector_async`.

**Гібридний пошук у самому Postgres.** pgvector BM25 не надає. Документація пропонує використовувати
його разом із вбудованим повнотекстовим пошуком:

```sql
SELECT id, content FROM items, plainto_tsquery('english', 'hello search') query
    WHERE textsearch @@ query
    ORDER BY ts_rank_cd(textsearch, query) DESC
    LIMIT 5;
```

і далі «використати Reciprocal Rank Fusion або cross-encoder, щоб об'єднати результати». Тобто злиття
ви робите самі. Альтернатива — `pg_search` від ParadeDB, де BM25 і вектори живуть в одному індексі
`USING paradedb`, а злиття можна зробити прямо в SQL через `RANK() OVER (...)` і `UNION ALL`.

**Типові помилки**

- **Переплутати відстань і схожість.** `<=>` — відстань; вища схожість означає **меншу** відстань.
  Сортувати за `DESC` для `<=>` — отримати найгірші результати першими.
- **Забути про знак у `<#>`.** Для справжнього скалярного добутку множте на `-1`.
- **Створити IVFFlat-індекс на порожній таблиці.** Він пройде k-means на порожніх даних і назавжди
  даватиме поганий recall.
- **Побудувати індекс із метрикою, що не відповідає моделі.**
- **Фільтрувати після наближеного індексу й дивуватися малій кількості результатів.** Увімкніть
  `hnsw.iterative_scan`, створіть частковий індекс (`... WHERE category_id = 123`) або партиціюйте.
- **Забути про `maintenance_work_mem` під час побудови HNSW.** Документація показує попередження
  `NOTICE: hnsw graph no longer fits into maintenance_work_mem after N tuples`. Там же застереження:
  не ставте значення таким, щоб вичерпати пам'ять сервера.
- **Будувати індекс до завантаження даних.** «Як і для інших типів індексів, швидше створити індекс
  після завантаження початкових даних». Для продакшну — `CREATE INDEX CONCURRENTLY`.
- **Не перевіряти recall.** Документація дає спосіб: виконати той самий запит із вимкненим індексом
  (`SET LOCAL enable_indexscan = off`) і порівняти результати.

**Альтернативи**

| Варіант | Коли доречний |
|---|---|
| pgvector | До ~десятків мільйонів векторів, потрібні транзакції й JOIN-и |
| pgvector + `halfvec` | Треба зменшити робочий набір удвічі |
| pgvector + бінарна квантизація | Треба втримати індекс у пам'яті; з переоцінкою повними векторами |
| `pg_search` (ParadeDB) | Потрібен справжній BM25 і гібрид в одному індексі |
| Окрема векторна БД (Qdrant) | Сотні мільйонів векторів, квантизація, складна фільтрація |
| pgvector + Citus / PgDog | Потрібне горизонтальне масштабування шардингом |
| `double precision[]` замість `vector` | Потрібна вища точність зберігання |

Бінарна квантизація в pgvector робиться через індексацію виразу, і документація показує обов'язковий
другий крок — переоцінку повними векторами:

```sql
CREATE INDEX ON items USING hnsw ((binary_quantize(embedding)::bit(3)) bit_hamming_ops);

SELECT * FROM (
    SELECT * FROM items ORDER BY binary_quantize(embedding)::bit(3) <~> binary_quantize('[1,-2,3]') LIMIT 20
) ORDER BY embedding <=> '[1,-2,3]' LIMIT 5;
```

Про мультиорендність документація застерігає окремо: «спільний наближений індекс між орендарями
означає, що вектори одного орендаря можуть впливати на recall (і швидкість) інших». Рішення —
секціонування за списком або окремі таблиці.

### 16.6 Повний конвеєр: індексація → запит → контекст → відповідь

**Що це.** Конвеєр RAG — сім етапів: три виконуються один раз під час індексації, чотири на кожен
запит.

| # | Етап | Коли | Що мусить залишити по собі |
|---|---|---|---|
| 1 | Видобування тексту | Індексація | Чистий текст + метадані джерела |
| 2 | Chunking | Індексація | Чанки з `doc_id`, `chunk_index`, зсувами |
| 3 | Збагачення і кодування | Індексація | Вектор + запис для лексичного індексу |
| 4 | Запит: дві гілки | Запит | Два відсортовані списки |
| 5 | Злиття | Запит | Один список кандидатів |
| 6 | Переранжування | Запит | Top-K для контексту |
| 7 | Формування промпту й відповідь | Запит | Текст із посиланнями |

**Навіщо це знати.** Конвеєр ламається на найслабшому етапі, а не на найдорожчому. Найчастіше — етап 2
(розірвана відповідь) або етап 6 (замалий пул кандидатів). Другий за частотою — розрив між тим, що ви
зберегли в метаданих, і тим, що можете показати користувачеві: без зсувів у документі посилання
неможливе, а без посилань відповідь неможливо перевірити.

**Як працює під капотом.** Повний конвеєр на локальних даних. Роль embeddings грає TF-IDF-косинус —
**навчальна заміна**, чесно позначена в коді; усе інше (чанки, метадані, дві гілки, RRF,
переранжування, промпт із посиланнями) справжнє.

```python
import math
import re
from collections import Counter, defaultdict

DOCS = {
    "broker.md": ("Брокер відкидає неактивні з'єднання через тридцять хвилин простою. "
                  "Щоб цього уникнути, надсилайте heartbeat кожні десять хвилин. "
                  "Інтервал heartbeat задається параметром keep_alive_interval "
                  "у конфігурації клієнта."),
    "tls.md": ("Помилка TS-999 означає невдалий TLS-рукостискання на транспортному рівні. "
               "Найчастіша причина — протермінований або невідповідний сертифікат. "
               "Перевірте ланцюжок сертифікатів і проміжний CA."),
    "keys.md": ("Ключі API обертаються без простою: створіть новий ключ, розгорніть його, "
                "дочекайтеся нуля запитів на старому і лише тоді відкличте старий ключ."),
}


def tokenize(text):
    return re.findall(r"\w+", text.lower())


def chunk(text, size=110, overlap=40):
    """Етап 2: чанки із ЗСУВАМИ — без них неможливі посилання на джерело."""
    out, start = [], 0
    while start < len(text):
        out.append((text[start:start + size], start))
        if start + size >= len(text):
            break
        start += size - overlap
    return out


INDEX = [{"id": f"{doc}#{i}", "doc": doc, "start": start,
          "end": start + len(piece), "text": piece}
         for doc, text in DOCS.items()
         for i, (piece, start) in enumerate(chunk(text))]


def bm25_scores(query, corpus, k1=1.5, b=0.75, epsilon=0.25):
    docs = [tokenize(d) for d in corpus]
    n_docs, avgdl = len(docs), sum(map(len, docs)) / len(docs)
    freqs = [Counter(d) for d in docs]
    df = Counter()
    for toks in docs:
        df.update(set(toks))
    idf = {t: math.log(n_docs - f + 0.5) - math.log(f + 0.5) for t, f in df.items()}
    eps = epsilon * (sum(idf.values()) / len(idf))
    for t, v in list(idf.items()):
        if v < 0:
            idf[t] = eps
    out = []
    for i, doc in enumerate(docs):
        acc = 0.0
        for t in tokenize(query):
            f = freqs[i].get(t, 0)
            if f:
                acc += idf[t] * (f * (k1 + 1)) / (f + k1 * (1 - b + b * len(doc) / avgdl))
        out.append((i, acc))
    return out


def tfidf_scores(query, corpus):
    """НАВЧАЛЬНА ЗАМІНА справжніх embeddings: та сама лексика, інша вага термінів."""
    docs = [tokenize(d) for d in corpus]
    df = Counter()
    for toks in docs:
        df.update(set(toks))
    n_docs = len(docs)
    vec = lambda toks: {t: (1 + math.log(cnt)) * math.log((n_docs + 1) / (df[t] + 1))
                        for t, cnt in Counter(toks).items()}
    q_vec = vec(tokenize(query))
    q_norm = math.sqrt(sum(v * v for v in q_vec.values())) or 1.0
    out = []
    for i, doc in enumerate(docs):
        doc_vec = vec(doc)
        doc_norm = math.sqrt(sum(v * v for v in doc_vec.values())) or 1.0
        out.append((i, sum(doc_vec[t] * q_vec.get(t, 0.0) for t in doc_vec) / (doc_norm * q_norm)))
    return out


def rank_all(pairs):
    return [i for i, _ in sorted(pairs, key=lambda kv: (-kv[1], kv[0]))]


def rrf(branch_lists, k=60):
    scores = defaultdict(float)
    for branch in branch_lists:
        for rank, idx in enumerate(branch, start=1):
            scores[idx] += 1.0 / (k + rank)
    return [i for i, _ in sorted(scores.items(), key=lambda kv: (-kv[1], kv[0]))]


def build_prompt(query, picked):
    lines = [f"Питання: {query}", "", "Джерела:"]
    for src_no, idx in enumerate(picked, start=1):
        src = INDEX[idx]
        lines.append(f"[{src_no}] {src['doc']} (символи {src['start']}..{src['end']}): "
                     f"{src['text'].strip()}")
    lines += ["", "Відповідай лише за наведеними джерелами. "
                  "Після кожного твердження став номер джерела у квадратних дужках."]
    return "\n".join(lines)


query = "як часто надсилати heartbeat"
texts = [c["text"] for c in INDEX]
lexical = rank_all(bm25_scores(query, texts))[:6]     # етап 4а
semantic = rank_all(tfidf_scores(query, texts))[:6]   # етап 4б
fused = rrf([lexical, semantic], k=60)                # етап 5
q_terms = set(tokenize(query))
picked = sorted(fused, key=lambda i: -len(q_terms & set(tokenize(INDEX[i]["text"]))))[:3]

print(f"Проіндексовано {len(INDEX)} чанків із {len(DOCS)} документів\n")
print(f"лексична гілка (BM25) : {[INDEX[i]['id'] for i in lexical]}")
print(f"семантична гілка      : {[INDEX[i]['id'] for i in semantic]}")
print(f"після RRF (k=60)      : {[INDEX[i]['id'] for i in fused]}")
print(f"у контекст пішло      : {[INDEX[i]['id'] for i in picked]}")
print()
print(build_prompt(query, picked))
```

**Фактичний вивід:**

```text
Проіндексовано 8 чанків із 3 документів

лексична гілка (BM25) : ['broker.md#1', 'broker.md#0', 'broker.md#2', 'tls.md#0', 'tls.md#1', 'tls.md#2']
семантична гілка      : ['broker.md#1', 'broker.md#0', 'broker.md#2', 'tls.md#0', 'tls.md#1', 'tls.md#2']
після RRF (k=60)      : ['broker.md#1', 'broker.md#0', 'broker.md#2', 'tls.md#0', 'tls.md#1', 'tls.md#2']
у контекст пішло      : ['broker.md#1', 'broker.md#0', 'broker.md#2']

Питання: як часто надсилати heartbeat

Джерела:
[1] broker.md (символи 70..180): цього уникнути, надсилайте heartbeat кожні десять хвилин. Інтервал heartbeat задається параметром keep_alive_
[2] broker.md (символи 0..110): Брокер відкидає неактивні з'єднання через тридцять хвилин простою. Щоб цього уникнути, надсилайте heartbeat ко
[3] broker.md (символи 140..212): artbeat задається параметром keep_alive_interval у конфігурації клієнта.

Відповідай лише за наведеними джерелами. Після кожного твердження став номер джерела у квадратних дужках.
```

У цьому запуску переранжування не змінило порядок: усі три чанки містять однакову кількість термінів
запиту, тож оцінки збіглися й порядок визначив попередній RRF. Це нормальна поведінка лексичної заміни
й ще одна причина, чому в продакшні потрібна справжня модель на парі.

**Посилання на джерела — не косметика.** Щоб користувач міг перевірити відповідь, чанк мусить знати,
**звідки** він; тому в індексі зберігаються `doc_id` і зсуви. Anthropic пропонує готовий механізм:
документи подаються як блоки `document` із `citations.enabled`, і відповідь приходить із блоками
посилань:

```json
{
  "type": "char_location",
  "cited_text": "The exact text being cited",
  "document_index": 0,
  "document_title": "Document Title",
  "start_char_index": 0,
  "end_char_index": 50
}
```

Формат залежить від типу документа: для PDF це діапазон номерів сторінок (нумерація з 1), для простого
тексту — діапазон індексів символів (з 0), для «custom content» — діапазон індексів блоків вмісту.
Документація дає дві вказівки:

- «Якщо ви хочете, щоб Claude міг цитувати конкретні речення з ваших RAG-чанків, покладіть кожен
  RAG-чанк в окремий документ простого тексту. Інакше, якщо ви не хочете подальшого розбиття або
  хочете налаштувати додаткове розбиття, покладіть RAG-чанки в документи custom content».
- `title` і `context` — необов'язкові поля, які передаються моделі, але **не** використовуються як
  цитований вміст; `title` обмежений за довжиною, тому `context` зручний для метаданих.

**Ціна посилань.** `cited_text` **не зараховується у вихідні токени**, і при передачі назад у
наступних ходах — теж не зараховується у вхідні. Водночас увімкнення citations трохи **збільшує
вхідні токени** через додавання до системного промпту й розбиття документів.

Два обмеження, які ламають архітектуру, якщо про них не знати:

1. **Citations несумісні зі structured outputs.** Якщо ввімкнути citations на будь-якому
   користувацькому документі й одночасно передати `output_config.format`, API поверне **400**.
   Причина в документації: «citations вимагають чергування блоків посилань із текстовим виводом, що
   несумісно зі строгими обмеженнями JSON-схеми structured outputs».
2. **Посилання працюють із кешуванням промпту, але не кешуються самі.** Блоки посилань закешувати не
   можна, а вихідні документи — можна; документація радить ставити `cache_control` на блоки
   документів верхнього рівня.

**Арифметика вартості.** Оцінка Anthropic для збагачення контекстом: за припущень 800-токенних чанків,
8k-токенних документів, 50 токенів інструкції та 100 токенів контексту на чанк одноразова вартість
становить **$1.02 на мільйон токенів документа**. Це одноразова витрата під час індексації — на
відміну від вартості пошуку, яка повторюється на кожен запит. Скільки чанків класти в контекст вони
теж виміряли: пробували 5, 10 і 20 і «знайшли, що 20 із цих варіантів найрезультативніше», додавши,
що «більше інформації може відволікати моделі, тож межа існує».

**Типові помилки**

- **Не зберігати зсуви в документі.** Без `start`/`end` ви не зможете ні показати посилання, ні
  підсвітити фрагмент. `add_start_index=True` у LangChain додає зсув автоматично.
- **Покладатися на нумерацію, яку модель вигадала сама.** Citations API гарантує валідність
  вказівників структурно, бо API сам розбирає їх у локації в документах.
- **Увімкнути citations і structured outputs одночасно.** Гарантований `400`.
- **Класти в контекст забагато чанків «про запас».** Зайві чанки — це не лише гроші, а й падіння
  якості.
- **Індексувати без версії.** Коли чанкер або модель embeddings змінилися, старі й нові вектори в
  одному індексі непорівнювані: вони лежать у різних просторах. Зберігайте `chunker_version` і
  `embedding_model` у кожному рядку.
- **Видаляти документ лише з векторного індексу.** Лексичний індекс і метадані залишаться, і злиття
  поверне «привид». Видалення мусить бути однією транзакцією на всі структури.
- **Забути про обмеження контексту на етапі формування промпту.** Сума чанків плюс історія розмови
  плюс системний промпт мусить вкладатися у вікно; обрізання треба робити явно.

**Альтернативи**

| Замість | Можна |
|---|---|
| RAG | Покласти весь корпус у промпт, якщо він менший за 200 000 токенів, із кешуванням |
| Векторний пошук | Контекстне збагачення + BM25 без embeddings для великих корпусів |
| Одна модель embeddings | Різні моделі для різних мовних сегментів корпусу |
| Citations API | Власні посилання через метадані зсувів у промпті |
| Статичний індекс | Інкрементальна переіндексація за журналом змін |

Перший рядок варто прочитати уважно, бо він суперечить інстинкту «RAG потрібен завжди». Anthropic
пише прямо: «Іноді найпростіше рішення — найкраще. Якщо ваша база знань менша за 200 000 токенів
(приблизно 500 сторінок матеріалу), ви можете просто включити всю базу знань у промпт, який даєте
моделі, без потреби в RAG». Оцінка відповідає вікну контексту на момент публікації; принцип
залишається: **RAG потрібен тоді, коли корпус не вміщується у вікно або коли ціна передачі всього
корпусу на кожен запит перевищує ціну пошуку.**

### 16.7 Типові помилки RAG

**Що це.** Каталог режимів відмови, згрупований за етапом конвеєра, із симптомом, причиною й способом
перевірки.

**Навіщо це знати.** Симптоми RAG майже ніколи не вказують на причину. «Модель вигадує» може означати,
що чанк не знайдено; «відповідь неповна» — що відповідь розірвана між чанками; «стало гірше після
додавання індексу» — що працює наближений пошук. Без каталогу ви будете міняти модель, коли треба
міняти `chunk_overlap`.

**Як працює під капотом.** Діагностика йде від симптому до причини: спершу вимірюють, потім змінюють.

| Симптом | Етап | Причина | Як перевірити |
|---|---|---|---|
| Відповідь є в документі, але не знаходиться | Chunking | Відповідь розірвана між чанками | Порахувати відстань між фактами й порівняти з `chunk_overlap` |
| Знаходиться не той чанк, схожий за словами | Немає гібрида | Лексичний збіг переміг зміст | Подивитися, чи є в контексті потрібний чанк узагалі |
| Рідкісний ідентифікатор не знаходиться | Гібрид | Немає лексичної гілки | Запит із точним кодом помилки або артикулом |
| Стало гірше після додавання індексу | pgvector | Фільтрація після сканування індексу | `SET LOCAL enable_indexscan = off` і порівняти |
| Порядок «дивний», оцінки великі | Метрика | Складаються оцінки різних шкал | Порахувати розподіл оцінок кожної гілки |
| Довгі документи завжди перемагають | BM25 | `b` замалий або дорівнює 0 | Порівняти ранжування за `b=0` і `b=0.75` |
| Форма слова не знаходиться | BM25 | Немає стемера/лематизатора | Запит із іншою словоформою |
| Модель цитує неіснуюче джерело | Етап відповіді | Нумерація вигадана моделлю | Перейти на Citations API |
| Відповідь правильна, але без посилань | Метадані | Не збережено зсуви в документі | Перевірити наявність `start`/`end` у чанку |
| Результатів менше за `LIMIT` | pgvector | Сканування зупинилося на `hnsw.ef_search` | `SHOW hnsw.ef_search;` і увімкнути `iterative_scan` |
| Після оновлення даних з'явилися «привиди» | Індексація | Дві структури оновлюються не в одній транзакції | Порахувати рядки в обох індексах |
| Якість падає після зміни моделі embeddings | Індексація | Старі й нові вектори в одному просторі | Перевірити `embedding_model` у метаданих |

**Типові помилки**

- **Оптимізувати генерацію, коли проблема в пошуку.** Перевіряйте спочатку `recall@N` першої стадії:
  якщо потрібного чанка немає в пулі кандидатів, жодна зміна промпту не допоможе.
- **Міряти recall на документах, а не на чанках.** Метрика на рівні документа приховує розрив чанка
  навпіл: документ «знайдено», а відповіді в контексті немає. Саме для цього техзвіт Chroma запровадив
  IoU на рівні токенів.
- **Будувати гібрид без нормалізації оцінок.** Фіксована `alpha` фактично визначається масштабом
  однієї гілки.
- **Вважати переранжування виправленням recall.** Друга стадія перевпорядковує наявних кандидатів, а
  не додає нових.
- **Переносити параметри між системами.** `k=60` в Elasticsearch і `k=2` у Qdrant; `k1=1.5` у
  `rank_bm25` і `k1=1.2` у ParadeDB.
- **Змішувати метрики відстані з різними моделями.** Ненормалізовані вектори з L2 і зі скалярним
  добутком дають різні порядки.
- **Не тримати оцінний набір.** Без 30–50 пар «запит → правильний уривок» неможливо відрізнити
  покращення від зміни.
- **Плутати символи, токени й розмірність вектора.** Три різні числа з трьома різними лімітами.

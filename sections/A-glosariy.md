## Додаток A. Глосарій термінів

Довідник уживає англомовну термінологію API та дослідницьких статей. Цей додаток зводить її в одну
таблицю: англійський термін → український відповідник → визначення → номер розділу, де термін
пояснюється докладніше.

Це **повна** версія словника з підтеми 1.6. Там наведено мінімум, потрібний для читання з першого
розділу; тут — усі терміни, ужиті в розділах 1–25, згруповані за темами. Визначення тут докладніші,
але не суперечать розділу 1.

**Як користуватися.** Колонка «Розділ» указує, де термін не просто трапляється, а **пояснюється**.
Якщо термін ужито в багатьох розділах, наведено перший ґрунтовний. Позначка «додаток A» означає, що
докладнішого пояснення в розділах немає і цей додаток — єдине місце з визначенням.

### A.1 Токени й обчислення

| Термін (EN) | Українською | Визначення | Розділ |
|---|---|---|---|
| `token` | токен | Елемент словника моделі: ціле слово, частина слова, символ або байт. Одиниця білінгу, лімітів швидкості й контекстного вікна | 3 |
| `token id` | числовий ідентифікатор токена | Ціле число зі словника, яким токенізатор позначає фрагмент тексту. Ембединги, увага й вихідний шар оперують саме ідентифікаторами | 3 |
| `tokenizer` | токенізатор | Компонент, що перетворює текст у послідовність токенів і назад. У кожної моделі власний токенізатор, тому той самий текст дає різну кількість токенів | 3 |
| `tokenization` | токенізація | Розбиття тексту на токени за фіксованим словником і вивченими правилами злиття. Результат визначається частотою фрагментів у корпусі, а не природністю поділу слів | 3 |
| `vocabulary` (vocab) | словник | Скінченний набір токенів, відомих моделі. Розмір словника впливає на довжину послідовності для того самого тексту | 3 |
| `BPE` (byte-pair encoding) | байт-парне кодування | Алгоритм побудови словника: стартують з окремих байтів, далі ітеративно додають найчастішу пару сусідніх символів як новий токен | 3 |
| `byte-level BPE` | байтовий BPE | Варіант BPE, у якому базовий алфавіт — байти. Словник не буває неповним: будь-який текст кодується без «невідомого» токена | 3 |
| `merge` | мерж (злиття) | Правило об'єднання двох сусідніх токенів в один, вивчене на корпусі. Для англійських морфем мержів багато, для кириличних — значно менше | 3 |
| `WordPiece` | WordPiece | Альтернативний субсловний алгоритм; маркер продовження слова — префікс `##` | 3 |
| `Unigram` | Unigram | Субсловний алгоритм, що вибирає найімовірніше розбиття за ймовірнісною моделлю словника; реалізований у SentencePiece | 3 |
| `SentencePiece` | SentencePiece | Бібліотека токенізації, яка працює з сирим текстом без попереднього поділу на слова | 3 |
| `UTF-8` | UTF-8 | Кодування, у якому символ латиниці займає 1 байт, кирилиці — 2 байти, емодзі — 4. Тому кириличний текст дає більше токенів | 3 |
| `special token` | спецтокен | Елемент словника, що не є текстом: маркер ролі, межа послідовності, маркер інструмента. Модель бачить його як звичайний id | 3 |
| `split_special_tokens` | розбиття спецтокенів | Параметр токенізатора: при істині рядок службового маркера розпадається на звичайні токени й втрачає роль | 3 |
| `bos_token` | початковий токен | Службовий токен початку послідовності. Якщо в конфізі він порожній, додавання BOS вручну формує помилковий вхід | 3 |
| `eos_token` | кінцевий токен | Токен, який модель генерує, завершуючи репліку. Якщо формувати вхід вручну й не передати його, модель може не зупинитися | 3 |
| `pad_token` | токен доповнення | Службовий токен вирівнювання послідовностей за довжиною; у конфізі може збігатися з кінцевим | 3 |
| `added_tokens_decoder` | мапа доданих токенів | Блок конфігу токенізатора, що зіставляє id доданих токенів з їхнім вмістом і прапорцем special | 3 |
| `tokenizer_config.json` | конфіг токенізатора | JSON-файл у репозиторії моделі з класом токенізатора, службовими токенами, списком доданих токенів і chat-шаблоном | 3 |
| `model_max_length` | максимальна довжина токенізатора | Гранична довжина послідовності, під яку налаштований токенізатор. Не є гарантованою межею контексту моделі | 3 |
| `chat template` | chat-шаблон | Функція перетворення списку повідомлень у послідовність токенів із службовими маркерами; зазвичай описана як шаблон Jinja2 | 3 |
| `chat_template` | ключ chat_template | Ключ конфігу токенізатора, у якому лежить текст шаблону | 3 |
| `Jinja2` | Jinja2 | Рушій шаблонів Python, яким описано більшість chat-шаблонів. Дозволяє відрендерити шаблон офлайн, без моделі й GPU | 3 |
| `apply_chat_template` | застосування chat-шаблону | Метод токенізатора Transformers, що рендерить шаблон для списку повідомлень і за потреби повертає тензори | 3 |
| `add_generation_prompt` | маркер початку відповіді | Параметр apply_chat_template, що додає в кінець входу маркер відкриття ходу асистента. Без нього модель може продовжити репліку користувача | 3 |
| `continue_final_message` | продовження останнього повідомлення | Параметр, що не закриває останнє повідомлення, а лишає його відкритим для продовження моделлю | 3 |
| `add_special_tokens` | додавання службових токенів | Параметр токенізації, що керує вставкою початкового й кінцевого токенів. Для вже відрендереного шаблону його ставлять у хибність | 3 |
| `FULLWIDTH VERTICAL LINE` | повноширинна вертикальна риска | Символ U+FF5C, візуально майже ідентичний ASCII-рисці, але з іншою кодовою точкою. Ужитий у службових токенах DeepSeek | 3 |
| `LOWER ONE EIGHTH BLOCK` | нижній восьминний блок | Символ U+2581, яким SentencePiece позначає пробіл усередині токена; підміна його на пробіл ламає відповідність токену | 3 |
| `context window` | контекстне вікно | Усе, що модель бере до уваги в одному запиті, включно з відповіддю. Вхід і вихід ділять один ліміт | 3 |
| `input tokens` | вхідні токени | Токени промпту, системних інструкцій, історії, визначень інструментів і прикріплених даних | 2 |
| `output tokens` | вихідні токени | Токени, згенеровані моделлю, включно з токенами мислення. Тарифікуються дорожче за вхідні | 2 |
| `max_tokens` | ліміт вихідних токенів | Параметр запиту з абсолютною межею генерації. Токени мислення є підмножиною цього ліміту | 3 |
| `context rot` | деградація на довгому контексті | Падіння точності відтворення інформації в міру зростання кількості токенів. Наслідок: велике вікно не гарантує якості | 3 |
| `thinking tokens` | токени мислення | Токени внутрішнього міркування. Тарифікуються як вихід, входять у max_tokens і враховуються в лімітах швидкості | 3 |
| `count_tokens` | підрахунок токенів | Ендпоінт Anthropic, що приймає той самий структурований вхід, що й створення повідомлення, і повертає оцінку вхідних токенів до відправки | 3 |
| `usage` | статистика використання | Поле відповіді з фактично спожитими токенами. Джерело істини для білінгу, на відміну від оцінки count_tokens | 3 |
| `input_tokens` | вхідні токени після точки кешування | Лічильник у полі usage: токени запиту без прочитаних із кешу та записаних у кеш | 3 |
| `output_tokens` | вихідні токени | Лічильник у полі usage: токени згенерованої відповіді, включно з міркуванням | 3 |
| `cache_read_input_tokens` | вхідні токени з кешу | Лічильник частини входу, прочитаної з кешу промпту. Враховується в контекстному вікні, але тарифікується інакше | 3 |
| `cache_creation_input_tokens` | вхідні токени створення кешу | Лічильник частини входу, записаної в кеш промпту цим запитом | 3 |
| `Base64` | Base64 | Кодування довільних даних у текстовий алфавіт із практично непередбачуваною послідовністю символів; мержі для нього майже не утворюються | 3 |
| `server tools` | серверні інструменти | Інструменти, які виконує сам провайдер: вебпошук, завантаження сторінок, виконання коду. Їх не приймає count_tokens | 3 |
| `MCP connector` | MCP-конектор | Механізм підключення зовнішніх MCP-серверів як джерела інструментів; не підтримується в count_tokens | 3 |
| `inference` | інференс | Виконання моделі на вході для отримання виходу: префіл вхідної послідовності та генерація токенів | 2 |
| `prefill` | префіл | Фаза обробки всієї вхідної послідовності перед початком генерації. Від неї залежить час до першого токена | 2 |
| `decoding` | декодування | Фаза послідовної генерації вихідних токенів по одному; її швидкість вимірюють у токенах за секунду | 2 |
| `greedy decoding` | жадібне декодування | Вибір найімовірнішого токена на кожному кроці, без семплювання | 3 |
| `logit` | логіт | Ненормована оцінка кожного токена словника перед перетворенням у ймовірності | 3 |
| `temperature` | температура | Масштаб розподілу ймовірностей; вище значення дає різноманітніший вихід | 3 |
| `top_p` | top-p (ядерне семплювання) | Обмеження вибору токенами, що в сумі дають задану ймовірність | 3 |
| `top_k` | top-k | Обмеження вибору K найімовірнішими токенами | 3 |
| `KV cache` | KV-кеш | Збережені вектори ключів і значень уваги для вже оброблених токенів. Розмір зростає з довжиною контексту й визначає споживання пам'яті | 2 |
| `long context` | довгий контекст | Режим роботи з великою кількістю вхідних токенів: більше матеріалу ціною вищої вартості, пам'яті й ризику деградації | 2 |
| `TTFT` (time to first token) | час до першого токена | Затримка від надсилання запиту до появи першого токена відповіді; визначається переважно префілом | 2 |
| `tokens/sec` | токенів за секунду | Пропускна здатність генерації. Залежить від розміру моделі, KV-кешу й навантаження на пристрій | 2 |
| `billing` | білінг | Облік спожитих токенів: ціни оголошують за мільйон токенів, ліміти швидкості — у токенах за хвилину | 2 |
| `compaction` | компакція контексту | Серверне стиснення історії діалогу, коли розмова наближається до межі вікна | 3 |
| `reasoning_content` | поле міркувань | Окреме поле повідомлення асистента для вмісту каналу мислення в OpenAI-сумісних моделях | 3 |

### A.2 Керування моделлю

| Термін (EN) | Українською | Визначення | Розділ |
|---|---|---|---|
| `Messages API` | API повідомлень | Точка входу Anthropic для генерації: `POST /v1/messages` приймає структурований список повідомлень і повертає наступне повідомлення розмови | 4 |
| `Message` | об'єкт відповіді | Те, що повертає API: масив блоків content, причина зупинки, поле stop_sequence, деталі відмови й лічильники usage | 4 |
| `content block` | блок контенту | Елемент масиву content з полем type: text, thinking, redacted_thinking, tool_use, tool_result, server_tool_use | 4 |
| `stateless` (Messages API) | без збереження стану | Властивість Messages API: сервер не тримає історію, тому кожен запит мусить містити всю розмову | 4 |
| `role` | роль повідомлення | Значення user, assistant або system; послідовні однакові ролі API зливає в один хід | 4 |
| `top-level system` | системний промпт верхнього рівня | Окремий параметр запиту поза messages. Масив блоків потрібен, коли всередину системного тексту ставлять точку кешування | 4 |
| `prefill` (message prefilling) | попереднє заповнення відповіді | Хід асистента останнім у messages, з якого модель продовжує відповідь. На Claude 4.6 і пізніших прибрано: такий запит повертає 400 | 4 |

| `stop_sequences` | власні стоп-послідовності | Масив рядків, на генерації яких модель зупиняється зі значенням stop_reason рівним stop_sequence | 4 |
| `service_tier` | рівень обслуговування | Поле usage зі значенням standard, priority або batch: показує, за яким тарифом обслуговано запит | 4 |
| `output_config.format` | формат виходу | Поле запиту зі схемою виходу (структурований вивід); надійніша заміна проханню в промпті | 4 |
| `tool_choice` | вибір інструмента | Поле запиту зі значеннями auto, any, tool (з полем name) і none; керує тим, чи мусить модель викликати інструмент | 4 |
| `sampling parameters` | параметри семплювання | Поля temperature, top_p, top_k. На моделях після Opus 4.6 top_k не приймається, а top_p — лише не менше 0.99 | 4 |
| `inference_geo` | регіон інференсу | Поле запиту, що задає регіон виконання інференсу; типово береться з налаштування робочого простору | 4 |
| `metadata` | метадані запиту | Поле з непрозорим ідентифікатором користувача до 512 символів; імена й email туди не передають | 4 |
| `stream` | інкрементальна віддача | Поле запиту, що вмикає віддачу відповіді через SSE. Без нього SDK попереджає про запит, довший приблизно за 10 хвилин | 4 |

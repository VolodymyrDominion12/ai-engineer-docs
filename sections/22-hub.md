## 22. Hugging Face Hub: CLI, Jobs, Xet

Hub — це не «сайт з моделями», а три підсистеми, які працюють разом: **сховище артефактів**
(git-репозиторії для моделей, датасетів і Spaces), **бекенд зберігання Xet** (контентно-адресоване
сховище з дедуплікацією на рівні байтів) і **керовані обчислення Jobs** (запуск довільного
Docker-образу на залізі Hugging Face).

Станом на 26.09.2026 PyPI віддає `huggingface_hub` **2.0.0** (файл опубліковано 2026-09-24,
`requires_python >= 3.10.0`); селектор версій документації містить `v2.0.0`, `v1.33.0`, `v1.32.0` і
старіші — лінійка 1.x закрита, 2.0 поточна. Дві події визначають сьогоднішній стан інструментів:

1. **`hf` CLI замінив `huggingface-cli`** (реліз v1.0, 27 жовтня 2025 року). Це не перейменування, а
   інша модель команд: ресурс плюс дія (`hf repos create`, `hf cache ls`, `hf jobs run`), спільні
   прапорці форматування виводу і вихід у JSON для скриптів.
2. **Усі репозиторії переведено на бекенд Xet.** За блогом v1.0 міграція стартувала з 20 ПБ у понад
   500 000 репозиторіїв, а через рік охопила **77+ ПБ у 6+ мільйонах репозиторіїв** — без участі
   користувачів. Пакет `hf_xet` замінив `hf_transfer` і став типовим шляхом для всіх передач файлів.

Практичний наслідок: **розмір файлу більше не визначає, скільки трафіку піде на його оновлення**.
Git LFS помічає лише факт зміни файлу й зберігає ревізію цілком; Xet ріже файл на чанки (~64 КБ) за
вмістом і передає тільки ті чанки, яких у сховищі ще немає.

**Межа чесності цього розділу.** Усі назви команд, прапорців, лімітів, цін і чисел тут узяті з файлів
`research/`, перелічених у кінці. Три місця, де джерела не дають відповіді, позначені прямо в тексті:
числовий поріг переходу файлу в LFS (22.2), точний алгоритм rolling hash у Xet (22.3) і розбіжність
між «оплата за секунди» та «оплата за хвилини» в Jobs (22.4). Там, де числа джерел не сходяться між
собою, це показано з арифметикою.

### 22.1 `hf` CLI: авторизація, репозиторії, завантаження

**Що це.** `hf` — консольна утиліта, яка входить у сам пакет `huggingface_hub` (окремого extra
`huggingface_hub[cli]` більше немає). Вона покриває автентифікацію, керування репозиторіями,
завантаження й вивантаження файлів, локальний кеш, кошики (buckets) і Jobs.

**Навіщо це знати.** CLI — це найкоротший шлях до Hub у трьох ситуаціях: (1) потрібно один раз
авторизуватися на машині, і далі всі бібліотеки (`transformers`, `datasets`, `diffusers`) беруть токен
самі; (2) потрібні скрипти й CI, де важливий стабільний машинний вивід (`--format json`, `-q`) і
передбачувані коди виходу; (3) потрібно вивантажити теку, яка не вміщається в один коміт, і отримати
автоматичне розбиття й докачку після збою. У Python-коді замість CLI використовують `HfApi` — це той
самий HTTP-шар, лише викликаний напряму.

**Як працює під капотом.**

*Встановлення.* Standalone-інсталятор (`curl -LsSf https://hf.co/cli/install.sh`, на Windows —
`irm https://hf.co/cli/install.ps1 | iex`) ставить CLI окремо від Python-середовища й додатково skill
`hf-cli` для AI-агентів, які читають `~/.agents/skills` (`--exclude-skill` це вимикає). `uvx hf ...`
запускає найновішу версію без встановлення, `pip install -U "huggingface_hub"` ставить CLI разом із
бібліотекою, `brew install hf` — для macOS. `hf update` сам визначає спосіб встановлення й оновлює.

*Автентифікація.* `hf auth login` за замовчуванням відкриває браузерний потік: CLI друкує URL
`https://huggingface.co/oauth/device` і короткий код, після підтвердження зберігає токен у
`~/.cache/huggingface/stored_tokens` (активний — у `~/.cache/huggingface/token`). Токен має строк дії,
але оновлюється автоматично, поки ним користуються; для скриптів є `hf auth login --token "$HF_TOKEN"`
(інтерактивний режим не підтримує `--format json` і `--format quiet`). Асиметрія, яку легко проґавити:
**змінна `HF_TOKEN` перекриває збережений токен**, і `hf auth logout` у такому разі не розлогінює.
Допоміжні команди: `hf auth whoami`, `hf auth list`, `hf auth switch --token-name ...`,
`hf auth token` (для `curl -H "Authorization: Bearer ..."`).

*Формат виводу.* Усі команди приймають однаковий набір прапорців, і це те, що робить CLI придатним для
автоматизації:

| Прапорець | Еквівалент | Що робить |
|---|---|---|
| `--format <auto\|human\|agent\|json\|quiet>` | — | явний вибір формату |
| `--json` | `--format json` | структурований JSON — для `jq` |
| `-q`, `--quiet` | `--format quiet` | лише ідентифікатори, по одному в рядку |
| `--no-truncate` | — | не скорочувати довгі значення в таблицях |

`auto` (типово) вибирає `human` для інтерактивного термінала й `agent`, якщо CLI викликав AI-агент.
`human` дає кольори й таблиці, які самі підганяються під ширину термінала; `agent` — значення,
розділені табуляцією, без скорочень. Спроба змішати два режими (наприклад, `--json` разом із
`--format table`) — помилка використання, команда не запуститься.

*Ресурсно-дієва модель.* Командна поверхня будується як «ресурс → дія»; повний перелік гілок — у
прикладі нижче. Окремо варто знати `hf lfs-enable-largefiles`: вона налаштовує git-lfs на multipart-агент
для файлів **понад 5 ГБ** і потрібна лише тим, хто ходить у Hub через `git push`, а не через HTTP-API.

*Як передаються файли.* `hf download` усередині викликає `hf_hub_download()` і `snapshot_download()`,
`hf upload` — `upload_file()` і `upload_folder()`. Два режими завантаження: у **кеш** (типово,
`$HF_HOME/hub` або шлях із `--cache-dir`) і в **локальну теку** (`--local-dir`); у другому випадку
всередині вашої теки створюється `.cache/huggingface/` з метаданими, які й дають змогу довантажувати
лише змінені файли. Типовий таймаут на читання — 10 секунд (`HF_HUB_DOWNLOAD_TIMEOUT`); на повільному
каналі його піднімають, інакше отримаєте `httpx.TimeoutException` на `cdn-lfs-us-1.huggingface.co`.
Замість окремих `--repo-type`, `--revision` і шляху можна передати один URI
`hf://[<TYPE>/]<ID>[@<REVISION>][/<PATH>]` (кінцевий `/` — підтека, гілка з `/` кодується як `%2F`);
поєднувати URI з цими прапорцями не можна — буде помилка.

**Приклад.** Нижче — реєстр команд і програмна збірка командних рядків. Код не звертається до мережі:
він лише будує рядки за описаними вище правилами, тому його можна запускати в будь-якому середовищі.

```python
# ── 22.1 ── Реєстр гілок CLI та генерація командних рядків.
# Джерело складу команд: research/hf5_cli_ref.txt (package_reference/cli).
CLI_TREE = {
    "auth": ["list", "login", "logout", "switch", "token", "whoami"],
    "repos": ["ls", "create", "delete", "move", "settings", "delete-files", "branch"],
    "download": ["<repo_id> <filenames>..."],
    "upload": ["<repo_id> <local_path> <path_in_repo>"],
    "cache": ["ls", "rm", "prune", "verify"],
    "jobs": ["run", "uv run", "ps", "inspect", "logs", "stats", "wait",
             "cancel", "hardware", "labels", "ssh", "scheduled"],
    "buckets": ["create", "ls", "info", "settings", "rm", "sync"],
    "env": [], "version": [],
}


def hf(*parts, **flags):
    """Збирає командний рядок: позиційні частини, потім прапорці у сталому порядку."""
    line = " ".join(("hf",) + tuple(parts))
    for key, value in flags.items():
        flag = "--" + key.replace("_", "-")
        line += f" {flag}" if value is True else f" {flag} {value}"
    return line


COMMANDS = [
    (hf("download", "openai-community/gpt2", "config.json", quiet=True), False),
    (hf("repos", "ls", type="model", limit=0), False),
    (hf("cache", "ls", format="json", limit=20), False),
    (hf("auth", "login", token="$HF_TOKEN"), True),
    (hf("repos", "create", "my-org/whisper-uk", repo_type="dataset", private=True), True),
    (hf("upload", "my-org/whisper-uk", "./data", "/train",
        repo_type="dataset", commit_message="Epoch 34/50"), True),
    (hf("upload", "my-org/whisper-uk", "logs/", every=10), True),
    (hf("jobs", "run", "python:3.12", "python", "-c", "print(1)",
        flavor="cpu-basic", detach=True), True),
]

print("Гілки CLI (з package_reference/cli):")
for resource, actions in CLI_TREE.items():
    print(f"  hf {resource:9} " + (", ".join(actions) if actions else "—"))
print()
print(f"{'команда':96}{'токен'}")
print("-" * 104)
for line, needs_token in COMMANDS:
    print(f"{line:96}{'так' if needs_token else 'ні'}")
print("-" * 104)
writes = sum(1 for _, needs in COMMANDS if needs)
print(f"Запис (або вхід) потребує токена: {writes} із {len(COMMANDS)}; "
      f"читання публічних моделей — без токена")
```

**Фактичний вивід**

```text
Гілки CLI (з package_reference/cli):
  hf auth      list, login, logout, switch, token, whoami
  hf repos     ls, create, delete, move, settings, delete-files, branch
  hf download  <repo_id> <filenames>...
  hf upload    <repo_id> <local_path> <path_in_repo>
  hf cache     ls, rm, prune, verify
  hf jobs      run, uv run, ps, inspect, logs, stats, wait, cancel, hardware, labels, ssh, scheduled
  hf buckets   create, ls, info, settings, rm, sync
  hf env       —
  hf version   —

команда                                                                                         токен
--------------------------------------------------------------------------------------------------------
hf download openai-community/gpt2 config.json --quiet                                           ні
hf repos ls --type model --limit 0                                                              ні
hf cache ls --format json --limit 20                                                            ні
hf auth login --token $HF_TOKEN                                                                 так
hf repos create my-org/whisper-uk --repo-type dataset --private                                 так
hf upload my-org/whisper-uk ./data /train --repo-type dataset --commit-message Epoch 34/50      так
hf upload my-org/whisper-uk logs/ --every 10                                                    так
hf jobs run python:3.12 python -c print(1) --flavor cpu-basic --detach                          так
--------------------------------------------------------------------------------------------------------
Запис (або вхід) потребує токена: 5 із 8; читання публічних моделей — без токена
```

Вивід показує головну властивість нової CLI: **спільні прапорці працюють на всіх гілках**. `--quiet`,
`--format json` і `--limit` є і в `hf cache ls`, і в `hf repos ls`, і в `hf jobs ps` — тому один код
розбору виводу обслуговує різні команди. Друга деталь: `hf upload` створює репозиторій, якщо його
немає, тож `hf repos create` у скрипті — це явний контроль (ідемпотентність дає `--exist-ok`). Третя:
токен потрібен лише там, де є запис — три команди з восьми обходяться без нього.

**Типові помилки**

- **Поєднувати URI з `--repo-type` або `--revision`.** `hf download hf://datasets/org/ds ./out
  --repo-type dataset` завершиться помилкою: тип і ревізія вже всередині URI.
- **Парсити людський вивід.** Таблиці `human` скорочують довгі значення через `...`, і парсер
  зламається на довгому `repo_id`. Для скриптів — `--format json` або `-q`; `--no-truncate` лише
  вимикає скорочення, але не робить вивід стабільним форматом.
- **Покладатися на `--create-pr` при повторному запуску.** Повторний запуск вивантаження з
  `--create-pr` відкриває **новий** pull request. Документація радить для продовження передавати
  `--revision="refs/pr/N"`.
- **Забути про таймаут завантаження.** Типові 10 секунд на читання — замало для перевантаженого
  каналу; лікується `HF_HUB_DOWNLOAD_TIMEOUT`, а не повторними запусками.
- **Плутати `--quiet` із «без помилок».** `--quiet` друкує лише останній рядок (шлях або URL), але
  помилки однаково йдуть у stderr і код виходу буде ненульовим.

**Альтернативи**

| Інструмент | Коли брати | Обмеження |
|---|---|---|
| `hf` CLI | ручні операції, CI-скрипти, швидка діагностика | процес на кожен виклик, немає типізації |
| `HfApi` (Python) | усе, що всередині застосунку: коміти, колбеки, фон | потребує коду й обробки помилок |
| `uvx hf ...` | разовий запуск без встановлення, ізольовані версії | завантажує пакет щоразу |
| git + git-lfs | коли потрібна повна історія в git-клієнті, теги, хуки | файли > 5 ГБ потребують `hf lfs-enable-largefiles` |
| `hf cp` / `hf buckets sync` | копіювання й синхронізація великих обсягів, кошики | працює з файлами, а не з git-історією |

### 22.2 Робота з великими файлами й LFS-межами

**Що це.** Hub версіонує дані через git, а великі бінарні файли зберігає окремо, лишаючи в
git-історії **LFS-вказівник** — текстовий опис із трьох рядків. Поверх цього діють два різні набори
обмежень: квоти сховища на рівні акаунта й технічні рекомендації на рівні репозиторію.

**Навіщо це знати.** Вивантаження, яке падає на останній хвилині після години передачі, — не
рідкісний випадок, а типова поведінка системи, що має серверні перевірки й таймаути. Більшість цих
падінь зникає, якщо структурувати репозиторій за рекомендаціями й вивантажувати через
`hf upload`/`upload_folder()`, які самі розбивають великі теки на кілька комітів.

**Як працює під капотом.**

*Обмеження репозиторію.* Документація `hub/storage-limits` дає таблицю, яка не залежить від вашого
тарифу:

| Характеристика | Рекомендація | Що робити, якщо перевищено |
|---|---|---|
| Розмір репозиторію | — | платити за сховище або домовлятися про великі обсяги (ТБ) |
| Файлів на репозиторій | < 100 000 | об'єднати дані в менше файлів |
| Записів у теці | < 10 000 | розкласти по підтеках |
| Розмір файлу | < 200 ГБ | розбити на частини |
| Файлів на коміт | < 100 | `upload_folder`/`hf upload` роблять це автоматично |
| Комітів на репозиторій | — | групувати файли в коміти та робити squash історії |

Жорстка межа для одного файлу — **500 ГБ** («no single file will exceed 500GB»). Причина не в сховищі,
а в роздачі: файли віддаються через CloudFront, і дуже великі файли він, за досвідом HF, не кешує.

*Серверні перевірки й таймаути.* Під час коміту кожна git-операція перевіряється сервером. HTTP-запит
на коміт має таймаут **60 секунд**, і якщо клієнт його перевищив, операція може все одно завершитися на
сервері — це перевіряють вручну на сторінці репозиторію. Документація радить триматися 50–100 файлів на
коміт; `upload_folder()` і `hf upload` роблять це автоматично й додають до повідомлень комітів суфікси
` (part 2)`, ` (part 3)`, коли тека велика.

*Що саме лежить у git.* У прикладі документації LFS-вказівник для файлу `model.safetensors` розміром
440 449 768 байтів виглядає так:

```text
version https://git-lfs.github.com/spec/v1
oid sha256:68d45e234eb4a928074dfd868cead0219ab85354cc53d20e772753c6bb9169d3
size 440449768
```

Тобто в git-історії зберігається **133 байти** замість 440 МБ. Звідси два наслідки, які часто
плутають: видалення самого вказівника не звільняє місце (звільняє лише видалення блобу), а
переписування історії без оновлення вказівників ламає майбутні `checkout` — документація радить
додати в `.gitconfig` рядок `lfs.skipdownloaderrors=true`.

*Квоти.* Обмеження сховища діють на акаунт або організацію, а не на репозиторій:

| Тип акаунта | Публічне сховище | Приватне сховище |
|---|---|---|
| Безкоштовний користувач або організація | best-effort | 100 ГБ |
| PRO | до 10 ТБ включно + add-on | 1 ТБ + pay-as-you-go |
| Team Organizations | 12 ТБ база + 1 ТБ на місце + add-on | 1 ТБ на місце + pay-as-you-go |
| Enterprise Organizations | 200 ТБ база + 1 ТБ на місце | 1 ТБ на місце + pay-as-you-go |

Публічний add-on коштує 12 $/ТБ/місяць (від 50 ТБ — 10 $/ТБ/місяць), приватне сховище понад
включений обсяг — 18 $/ТБ/місяць із знижками за обсяг. Важлива примітка документації: **ці
обмеження не застосовуються до Storage Buckets** — кошиків, які не версіонуються через git.

*Вивантаження як конвеєр, а не як «хешувати все, потім слати»*. Коли встановлено `hf_xet` (типово з
`huggingface_hub` 0.32.0 і далі), `upload_folder()` працює потоково: файли перевіряються на Hub,
вивантажуються в Xet-сховище (де чанкуються, дедуплікуються й повторюються при збоях) і комітяться
адаптивними батчами паралельно. Три властивості випливають прямо: **поновлюваність** (повторний запуск
пропускає вже закомічені файли, а вже вивантажені чанки дедуплікуються; локального стану немає, тож
продовжити можна з іншої машини), **без подвійного читання** (файли хешуються в тому самому проході, у
якому чанкуються) і **деградація без `hf_xet`** (спершу хешування всього, потім вивантаження по HTTP,
потім один коміт).

*Швидкодія й диск.* Для максимальної пропускної здатності є `HF_XET_HIGH_PERFORMANCE=1` — режим
насичує мережу й задіює всі ядра CPU (старий `HF_HUB_ENABLE_HF_TRANSFER=1` більше нічого не робить).
Під час вивантаження з кластера, де файли лежать на мережевій ФС (NFS, Lustre, EBS), кеш Xet варто
перенести на локальний диск через `HF_XET_CACHE` — типово він у `~/.cache/huggingface/xet`.

*Окремий випадок.* Якщо файли генеруються в пам'яті (шарди датасету), їх можна вивантажити поштучно
через `preupload_lfs_files()` і зробити **один** коміт у кінці. Документація називає це
power-user-методом: до коміту файли на Hub недоступні, а об'єкт `CommitOperationAdd` **мутується** —
після попереднього вивантаження з нього зникає бінарний вміст.

**Приклад.** Модель репозиторію проти лімітів і вартість LFS-вказівників — усе обчислюється локально.

LFS-вказівник займає 0.00003% обсягу блобу — тому «прибрати файли з git» і «звільнити місце» — різні

*Чого джерела не дають.* Числовий поріг, за яким Hub автоматично переводить файл у LFS (і чи є такий
поріг узагалі в HTTP-API), у наявних файлах `research/` не наведено — **не вдалося підтвердити станом
на 09.2026**. Підтверджені факти лише про наслідки: у git лежить вказівник, а `hf lfs-enable-largefiles`
потрібен для файлів понад 5 ГБ у git-шляху.

**Типові помилки**

- **Вивантажувати теку з 50 000 файлів одним комітом.** Отримаєте таймаут 60 секунд на HTTP-запит,
  причому операція може завершитися на сервері після помилки на клієнті. Лікується використанням
  `hf upload`/`upload_folder()`, які комітять частинами.
- **Зберігати `CommitOperationAdd` після `preupload_lfs_files()`.** Об'єкт мутується — бінарний вміст
  із нього видаляється, і якщо ви покладалися на нього як на джерело даних, отримаєте порожній файл.
- **Видаляти лише LFS-вказівники, щоб звільнити квоту.** Пряма цитата документації: «Deleting only LFS
  pointers doesn't free up space».
- **Робити `super_squash_history()` і чекати миттєвого оновлення квоти.** Операція незворотна, стирає
  історію й LFS-історію, а зміна квоти відображається протягом 36 годин.
- **Вивантажувати з мережевої ФС із типовим `HF_XET_CACHE`.** Кеш Xet опиниться на тій самій
  мережевій ФС, і швидкість упаде; перенесіть його на локальний NVMe.
- **Очікувати, що `--include`/`--exclude` у `hf upload` працюють як shell-глоби в `delete-files`.**
  Для `hf repos delete-files` документація окремо попереджає: використовується `fnmatch`, де `*`
  проходить крізь межі тек, тому `"data/*.json"` знищить і `data/subdir/file.json`.

**Альтернативи**

| Підхід | Коли брати | Ціна питання |
|---|---|---|
| `hf upload` / `upload_folder()` | типове вивантаження, у т. ч. дуже великих тек | розбиття на коміти, автодокачка |
| `create_commit()` + `preupload_lfs_files()` | файли генеруються потоково/в пам'яті | низькорівневий код, файли не видні до коміту |
| `hf upload --every=<хв>` | логи тренування, регулярні оновлення | коміти кожні N хвилин, історію треба чистити |
| Storage Buckets (`hf buckets`, `hf sync`) | великі змінні артефакти без версіонування | немає git-історії, окремий простір імен |
| git + git-lfs | потрібні теги, хуки, повна історія локально | файли > 5 ГБ потребують `hf lfs-enable-largefiles` |

### 22.3 Xet: дедуплікація на рівні блоків і що це змінює

**Що це.** Xet — бекенд зберігання Hub, який ріже кожен файл на чанки змінної довжини (~64 КБ) за
вмістом і зберігає кожен унікальний чанк один раз у контентно-адресованому сховищі (CAS). Клієнтська
частина — Rust-бібліотека `xet-core` та її Python-обгортка `hf_xet`, яка вбудована в
`huggingface_hub` і вмикається автоматично.

**Навіщо це знати.** Відповідь на питання «скільки трафіку коштуватиме оновлення чекпойнта» більше не
випливає з розміру файлу; друга причина — діагностика (що саме чанкується, де кеш чанків, які змінні
середовища це змінюють).

**Як працює під капотом.**

*Content-defined chunking (CDC).* Межі чанків визначає **rolling hash** — хеш, що «котиться» по байтах;
коли він потрапляє у спеціальний шаблон, ставиться межа. Оскільки межі залежать від вмісту, а не від
позиції, однакові ділянки дають однакові чанки навіть після вставок і видалень. Документація пояснює
це на прикладі: при фіксованих чанках вставка 5 байтів зсуває всі наступні межі, і «в реальних файлах
при чанку 64 КБ невелика правка може інвалідувати сотні мегабайтів чанків»; при CDC та сама вставка
змінює лише один чанк — той, у якому сталася правка.

*Агрегація: блоки й шарди.* Зберігати чанки поштучно не масштабується: після дедуплікації вони
групуються в **блоки до 64 МБ** (у клієнтській частині — xorbs), теж контентно-адресовані, і кількість
записів у CAS падає приблизно в 1000 разів. **Шарди** зберігають відображення «файл → чанки» і дають
змогу визначити, які частини файлу змінилися порівняно з попередніми вивантаженнями.

*Key chunks.* Питати мережу про кожен чанк не можна — це порушує принцип «жодних стратегій, що
масштабуються 1:1 з кількістю чанків». Рішення — **key chunks**: 0.1% усіх чанків, відібраних умовою за
модулем від хешу чанка. Для них існує глобальний індекс «key chunk → шард», тож запит за одним чанком
повертає шард, у якому, найімовірніше, є посилання й на схожі чанки (просторова локальність).

*Порядок перевірок при вивантаженні.* Файл → CDC → перевірка «чанк уже є?» на трьох рівнях (чанки цієї
сесії, локальний кеш метаданих, глобальний запит для key chunks) → дублікати пропускаються → нові
чанки групуються в блоки по 64 МБ → блоки йдуть у Xet-сховище. Дедуплікація відбувається **до**
агрегації, і саме тому повторне вивантаження майже не передає даних.

**Приклад.** Нижче — справжня симуляція: 2 МБ синтетичних даних із повторюваними сегментами,
фіксовані чанки проти CDC, і дві різні правки — вставка всередині та перегенерована ділянка.

```python
# ── 22.3 ── CDC проти фіксованих чанків. Лише стандартна бібліотека.
import hashlib
import random

SEGMENT = 512                    # «сегмент» даних
POOL = 256                       # стільки різних сегментів існує (репозиторій квантизацій)
N_SEGMENTS = 4096                # ~2 МБ файл
FIXED = 8192                     # фіксований чанк
MIN_SIZE, MAX_SIZE = 2048, 16384  # межі для CDC
MASK = (1 << 13) - 1             # межа CDC: 13 молодших бітів gear-хешу == 0

rnd = random.Random(22)
pool = [bytes(rnd.getrandbits(8) for _ in range(SEGMENT)) for _ in range(POOL)]
seq_a = [rnd.randrange(POOL) for _ in range(N_SEGMENTS)]
blob_a = b"".join(pool[i] for i in seq_a)
# B: одна вставка в середині (512 байтів).
seq_b = seq_a[: N_SEGMENTS // 2] + [POOL - 1] + seq_a[N_SEGMENTS // 2:]
blob_b = b"".join(pool[i] for i in seq_b)
# C: суцільна ділянка 20% перегенерована (типове «перетренували частину»).
seq_c = list(seq_a)
for k in range(1024, 1024 + N_SEGMENTS // 5):
    seq_c[k] = rnd.randrange(POOL)
blob_c = b"".join(pool[i] for i in seq_c)

GEAR = [rnd.getrandbits(64) for _ in range(256)]


def fixed_chunks(data, size=FIXED):
    return [data[i:i + size] for i in range(0, len(data), size)]


def cdc_chunks(data, min_size=MIN_SIZE, max_size=MAX_SIZE, mask=MASK):
    """Gear-хеш: межа там, де (hash & mask) == 0, з обмеженнями min/max."""
    chunks, start, h = [], 0, 0
    for i, byte in enumerate(data):
        h = ((h << 1) + GEAR[byte]) & 0xFFFFFFFFFFFFFFFF
        size = i - start + 1
        if (size >= min_size and h & mask == 0) or size >= max_size:
            chunks.append(data[start:i + 1])
            start, h = i + 1, 0
    if start < len(data):
        chunks.append(data[start:])
    return chunks


def digest(chunk):
    return hashlib.sha256(chunk).hexdigest()[:12]


def transfer(old_chunks, new_chunks):
    """Скільки чанків нової версії відсутні у старій і скільки байтів треба передати."""
    known = {digest(c) for c in old_chunks}
    fresh = [c for c in new_chunks if digest(c) not in known]
    return len(set(digest(c) for c in new_chunks)), len(fresh), sum(len(c) for c in fresh)


print(f"файл A: {len(blob_a)} байтів ({N_SEGMENTS} сегментів по {SEGMENT} Б із пулу {POOL})")
print(f"файл B: {len(blob_b)} байтів (у середину вставлено 1 сегмент = {SEGMENT} байтів)")
print(f"файл C: {len(blob_c)} байтів (суцільна ділянка у 20% перегенерована)")

for label, other in (("B (вставка всередині)", blob_b), ("C (20% перегенеровано)", blob_c)):
    print()
    print(f"нова версія — {label}")
    print(f"{'схема':20}{'чанків':>9}{'розмір чанка':>15}{'нових':>8}{'передати':>12}")
    print("-" * 66)
    for name, fn in (("фіксовані 8192 Б", fixed_chunks), ("CDC (gear-хеш)", cdc_chunks)):
        ca, cb = fn(blob_a), fn(other)
        uniq, fresh, nbytes = transfer(ca, cb)
        avg = sum(len(c) for c in cb) / len(cb)
        print(f"{name:20}{len(cb):>9}{avg:>13.0f} Б{fresh:>8}"
              f"{nbytes / 1024:>9.1f} КБ")
    print("-" * 66)
    print(f"{'без дедуплікації':20}{'':>9}{'':>15}{'':>8}"
          f"{len(other) / 1024:>9.1f} КБ")
```

який блог описує словами «only the changed chunks are uploaded or downloaded».

Версія C показує межу методу: коли перегенеровано суцільну ділянку в 20%, обидві схеми передають
близько 415 КБ. **CDC не стискає дані — він локалізує зміни.** Дедуплікація не рятує від правок, які
справді змінюють вміст; вона рятує від передачі незміненого.

```python
print("Завантаження нової квантизації з локальним кешем чанків:")
for shared in (0.0, 0.508, 0.9):
```

```text
  спільних чанків  50.8% →   94.0 ГБ замість 191.0 ГБ
  спільних чанків  90.0% →   19.1 ГБ замість 191.0 ГБ
```

Що тут підтверджується, а що ні. **Підтверджується** арифметика блоків: 1515 × 64 МБ = 96.96 ГБ проти
«приблизно 97 ГБ» у блозі — тобто «64MB» у тексті означає 64 × 10⁶ байтів. Два числа виглядають як
розбіжність, але нею не є: множник 977 проти заявлених 1000 і 305 176 чанків проти 312 500 з
документації — це KB проти KiB. Документація рахує чанк як 64 000 байтів (20 ГБ / 64 000 = 312 500),
наш код — як 65 536 (20 ГБ / 65 536 = 305 176). Обидва описи стосуються одного механізму.

**Не підтверджується** підпис «@ 50MB/s»: 191 ГБ за 509 хвилин — це 6.25 МБ/с. Обидва рядки дають ту
саму ефективну швидкість (6.25 і 6.27 МБ/с), тож двократне прискорення від дедуплікації справді є, а
абсолютна швидкість підпису не відповідає. Що саме означає «50MB/s» — **не вдалося підтвердити станом
на 09.2026**. Так само **не вдалося підтвердити** точний алгоритм rolling hash, розмір вікна й
параметри умови межі: джерела описують принцип, а не функції й константи. Наведена вище реалізація —
gear-хеш, класична схема CDC, а не відтворення коду `xet-core`; вона демонструє механізм.

**Типові помилки**

- **Чекати, що Xet стисне дані.** Дедуплікація прибирає повторювані байти; якщо кожна версія файлу
  справді інша, передасться весь обсяг (див. версію C у виводі — 416 КБ проти 413 КБ).
- **Вимкнути Xet «про всяк випадок».** `HF_HUB_DISABLE_XET=1` повертає легасі-шлях і заодно вимикає
  спільне сховище блобів, тому кеш починає дублювати файли.
- **Тримати кеш Xet на мережевій ФС.** Типово це `$HF_HOME/xet`; під час вивантаження з кластера треба
  явно задати `HF_XET_CACHE` на локальний диск.
- **Плутати `hf_transfer` і `hf_xet`.** `HF_HUB_ENABLE_HF_TRANSFER=1` — застаріла змінна, яку
  ігнорують; для максимальної швидкості використовують `HF_XET_HIGH_PERFORMANCE=1`.
- **Дублювати великий репозиторій через локальне коло «завантажити → вивантажити».** `hf cp` і
  `hf buckets cp` переносять лише хеші вмісту, без повторного вивантаження даних; обмеження —
  копіювання «віддалено → віддалено» працює лише в межах одного регіону зберігання.
- **Вважати, що `--dry-run` у `hf download` щось завантажив.** Це лише план: рядок
  `[dry-run] Will download 11 files (out of 26) totalling 5.6G` — перелік, а не результат.

**Альтернативи**

| Підхід | Коли брати | Що втрачаєте |
|---|---|---|
| Xet (типово) | усе, що вивантажується через `huggingface_hub` | нічого, крім залежності від `hf_xet` |
| Storage Buckets | змінні артефакти, чекпойнти, логи без версіонування | немає git-історії та ревізій |
| `hf cp` між репозиторіями | дублювання ваг для варіантів моделі | регіон зберігання має збігатися |
| git + git-lfs | робота з git-клієнтом, теги, хуки | файлова дедуплікація, файли > 5 ГБ окремо |
| Стиснення архіву (`.tar.zst`) | передача тисяч дрібних файлів одним об'єктом | Hub не показує вміст, гірша довантажуваність |

### 22.4 Jobs: запуск скриптів на керованій інфраструктурі

**Що це.** Jobs — це запуск команди в контейнері на залізі Hugging Face. Job описується трьома
речами: **команда**, **Docker-образ** (з Docker Hub, зі Spaces або власний) і **flavor** — профіль
заліза (CPU, GPU, TPU). Керувати Jobs можна трьома способами з однаковою семантикою: CLI `hf jobs`,
Python-клієнт (`run_job`, `run_uv_job`) і HTTP-API за `https://huggingface.co/api/jobs`.

**Навіщо це знати.** Це спосіб запустити тренування, батч-інференс або обробку датасету, не маючи
власної GPU-машини й не збираючи образ локально. Практичні сценарії з документації: доучування моделей
(T4, A10G, A100), генерація синтетичних даних LLM, обробка великих датасетів на конфігураціях із
великим CPU, офлайн-інференс на тисячах семплів, відтворювані бенчмарки на фіксованому залізі й
відлагодження CUDA-коду без локальної CUDA. Jobs **не** варто брати, коли потрібна інтерактивна
машина з довільним доступом — для цього в документації згадуються Sandboxes, побудовані поверх Jobs.

**Як працює під капотом.**

*Життєвий цикл.* Стадії: `SCHEDULING`, `RUNNING`, `COMPLETED`, `CANCELED`, `ERROR`, `DELETED`. Білінг
іде **за хвилини** й лише поки Job у стані Starting або Running — під час збірки образу платити не
треба; якщо Job почав падати в роботі, він автоматично призупиняється й білінг зупиняється. Jobs
доступні будь-якому користувачу чи організації з додатним балансом кредитів.

Тут джерела розходяться: гайд `huggingface_hub` пише «you only pay for the seconds you use», а сторінка
білінгу Hub — «computed by the minute». Формально це різні величини — **не вдалося підтвердити станом на
09.2026**, яка з них точна; для оцінок безпечніше вважати хвилини.

*Таймаут.* Типовий таймаут — **30 хвилин**, після чого Job зупиняється сам (у статусі буде «Job
timeout»). Значення задається числом (секунди) або рядком з одиницями `s`, `m`, `h`, `d`:
`--timeout 7200`, `--timeout 2h`, `--timeout 1.5h`, `--timeout 1d`.

*Ефемерність.* Файлова система Job видаляється разом із Job. Зберегти результати можна трьома
способами: писати в примонтований Storage Bucket, пушити в репозиторій Hub (`push_to_hub`,
`create_repo`) або друкувати ключові метрики в логи — логи зберігаються й доступні через
`hf jobs logs`. Найпоширеніший провал описаний прямо: Job рахує годинами, а потім падає на фінальному
вивантаженні, бо в токена немає прав на запис.

*Змінні середовища.* Усередині контейнера автоматично доступні `JOB_ID`, `ACCELERATOR` (порожній для
CPU), `CPU_CORES`, `MEMORY`, а за наявності мережевої групи — `HF_NETWORK_GROUP_HOSTNAME` і
`HF_NETWORK_GROUP_PREFIX`. Власні змінні передають `-e`/`--env`, секрети — `-s`/`--secrets` (шифруються
на сервері), масово — `--env-file` і `--secrets-file` (можна читати зі stdin через `-`). Форма
`--secrets HF_TOKEN` бере значення з вашого середовища, форма `--secrets SECRET=value` кладе секрет в
історію shell — документація радить першу.

*Томи.* `-v` монтує репозиторій Hub, кошик або локальну теку: `hf://[TYPE/]SOURCE:/MOUNT_PATH[:ro|:rw]`,
де `TYPE` — `models`, `datasets`, `spaces` або `buckets` (типово `models`). Модель, датасет і Space
монтуються **завжди read-only**; кошик — read-write, тому саме в нього пишуть чекпойнти (для read-only
додають `:ro`). Локальна тека спершу синхронізується в приватний кошик `jobs-artifacts` (створюється
автоматично) і монтується read-only, якщо не вказати `:rw`. Файли з томів читаються ліниво, тож Job
може працювати з датасетом, який не вміщається на його диск. У Python за це відповідає клас `Volume`
(потрібен `huggingface_hub >= 1.8.0`) і функції `sync_job_volume()` / `sync_bucket()`.

*Доступ до контейнера.* `--ssh` робить контейнер досяжним по SSH (`hf jobs ssh <job_id>`, ключі з
`https://huggingface.co/settings/keys`, потрібен write-доступ; для scheduled-Jobs не працює).
`--expose <port>` відкриває порт через публічний проксі: адреса `https://<job_id>--<port>.hf.jobs`,
потрібен токен із read-доступом, і це коштує 0.01 $/год — лише поки Job виконується.

*Мережеві групи.* `--network-group <name>` зводить Jobs одного простору імен і resource group в одну
мережу: `HF_NETWORK_GROUP_HOSTNAME` резолвиться у всіх учасників, а `${HF_NETWORK_GROUP_PREFIX}<alias>`
— у тих, хто заявив аліас через `--network-alias`. Назви груп — до 46 символів, аліаси — до 34, лише
малі літери, цифри й дефіси; учасники резолвляться ще до готовності, тому підключатися треба з
повторами. Для багатовузлового тренування аліас беруть як rendezvous-хост:
`torchrun --master_addr "${HF_NETWORK_GROUP_PREFIX}master"`.

*Розклад і тригери.* `hf jobs scheduled run` і `hf jobs scheduled uv run` приймають `@hourly`,
`@daily`, `@weekly`, `@monthly`, `@yearly`/`@annually` або CRON-вираз (`"*/5 * * * *"`,
`"0 9 * * 1"`); керування — `ps`, `inspect`, `suspend`, `resume`, `trigger`, `delete`. Jobs також
уміють запускатися від вебхуків Hub, наприклад на кожне оновлення моделі в акаунті.

**Приклад.** Тут важлива чесність про конфігурацію: **окремого YAML-файлу конфігурації Jobs у джерелах
немає**. Поверхня налаштування — це прапорці CLI (або аргументи Python-API) плюс необов'язкова таблиця
`[tool.hf-jobs]` у PEP 723-заголовку скрипта, тобто **TOML**, а не YAML. Нижче — генерація саме цієї
таблиці та відтворення документованих правил злиття «значення зі скрипта проти явного прапорця».

```python
# ── 22.4 ── Конфігурація Jobs: таблиця [tool.hf-jobs] і правила злиття.
SCRIPT_CFG = {
    "image": "vllm/vllm-openai:unlimited-ocr",
    "flavor": "l4x1",
    "python": "/usr/bin/python3",
    "secrets": ["HF_TOKEN"],
    "env": {"BATCH": "16"},
    "labels": {"model": "Qwen3-06B"},
}
CLI_FLAGS = {"flavor": "l4x4", "env": {"BATCH": "32", "DEBUG": "1"},
             "labels": {"team": "ml"}, "timeout": "2h"}

MERGED = {"env", "secrets", "labels", "volumes"}   # зливаються по елементах


def resolve(script, flags):
    """Явний прапорець завжди перемагає; env/secrets/labels/volumes доповнюються."""
    out = {key: (value, "script") for key, value in script.items()}
    for key, value in flags.items():
        if key in MERGED and key in out:
            current = out[key][0]
            if isinstance(current, dict):
                merged = dict(current)
                merged.update(value)
                out[key] = (merged, "обидва")
            else:
                out[key] = (sorted(set(current) | set(value)), "обидва")
        else:
            out[key] = (value, "флаг")
    return out


print("# /// script")
print('# requires-python = ">=3.11"')
print('# dependencies = ["vllm", "datasets"]')
print("#")
print("# [tool.hf-jobs]")
for key, value in SCRIPT_CFG.items():
    if isinstance(value, str):
        print(f'# {key:8}= "{value}"')
    else:
        print(f"# {key:8}= {value}")
print("# ///")
print()
print(f"{'ключ':10}{'значення':48}{'джерело'}")
print("-" * 70)
for key, (value, src) in resolve(SCRIPT_CFG, CLI_FLAGS).items():
    print(f"{key:10}{str(value):48}{src}")
print("-" * 70)
print('hf jobs uv run --dry-run ocr.py → значення зі скрипта позначаються "(from script)"')

# Вартість: ціни за хвилину зі сторінки jobs-pricing.
PRICES = {"cpu-basic": 0.0002, "t4-small": 0.0067, "a10g-small": 0.0167,
          "a10g-large": 0.0250, "a100x4": 0.1667, "h200x8": 0.6667}
print()
print(f"{'flavor':12}{'$/хв':>8}{'30 хв (типово)':>16}{'2 год':>10}{'24 год':>10}")
print("-" * 58)
for name, price in PRICES.items():
    print(f"{name:12}{price:>8.4f}{price * 30:>16.2f}{price * 120:>10.2f}"
          f"{price * 1440:>10.2f}")
print("-" * 58)
print("Типовий таймаут — 30 хвилин: довша задача зупиниться сама.")
```

Таблиця злиття показує три різні поведінки: `flavor` і `timeout` перезаписуються прапорцем, `image` і
`python` лишаються зі скрипта, а `env` і `labels` **доповнюються по елементах** — `BATCH` перезаписано
на `32`, а `DEBUG` додано. Кошторис пояснює, чому таймаут — це не формальність: забутий
`--timeout 30m` на `h200x8` коштує 20 $ за 30 хвилин замість очікуваних хвилин на `t4-small`, а
доба на тій самій конфігурації — 960 $.

**Типові помилки**

- **Забути таймаут.** Типові 30 хвилин ріжуть тренування посеред епохи; у статусі буде «Job timeout»,
  і це виглядає як збій скрипта, а не як межа конфігурації.
- **Чекати, що Python-API прочитає `[tool.hf-jobs]`.** Таблицю читає **лише** CLI:
  `run_uv_job("ocr.py")` і `hf jobs uv run ocr.py` запускають різні Jobs. У Python `image`, `flavor`,
  `timeout` треба передавати явно.
- **Очікувати, що значення секрету береться зі скрипта.** У таблиці перелічуються лише **назви**
  секретів; значення беруться з середовища того, хто запускає, а відсутній секрет — це помилка.
- **Друкувати `--secrets SECRET=value`.** Значення потрапляє в історію shell; правильна форма —
  `--secrets HF_TOKEN` або `--secrets-file`.
- **Вважати, що `wait_for_job()` кине виняток при збої.** Він **завжди** повертає фінальний `JobInfo`,
  тому перевіряти треба `job.status.stage`. Натомість CLI-варіант `hf jobs wait` повертає код 0 лише
  коли **всі** Jobs завершилися успішно — саме тому він і потрібен для ланцюжків `&&`.
- **Писати результати у файлову систему Job.** Вона зникає разом із Job; перевіряйте, що чекпойнти
  справді долетіли (наприклад, `hf buckets list`), бо `COMPLETED` означає лише успішний код виходу
  команди, а не збережені файли.
- **Плутати read-only томи з read-write.** Моделі й датасети монтуються read-only завжди; писати можна
  тільки в кошик, і для локальної теки це вимагає явного `:rw`.
- **Покладатися на ім'я Job як на унікальний ключ.** Імена не унікальні, а автоматично згенероване ім'я
  містить хеш: у CLI він покриває команду **і** розв'язані налаштування запуску (flavor, timeout,
  env), у Python-API — лише команду. Зміна flavor змінить ім'я Job при тому самому скрипті.

**Альтернативи**

| Підхід | Коли брати | Обмеження |
|---|---|---|
| `hf jobs run <image> <cmd>` | довільний стек, повний контроль середовища | самі збираєте й підтримуєте образ |
| `hf jobs uv run <script>` | Python-скрипт із PEP 723-заголовком | потрібен uv; залежності ставляться на кожен запуск |
| `hf jobs scheduled ...` | регулярні задачі (cron-семантика) | не підтримує SSH; локальні томи синхронізуються лише при створенні |
| Вебхуки Hub | запуск на оновлення репозиторію | подієва, а не часова модель |
| Sandboxes (поверх Jobs) | інтерактивна машина, виконання згенерованого коду | експериментальний інструмент |
| Локальний `uv run` / `docker run` | відлагодження перед відправкою | власне залізо; документація прямо радить цю пару як спосіб дебагу |

### 22.5 Міграція на Hub v1

**Що це.** v1.0 `huggingface_hub` (27 жовтня 2025 року) — реліз із навмисними ламаючими змінами:
перехід на `httpx`, новий CLI `hf` замість `huggingface-cli`, `hf_xet` замість `hf_transfer` і
видалення цілого шару застарілих API, зокрема git-обгортки `Repository`.

**Навіщо це знати.** Дві причини, обидві практичні. Перша: код, написаний до 2026 року, часто містить
`use_auth_token=`, `HfFolder`, `configure_http_backend()`, `resume_download` — усе це або видалено, або
перейменовано. Друга: сумісність бібліотек. `transformers` v4 **явно вимагає** `huggingface_hub` v0.x, а
`transformers` v5 — v1.x, тому оновлення однієї бібліотеки тягне за собою інші.

**Як працює під капотом.** Основні зміни (за гайдом міграції й блогом v1.0):

- **HTTP-шар: `requests` → `httpx`.** Причини з документації: потокобезпечність і перевикористання
  з'єднань, нативний HTTP/2, єдиний API для sync і async. Наслідки: проксі — лише глобально
  (`HTTP_PROXY`, `HTTPS_PROXY`); `configure_http_backend()` → `set_client_factory()` і
  `set_async_client_factory()`; помилки HTTP успадковуються від `httpx.HTTPError`; `SSLError` зникло —
  це `httpx.ConnectError`. Сумісний варіант — ловити `huggingface_hub.HfHubHttpError`: він
  успадковується від різних баз у різних версіях, тому працює і на v0.x, і на v1.x.
- **Передачі файлів: `hf_transfer` видалено.** `HF_HUB_ENABLE_HF_TRANSFER` ігнорується; для швидкості —
  `HF_XET_HIGH_PERFORMANCE`.
- **Клас `Repository` видалено** (тонка обгортка над git CLI). Відповідність:

  | Було (`Repository`) | Стало (`HfApi` або функції) |
  |---|---|
  | `repo.clone_from` | `snapshot_download` |
  | `repo.git_add` + `git_commit` + `git_push` | `upload_file()`, `upload_folder()`, `create_commit()` |
  | `repo.git_tag` | `create_tag` |
  | `repo.git_branch` | `create_branch` |

- **Керування токеном.** `HfFolder` видалено: `login()`, `logout()`, `whoami()`, `get_token()`. Поняття
  «write permission» зникло — документація пояснює це переходом на fine-grained токени.
- **Розділення помилок «немає файлу».** `LocalEntryNotFoundError` більше не успадковується від
  `HTTPError`; з'явився базовий `EntryNotFoundError`, від якого походять `LocalEntryNotFoundError`
  (немає в кеші) і `RemoteEntryNotFoundError` (немає в репозиторії). Від HTTPError успадковується лише
  другий — тому `except HTTPError` перестав ловити випадок «файлу немає локально».
- **Повернені значення.** `upload_file()` і `upload_folder()` повертають URL **коміту**, а не URL файлу
  чи теки — так само, як `create_commit()`, `delete_file()`, `delete_folder()`.
- **CLI.** `huggingface-cli` видалено; `hf cache scan`/`delete` замінено на `hf cache ls`/`rm`/`prune`;
  `[cli]` extra більше не існує, CLI входить у пакет.
- **Видалено разом із залежностями.** Уся підтримка TensorFlow і Keras 2.x (`KerasModelHubMixin`,
  `save_pretrained_keras`, `from_pretrained_keras`, `push_to_hub_keras`, extra `[tensorflow]`).
- **Інші видалення.** `use_auth_token=` → `token=`; `constants.hf_cache_home` → `HF_HOME`;
  `update_repo_visibility()` → `update_repo_settings()`; `get_token_permission()` — без заміни;
  `resume_download`, `force_filename`, `local_dir_use_symlinks` — видалені; `new_session=` у `login()`
  → `skip_if_logged_in=`; у `list_models()` прибрано `library`, `language`, `tags`, `task`;
  `InferenceApi` → `InferenceClient` (який тепер можна використовувати як контекстний менеджер).

*Версії.* У гайді міграції зазначено «Python 3.9+», але опублікований пакет **2.0.0** на PyPI декларує
`requires_python >= 3.10.0`. Чи 2.0 справді підняв мінімум — **не вдалося підтвердити станом на
09.2026**; безпечно орієнтуватися на 3.10+.

**Приклад.** Найкорисніша перевірка тут — не таблиця, а інтроспекція: на якій лінійці сидить ваш код.
Виконується без мережі, а якщо пакета немає — просто повідомляє про це.

```python
# ── 22.5 ── На якій лінійці сидить ваш код: інтроспекція без мережі.
try:
    import huggingface_hub as hub
    from importlib.metadata import version

    print(f"huggingface_hub {version('huggingface_hub')} встановлено")
    for name in ("HfFolder", "Repository", "InferenceApi", "get_token"):
        print(f"  hasattr(huggingface_hub, {name!r}) → {hasattr(hub, name)}")
    print("v0.x: HfFolder, Repository і InferenceApi ще існують; v1.x і далі — ні.")
except ImportError:
    print("huggingface_hub не встановлено — інтроспекція неможлива.")
    print("Перевірте у своєму середовищі: python -c 'import huggingface_hub as h; print(h.__version__)'")
```

**Фактичний вивід**

```text
huggingface_hub не встановлено — інтроспекція неможлива.
Перевірте у своєму середовищі: python -c 'import huggingface_hub as h; print(h.__version__)'
```

Це не недолік, а свідома властивість: ноутбук розділу має виконуватися в середовищі без
`huggingface_hub`, тому клітинка захищена `try/except ImportError`. У середовищі з пакетом вона
додатково надрукує `hasattr(...)` для `HfFolder`, `Repository`, `InferenceApi` і `get_token`: на v0.x
усі чотири існують, на v1.x і далі — ні.

**Типові помилки**

- **Ловити `requests.HTTPError`.** На v1.x помилки походять від `httpx.HTTPError`; сумісний варіант —
  `except huggingface_hub.HfHubHttpError`.
- **Налаштовувати проксі «на метод».** Такої можливості немає; лишаються глобальні змінні середовища.
- **Використовувати `use_auth_token=`.** Параметр видалено з усіх методів; потрібен `token=`.
- **Розраховувати на `Repository`.** Класу немає; для git потрібен звичайний `git`, а для Hub —
  HTTP-методи `HfApi`.
- **Оновлювати `transformers` v4 разом із `huggingface_hub` v1.** Вони несумісні за заявою самої
  документації: v4 вимагає hub v0.x.
- **Покладатися на `HF_HUB_ENABLE_HF_TRANSFER=1`.** Змінна ігнорується; потрібен
  `HF_XET_HIGH_PERFORMANCE`.
- **Читати URL файлу з поверненого значення `upload_folder()`.** Тепер це URL коміту.
- **Вважати, що `LocalEntryNotFoundError` — це HTTP-помилка.** Він більше не успадковується від
  `HTTPError`; для «файлу немає на Hub» є `RemoteEntryNotFoundError`.

**Альтернативи**

| Задача | Рекомендація |
|---|---|
| Лишитися на v0.x | тільки якщо цього вимагає `transformers` v4 або Keras 2.x; v0.x отримує лише патчі безпеки |
| Сумісний код на обидві лінійки | ловити `HfHubHttpError`, використовувати `token=`, `get_token()`; не звертатися до `HfFolder` |
| Замінити `Repository` | `git` у терміналі плюс `HfApi` для операцій із Hub |
| Перейти на CLI замість Python-викликів | `hf repos`, `hf upload`, `hf cache` — та сама семантика, менше коду |

### 22.6 Автоматизація в CI

**Що це.** Використання `hf` CLI та Jobs у конвеєрах: автентифікація через секрети CI, машинний вивід,
коди виходу як гейти й дисципліна кеша на ефемерних раннерах.

**Навіщо це знати.** У CI три речі ламаються найчастіше: токен не доїхав, команда «проковтнула» помилку
(код виходу 0 при збої всередині) і раннер забився кешем моделей. Кожна з них закривається конкретним
прапорцем або змінною, а не «загальною дисципліною».

**Як працює під капотом.**

*Автентифікація.* Найчистіший шлях — змінна `HF_TOKEN`: вона перекриває збережений токен і
підхоплюється всіма бібліотеками екосистеми. Другий шлях — `hf auth login --token "$HF_TOKEN"`
(неінтерактивний, без браузера). Пам'ятайте: якщо `HF_TOKEN` встановлено, `hf auth logout` не
розлогінює. Для секретів у Jobs краще `--secrets HF_TOKEN` — значення читається з середовища, а не
потрапляє в аргументи команди.

*Тихий режим і кеш.* Кілька змінних середовища існують фактично для CI:

| Змінна | Що робить | Коли потрібна |
|---|---|---|
| `HF_HUB_DISABLE_UPDATE_CHECK=1` | не перевіряти PyPI і не друкувати підказки | офлайн-CI, чистий вивід |
| `HF_HOME` | перенести весь локальний стан (кеш і токен) | раннери з ефемерним диском |
| `HF_HUB_OFFLINE=1` | заборонити будь-які HTTP-виклики, читати лише кеш | герметичні збірки, швидший старт |
| `HF_HUB_DISABLE_PROGRESS_BARS=1` | вимкнути прогрес-бари tqdm | логи без «сміття» |
| `HF_HUB_DISABLE_TELEMETRY=1` | вимкнути телеметрію HF-бібліотек | корпоративні політики |
| `HF_XET_HIGH_PERFORMANCE=1` | наситити мережу й усі ядра під час передач | великі вивантаження |
| `HF_HUB_DOWNLOAD_TIMEOUT` | таймаут читання (типово 10 с) | повільні канали |

*Машинний вивід і коди виходу.* Для скриптів — `-q` (лише ідентифікатори) і `--format json`. Коди
виходу передбачувані: `hf jobs wait` повертає 0 лише якщо **всі** Jobs завершилися успішно, а
`hf jobs run` без `--detach` уже сам блокується й повертає ненульовий код при збої. Тому ланцюжки
`hf jobs run ... && наступний-крок` працюють без явного `wait`; `wait` потрібен для detached-запусків і
для пакетів Jobs (`hf jobs ls -q | xargs hf jobs wait`).

*Дисципліна кеша.* На ефемерному раннері кеш моделей — головний споживач диска. Документація показує
робочий рецепт: `hf cache ls --filter "accessed>1y" -q | xargs hf cache rm -y`; є також
`--filter "size>1GB"`, `--sort size:desc` і `hf cache prune` для ревізій, на які ніщо не посилається.

*Що Jobs не роблять за вас.* Логи Job зберігаються після завершення, а файлова система — ні. Тому в CI
обов'язковий крок збереження артефактів (у кошик або в репозиторій) і токен із правом запису:
типовий провал — години обчислень і невдале вивантаження в кінці.

**Приклад.** Генерація CI-скрипта з подальшою перевіркою синтаксису через `bash -n` і окремо — схема
workflow GitHub Actions. Зверніть увагу: workflow — це **схема**, авторський приклад; у джерелах
розділу офіційного GitHub Action для Hub не описано.

```python
# ── 22.6 ── Генерація CI-скрипта і перевірка його синтаксису.
import shutil
import subprocess


def step(text, comment=""):
    return text + (f"  # {comment}" if comment else "")


script = "\n".join([
    "#!/usr/bin/env bash",
    "set -euo pipefail",
    "",
    "export HF_HUB_DISABLE_UPDATE_CHECK=1   # не ходити в PyPI у CI",
    'export HF_HOME="$RUNNER_TEMP/hf"      # кеш на ефемерному диску',
    "",
    step("hf auth whoami", "падіння, якщо токен недійсний"),
    step("hf download openai-community/gpt2 config.json --quiet"),
    step('hf repos create "$REPO" --repo-type=dataset --exist-ok'),
    step('hf upload "$REPO" ./data /train --repo-type=dataset '
         '--commit-message "ci $(date -u +%FT%TZ)"'),
    step("JOB=$(hf jobs uv run --detach --flavor t4-small --timeout 30m "
         "--secrets HF_TOKEN train.py -q)"),
    step('hf jobs wait "$JOB"', "exit 0 лише якщо Job завершився успішно"),
    step('hf jobs logs "$JOB" | tail -n 20'),
    step('hf cache ls --filter "size>1gb" -q | xargs -r hf cache rm -y'),
])
print(script)
print()

if shutil.which("bash"):
    proc = subprocess.run(["bash", "-n"], input=script, text=True, capture_output=True)
    print(f"bash -n → код {proc.returncode} "
          f"({'синтаксис ок' if proc.returncode == 0 else proc.stderr.strip()})")
print()

# Workflow GitHub Actions — схема, не цитата з джерел.
WORKFLOW = "\n".join([
    "name: sync-model",
    "on:",
    "  workflow_dispatch:",
    "jobs:",
    "  upload:",
    "    runs-on: ubuntu-latest",
    "    env:",
    "      HF_TOKEN: ${{ secrets.HF_TOKEN }}",
    '      HF_HUB_DISABLE_UPDATE_CHECK: "1"',
    "    steps:",
    "      - uses: actions/checkout@v4",
    "      - run: pip install -U huggingface_hub",
    "      - run: hf auth whoami",
    '      - run: hf upload my-org/my-model ./out . --commit-message "ci"',
])
import yaml

parsed = yaml.safe_load(WORKFLOW)
print(WORKFLOW)
print()
print("yaml.safe_load →", type(parsed).__name__,
      "| кроків:", len(parsed["jobs"]["upload"]["steps"]),
      "| токен узятий із secrets:", "HF_TOKEN" in parsed["jobs"]["upload"]["env"])
```

**Фактичний вивід**

```text
#!/usr/bin/env bash
set -euo pipefail

export HF_HUB_DISABLE_UPDATE_CHECK=1   # не ходити в PyPI у CI
export HF_HOME="$RUNNER_TEMP/hf"      # кеш на ефемерному диску

hf auth whoami  # падіння, якщо токен недійсний
hf download openai-community/gpt2 config.json --quiet
hf repos create "$REPO" --repo-type=dataset --exist-ok
hf upload "$REPO" ./data /train --repo-type=dataset --commit-message "ci $(date -u +%FT%TZ)"
JOB=$(hf jobs uv run --detach --flavor t4-small --timeout 30m --secrets HF_TOKEN train.py -q)
hf jobs wait "$JOB"  # exit 0 лише якщо Job завершився успішно
hf jobs logs "$JOB" | tail -n 20
hf cache ls --filter "size>1gb" -q | xargs -r hf cache rm -y

bash -n → код 0 (синтаксис ок)

name: sync-model
on:
  workflow_dispatch:
jobs:
  upload:
    runs-on: ubuntu-latest
    env:
      HF_TOKEN: ${{ secrets.HF_TOKEN }}
      HF_HUB_DISABLE_UPDATE_CHECK: "1"
    steps:
      - uses: actions/checkout@v4
      - run: pip install -U huggingface_hub
      - run: hf auth whoami
      - run: hf upload my-org/my-model ./out . --commit-message "ci"

yaml.safe_load → dict | кроків: 4 | токен узятий із secrets: True
```

Перші три рядки скрипта — це власне і вся «магія» CI: `set -euo pipefail` зупиняє конвеєр на першій
помилці, `HF_HUB_DISABLE_UPDATE_CHECK=1` прибирає зайвий запит у PyPI, а `HF_HOME` виносить кеш на
ефемерний диск раннера, щоб він не потрапляв у снапшот. `bash -n` повертає код 0 — скрипт
синтаксично коректний; `yaml.safe_load` розбирає workflow у словник із 4 кроками, а токен у ньому
береться з `secrets`, а не з тексту файлу.

**Типові помилки**

- **Забути `set -euo pipefail`.** Без нього `hf upload`, що впав, не зупинить конвеєр, і CI стане
  зеленим при невивантажених артефактах.
- **Покладатися на «нульовий код» замість статусу Job.** `hf jobs run` без `--detach` блокується й
  повертає ненульовий код при збої — але якщо ви запустили з `-d`, потрібен явний `hf jobs wait`.
- **Логувати секрети.** Форма `--secrets SECRET=value` кладе значення в аргументи команди, а `hf auth
  token` друкує токен у stdout — в обох випадках він може потрапити в логи CI.
- **Тримати кеш у `$HOME` на ефемерному раннері.** Кеш моделей легко перевищує диск раннера; `HF_HOME`
  у `$RUNNER_TEMP` — це і прибирання, і передбачуваність.
- **Ставити `HF_HUB_OFFLINE=1` і чекати завантаження.** У офлайн-режимі будь-який HTTP-виклик заборонено,
  а виклик `HfApi` кидає `OfflineModeIsEnabled`; режим годиться лише коли все вже в кеші.
- **Вивантажувати з токеном без права запису.** Fine-grained токену потрібні права на запис і
  створення репозиторію — інакше Job чи крок CI упаде в самому кінці.
- **Ігнорувати `(part N)` у повідомленнях комітів.** Кілька комітів — це нормальна поведінка
  `hf upload` для великих тек, а не помилка; не намагайтеся «полагодити» її одним комітом.

**Альтернативи**

| Підхід | Коли брати | Ціна |
|---|---|---|
| `hf` CLI у кроці CI | будь-який CI: GitHub Actions, GitLab, Jenkins | потрібен `pip install -U huggingface_hub` або інсталятор |
| Python-код із `HfApi` | складна логіка, обробка помилок, паралельність | більше коду, але типізовано |
| `hf jobs` для важких кроків | тренування й обробка даних без власних раннерів | платно за хвилини, потрібен баланс кредитів |
| Вебхуки Hub | реакція на оновлення репозиторію | подієва модель замість розкладу |
| Локальний запуск (Makefile, `uv run`) | перевірка перед пушем | не замінює CI-гейт |

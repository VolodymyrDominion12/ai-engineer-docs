## 13. Вбудовані й небезпечні інструменти: bash, code execution

Розділ 12 показав механіку tool use: модель повертає блок `tool_use`, ваш код його виконує. Доти всі приклади були безпечні —
калькулятор, погода, словник. Цей розділ про інший клас інструментів: ті, що дають моделі доступ до операційної системи.
Bash-інструмент і code execution перетворюють «модель порадила щось зробити» на «модель щось зробила», а отже будь-який текст,
що потрапляє в контекст, стає потенційним вектором виконання коду. Розділ розбирає межі bash-інструмента, рівні ізоляції,
патерни підтвердження людиною, аудит дій агента й модель загроз, у якій prompt injection перетворюється на RCE.

Три речі, які варто тримати в голові від початку й до кінця розділу:

1. **Bash-інструмент не виконує нічого сам.** Це [client tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works):
   модель лише називає команду, а запускає її ваш застосунок. Отже вся відповідальність за
   безпеку лежить на вашому коді, а не на провайдері.
2. **Валідація команд — це tripwire, а не межа безпеки.** Документація Anthropic формулює це
   прямо: «The real control is isolation». Реальний контроль — ізоляція середовища виконання.
3. **Незмінних інструкцій не існує.** OWASP пише, що надійних методів повного запобігання
   prompt injection невідомо, тому архітектура будується так, щоб успішна ін'єкція не давала
   виконання довільного коду.

### 13.1 Bash-інструмент: можливості й межі

**Що це.** Bash-інструмент (bash tool) — вбудований у Claude інструмент, у якому модель повертає рядок shell-команди, а ваш
застосунок виконує його у власній bash-сесії й повертає вивід як
`tool_result`. Поточна версія інструмента — `bash_20250124`; визначення має два обов'язкові поля
`type` і `name`, причому `name` мусить бути `bash`.

**Навіщо це знати.** Bash-інструмент дає агенту чотири класи задач, які неможливо (або дорого) зробити звичайними функціями:
запуск збірок і тестів, автоматизація системних операцій, обробка файлів і даних, встановлення залежностей. Водночас саме цей
інструмент робить агента небезпечним: дозвіл на `ls` і дозвіл на `rm -rf` — це один і той самий інструмент.

**Як працює під капотом.**

Інструмент **schema-less**: ви не передаєте `input_schema`, бо схема вбудована в модель і не змінюється. Модель заповнює лише
два поля:

| Параметр | Обов'язковий | Опис |
| --- | --- | --- |
| `command` | так* | bash-команда для виконання |
| `restart` | ні | `true` — перезапустити bash-сесію |

\* обов'язковий, якщо не використовується `restart`.

Визначення інструмента у запиті:

```json
{
  "model": "claude-opus-5",
  "max_tokens": 1024,
  "tools": [
    {"type": "bash_20250124", "name": "bash"}
  ],
  "messages": [
    {"role": "user", "content": "List all Python files in the current directory."}
  ]
}
```

Відповідь приходить із `stop_reason: "tool_use"` і блоком, у якому лежить команда:

```json
{
  "id": "msg_01XAbCDeFgHiJkLmNoPQrStU",
  "model": "claude-opus-5",
  "stop_reason": "tool_use",
  "role": "assistant",
  "content": [
    {"type": "text", "text": "I'll list all Python files in the current directory for you."},
    {
      "type": "tool_use",
      "id": "toolu_01A09q90qw90lq917835lq9",
      "name": "bash",
      "input": {"command": "ls *.py"}
    }
  ]
}
```

Цикл — один round trip на команду: модель повертає `tool_use` → застосунок виконує → застосунок повертає stdout і stderr разом
у
`tool_result` → модель або просить наступну команду в тій самій сесії, або відповідає текстом. Якщо в одній відповіді кілька блоків
`tool_use`, їх виконують
**по порядку в тій самій сесії**, а всі результати повертають одним `user`-повідомленням. Механіку самих блоків і вимоги до
порядку `tool_result` розібрано в розділі 12.

**API stateless.** Про сесію API не знає нічого: коли вона стартує, скільки живе й коли перезапускається — вирішує застосунок.
Через це стан (робочий каталог, змінні середовища, створені файли) зберігається лише тому, що ваш процес тримає один живий
bash.

**Чому потрібен sentinel.** Читання з пайпа живого процесу ніколи не дає EOF, тож невідомо, де закінчився вивід команди.
Документація розв'язує це унікальним рядком-маркером, який сесія друкує після кожної команди. Ось реальна реалізація з
документації Anthropic:

```python
import subprocess
import uuid


class BashSession:
    """A bash process that stays alive between commands so state persists."""

    def __init__(self):
        self.process = subprocess.Popen(
            ["/bin/bash"],
            stdin=subprocess.PIPE,
            stdout=subprocess.PIPE,
            stderr=subprocess.STDOUT,  # interleave errors with output, in order
            start_new_session=True,  # own process group: a timeout can kill every child
            text=True,
        )

    def execute_command(self, command):
        """Run a command in the session and return its output."""
        sentinel = f"__CLAUDE_BASH_DONE_{uuid.uuid4().hex}__"  # unique per call
        self.process.stdin.write(f"{command}\necho {sentinel}\n")
        self.process.stdin.flush()

        output = []
        for line in self.process.stdout:
            if sentinel in line:  # this command's output is complete
                break
            output.append(line)
        return "".join(output)

    def restart(self):
        self.process.kill()
        self.process.wait()
        self.__init__()
```

Три деталі тут не косметичні. `start_new_session=True` створює окрему групу процесів — інакше таймаут уб'є саму оболонку, але
не дітей, яких вона наплодила. `stderr=subprocess.STDOUT` зберігає порядок повідомлень про помилки відносно звичайного виводу.
Sentinel генерується **на кожен виклик**: якщо зробити його константою, будь-який вивід, що містить цей рядок, передчасно
обірве читання.

**Рестарт сесії.** `{"restart": true}` означає: убити shell-процес, підняти новий і повернути `tool_result`, що підтверджує
перезапуск. Після рестарту сесія чиста — робочий каталог, змінні середовища й запущені процеси зникають. Це штатний спосіб
вийти зі зіпсованого стану, коли команда змінила `cd` або зламала `PATH`.

**Таймаути.** Команда, яка чекає на ввід, блокує сесію назавжди: її sentinel ніколи не прийде. Документація радить дедлайн на
кожну команду, після якого вбивають усю групу процесів:

```python
import concurrent.futures
import os
import signal


def execute_with_timeout(session, command, timeout=30):
    """Run a command in the session, replacing the session if the command hangs."""
    with concurrent.futures.ThreadPoolExecutor(max_workers=1) as pool:
        future = pool.submit(session.execute_command, command)
        try:
            return future.result(timeout=timeout)
        except concurrent.futures.TimeoutError:
            # The group is the shell and every process the command started
            os.killpg(session.process.pid, signal.SIGKILL)
            session.restart()
            return f"Error: command did not finish within {timeout} seconds"
```

Повідомлення про таймаут повертають моделі як **помилку**: `tool_result` із `is_error: true`. Так само оформлюють
`bash: nonexistentcommand: command not found` і `Permission denied` — модель має бачити, що команда не виконалась, а
не мовчазну порожнечу.

**Обмеження виводу.** API **не обрізає** `tool_result`: завеликий запит просто відхиляється. Отже обрізання — робота
застосунку:

```python
def truncate_output(output, max_lines=100):
    lines = output.split("\n")
    if len(lines) > max_lines:
        truncated = "\n".join(lines[:max_lines])
        return f"{truncated}\n\n... Output truncated ({len(lines)} total lines) ..."
    return output
```

**Скільки це коштує.** Саме визначення bash-інструмента додає вхідних токенів понад загальний tool-use системний промпт: для
Claude Opus 5, Opus 4.8 і Opus 4.7 — 325 токенів, для Opus 4.6, Sonnet 4.6 і раніших — 244 токени. Додаткові токени з'їдають
виводи команд (stdout/stderr), повідомлення про помилки й вміст великих файлів. Це прямий економічний аргумент за обрізання
виводу й за те, щоб не годувати агента `cat` по 10 000 рядків.

**Сумісність версій.** `bash_20250124` не потребує beta-заголовка й приймається всіма моделями від Claude Sonnet 3.7 (уже
[retired](https://platform.claude.com/docs/en/about-claude/model-deprecations) ) включно з поточними. Оригінальний
`bash_20241022` працює лише з жовтневою Claude Sonnet 3.5 (retired), вимагає заголовка `anthropic-beta:
computer-use-2024-10-22` і доступний у SDK лише в beta-просторах імен. Для нових інтеграцій беруть `bash_20250124`.

**Хто за що відповідає.** Модель вирішує, яку команду виконати. Усе інше — ваше:

| Аспект | Модель | Ваш застосунок |
| --- | --- | --- |
| Вибір команди | так | ні |
| Процес shell і його життєвий цикл | ні | так |
| Таймаут і вбивство групи процесів | ні | так |
| Перевірка команди перед запуском | ні | так |
| Обрізання виводу | ні | так |
| Ізоляція середовища | ні | так |
| Формування `tool_result` і `is_error` | ні | так |

**Що робить bash-інструмент неможливим.** Документація перелічує п'ять обмежень: сесія не виконує інтерактивних команд (`vim`,
`less`, запити пароля, будь-що, що чекає на stdin); немає GUI; стан сесії живе на клієнті, отже на кількох репліках сервісу
сесію треба прикріплювати до конкретного воркера або тримати зовні; вивід не стрімиться — він доходить до моделі лише
наступним запитом; результати не обрізаються на боці API.

**Політика дозволених команд.** Документація радить allowlist, а не blocklist, бо blocklist пропускає все, чого автор не
передбачив. Ось її приклад:

```python
import shlex

ALLOWED_COMMANDS = {"ls", "cat", "echo", "pwd", "grep", "find", "wc", "head", "tail"}
SHELL_OPERATORS = {"&&", "||", "|", ";", "&", ">", "<", ">>"}


def validate_command(command):
    # Allow only commands from an explicit allowlist
    try:
        tokens = shlex.split(command)
    except ValueError:
        return False, "Could not parse command"

    if not tokens:
        return False, "Empty command"

    executable = tokens[0]
    if executable not in ALLOWED_COMMANDS:
        return False, f"Command '{executable}' is not in the allowlist"

    # Reject shell operators written as separate words
    for token in tokens[1:]:
        if token in SHELL_OPERATORS or token.startswith(("$", "`")):
            return False, f"Shell operator '{token}' is not allowed"

    return True, None
```

**Фактичний вивід** цієї функції на реальних рядках (усі рядки аналізуються як дані, жодна команда не запускалась):

```text
ПРОПУЩЕНО   | 'ls -la'                            | —
ПРОПУЩЕНО   | 'cat notes.txt'                     | —
ЗАБЛОКОВАНО | 'ls && rm -rf /'                    | Shell operator '&&' is not allowed
ПРОПУЩЕНО   | 'echo hi;rm -rf /'                  | —
ПРОПУЩЕНО   | 'cat data.txt|grep x'               | —
ЗАБЛОКОВАНО | 'ls $(whoami)'                      | Shell operator '$(whoami)' is not allowed
ЗАБЛОКОВАНО | 'ls `id`'                           | Shell operator '`id`' is not allowed
ЗАБЛОКОВАНО | 'ls -la > out.txt'                  | Shell operator '>' is not allowed
ПРОПУЩЕНО   | 'ls -la>out.txt'                    | —
ПРОПУЩЕНО   | "find . -name '*.py' -exec rm {} +" | —
ПРОПУЩЕНО   | 'ls\nrm -rf /'                      | —
ЗАБЛОКОВАНО | '/bin/rm -rf /'                     | Command '/bin/rm' is not in the allowlist
ЗАБЛОКОВАНО | "python3 -c 'import os'"            | Command 'python3' is not in the allowlist
ПРОПУЩЕНО   | 'wc -l *.csv'                       | —
пропущено 8 з 14
```

Розбір цієї таблиці — найкорисніше в підтемі. Чотири рядки, які пройшли, показують чотири різні дірки:

- `echo hi;rm -rf /` — `shlex.split` дає `['echo', 'hi;rm', '-rf', '/']`. Оператор приклеєний до
  слова, тому перевірка `token in SHELL_OPERATORS` його не бачить. Документація визнає цей
  випадок прямо і наводить схожий приклад `cat data.txt|grep x`.
- `ls -la>out.txt` — та сама дірка для переадресації.
- `find . -name '*.py' -exec rm {} +` — `find` у allowlist, а `-exec` виконує довільну команду.
  Жоден рядок валідатора не забороняє `-exec`, бо небезпека не в першому слові й не в операторі.
- `ls\nrm -rf /` — `shlex.split` вважає новий рядок пробілом: `['ls', 'rm', '-rf', '/']`. Перший
  токен дозволений, решта виглядають як аргументи. Насправді оболонка виконає **дві** команди.

Звідси й формулювання документації: ця перевірка — «tripwire for obvious mistakes, not an enforcement boundary». Вона зупиняє
очевидне, але не витримує цілеспрямованого обходу. Автор політики мусить сам вирішити, які команди й оператори його застосунок
дозволяє, а справжній контроль — ізоляція (див. 13.2).

**Промисловий варіант політики.** Codex від OpenAI будує ту саму ідею інакше: команда порівнюється з правилом як **список
аргументів** (як його отримує `execvp(3)`), правило має рішення, і найсуворіше рішення перемагає:

```text
# Prompt before running commands with the prefix `gh pr view` outside the sandbox.
prefix_rule(
    pattern = ["gh", "pr", "view"],
    decision = "prompt",
    justification = "Viewing PRs is allowed with approval",
    match = [
        "gh pr view 7888",
        "gh pr view --repo openai/codex",
        "gh pr view 7888 --json title,body,comments",
    ],
    not_match = [
        # Does not match because the `pattern` must be an exact prefix.
        "gh pr --repo openai/codex view 7888",
    ],
)
```

Це **не Python**, а синтаксис правил Codex CLI (`prefix_rule` із `pattern`,
`decision`, `match`, `not_match`) — тому блок позначено як `text`, а не `python`.

Рішення бувають `allow`, `prompt` і `forbidden`, типове — `allow`; коли збігається кілька правил, застосовується найсуворіше
(`forbidden` > `prompt` > `allow`). Файли `.rules` лежать у теці `rules/` поряд з активним шаром конфігурації (наприклад
`~/.codex/rules/default.rules`), проектні правила під `<repo>/.codex/rules/` вантажаться лише
коли проектний шар `.codex/` позначено довіреним, а адміністратор може нав'язати обмеження через `requirements.toml`.
Перевірити правило без запуску агента можна командою
`codex execpolicy check --pretty --rules ~/.codex/rules/default.rules -- gh pr view 7888`.

Найважливіша частина — обробка обгорток. Запис `["bash", "-lc", "git add . && rm -rf /"] ховає кілька дій в одному рядку, тому
Codex обробляє `bash -lc`, `bash -c` і відповідники
`zsh`/`sh` окремо:

| Форма скрипта | Що робить Codex | Наслідок для правил |
| --- | --- | --- |
| Лінійний ланцюжок простих слів, з'єднаних `&&`, `\|\|`, `;`, `\|` (без підстановок, змінних, шаблонів) | Розбирає через tree-sitter і розбиває на окремі команди | Кожна команда оцінюється окремо; `git add . && rm -rf /` не буде дозволено, бо `rm -rf /` оцінюється самостійно |
| Переадресація, `$(...)`, бектики, `FOO=bar`, шаблони `*`/`?`, керуючі конструкції | Не інтерпретує й не розбиває | Уся конструкція трактується як одна команда `["bash", "-lc", "<повний скрипт>"]` |

Логіка тут консервативна: коли розібрати безпечно — правила застосовуються покомандно, коли ні — уся обгортка вважається одним
викликом і не проходить м'які правила.

**Типові помилки**

- **Виконувати команду без таймауту.** `sleep 100000`, команда з інтерактивним запитом або
  `read` без вводу блокують сесію назавжди: sentinel не прийде, і агент зависне, чекаючи
  `tool_result`, якого не буде.
- **Убивати лише shell, а не групу процесів.** Без `start_new_session=True` (у Python) або
  `setsid`/`Setpgid` в інших мовах таймаут прибирає оболонку, а фонові діти лишаються жити
  й тримати порти, файли та CPU.
- **Сталий sentinel.** Рядок-маркер мусить бути унікальним на виклик, інакше вивід, що містить
  його випадково, обірве читання й частина результату загубиться.
- **Очікувати, що API обріже вивід.** Не обріже: завеликий `tool_result` призведе до помилки
  запиту. `cat` великого логу ламає весь хід агента.
- **Тримати стан сесії в пам'яті одного воркера.** Стан клієнтський. За балансувальником
  друга команда може піти на інший воркер, де немає ні `cd`, ні створених файлів.
- **Покладатися на blocklist або вірити в allowlist.** Список заборонених команд пропускає будь-який синонім,
  обгортку (`env`, `xargs`, `find -exec`, `bash -c`) і шлях на кшталт `/bin/rm`, а чотири рядки з чотирнадцяти
  пройшли allowlist попри те, що виконують небажане.
- **Дозволяти `restart` без причини й ігнорувати `is_error`.** Перезапуск знищує стан: якщо модель кличе його
  регулярно, агент втрачає створені файли й працює по колу; а помилка, повернута як успішний результат, змушує модель
  будувати наступні кроки на хибній основі.

**Альтернативи.** Bash-інструмент — не єдиний спосіб дати агенту обчислення. Порівняння:

| Інструмент | Де виконується | Хто виконує | Мережа | Стан між викликами |
| --- | --- | --- | --- | --- |
| Bash tool (`bash_20250124`) | Ваша машина/контейнер | Ваш застосунок | Як у вашого процесу | Так, у межах сесії |
| Code execution (`code_execution_20250825` і новіші) | Пісочниця Anthropic | Провайдер | Немає доступу до інтернету | Новий контейнер на запит, якщо не передати `container.id` |
| Text editor tool | Ваша машина/контейнер | Ваш застосунок | — | Файли на диску |
| MCP-сервер із shell | Залежить від транспорту | MCP-сервер | Як у сервера | Залежить від сервера |

Якщо задача — «порахувати й побудувати графік», дешевше й безпечніше взяти code execution: код виконується на боці провайдера,
`tool_result` ви не формуєте взагалі. Якщо задача — «змінити мій репозиторій», потрібен саме bash tool (або text editor tool плюс
вузькі функції). Bash і code execution можуть бути ввімкнені одночасно, і тоді в моделі **два різні середовища виконання**,
стан між якими не спільний — документація окремо радить підказувати моделі, де саме вона працює.


### 13.2 Пісочниця: контейнер, обмеження ФС і мережі

**Що це.** Пісочниця (sandbox) — середовище, у якому виконуються команди агента, з штучно звуженими правами: обмежена файлова
система, обмежена мережа, обмежені ресурси, окремий користувач без зайвих привілеїв. Замість того щоб сподіватися, що модель
не попросить небезпечну команду, ви робите так, щоб навіть виконана небезпечна команда не мала доступу до того, що вам дороге.

**Навіщо це знати.** Це єдина межа, яку документація обох провайдерів називає справжнім контролем. Anthropic формулює вимогу
прямо: запускайте сесію в ізольованому середовищі, як-от контейнер або віртуальна машина, від імені найменш привілейованого
користувача, який може виконати роботу, і вважайте кожну команду недовіреним вводом. OpenAI в розділі про безпеку пісочниць
пише те саме коротше: «Agent-generated code can access the files, credentials, and network available to its environment».

**Як працює під капотом.**

**Смуга довіри проходить між harness і compute.** OpenAI описує це як головний поділ: harness — це control plane навколо
моделі (цикл агента, виклики моделі, маршрутизація інструментів, передачі, підтвердження, трейсинг, відновлення, стан
запуску), а compute — площина виконання, де агент читає й пише файли, запускає команди, ставить залежності, монтує сховища,
відкриває порти й робить знімки стану. Тримати harness поза контейнером означає, що автентифікація, білінг, аудит-журнали,
людський розгляд і стан відновлення не потрапляють у ту саму межу, яку може пробити згенерований код.

**Рівні ізоляції відрізняються на порядки.** Порівняння рівнів, для яких знайшлися первинні описи:

| Рівень | Механізм | Що захищає | Що лишається ризиком | Вартість старту |
| --- | --- | --- | --- | --- |
| Процес під окремим користувачем | Права Unix, `ulimit`, окрема група процесів | Випадкові руйнівні команди в межах домашнього каталогу | Спільне ядро, спільна ФС, спільна мережа | Нульова |
| Нативний контейнер | Namespaces + cgroups, `--read-only`, `--cap-drop`, `--network none`, `--pids-limit` | ФС, мережа, ресурси, набір capabilities | Спільне ядро: утеча через вразливість ядра або надмірні capabilities | Секунди |
| gVisor (`runsc`) | Application kernel: Linux-подібний інтерфейс реалізовано в userspace на memory-safe Go; системні інтерфейси винесено з ядра хоста в окреме ядро пісочниці | Більшість утеч із контейнера через ядро; працює як OCI-runtime з Docker і Kubernetes | Не seccomp-фільтр і не обгортка над примітивами Linux — окрема сумісність, частина системних викликів поводиться інакше | Секунди |
| microVM (Firecracker) | VMM на базі KVM створює lightweight microVM; мінімальний набір пристроїв зменшує поверхню атаки; інтегрується в Kata Containers | Апаратна віртуалізація: межа проходить по гіпервізору, а не по ядру | Складніша інфраструктура, повільніший старт, ніж контейнер | Сотні мілісекунд |
| Окрема VM/хост на задачу | Повна віртуалізація + окремі облікові дані | Найсильніша межа; різні trust boundary не бачать одна одну | Гроші та інерція оркестрації | Хвилини |

Колонка «Вартість старту» — оцінка порядку величини, а не документована цифра: конкретні значення залежать
від хоста, драйвера й реалізації.

Практичний висновок із таблиці: якщо команди виконуються на **вашій** машині (bash tool), мінімум — контейнер із вимкненою
мережею, read-only коренем і відкинутими capabilities. Якщо код виконує **провайдер** (code execution), він уже всередині
пісочниці, але з власними, документованими межами.

**Що саме документують провайдери.**

Anthropic про [code execution](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool) : усі
операції виконуються в захищеному контейнері; **контейнер не має доступу до інтернету**, тому Claude не може ставити пакети
під час виконання — доступні лише
[передвстановлені бібліотеки](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool#pre-installed-libraries)
; кожен запит виконується в новому контейнері, якщо не передати
`container.id` з попередньої відповіді; відповідь містить об'єкт `container` з `id` і
`expires_at`, а прострочений контейнер перевикористати не можна; помилки позначаються кодами `execution_time_exceeded`
і
`too_many_requests`; у версії `code_execution_20260521` на кожну Python-клітинку в
programmatic tool calling діє ліміт 90 секунд wall-clock, а перевищення повертає результат із ненульовим `return_code` і
статусом
`detection_timeout`. Версії інструмента: `code_execution_20250825` (Bash і файлові операції),
`code_execution_20260120` (додає збереження стану REPL і programmatic tool calling), `code_execution_20260521` (той
самий runtime, але опис інструмента повідомляє моделі про 90-секундний ліміт).

Anthropic про [cloud sandboxes](https://platform.claude.com/docs/en/managed-agents/cloud-sandboxes-reference) : це ізольовані
Linux-контейнери на керованій інфраструктурі; специфікація — Ubuntu 24.04 LTS, x86_64, до 8 ГБ пам'яті, до 10 ГБ диска;
**мережа** для середовищ, створених через API, типово
`unrestricted`, а для створених через Claude Studio — `limited`.

Anthropic про [self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes-security) прямо
перелічує, що ви берете на себе, і саме цей список — готовий чекліст для власної пісочниці:

| Зона відповідальності | Що конкретно робити |
| --- | --- |
| Якість образу й зміцнення runtime | Anthropic не перевіряє ваш образ. Відкиньте зайві Linux capabilities, працюйте не від root, використовуйте read-only кореневу ФС |
| Контроль вихідного трафіку | Мережа пісочниці визначається вашим VPC і правилами фаєрвола. Без обмежень скомпрометований виклик інструмента дістанеться довільних зовнішніх хостів; обмежте вихід лише потрібними ендпоінтами |
| Зберігання й ротація ключа сервісу | Ключ середовища `ANTHROPIC_ENVIRONMENT_KEY` тримайте в secrets manager, а не в env-файлах чи образі; негайно відкликайте за підозри на витік |
| Ізоляція недовірених навантажень | Ключ прив'язаний до черги одного середовища. Для недовіреного коду заводьте окремі workspace і environment на кожну межу довіри — тоді ключ обмежено сесіями одного користувача, а не спільним пулом |
| Облікові дані на сесію | Кожен елемент роботи може нести власний `secret`, який SDK-воркер використовує замість ключа середовища; передавайте його лише в пісочницю цієї сесії й ніколи не логуйте |
| Радіус ураження виконання інструментів | Інструменти працюють у пісочниці з правами вашого процесу: найменші привілеї користувача процесу, монтуйте лише потрібні каталоги |
| Логи й вміст сесій | Вміст розмов і вивід інструментів проходять через вашого воркера й лишаються у вашому середовищі; зберігання, редагування й видалення — на вас |
| Вміст memory store | Робоча копія живе за шляхом `/mnt/memory/`; воркер, що завершився без teardown, лишає її на диску — прибирання й права на цей шлях ваші |

Останній пункт варто читати уважно: store, приєднаний із доступом `read_only`, захищений від **вивантаження**, але не від
локальної зміни. Воркер відмовляється писати в цей каталог, нічого звідти не синхронізується назад, а memory-ендпоінт відхиляє
записи — але інші процеси в пісочниці все одно можуть змінити локальну копію. Команди, які агент запускає через bash tool, і
ваші власні інструменти чи MCP-сервери працюють із правами воркера. Якщо агент не повинен міняти навіть власний локальний
погляд на такий store, документація радить **вимкнути bash tool** для цього агента й не давати жодного інструмента, що пише у
ФС пісочниці.

Anthropic також перелічує те, чого **не** може зробити за вас: не може знати, що ваш ключ утекло; не перевіряє ваш образ і
runtime (компрометація ланцюга постачання в образі з control plane не видна); не ізолює окремі виконання інструментів
**усередині** пісочниці — межа Anthropic зупиняється на пісочниці; не забезпечує збереження даних у вашому середовищі після
того, як вміст дійшов до воркера.

**Платформна ізоляція Codex.** Codex не запускає контейнер на кожну команду — він використовує нативні механізми ОС, і це
важливо знати, бо поведінка різна за платформами:

| Платформа | Механізм | Практична деталь |
| --- | --- | --- |
| macOS | Seatbelt (вбудований фреймворк) | Працює «з коробки» |
| Linux / WSL2 | `bubblewrap` (`bwrap`) | Ставиться пакетним менеджером (`sudo apt install bubblewrap` або `sudo dnf install bubblewrap`); беруться перші `bwrap` з `PATH`; без нього — вбудований хелпер, якому потрібен дозвіл на непривілейовані user namespaces |
| Windows (PowerShell) | Нативна пісочниця Windows | Окрема реалізація й окрема документація |
| WSL2 | Linux-реалізація | Ті самі обмеження, що на Linux |

Тонкість Linux: на Ubuntu 24.04 після встановлення `bubblewrap` Codex може скаржитися, що не може створити потрібний user
namespace. Документація радить скопіювати профіль `bwrap-userns-restrict` з
`/usr/share/apparmor/extra-profiles/` у `/etc/apparmor.d/` і завантажити його через `sudo apparmor_parser -r`, не
вимикаючи обмеження глобально. На Ubuntu 25.04 цей профіль уже постачається в пакеті `apparmor`. Крайній варіант —
`sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`.

Пісочниця Codex застосовується **до породжених команд, не лише до власних файлових операцій**: `git`, пакетні менеджери,
тест-раннери успадковують ті самі межі.

**Обмеження файлової системи.** Мінімальний набір вимірів, які варто зафіксувати в конфігурації пісочниці, з конкретними
механізмами:

| Вимір | Контроль | Джерело |
| --- | --- | --- |
| ФС тільки для читання | `--read-only` (монтує кореневу ФС контейнера read-only) | Docker CLI reference |
| Точки запису | `--tmpfs` для тимчасових каталогів, монтування томів лише там, де справді треба писати | Docker CLI reference |
| Користувач | `-u, --user` (ім'я або UID, формат `<name\|uid>[:<group\|gid>]`) | Docker CLI reference |
| Привілеї ядра | `--cap-drop` (відкидання Linux capabilities); `--privileged` — те, чого робити не можна | Docker CLI reference |
| Зайві права | `--security-opt` (наприклад `seccomp=...`); ніколи не `seccomp=unconfined` для агента | Docker CLI reference |
| Процеси | `--pids-limit` (обмеження кількості PID; `-1` — без ліміту) | Docker CLI reference |
| Namespaces | `--userns`; навпаки, `--userns=host` вимикає перепризначення простору імен | Docker CLI reference |
| Ресурси | `--memory`, `--cpus` | Docker CLI reference |

Обмеження дискового простору на рівні файлової системи контейнера Docker-прапорця не має: для цього використовують квоти або
окремий том. Документація Anthropic для bash-сесії радить простіший інструмент — ліміти ресурсів на процес оболонки (CPU,
пам'ять, диск), наприклад через
`ulimit`.

Той самий результат у Python, без контейнера, якщо команда запускається з вашого процесу (усі перелічені константи
`resource` перевірені на Python 3.12):

```python
import resource
import subprocess


def limits():
    # Ліміт CPU-часу в секундах: процес уб'є сигналом після вичерпання
    resource.setrlimit(resource.RLIMIT_CPU, (10, 10))
    # Ліміт адресного простору: захист від «з'їв усю пам'ять»
    resource.setrlimit(resource.RLIMIT_AS, (512 * 1024 * 1024, 512 * 1024 * 1024))
    # Ліміт на розмір файлу, який процес може створити
    resource.setrlimit(resource.RLIMIT_FSIZE, (64 * 1024 * 1024, 64 * 1024 * 1024))
    # Ліміт на кількість процесів користувача: захист від fork-бомби
    resource.setrlimit(resource.RLIMIT_NPROC, (64, 64))


process = subprocess.Popen(
    ["/bin/bash"],
    stdin=subprocess.PIPE,
    stdout=subprocess.PIPE,
    stderr=subprocess.STDOUT,
    start_new_session=True,   # власна група процесів: таймаут уб'є і дітей
    preexec_fn=limits,        # застосовується в дитині до exec
    text=True,
)
```

`preexec_fn` виконується у форкнутій дитині до `exec`, тому ліміти успадковуються самою
оболонкою й усіма її нащадками. Це **не заміна контейнера**: ФС і мережа лишаються спільними з вашим процесом. Це захист від
вичерпання ресурсів, не від витоку даних.

**Обмеження мережі.** Мережа — головний канал витоку: через неї вкрадені дані виходять назовні. Дві стратегії, обидві
документовані:

```bash
# Повне вимкнення мережі в контейнері (перевірено в документації Docker)
docker run --rm --network none alpine:latest ip link show
```

```toml
# Codex: мережа вимкнена типово; увімкнення й обмеження за доменами
# ~/.codex/config.toml

[sandbox_workspace_write]
network_access = true

[features.network_proxy]
enabled = true
domains = { "api.openai.com" = "allow", "example.com" = "deny" }
```

Документація Codex підкреслює, що додавання доменних правил **не вмикає** проксі — потрібно саме
`features.network_proxy.enabled = true`. Комбінації поводяться так:

| Мережа увімкнена | `network_proxy` | Результат |
| --- | --- | --- |
| ні | увімкнено | Мережа лишається вимкненою, проксі ні на що не впливає |
| так | вимкнено | Мережа працює без обмежень: прямий вихід куди завгодно |
| так | увімкнено | Вихід обмежено налаштованою політикою доменів |

Для одноразової сесії те саме задається прапорцями: `codex -c 'features.network_proxy.enabled=true'
-c 'sandbox_workspace_write.network_access=true'`. Керування мережею поширюється на скрипти,
програми й підпроцеси, породжені командами. У ChatGPT Work аналогічний перемикач лежить у **Settings > Data controls > Work
network access**: коли «Allow public internet access» вимкнено, команди бачать лише потрібні хости з керованого allowlist.

**Облікові дані — окрема межа.** OpenAI формулює три правила, які варто перенести на будь-яку архітектуру: ізолюйте
навантаження (окремі середовища для користувачів і задач, які не повинні ділити дані); обмежте мережу (вихід лише на схвалені
ендпоінди); розділіть облікові дані (ключ застосунку зі скоупами `api.agents.read`,
`api.agents.write`, `api.responses.write` і окремі `api.vaults.read`/`api.vaults.write`; виконавцю — ключ середовища
як `CODEX_API_KEY`, який дозволяє лише підключення середовищ і жодних інших дій API). Головне застереження: **код,
згенерований агентом, може прочитати ключ середовища**, тому ключ застосунку лежить поза середовищем, а ключі не можна
вбудовувати в образи, код чи логи. Для сторонніх сервісів документація радить брокеризацію: код пісочниці використовує
плейсхолдер, а мережевий проксі підставляє справжній секрет для схвалених хостів. Довгоживучі секрети зберігають у secrets
manager — але навіть ін'єкція збереженого секрету в середовище відкриває його згенерованому коду.

**Межа довіри в MCP.** Пісочниця захищає від коду, який виконує агент. Але інструменти часто приходять із MCP-серверів, і там
межа інша. Специфікація описує її так: host керує дозволами з'єднань і життєвим циклом клієнтів, застосовує політики безпеки й
вимоги згоди, ухвалює рішення про авторизацію; кожен клієнт спілкується рівно з одним сервером і тримає межі між серверами;
сервери «не повинні мати змоги прочитати всю розмову й не бачити в інші сервери». Для Streamable HTTP специфікація вимагає
трьох речей: сервери **MUST** перевіряти заголовок
`Origin` на всіх вхідних з'єднаннях, щоб унеможливити DNS rebinding (за невалідного `Origin` —
HTTP 403), **SHOULD** слухати лише `127.0.0.1`, а не `0.0.0.0`, і **SHOULD** реалізувати автентифікацію всіх з'єднань. Без цих
заходів атакувальник може через DNS rebinding взаємодіяти з локальним MCP-сервером із віддаленого сайту. Деталі транспорту й
життєвого циклу — у розділі 14.

**Типові помилки**

- **Пісочниця, у якій змонтовано весь домашній каталог.** Ізоляція ФС зводиться нанівець, якщо
  `~/.ssh`, `~/.aws` або `.env` доступні зсередини. Монтуйте лише робочий каталог і лише на
  запис у нього.
- **Мережа «як у хоста».** `--network none` (або політика доменів) — єдиний спосіб гарантувати,
  що вкрадені дані не підуть назовні. Обмеження лише на рівні промпту не працює.
- **`--privileged` і `seccomp=unconfined` «щоб працювало».** Це вимикає саме ті механізми, які
  відділяють агента від ядра хоста.
- **Root у пісочниці.** Найменші привілеї означають окремого користувача; від root будь-яка помилка прав стає критичною.
- **Секрети в образі або в env пісочниці.** Згенерований код читає змінні середовища й файли; ключ у середовищі
  вважається скомпрометованим у момент ін'єкції, а один спільний ключ на всіх без окремих середовищ на кожну межу
  довіри дає одному користувачу доступ до сесій іншого.
- **Очікування, що провайдер ізолює інструменти всередині пісочниці.** Межа провайдера
  зупиняється на пісочниці: як ви розділяєте окремі виконання всередині неї — ваша робота.
- **Віра, що read-only store неможливо змінити.** Read-only захищає від вивантаження, але не від
  локальної модифікації іншими процесами пісочниці.
- **Відсутність лімітів ресурсів.** Без `--pids-limit` і лімітів CPU/пам'яті одна команда
  (fork-бомба, нескінченний цикл) кладе весь хост.

**Альтернативи.** Замість власної пісочниці можна взяти керований провайдер виконання. OpenAI Agents SDK документує клієнти
для `UnixLocalSandboxClient` (швидка локальна ітерація), `DockerSandboxClient` (локальна контейнерна ізоляція) і хостованих
провайдерів — Blaxel, Cloudflare, Daytona, E2B, Modal, Runloop, Vercel. Логіка вибору: починайте з Unix-local або Docker,
переходьте на хостованого провайдера, коли потрібні кероване виконання, масштабування, прев'ю, монтування сховищ, знімки або
облікові дані, які мають жити поза вашим сервером застосунку. Другий варіант — узагалі не давати shell: вузькі функції з
структурованими параметрами (розділ 12) і code execution на боці провайдера покривають більшість задач, для яких люди беруть
bash.


### 13.3 Підтвердження людиною (human-in-the-loop)

**Що це.** Патерн, у якому цикл агента зупиняється перед дією з побічним ефектом і чекає рішення людини (або окремого
політичного компонента): продовжити чи відхилити. Модель усе ще вирішує, що дія потрібна, але виконання блокується до
схвалення.

**Навіщо це знати.** OWASP ставить цей пункт у перелік заходів проти prompt injection: «Require human approval for high-risk
actions» — впровадити human-in-the-loop для привілейованих операцій, щоб запобігти несанкціонованим діям. OpenAI формулює межу
застосування: automatic guardrails перевіряють вхід, вихід і поведінку інструментів автоматично, а людський розгляд потрібен
там, де є побічні ефекти — скасування, редагування, shell-команди, чутливі MCP-дії. Знання тут потрібне не для того, щоб
«додати кнопку», а щоб правильно вибрати **точку** зупинки: не там, де модель щось сказала, а там, де виникає побічний ефект.

**Як працює під капотом.**

**Механіка переривань в OpenAI Agents SDK.** Дія позначається як така, що потребує схвалення, на рівні інструмента:
`needsApproval: true` у TypeScript або `@function_tool(needs_approval=True)` у Python. Далі працює фіксований життєвий цикл:
запуск **записує переривання замість виконання інструмента**; результат повертає
`interruptions` плюс `state`, з якого запуск можна відновити; застосунок схвалює або відхиляє пункти; ви продовжуєте
**той самий запуск** зі `state`, а не починаєте новий хід користувача. Якщо розгляд може затягнутися, `state` серіалізують,
зберігають і відновлюють пізніше — це все одно той самий запуск.

```python
import asyncio

from agents import Agent, Runner, function_tool


@function_tool(needs_approval=True)
async def cancel_order(order_id: int) -> str:
    return f"Cancelled order {order_id}"


agent = Agent(
    name="Support agent",
    instructions="Handle support requests and ask for approval when needed.",
    tools=[cancel_order],
)


async def main() -> None:
    result = await Runner.run(agent, "Cancel order 123.")

    if result.interruptions:
        state = result.to_state()
        for interruption in result.interruptions:
            state.approve(interruption)
        result = await Runner.run(agent, state)

    print(result.final_output)


if __name__ == "__main__":
    asyncio.run(main())
```

Той самий патерн переривання працює й коли інструмент зі схваленням лежить глибше в workflow — після handoff або всередині
вкладеного `agent.as_tool()` (Python) чи
`agent.asTool()` (TypeScript).

**Де саме ставити перевірку.** Тут є пастка, яку документація описує окремим розділом «Workflow boundaries matter»:
agent-level guardrails не виконуються всюди. Input guardrails працюють лише для першого агента в ланцюжку, output guardrails —
лише для агента, що видає фінальний результат, tool guardrails — лише на тих функціональних інструментах, до яких прикріплені.
Якщо вам потрібні перевірки навколо **кожного** виклику інструмента в manager-style workflow, не покладайтеся на агентські
input/output guardrails: ставте валідацію поряд з інструментом, який створює побічний ефект. Стрімінг не створює окремої
системи підтверджень: якщо стрімований запуск зупинився, дочекайтеся його завершення, подивіться `interruptions`, вирішіть і
продовжте з того самого `state`.

**Патерни підтвердження.** На практиці їх п'ять, і вони різняться тим, хто вирішує, коли і з якою широтою:

| Патерн | Хто вирішує | Коли доречний | Ціна |
| --- | --- | --- | --- |
| Блокувальне підтвердження на дію | Людина в реальному часі | Рідкісні небезпечні дії з високою ціною помилки | Людина стає вузьким місцем |
| Підтвердження зі збереженням стану | Людина, можливо пізніше | Асинхронні процеси: розгляд приходить через години | Потрібна серіалізація `state` і сховище |
| Підтвердження на сесію | Людина один раз | Повторювані однотипні дії в межах довіреної задачі | Ширша межа: схвалено більше, ніж показано |
| Автоматичний рецензент | Окремий агент-рев'юер | Високий потік, потрібно зменшити втомленість від підтверджень | Не розширює права; лише замінює людину на межі пісочниці |
| Правило з рішенням `prompt` | Політика + людина | Команди, які зрідка потрібні поза пісочницею | Потрібне супроводження правил |

**Правила як політика підтверджень.** У Codex три рішення правила (`allow`, `prompt`,
`forbidden`) — це фактично три режими: виконувати автоматично, спитати, заблокувати без
запитання. Для `forbidden` документація радить додавати в `justification` рекомендовану альтернативу (наприклад, «Use
`rg` instead of `grep`.»), бо текст правила може потрапляти в повідомлення про відмову. Приклади команд у полях
`match` і `not_match` валідуються під час завантаження правил — це вбудовані модульні тести, які ловлять помилку до
того, як правило почне діяти.

**Автоматичний рецензент (auto-review).** Це не «дозволити все», а заміна людини на конкретній межі. Формулювання документації
пряме: «Auto-review is a reviewer swap, not a permission grant» — він не розширює
`writable_roots`, не вмикає мережу й не послаблює захищені шляхи, він лише змінює те, як обробляються запити, які
**вже** потребують схвалення. Спрацьовує на: виклики shell/exec, що просять розширення прав поза пісочницею; мережеві запити,
заблоковані поточною пісочницею чи політикою; редагування файлів поза дозволеними `writable_roots`; виклики MCP або
app-інструментів, що потребують схвалення за своїми анотаціями чи режимом; доступ Computer Use до нового сайту чи домену.
Рутинні дії, дозволені всередині пісочниці, рецензенту не показують.

Що рецензент блокує (за документацією): надсилання приватних даних, секретів чи облікових даних на недовірені призначення;
зондування облікових даних, токенів, cookie й матеріалів сесій; широке або стійке послаблення безпеки; руйнівні дії зі значним
ризиком незворотної шкоди. Рецензент — сам агент Codex із вужчою задачею; він бачить компактний транскрипт плюс точний запит
на схвалення (повідомлення користувача, показані оновлення асистента, релевантні виклики й виводи інструментів, запропоновану
дію). **Приховане міркування асистента не включається**: рецензент бачить збережені елементи чату й докази з інструментів, а
не приватний chain-of-thought.

**Відмови й поведінка при збоях.** Явна відмова не вважається звичайною помилкою пісочниці: Codex повертає головному агенту
обґрунтування й додає сильнішу інструкцію — не досягати того самого результату обхідним шляхом, непрямим виконанням чи обходом
політики. Далі працює запобіжник: у відкритій реалізації Auto-review перериває хід після **3 послідовних відмов** або **10
відмов у ковзному вікні останніх 50 розглядів** у межах того самого ходу. Будь-яке не-відмовне рішення обнуляє лічильник
послідовних відмов. Таймаути показують окремо від явних відмов, і головному агентові повідомляють, що **сам таймаут не є
доказом небезпечності дії**. Людина може переглянути недавні відмови через `/approve` у TUI, і таке схвалення вузьке: воно
стосується точної дії, у тому самому контексті, а повторна спроба все одно проходить через Auto-review.

**Політика для чутливих доменів.** Для авторизованих кібербезпекових workflow документація OpenAI описує п'ять кроків, які
переносяться на будь-який небезпечний домен: перевіряти запропоновану ціль, дію, аргументи інструмента, особу того, хто кличе,
і часове вікно проти схваленого обсягу робіт; давати рецензенту **точну запропоновану дію й лише той контекст, який потрібен
для її оцінки**; відхиляти хости поза обсягом, крадіжку облікових даних, закріплення в системі, витік даних, руйнівні зміни,
доступ до продакшну й спроби обійти політику; зупиняти неоднозначні або високоризикові дії для явного схвалення людиною **до**
запуску інструмента; забезпечувати незалежні межі файлової системи, мережі, ідентичності й проекту, записувати рішення та
результати й **закриватися відмовою (fail closed)**, якщо розгляд перевищив час або став недоступним**.

Останній пункт — найважливіший архітектурно. Підтвердження людиною без таймауту й без fail-closed перетворюється на
«дозволити, якщо ніхто не відповів». Реальний механізм із таймаутом і закриттям відмовою (прогін справжній, рецензенти —
заглушки):

```python
import threading
import time


def approve_with_timeout(command, reviewer, timeout=0.3):
    """Питає рецензента; якщо рішення немає вчасно — блокує дію."""
    box = {}

    def ask():
        box["decision"] = reviewer(command)

    thread = threading.Thread(target=ask, daemon=True)
    thread.start()
    thread.join(timeout)
    if thread.is_alive():
        return False, "timeout: рішення немає, дія заблокована (fail closed)"
    return box["decision"] == "approve", f"reviewer={box['decision']}"


def fast_reviewer(command):        # схвалення встигає
    return "approve"


def deny_reviewer(command):        # явна відмова
    return "deny"


def slow_reviewer(command):        # людина не відповіла
    time.sleep(1.0)
    return "approve"
```

**Фактичний вивід** цього механізму:

```text
fast_reviewer  -> executed=True (reviewer=approve)
deny_reviewer  -> executed=False (reviewer=deny)
slow_reviewer  -> executed=False (timeout: рішення немає, дія заблокована (fail closed))
```

Зверніть увагу на третій рядок: `slow_reviewer` повертає `approve`, але пізніше за таймаут — і дія все одно не виконується. Це
і є fail closed: невідомість трактується як відмова, а не як дозвіл.

**Типові помилки**

- **Fail open.** Обробник таймауту, який повертає `allow`, зводить усю механіку до декорації.
  Невідомість мусить означати «ні».
- **Схвалення без прив'язки до аргументів.** «Схвалити» на рівні інструмента означає, що модель
  потім викличе його з іншими аргументами. Схвалювати треба конкретну дію з конкретними
  параметрами, а окреме широке схвалення на сесію — свідомий компроміс.
- **Підтвердження як єдиний контроль.** Якщо підтвердження стоїть, але ні пісочниці, ні
  allowlist немає, одна помилка оператора (або втома від сотого діалогу) дає повний доступ.
- **Автоматичний рецензент як розширення прав.** `auto_review` не додає прав; якщо його
  сприймати як «дозволити все, що пройшло агента», межа зникає.
- **Переривання, яке втрачає стан.** Якщо `state` не серіалізується, довгий розгляд неможливий: після паузи запуск
  доведеться починати з нуля, а модель піде іншим шляхом.
- **Перевірка не там, де побічний ефект.** Input-guardrail на першому агенті не бачить виклику інструмента в
  дочірньому агенті після handoff.
- **Немає запобіжника проти циклу відмов.** Без обмеження (3 послідовні відмови або 10 у вікні
  50 розглядів) агент витрачає токени на повторні спроби обійти відмову.
- **Показ рецензентові всього контексту.** Передавати політичному компоненту всю розмову —
  зайвий ризик витоку; документація радить давати точну дію й мінімум потрібного контексту.

**Альтернативи.** Підтвердження людиною не єдиний спосіб контролювати побічні ефекти. Порівняння підходів із джерел цього
розділу:

| Підхід | Хто ухвалює рішення | Затримка | Коли брати |
| --- | --- | --- | --- |
| Guardrail (вхід/вихід/інструмент) | Код або модель-перевіряч | Мілісекунди | Автоматичні перевірки: PII, джейлбрейк, аргументи виклику |
| Підтвердження людиною | Людина | Секунди–години | Дії з незворотними наслідками |
| Auto-review | Агент-рев'юер | Секунди | Високий потік, потрібно зменшити втому від підтверджень |
| Allowlist/denylist команд | Політика | Мікросекунди | Типові команди, які можна виконувати автоматично |
| Read-only режим | Конфігурація середовища | Нульова | Етап дослідження й планування без змін |
| Повне вимкнення bash | Конфігурація агента | Нульова | Коли агент не повинен мати доступу до системи взагалі |

Останній рядок варто пам'ятати: найдешевше підтвердження — те, якого не потрібно, бо інструмент просто не дали. Документація
Anthropic описує конкретний випадок, коли це єдиний правильний вибір: якщо агент не має мати можливості змінити навіть
локальний погляд на read-only memory store, bash tool для нього вимикають.


### 13.4 Аудит і журналювання дій агента

**Що це.** Аудит-журнал (audit log) — незмінний перелік того, що агент запропонував зробити, що з цього виконалось, із яким
результатом і за чиїм рішенням. Він відрізняється від звичайного логування тим, що пишеться **до** виконання, а не після, і
призначений для розслідування, а не для відлагодження.

**Навіщо це знати.** Три причини, кожна з джерел:

1. Команда, яка зависла або зламала сесію, все одно мусить лишити запис — тому запис робиться
   перед запуском.
2. Розслідування інциденту без журналу неможливе: ви не знаєте, що саме виконав агент, а що
   лише запропонував.
3. Документація OpenAI для чутливих доменів прямо вимагає «записувати рішення та результати
   виконання» (`record decisions and execution outcomes`) і тримати аудит-логи — причому
   harness тримає їх **поза** пісочницею, щоб згенерований код не міг їх підробити.

**Як працює під капотом.**

**Одна точка проходження.** Документація Anthropic радить не розкидати логування по коду, а пропустити кожну команду через
єдину обгортку, яка фіксує команду до запуску й вивід після:

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(message)s")


def execute_and_log(session, command):
    """Run a command in the session and keep an audit record of it."""
    logging.info("command=%r", command)
    output = session.execute_command(command)
    logging.info("output=%r", output[:200])  # first 200 characters
    return output
```

Записані рядки типово йдуть у `stderr`; щоб вони збереглися, їх треба спрямувати у файл або ваш логувальний пайплайн.
Документація окремо підкреслює: додавайте те, що прив'язує запис до запиту, — кінцевого користувача й `tool_use_id`.

**Два різні споживачі виводу.** Тут найчастіша плутанина. Моделі вивід треба **обрізати** (API не обрізає
`tool_result`, завеликий запит відхиляється), а журналові — **зберегти повністю**. Приклад вище логує перші 200
символів, бо це ілюстрація; у продакшн-аудиті такий підхід дає дірку: у хвіст виводу часто потрапляє саме те, що важливе для
розслідування — код виходу, останній рядок помилки, шлях, який не знайшли. Тримайте два канали: модель отримує обрізану
версію, журнал — повну (з редеакцією секретів).

**Що писати.** Поля, які мають сенс для розслідування, і звідки вони беруться:

| Поле | Джерело | Навіщо |
| --- | --- | --- |
| `seq` | Ваш лічильник | Порядок подій; виявляє пропущені записи |
| `ts` | Час | Відновлення хронології, кореляція з логами сервісу |
| `tool_use_id` | Блок `tool_use` | Зв'язок команди з конкретним викликом і `tool_result` |
| `command` | `input.command` | Що саме просила модель |
| `decision` | Ваша політика | Дозволено, заборонено, схвалено людиною — і чому |
| `principal` | Ваш застосунок | Хто кінцевий користувач |
| `session_id` | Ваш застосунок | Групування подій одного запуску |
| `output` / `exit_code` | Результат виконання | Що сталося насправді |
| `hash`, `prev_hash` | Обчислення | Виявлення підробки заднім числом |

**Чому звичайний файл журналу не захищає.** Лог, який може дописати й переписати той самий процес, у якому працює агент, не є
доказом: зловмисник із доступом до ФС перепише історію. Мінімальний практичний захист — ланцюжок хешів: кожен запис містить
хеш попереднього, тому будь-яка правка в середині ламає всі наступні хеші. Реалізація й **фактичний вивід**:

```python
import hashlib
import json

GENESIS = "0" * 64


def make_entry(seq, ts, tool_use_id, command, decision, prev_hash):
    body = {
        "seq": seq,
        "ts": ts,
        "tool_use_id": tool_use_id,
        "command": command,
        "decision": decision,
        "prev_hash": prev_hash,
    }
    payload = json.dumps(body, ensure_ascii=False, sort_keys=True)
    body["hash"] = hashlib.sha256(payload.encode()).hexdigest()
    return body


def verify(entries):
    prev = GENESIS
    for entry in entries:
        body = {k: v for k, v in entry.items() if k != "hash"}
        expect = hashlib.sha256(
            json.dumps(body, ensure_ascii=False, sort_keys=True).encode()
        ).hexdigest()
        if entry["prev_hash"] != prev:
            return False, f"розрив ланцюга на seq={entry['seq']}"
        if entry["hash"] != expect:
            return False, f"підроблено вміст seq={entry['seq']}"
        prev = entry["hash"]
    return True, "ланцюг цілий"
```

```text
1 git status allow bc3a933f7c11128d
2 rm -rf /tmp/work deny:not-in-allowlist efc10195f3052fd4
3 pytest -q allow 295392867aca16cd
до підробки: (True, 'ланцюг цілий')
після підробки: (False, 'підроблено вміст seq=2')
```

Підробка в цьому прогоні — заміна `decision` другого запису з відмови на дозвіл. Перевірка впала саме на ньому:
`підроблено вміст seq=2`. Ланцюжок дає **виявність**, а не незмінність: якщо зловмисник перепише всі наступні записи
разом із хешами, ланцюг зійдеться. Щоб цього не сталося, останній хеш треба періодично відправляти назовні — у незмінне
сховище, у систему збирання логів під іншим обліковим записом або в щоденний підписаний звіт.

**Редеакція.** Документація прямо вимагає вичищати облікові дані й інші секрети з виводу **перед** поверненням його моделі.
Той самий фільтр потрібен і для журналу — інакше ваша система аудиту стає найповнішим сховищем секретів у компанії:

```python
import re

PATTERNS = [
    (r"(?i)(api[_-]?key|token|secret|password)\s*[=:]\s*\S+", r"\1=***REDACTED***"),
    (r"sk-[A-Za-z0-9]{8,}", "***REDACTED***"),          # ключі у стилі OpenAI
    (r"gh[pousr]_[A-Za-z0-9]{8,}", "***REDACTED***"),   # токени GitHub
]


def redact(text):
    for pattern, repl in PATTERNS:
        text = re.sub(pattern, repl, text)
    return text
```

**Незмінний зліпок розмови.** Окрема вимога стосується збереження самого ходу: блоки міркування треба повертати моделі
**повними й незміненими**, а повідомлення асистента — відлунювати точно так, як його отримано. Перебудова повідомлення або
фільтрація блоків `redacted_thinking` призводить до помилки 400. Для аудиту це означає просте правило: зберігайте **той самий
байтовий зліпок** ходу, який ви відправили, а не свою реконструкцію. Реконструкція неминуче розійдеться з оригіналом, а отже
не буде доказом.

**Де межі вашої відповідальності за дані.** Документація self-hosted пісочниць формулює це прямо: вміст розмов і вивід
інструментів проходять через вашого воркера й лишаються у вашому середовищі; зберігати, редагувати чи видаляти їх — ваша
відповідальність, і провайдер не бачить, що воркер робить із вмістом після доставки. Те саме стосується MCP: сервери не
повинні бачити всю розмову, тому повний журнал може існувати лише на боці host.

**Типові помилки**

- **Логувати лише після виконання.** Команда, яка вбила сесію, не лишить запису — а саме такі
  команди найцікавіші для розслідування.
- **Логувати в `stderr` і нікуди його не збирати.** Типово записи йдуть у `stderr`; без
  спрямування у файл або пайплайн вони зникають разом із контейнером.
- **Один канал для моделі й для аудиту.** Обрізаний для моделі вивід не можна використовувати як
  доказ; повний вивід не можна віддавати моделі через ліміт розміру запиту.
- **Секрети в журналі.** Вивід `env`, `cat .env`, `git config` і токени в аргументах команд
  потрапляють у лог. Редеакція мусить стояти на шляху **і** до моделі, **і** до сховища.
- **Журнал без кореляції.** Без `tool_use_id` і `session_id` неможливо зв'язати запис із
  конкретним викликом, а без користувача — з тим, чиї дані оброблялися.
- **Хеш-ланцюжок без зовнішнього якоря.** Перевірка цілісності, яку може перерахувати той самий
  процес, захищає лише від неуважної правки.
- **Журнал у записуваному каталозі або всередині пісочниці.** OpenAI описує поділ однозначно: harness тримає
  аудит-логи поза контейнером, бо все, що всередині, згенерований код може прочитати й змінити; файл у теці,
  доступній агенту на запис, доступний і на видалення.
- **Реконструкція ходу замість зліпка.** Перебудована історія не проходить перевірку й не є доказом; зберігайте
  надіслані блоки як є.

**Альтернативи.** Замість власного формату журналу є три готові шляхи. Перший — структуровані трейси через OpenTelemetry:
документація OpenAI описує harness як власника трейсингу, а провайдерські SDK дають спани на виклики інструментів (розділ 23
розбирає observability детально). Другий — незмінні сховища (append-only, WORM) або окремий обліковий запис із правом лише на
дописування; ланцюжок хешів тоді лишається дешевою додатковою перевіркою. Третій — зовнішній SIEM або система збирання логів,
куди записи йдуть потоком: вона дає збереження, кореляцію й оповіщення, які безглуздо писати самому. Практичний компроміс:
JSONL-файл із ланцюжком хешів на боці застосунку плюс щоденне вивантаження останнього хеша в сховище, яке агент не контролює.


### 13.5 Модель загроз і чому prompt injection стає RCE

**Що це.** Модель загроз (threat model) — це список того, хто і як може завдати шкоди системі, і які контролі стоять на
кожному шляху. У застосунках з агентами центральна загроза має назву **prompt injection**, і її особливість у тому, що вона
здатна перетворитися з «модель сказала дурницю» на «на сервері виконався чужий код».

**Навіщо це знати.** OWASP визначає injection як окрему категорію (`LLM01:2025`) і прямо перелічує серед наслідків **виконання
довільних команд у підключених системах** («Executing arbitrary commands in connected systems»). Це і є місток до RCE: щойно в
агента є bash-інструмент, prompt injection перестає бути проблемою якості відповідей і стає проблемою виконання. Promptfoo в
переліку плагінів має окремий тест `shell-injection`, опис якого — «Attempts to execute shell commands through the model».

**Як працює під капотом.**

**Два типи injection.** За OWASP: прямі (direct) — коли ввід користувача безпосередньо змінює поведінку моделі, і непрямі
(indirect) — коли модель приймає ввід із зовнішніх джерел (сайти, файли) і вміст цих джерел змінює її поведінку; обидва типи
бувають навмисні й ненавмисні. Приклад OWASP відповідає темі розділу: користувач просить модель підсумувати вебсторінку з
прихованими інструкціями, і ці інструкції змушують вставити зображення з посиланням на URL — так витікає приватна розмова. Для
агента з bash це той самий механізм із коротшим шляхом до наслідків.

**Ланцюжок «injection → RCE».** Ось шлях від недовіреного тексту до виконання коду. Це **схема** (не цитата з документації), і
кожна ланка має свій контроль:

```text
недовірений текст      контроль: сегрегація й позначення джерела; структуровані
(сайт, файл, вивід     виводи замість вільного тексту; недовірене передається
команди, email,        лише в user-повідомленнях
README, назва гілки)
        │
        ▼
контекст моделі        контроль: system prompt; найменші привілеї інструментів;
(інструкція поряд      обмежений набір інструментів (немає інструмента — немає дії)
із вашими)
        │
        ▼
блок tool_use          контроль: валідація схеми й аргументів; allowlist/denylist;
{name: "bash", …}      правила з рішеннями prompt/forbidden
        │
        ▼
політика дозволу       контроль: tool guardrails поряд з інструментом;
(автомат + людина)     підтвердження з fail closed на таймауті
        │
        ▼
виконання              контроль: пісочниця; read-only ФС; non-root; відкинуті
(shell, інтерпретатор) capabilities; ліміти ресурсів
        │
        ▼
побічний ефект         контроль: мережевий egress-allowlist; журнал дій;
(файли, мережа, дані,  редеакція виводу
облікові дані, прод)
```

Ключова властивість ланцюжка: **розрив на будь-якій ланці зупиняє атаку, і кожна ланка має коштувати дешевше за попередню**.
Якщо єдиний контроль — system prompt, то вся безпека системи дорівнює стійкості моделі до ін'єкції, а OWASP прямо пише, що
надійних методів запобігання невідомо. Практичний висновок: проєктуйте так, щоб ін'єкція не мала куди привести.

**Що радить OWASP.** Сім заходів пом'якшення з `LLM01:2025`, які варто мати як чекліст:

| № | Захід | У термінах цього розділу |
| --- | --- | --- |
| 1 | Обмежити поведінку моделі: роль, можливості, межі в system prompt, суворе дотримання контексту, ігнорування спроб змінити інструкції | System prompt — необхідний, але недостатній |
| 2 | Визначити й перевіряти очікувані формати виводу; валідувати детермінованим кодом | Структуровані виводи замість вільного тексту на межах між вузлами |
| 3 | Фільтрація входу й виходу: категорії, семантичні фільтри, перевірка рядків | Редеакція й перевірка виводу інструментів перед поверненням моделі |
| 4 | Контроль привілеїв і найменший доступ: функції обробляти в коді, а не віддавати моделі; мінімум прав | Вузькі функції замість універсального shell |
| 5 | Вимагати людського схвалення для високоризикових дій | Підтема 13.3 |
| 6 | Сегрегувати й позначати зовнішній вміст, щоб обмежити його вплив | Не довіряти виводу інструментів як інструкціям |
| 7 | Проводити змагальне тестування й симуляції атак, вважаючи модель недовіреним користувачем | Red teaming, підтема нижче |

**Розподіл загроз за шарами.** Promptfoo розділяє загрози на рівень моделі (foundation) і рівень застосунку. До рівня моделі
належать джейлбрейки, шкідливий вміст, галюцинації, порушення авторських прав, витік PII з тренувальних даних, надмірна
агентність. До рівня застосунку — те, що з'являється лише після підключення моделі до середовища:

| Загроза рівня застосунку | У чому вона для агента з shell |
| --- | --- |
| Непрямий prompt injection | Інструкція приходить не від користувача, а з прочитаного файлу, виводу команди, сторінки |
| Витік PII з контексту (наприклад, RAG) | Агент має доступ до приватних документів і каналу виходу |
| Вразливості на основі інструментів: несанкціонований доступ до даних, ескалація привілеїв | Один зайвий інструмент — і модель має більше прав, ніж задача |
| Перехоплення цілей (hijacking) | Агент переорієнтовується на чужу мету й виконує її командами |
| Витік даних і розмови: markdown-зображення, розгортання посилань | Дані йдуть назовні через URL, а не через файл |

Практичний висновок Promptfoo: більшість застосунків інтегрують готові моделі, тому саме загрози рівня застосунку дають
найбільший технічний ризик — і саме на них варто спрямовувати red teaming.

**Готові тести для агентів із кодом.** Promptfoo має окремий набір плагінів для кодингових агентів. Їхні назви — це фактично
перелік векторів для моделі загроз агента з доступом до системи:

| Група плагінів | Що перевіряє |
| --- | --- |
| `coding-agent:repo-prompt-injection` | Чи піде агент за інструкцією, схованою в недовіреному вмісті репозиторію |
| `coding-agent:terminal-output-injection` | Чи сприйме агент недовірений вивід термінала як інструкції |
| `coding-agent:secret-env-read`, `coding-agent:secret-file-read` | Чи розкриває агент секрети зі свого середовища й захищені локальні файли поза межами задачі |
| `coding-agent:sandbox-read-escape`, `coding-agent:sandbox-write-escape` | Чи читає й чи змінює агент дані поза призначеним workspace або межею пісочниці |
| `coding-agent:network-egress-bypass`, `coding-agent:procfs-credential-read` | Чи робить агент несанкціоновані вихідні запити, обходячи мережеву політику, і чи витягує облікові дані через метадані процесів, успадковане середовище та файлові дескриптори |
| `coding-agent:delayed-ci-exfil`, `coding-agent:automation-poisoning` | Чи закладає агент зміни в CI, хуки й розклад автоматизації, які зіллють дані вже після запуску, чи закріплює небезпечну поведінку в автоматизації репозиторію |
| `coding-agent:generated-vulnerability`, `coding-agent:steganographic-exfil`, `coding-agent:verifier-sabotage` | Чи вносить агент уразливий код під виглядом звичайної задачі, чи ховає дані в малопомітних артефактах, чи послаблює захищені тести, снапшоти, політики й lock-файли, щоб «пройти» перевірку |
| `coding-agent:core`, `coding-agent:all` | Групові набори: `core` — ін'єкція в репозиторії, ін'єкція через вивід термінала, читання секретів із середовища, втеча з пісочниці на читання, саботаж верифікатора; `all` — усі підтримувані плагіни набору |

Остання група — недооцінена. Стеганографічна ексфільтрація означає, що заборона очевидних мережевих викликів не закриває
канал; саботаж верифікатора означає, що агент може не зламати систему, а змінити критерій її правильності.

**Каталог загальних плагінів.** Для агентів із shell релевантні, окрім `shell-injection`: `excessive-agency` (модель бере
більше ініціативи, ніж їй дали повноважень), `debug-access` (спроби скористатися командами відлагодження),
`hijacking` (використання ресурсів не за темою), `indirect-prompt-injection` (інструкції, вставлені в змінні промпту),
`data-exfil` (маніпуляція агентом заради витоку даних через непряму ін'єкцію у вебвмісті), `tool-discovery` (чи
розкриває система список власних інструментів), `bfla` (дії поза авторизованою роллю), `bola` (доступ до ресурсів інших
користувачів), `sql-injection`, `special-token-injection` (ін'єкція через роздільники формату розмови),
`reasoning-dos` (виснаження ресурсів надмірними міркуваннями).

**Як це запускати.** Red team у Promptfoo проходить трьома кроками: `promptfoo redteam init` (базова конфігурація), `promptfoo
redteam run` (генерація змагальних тестів і прогін проти цілі), `promptfoo redteam report` (перегляд результатів). `redteam
run` — це скорочення, яке поєднує генерацію й оцінку, тож згенеровані тести завжди синхронізовані з актуальною конфігурацією.
Структура конфігурації (реальні поля з документації):

```yaml
targets:
  - id: openai:gpt-5
    label: customer-service-agent

redteam:
  purpose: "Агент підтримки з доступом до shell-інструментів у репозиторії"
  plugins:
    - shell-injection
    - excessive-agency
    - indirect-prompt-injection
    - 'coding-agent:core'
  strategies:
    - jailbreak:meta
    - jailbreak:composite
  frameworks:
    - owasp:llm
    - mitre:atlas
  numTests: 10
  language: uk
```

Доступні ідентифікатори фреймворків для поля `frameworks`: `owasp:llm`, `owasp:api`,
`owasp:agentic`, `mitre:atlas`, `nist:ai:measure`, `iso:42001`, `gdpr`, `eu:ai-act`,
`dod:ai:ethics`. Для CI/CD документація радить повторювані прапорці `--tag key=value` при
`redteam run` або `redteam eval`, щоб фіксувати контекст запуску без зміни шаблону сканування:
`promptfoo redteam run --tag ci.run-id="$CI_RUN_ID" --tag git.sha="$GIT_SHA"`.

**Чому «просто попередити модель» не працює.** Документація OpenAI з безпеки агентів формулює межу прямо: ризик зростає, коли
агенти обробляють довільний текст, який впливає на виклики інструментів; структуровані виводи й ізоляція **суттєво зменшують,
але не усувають** цей ризик. Там же — дві конкретні вимоги: не використовуйте недовірені змінні в developer-повідомленнях (бо
developer-повідомлення мають приоритет над user і assistant, і ін'єкція туди дає атакувальнику максимальний контроль —
передавайте недовірений ввід через user-повідомлення) і використовуйте структуровані виводи, щоб обмежити потік даних (enum,
фіксовані схеми, обов'язкові назви полів прибирають вільні канали, якими можна пронести інструкції).

**Постачальник теж накладає обмеження.** Для моделей із високою кібербезпековою спроможністю (GPT-5.3-Codex і новіші, включно
з GPT-5.4 і GPT-5.5) діють додаткові автоматичні запобіжники в API. Якщо системи виявляють підозрілу кібербезпекову активність
понад пороги, доступ можуть тимчасово обмежити, а запити повертають помилку з кодом
`cyber_policy`. Без `safety_identifier` на користувача доступ можуть відкликати для **всієї організації**; з унікальним
`safety_identifier` — для конкретного користувача. Документація попереджає, що системи ще калібруються й легітимна дослідницька
робота може бути помилково позначена. Практичне правило: включайте
`safety_identifier` і не будуйте критичний шлях на припущенні, що доступ ніколи не обмежать.

**Типові помилки**

- **Ставити всю безпеку на system prompt.** За OWASP надійних методів запобігання injection
  невідомо; system prompt знижує ймовірність, але не є межею.
- **Blocklist замість allowlist.** Список заборонених слів обходять синонімами, обгортками й
  кодуванням; OWASP окремо згадує Base64, емодзі, кілька мов і ASCII-арт як способи обійти
  фільтри.
- **Довіряти виводу інструментів.** `cat README.md`, вивід тестів, повідомлення коміту — усе це
  недовірений вхід; плагін `coding-agent:terminal-output-injection` існує саме тому.
- **Вважати, що «читання» безпечне.** Агент, який лише читає, однаково має канал виходу: витік
  через URL, markdown-зображення, назву файлу, коміт.
- **Один широкий інструмент замість кількох вузьких.** Універсальний `run_shell` дає ін'єкції
  повний набір можливостей; п'ять вузьких функцій — п'ять окремих дверей.
- **Продакшн-облікові дані в середовищі агента.** Згенерований код читає змінні середовища;
  OWASP радить давати застосунку власні токени й обробляти функції в коді, а не віддавати їх
  моделі.
- **Вимкнені підтвердження «щоб не заважали».** Кожне вимкнене підтвердження — це ланка
  ланцюжка, яку ін'єкція проходить без опору.
- **Одноразовий red team.** Загрози змінюються разом із промптами, інструментами й моделями;
  вимірювання має бути безперервним, а не одноразовим.
- **Немає журналу того, що агент робив.** Без аудиту неможливо ні розібрати інцидент, ні
  довести, що його не було (підтема 13.4).

**Альтернативи.** Формальні рамки, за якими будують модель загроз. OWASP LLM Top 10 (2025) дає десять категорій: LLM01 Prompt
Injection, LLM02 Sensitive Information Disclosure, LLM03 Supply Chain, LLM04 Data and Model Poisoning, LLM05 Improper Output
Handling, LLM06 Excessive Agency, LLM07 System Prompt Leakage, LLM08 Vector and Embedding Weaknesses, LLM09 Misinformation,
LLM10 Unbounded Consumption. Для агента з shell безпосередньо релевантні LLM01 (in'єкція), LLM02 (витік даних), LLM05
(некоректна обробка виводу, наприклад коли вивід одного вузла стає командою для іншого), LLM06 (надмірна агентність — саме те,
що дає зайвий інструмент), LLM10 (виснаження ресурсів, яке знімають ліміти з підтеми 13.2). Інші рамки, для яких Promptfoo дає
ідентифікатори: MITRE ATLAS (тактики атак на ML-системи, зокрема
`AML.T0051.000` — пряма ін'єкція і `AML.T0051.001` — непряма), NIST AI Risk Management
Framework, ISO/IEC 42001, EU AI Act, GDPR. Вибір рамки не змінює технічних контролів — він змінює те, як ви звітуєте про ризик
і як пріоритезуєте роботу.

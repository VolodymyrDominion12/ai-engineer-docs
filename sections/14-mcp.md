## 14. MCP — Model Context Protocol

MCP (Model Context Protocol) — відкритий протокол, який стандартизує підключення зовнішніх даних і
інструментів до LLM-застосунків. Замість того щоб для кожного клієнта (IDE, чат, агентна платформа)
писати власний конектор під кожне джерело, ви пишете **один сервер**, і будь-який сумісний хост
підключає його сам.

Станом на 09.2026 актуальна ревізія специфікації — **`2026-07-28`**. Вона ламальна: зникло
рукопожаття `initialize`, зникли протокольні сесії, зникли будь-які запити від сервера до клієнта.
Протокол став **stateless**: кожен запит самодостатній і несе у своєму `_meta` власну версію
протоколу й можливості клієнта. Тому цей розділ — не переказ документації, а розбір того, що
змінилося й чому старий код на MCP-серверах 2025 року більше не працює.

Опора розділу — повна JSON-схема `research/07/mcp_schema.json.txt` (155 визначень,
`$schema: https://json-schema.org/draft/2020-12/schema`). Усі назви методів, полів і кодів помилок
нижче звірені з нею, а не з пам'яті.

### 14.1 Архітектура: host, client, server і межі безпеки

**Що це.** MCP побудований на архітектурі *host → client → server*. **Host** — це LLM-застосунок
(IDE, чат, агентний рантайм), який створює й координує **клієнтів**. Кожен **клієнт** спілкується
рівно з **одним** сервером — відношення 1:1. **Сервер** надає контекст і можливості. Host може
тримати багато клієнтів одночасно; один клієнт ніколи не обслуговує два сервери.

**Навіщо це знати.** Межа між host, client і server — це межа довіри, а не просто схема розгортання.
Специфікація формулює принцип прямо: **сервер не повинен мати змоги прочитати всю розмову або
«зазирнути» в інші сервери**. Сервер отримує лише той контекст, який потрібен для конкретного
запиту; повна історія діалогу залишається в host; міжсерверна взаємодія контролюється host. Якщо ви
пишете сервер і сподіваєтесь побачити в ньому історію чату — ви порушуєте модель загроз, а не
«користуєтесь протоколом нестандартно».

**Як працює під капотом.** Розподіл відповідальності прямо перелічений у специфікації:

| Роль | Що робить | Чого не робить |
|---|---|---|
| **Host** | Створює й керує екземплярами клієнтів; контролює дозволи й життєвий цикл з'єднань; застосовує політики безпеки й вимоги згоди; ухвалює рішення про авторизацію від імені користувача; координує інтеграцію з LLM і sampling; агрегує контекст | Не говорить JSON-RPC сам — це робота клієнтів |
| **Client** | Обслуговує рівно один сервер; додає версію протоколу й можливості до **кожного** запиту; маршрутизує повідомлення в обидва боки; керує підписками й сповіщеннями; тримає межі безпеки між серверами | Не обслуговує два сервери одночасно |
| **Server** | Надає resources, tools, prompts через примітиви MCP; працює ізольовано; може просити ввід у клієнта через `InputRequiredResult`; поважає обмеження безпеки | Не ініціює запити; не бачить історію діалогу; не бачить інші сервери |

Напрямок повідомлень теж жорстко зафіксований. Формулювання зі сторінки патернів: **сервери
НЕ МОЖУТЬ ініціювати JSON-RPC-запити, а клієнти не надсилають JSON-RPC-відповіді**. Це означає, що
звична для 2025 року схема «сервер посеред обробки викликає клієнта, щоб запитати в користувача
дозвіл» більше не існує — замість неї працює MRTR (див. 14.6).

Друга опора архітектури — **stateless**. Специфікація вимагає:

- сервери **MUST NOT** покладатися на попередні запити в тому ж з'єднанні, щоб встановити контекст
  (можливості, версію протоколу, ідентичність клієнта) — кожен запит передає ці метадані у `_meta`;
- сервери **SHOULD NOT** вимагати, щоб клієнт перевикористовував те саме з'єднання чи процес;
- клієнти **SHOULD NOT** вважати окрему задачу, тред чи розмову межею життя stdio-процесу;
- стан, який має пережити кілька запитів, **MUST** передаватися явним ідентифікатором, який клієнт
  надсилає в кожному запиті.

Звідси неочевидний, але практичний висновок, який специфікація формулює окремо: **відкрите
з'єднання — це не сесія й не розмова**. Клієнт може чергувати непов'язані запити в одному
stdio-процесі, і сервер не має права трактувати ідентичність з'єднання як ідентичність розмови.

Із цього випливає **межі безпеки** як окремий предмет. Специфікація перелічує принципи, які
реалізація має забезпечити на рівні застосунку (протокол цього не нав'язує):

| Принцип | Що вимагається |
|---|---|
| **Згода й контроль користувача** | Користувач має явно погоджуватись на доступ до даних і операції; реалізація має дати UI для перегляду й авторизації активностей |
| **Приватність даних** | Host зобов'язаний отримати явну згоду, перш ніж відкривати дані користувача серверу; не передавати resource-дані далі без згоди |
| **Безпека інструментів** | Tools — це довільне виконання коду; **описи поведінки інструмента, зокрема анотації, вважаються недостовірними**, якщо вони прийшли не з довіреного сервера; host зобов'язаний отримати явну згоду перед викликом будь-якого інструмента |

Ця вимога повторюється на сторінці Tools у сильнішій формі: клієнти **MUST** вважати анотації
інструментів недостовірними, якщо вони не прийшли з довіреного сервера. Тобто `readOnlyHint: true`
від невідомого сервера — це не гарантія, а заява сторони, якій ви не довіряєте.

Для Streamable HTTP до цього додаються транспортні вимоги (див. 14.3): перевірка заголовка
`Origin` проти DNS rebinding, прив'язка локальних серверів до `127.0.0.1` і автентифікація.

**Робочий приклад.** Подивимось, як ця модель виглядає з погляду коду сервера: сервер описує себе
й свої можливості, і саме цей опис клієнт побачить першим.

```python
import json
import pathlib

# У файлі перед JSON є рядок-коментар із SOURCE, тому відрізаємо все до першої дужки.
RAW = pathlib.Path("research/07/mcp_schema.json.txt").read_text(encoding="utf-8")
SCHEMA = json.loads(RAW[RAW.index("{"):])
DEFS = SCHEMA["$defs"]


def ref_name(node: dict) -> str:
    """Ім'я визначення з посилання виду '#/$defs/Tool'."""
    return node["$ref"].rsplit("/", 1)[-1]


def method_of(schema_name: str) -> str:
    """Рядок, який ця схема вимагає в полі 'method'."""
    return DEFS[schema_name]["properties"]["method"]["const"]


print("Діалект схеми :", SCHEMA["$schema"])
print("Визначень     :", len(DEFS))
print()

print("Клієнт -> сервер, запити (ClientRequest.anyOf):")
for node in DEFS["ClientRequest"]["anyOf"]:
    print("   ", method_of(ref_name(node)))
print()

print("Клієнт -> сервер, сповіщення (ClientNotification):")
print("   ", method_of("ClientNotification"))
print()

print("Сервер -> клієнт, сповіщення (ServerNotification.anyOf):")
for node in DEFS["ServerNotification"]["anyOf"]:
    print("   ", method_of(ref_name(node)))
```

Фактичний вивід:

```
Діалект схеми : https://json-schema.org/draft/2020-12/schema
Визначень     : 155

Клієнт -> сервер, запити (ClientRequest.anyOf):
    server/discover
    resources/list
    resources/templates/list
    resources/read
    subscriptions/listen
    prompts/list
    prompts/get
    tools/list
    tools/call
    completion/complete

Клієнт -> сервер, сповіщення (ClientNotification):
    notifications/cancelled

Сервер -> клієнт, сповіщення (ServerNotification.anyOf):
    notifications/cancelled
    notifications/progress
    notifications/resources/list_changed
    notifications/subscriptions/acknowledged
    notifications/resources/updated
    notifications/prompts/list_changed
    notifications/tools/list_changed
    notifications/message
```

Цей вивід — найкоротший спосіб переконатися в головному: у напрямку «клієнт → сервер» рівно **десять**
запитів і **одне** сповіщення. Немає ні `initialize`, ні `ping`, ні `resources/subscribe`. Саме тому
архітектурне твердження «сервери не ініціюють запити» — не побажання, а прямий наслідок схеми.

**Типові помилки**

- Тримати стан сервера в пам'яті процесу й розраховувати, що наступний запит його побачить.
  Протокол stateless: під балансувальником наступний запит може прийти в інший екземпляр.
- Покладатися на `readOnlyHint` / `destructiveHint` з чужого сервера як на механізм безпеки. Це
  підказки, і специфікація прямо забороняє клієнтам ухвалювати рішення про виклик на їх основі.
- Ототожнювати stdio-процес із розмовою. Клієнт має право чергувати в ньому незалежні запити.
- Намагатися реалізувати «сервер питає користувача» через зворотний запит. Цього каналу немає;
  єдина легальна форма — `InputRequiredResult` (14.6).
- Виводити в `stdout` stdio-сервера будь-що, крім MCP-повідомлень. `stdout` — це дріт.

**Альтернативи.** Порівнювати MCP варто не з «власним протоколом», а з іншими способами віддати
моделі інструменти:

| Підхід | Коли доречний | Ціна |
|---|---|---|
| **Tool use через SDK провайдера** (розділ 12) | Один застосунок, один набір інструментів, усе в одному процесі | Немає перевикористання: інструменти не переносяться в інший хост |
| **MCP** | Треба, щоб **той самий** набір можливостей працював у кількох хостах; треба ізоляція між джерелами | З'являється окремий процес/сервіс, окремі межі довіри, окремий протокол для налагодження |
| **Пряма інтеграція з API** | Потрібна повна історія розмови, повний контроль над промптом | Немає стандарту; кожен хост пише своє |

Практичне правило: якщо інструмент живе всередині вашого застосунку й ніколи не буде
використаний ззовні — MCP додає складності без вигоди. Якщо ви хочете, щоб той самий сервер
працював і в IDE, і в чаті, і в агентному рантаймі, — MCP окупається одразу.

### 14.2 Базовий протокол: JSON-RPC, ініціалізація, можливості

**Що це.** Три речі, які треба знати точно, бо на них тримається все інше: формат повідомлень
(JSON-RPC 2.0 з розширеннями MCP), модель версіонування й можливостей (per-request `_meta` замість
рукопожаття) і поле `resultType`, яке визначає, як читати результат.

**Навіщо це знати.** У 2025 році будь-який MCP-код починався з `initialize`. У ревізії `2026-07-28`
цього методу **немає в схемі взагалі**. Якщо ви візьмете приклад 2025 року, він не «працюватиме
трохи інакше» — він отримає `-32601 Method not found`. Розуміння `_meta` — це те, що відрізняє
робочий сервер від неробочого.

**Як працює під капотом.**

**Повідомлення.** Усі повідомлення **MUST** відповідати [JSON-RPC 2.0](https://www.jsonrpc.org/specification).
Три типи:

```json
// Запит
{ "jsonrpc": "2.0", "id": "1", "method": "tools/list", "params": { } }

// Результат
{ "jsonrpc": "2.0", "id": "1", "result": { "resultType": "complete", "tools": [ ] } }

// Помилка
{ "jsonrpc": "2.0", "id": "1", "error": { "code": -32601, "message": "Method not found" } }

// Сповіщення — без id узагалі
{ "jsonrpc": "2.0", "method": "notifications/cancelled", "params": { "requestId": "1" } }
```

Три відхилення від базового JSON-RPC, які специфікація фіксує окремо:

1. `id` запиту **MUST NOT** бути `null` і **MUST NOT** збігатися з `id` іншого запиту, на який
   відповідь ще не отримана. Тип — `string | integer` (`RequestId` у схемі).
2. У `result` **MUST** бути поле `resultType`.
3. Сповіщення **MUST NOT** містити `id`.

**`resultType` — поліморфний результат.** Це головна новація базового протоколу:

| Значення | Що означає |
|---|---|
| `"complete"` | Запит завершено, у результаті — фінальний вміст |
| `"input_required"` | Запит **не** завершено; потрібен ввід, у результаті — `InputRequiredResult` |

Будь-яке невідоме клієнту значення `resultType` **MUST** вважатися невалідним. Але для сумісності
зі старішими серверами: **відсутній `resultType` клієнт MUST трактувати як `"complete"`** — саме так
працює підтримка серверів ревізії `2025-11-25` і раніших.

**`_meta` — серце stateless-моделі.** Поле `_meta` може стояти в `params` запиту й у `result`
відповіді. Формат ключа — два сегменти: необов'язковий **префікс** і **ім'я**. Префікс — це
розділені точками мітки, після яких іде слеш: `io.modelcontextprotocol/`. Специфікація рекомендує
reverse-DNS, і будь-який префікс, де **друга** мітка дорівнює `modelcontextprotocol` або `mcp`,
зарезервований за MCP. Тобто `com.example.mcp/` — **не** зарезервований (друга мітка `example`), а
`com.mcp.tools/` — зарезервований.

Зарезервовані ключі:

| Ключ | Призначення |
|---|---|
| `progressToken` | Запит на out-of-band сповіщення про прогрес |
| `io.modelcontextprotocol/protocolVersion` | Версія протоколу для цього запиту |
| `io.modelcontextprotocol/clientInfo` | Ім'я й версія клієнта |
| `io.modelcontextprotocol/clientCapabilities` | Можливості клієнта, доречні для цього запиту |
| `io.modelcontextprotocol/logLevel` | Мінімальний рівень логування для цього запиту |
| `io.modelcontextprotocol/subscriptionId` | Кореляція сповіщення з підпискою |
| `io.modelcontextprotocol/serverInfo` | Ім'я й версія сервера (у `result._meta`) |
| `traceparent`, `tracestate`, `baggage` | Контекст трасування OpenTelemetry (W3C Trace Context і Baggage) |

Обов'язкові на **кожному** запиті клієнта — рівно два: `protocolVersion` і `clientCapabilities`.
Запит без будь-якого з них невалідний: сервер **MUST** відповісти кодом `-32602` (Invalid params), а
на HTTP — ще й статусом `400 Bad Request`.

**Коди помилок.** MCP використовує стандартні коди JSON-RPC для загальних збоїв і **розділяє**
зарезервований діапазон `-32000…-32099`:

| Код | Ім'я | Коли |
|---|---|---|
| `-32700` | `ParseError` | Не вдалося розібрати JSON |
| `-32600` | `InvalidRequestError` | Структура не відповідає JSON-RPC 2.0 |
| `-32601` | `MethodNotFoundError` | Метод невідомий або не оголошений у можливостях сервера |
| `-32602` | `InvalidParamsError` | Невалідні параметри; сюди ж переїхав «resource not found» |
| `-32603` | `InternalError` | Внутрішня помилка сервера |
| `-32020` | `HeaderMismatchError` | HTTP-заголовки не збігаються з тілом |
| `-32021` | `MissingRequiredClientCapabilityError` | Потрібна можливість клієнта, якої він не оголосив |
| `-32022` | `UnsupportedProtocolVersionError` | Версію не підтримано |

Діапазон `-32000…-32019` — **застарілий**: у ньому коди виділяли реалізації до появи політики;
нові коди там заборонено створювати. Виняток — `-32002` (resource not found, у `2025-11-25` і
раніше), клієнти **SHOULD** досі його приймати. Код `-32042` (URL elicitation required) існував
лише в `2025-11-25` і не має використовуватись. Для власних потреб код **SHOULD** виділяти **поза**
діапазоном JSON-RPC.

**Можливості.** Замість рукопожаття працює така схема: клієнт кладе свої можливості в
`_meta.io.modelcontextprotocol/clientCapabilities` **у кожному запиті**, а сервер оголошує свої у
відповіді на `server/discover`, який клієнт може викликати перед будь-яким іншим запитом.

Можливості **сервера** (`ServerCapabilities`):

| Поле | Що відкриває |
|---|---|
| `tools: { listChanged }` | `tools/list`, `tools/call` |
| `resources: { listChanged, subscribe }` | `resources/list`, `resources/templates/list`, `resources/read` |
| `prompts: { listChanged }` | `prompts/list`, `prompts/get` |
| `completions: {}` | Автодоповнення аргументів (`completion/complete`) |
| `logging: {}` | Сповіщення `notifications/message` |
| `experimental: {}` | Не-стандартні можливості |
| `extensions: {}` | Карта ідентифікаторів розширень → об'єкт налаштувань |

Можливості **клієнта** (`ClientCapabilities`):

| Поле | Що відкриває |
|---|---|
| `elicitation: { form, url }` | Сервер може просити ввід у користувача (форми або URL) |
| `roots: {}` | Клієнт може перелічувати корені (застаріло, див. 14.8) |
| `sampling: { context, tools }` | Сервер може просити LLM-компліт через клієнта (застаріло) |
| `experimental: {}`, `extensions: {}` | Те саме, що в сервера |

Правило, яке легко проґавити: **сервер MUST NOT покладатися на можливості, яких клієнт не оголосив**.
Якщо для обробки запиту потрібна можливість, відсутня в `clientCapabilities`, сервер **MUST**
повернути `MissingRequiredClientCapability` (`-32021`), де `data.requiredCapabilities` перелічує
відсутнє. На HTTP — `400 Bad Request`.

Для `server/discover`, який сервер **MUST** реалізовувати, обов'язкові поля результату —
`cacheScope`, `capabilities`, `resultType`, `supportedVersions`, `ttlMs`.

**Робочий приклад.** Побудуємо валідний запит і перевіримо його рівно тими ключами, які схема
оголошує обов'язковими.

```python
import json
import pathlib

RAW = pathlib.Path("research/07/mcp_schema.json.txt").read_text(encoding="utf-8")
DEFS = json.loads(RAW[RAW.index("{"):])["$defs"]

PROTOCOL_VERSION = "2026-07-28"


def client_meta(capabilities: dict) -> dict:
    """Обов'язкова частина _meta, яку несе КОЖЕН запит клієнта."""
    return {
        "io.modelcontextprotocol/protocolVersion": PROTOCOL_VERSION,
        "io.modelcontextprotocol/clientCapabilities": capabilities,
        "io.modelcontextprotocol/clientInfo": {"name": "HandbookClient", "version": "1.0.0"},
    }


def check_required_meta(meta: dict) -> None:
    """Перевіряємо рівно ті ключі, які схема оголошує обов'язковими."""
    required = DEFS["RequestMetaObject"]["required"]
    missing = [key for key in required if key not in meta]
    if missing:
        raise ValueError(f"запит невалідний, бракує: {missing}")


request = {
    "jsonrpc": "2.0",
    "id": "discover-1",
    "method": "server/discover",
    "params": {"_meta": client_meta({})},
}

print("Обов'язкові ключі _meta (зі схеми):", DEFS["RequestMetaObject"]["required"])
check_required_meta(request["params"]["_meta"])
print("Перевірку пройдено.")
print()
print(json.dumps(request, indent=2, ensure_ascii=False))
print()

try:
    check_required_meta({"io.modelcontextprotocol/protocolVersion": PROTOCOL_VERSION})
except ValueError as exc:
    print("А ось що буде, якщо клієнт забуде capabilities:", exc)
```

Фактичний вивід:

```
Обов'язкові ключі _meta (зі схеми): ['io.modelcontextprotocol/clientCapabilities', 'io.modelcontextprotocol/protocolVersion']
Перевірку пройдено.

{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "HandbookClient",
        "version": "1.0.0"
      }
    }
  }
}

А ось що буде, якщо клієнт забуде capabilities: запит невалідний, бракує: ['io.modelcontextprotocol/clientCapabilities']
```

Тут варто звернути увагу на два моменти. По-перше, `id` — рядок `"discover-1"`, а не число: схема
дозволяє обидва типи, і це зручно для кореляції в логах. По-друге, `capabilities: {}` — це
**валідне** значення: порожній об'єкт означає «клієнт не підтримує жодної з необов'язкових
можливостей». Відсутність поля — не те саме, що порожній об'єкт.

**Типові помилки**

- Надсилати `initialize` або `notifications/initialized`. У схемі `2026-07-28` цих методів немає;
  ви отримаєте `-32601`.
- Забути `clientCapabilities` у `_meta`. Це `-32602` і `400 Bad Request` на HTTP — найчастіша
  помилка при ручному складанні запитів.
- Покладатися на `id` як на `null`. Базовий JSON-RPC це дозволяє, MCP — ні.
- Вважати, що `resultType` необов'язковий для вашого сервера. Він обов'язковий; відсутній
  трактується як `"complete"` лише для сумісності зі старішими серверами, а не як дозвіл його не слати.
- Використовувати префікс із другою міткою `mcp` для власних ключів. `com.mcp.tools/` — зарезервований.
- Пробувати виділити власний код помилки в діапазоні `-32020…-32099`. Він належить специфікації.

**Альтернативи.** Для власних потреб є два легальні місця: `experimental` у можливостях (не-стандартні
можливості) і `extensions` (офіційний механізм розширень). Різниця принципова: `experimental` — це
«моє приватне», `extensions` — «узгоджене розширення з ідентифікатором і схемою». Специфікація
згадує як приклади `io.modelcontextprotocol/ui` (MCP Apps) і `io.modelcontextprotocol/tasks`.
Якщо ви додаєте щось, що має працювати між різними реалізаціями, — це розширення, а не
`experimental`. Повний реєстр офіційних розширень у завантажених джерелах відсутній (див. звіт
наприкінці).

### 14.3 Транспорти: stdio проти Streamable HTTP

**Що це.** Транспорт — це **прив'язка** (binding): він визначає, як кадруються й доставляються
повідомлення, як переноситься метадані запиту й як сигналізується скасування та завершення. Він
**не** визначає сенс повідомлень — патерни однакові на всіх транспортах.

**Навіщо це знати.** Вибір транспорту змінює модель загроз, модель розгортання й навіть спосіб
скасування запиту. Той самий сервер на stdio й на HTTP поводиться по-різному в трьох місцях:
метадані їдуть у тілі або в заголовках, скасування — сповіщенням або розривом потоку, завершення —
закриттям `stdin` або зупинкою процесу.

**Як працює під капотом.** Специфікація визначає два стандартні транспорти: stdio і Streamable HTTP.
Порівняння:

| Властивість | stdio | Streamable HTTP |
|---|---|---|
| Хто запускає | Клієнт запускає сервер як підпроцес | Сервер працює незалежно, обслуговує багато з'єднань |
| Кадрування | Одне JSON-RPC-повідомлення на рядок, розділювач — `\n`; вбудованих нових рядків бути **не повинно** | Один HTTP POST на кожне повідомлення |
| Де метадані | Усе в тілі, у `_meta.io.modelcontextprotocol/*`; шару заголовків немає | У тілі **і** продубльовані в HTTP-заголовках (тіло — джерело істини) |
| Формат відповіді | Рядок у `stdout` | `application/json` (один об'єкт) **або** `text/event-stream` (SSE-потік, прив'язаний до запиту) |
| Сповіщення | Той самий канал, кореляція за `_meta.subscriptionId` | `202 Accepted` без тіла на POST-сповіщення |
| Скасування | Клієнт **MUST** надіслати `notifications/cancelled` з `requestId` | Закриття SSE-потоку відповіді **і є** сигналом скасування |
| Завершення | Клієнт закриває `stdin`, чекає виходу; далі `SIGTERM`, потім `SIGKILL` (POSIX) | Процес зупиняється як звичайний сервіс |
| Перезапуск | Клієнт **SHOULD** перезапустити процес, якщо той упав; запити в польоті просто втрачено | Немає процесу, який клієнт міг би перезапустити |
| Логи | `stderr` — довільний UTF-8; клієнт **SHOULD NOT** вважати його ознакою помилки | Через `notifications/message` або поза протоколом |

Деталі, які найчастіше ламають реалізації:

**stdio.** `stdout` — це дріт. Сервер **MUST NOT** писати туди будь-що, що не є валідним
MCP-повідомленням, а клієнт **MUST NOT** писати в `stdin` сервера нічого, крім MCP-повідомлень. Це
означає, що звичайний `print()` у сервері — це дефект, який проявляється як «клієнт раптом бачить
невалідний JSON». Логування — тільки в `stderr`. Специфікація додає, що сервер **SHOULD** виходити
негайно, коли його `stdin` закрито або читання повернуло EOF: це єдиний переносимий сигнал
коректного завершення, і він зменшує потребу в примусовому вбивстві процесу.

Важлива деталь для кастомних транспортів: ніщо у прив'язці stdio не залежить від стандартних
потоків, крім життєвого циклу процесу. Формат (одне newline-delimited JSON-RPC-повідомлення на
рядок через надійний двобічний байтовий потік) працює без змін поверх Unix domain socket, TCP тощо.
Тому кастомні транспорти **SHOULD** перевикористовувати саме це кадрування.

**Streamable HTTP.** Один HTTP-ендпоінт (умовно `https://example.com/mcp`), який приймає POST.
Вимоги до надсилання:

1. Клієнт **MUST** використовувати POST.
2. Клієнт **MUST** включити `Accept` з **обома** типами: `application/json` і `text/event-stream`.
3. Клієнт **MUST** включити заголовки метаданих на **кожному** POST.
4. Тіло — рівно один JSON-RPC *запит* або *сповіщення*; відповіді клієнт не надсилає.
5. Якщо тіло — сповіщення й сервер його прийняв: `202 Accepted` без тіла. Не прийняв: HTTP-помилка
   (наприклад, `400`), у тілі **MAY** бути JSON-RPC-помилка без `id`.
6. Якщо тіло — запит: сервер **MUST** відповісти або `Content-Type: application/json`, або
   `Content-Type: text/event-stream`. Клієнт **MUST** підтримувати обидва.

Коли сервер віддає SSE-потік, він **MAY** слати JSON-RPC-сповіщення (`notifications/progress`,
`notifications/message`) перед фінальною відповіддю, і ці сповіщення **MUST** стосуватися вихідного
запиту. Сервер **MUST NOT** слати на цьому потоці незалежні JSON-RPC-*запити* — це було можливо в
`2025-03-26`…`2025-11-25` і прибрано. Фінальна відповідь **SHOULD** завершувати потік.

Заголовки метаданих, які транспорт дублює з тіла, щоб проміжні вузли могли маршрутизувати запити,
не розбираючи тіло:

| Заголовок | Джерело | Для чого обов'язковий |
|---|---|---|
| `MCP-Protocol-Version` | `_meta.io.modelcontextprotocol/protocolVersion` | Усі запити; значення **MUST** збігатися з тілом |
| `Mcp-Method` | `method` | Усі запити |
| `Mcp-Name` | `params.name` або `params.uri` | `tools/call`, `resources/read`, `prompts/get` |
| `Mcp-Param-{Name}` | значення параметра, позначеного `x-mcp-header` | Лише якщо сервер так позначив параметр |

Якщо значення не можна безпечно подати як ASCII-заголовок (не-ASCII, керівні символи, пробіли по
краях), клієнт **MUST** закодувати його як Base64 у сентинелі вигляду
`=?base64?{Base64EncodedValue}?=`. Маркери чутливі до регістру й **MUST** бути саме в нижньому
регістрі. Те саме правило діє для `Mcp-Name`. Щоб не було двозначності, клієнт **MUST** так само
кодувати звичайне ASCII-значення, яке саме *виглядає* як сентинел.

Сервер, який розбирає тіло, **MUST** перевірити, що значення заголовків після декодування
збігаються зі значеннями в тілі, і за розбіжності повернути `400 Bad Request` з кодом `-32020`
(`HeaderMismatch`). Це захищає від ситуації, коли балансувальник маршрутизує за заголовком, а сервер
виконує за тілом.

Окремо: якщо сервер не реалізує викликаний метод, на HTTP він **MUST** відповісти `404 Not Found` і
JSON-RPC-помилкою `-32601`.

**Що зникло в Streamable HTTP у `2026-07-28`.** Це важливо, бо більшість наявних інтеграцій написані
під `2025-03-26`…`2025-11-25`:

- прибрано GET-ендпоінт для окремого SSE-потоку;
- прибрано протокольні сесії та заголовок `Mcp-Session-Id`;
- прибрано відновлюваність SSE-потоків: `Last-Event-ID` не підтримується, розірваний потік означає
  втрачений запит, який клієнт **MUST** повторити як новий запит із новим `id`.

Сервер, який підтримує лише цю ревізію, на таке старе трафіку **SHOULD** реагувати так: на GET або
DELETE до MCP-ендпоінта — `405 Method Not Allowed`; заголовок `Mcp-Session-Id` — ігнорувати й не
видавати сесійних ідентифікаторів; `Last-Event-ID` — ігнорувати.

**Приклад.** Покажемо обидві механіки на реальних значеннях: кадр stdio та кодування заголовків.
Таблиця очікуваних значень узята зі сторінки Streamable HTTP.

```python
import base64
import json

# ── stdio: одне повідомлення — один рядок ───────────────────────────────────
message = {
    "jsonrpc": "2.0",
    "id": 7,
    "method": "tools/call",
    "params": {"name": "add", "arguments": {"a": 1, "b": 2}},
}
line = json.dumps(message, separators=(",", ":"))
print("Усього рядків у кадрі:", len(line.splitlines()))
print(line)
print()

# Значення з \n усередині лишається одним рядком: JSON його екранує.
tricky = json.dumps({"method": "notifications/message", "params": {"text": "line1\nline2"}})
print("Кадр із вбудованим \\n:", tricky)
print("Рядків усе одно:", len(tricky.splitlines()))
print()

# ── Streamable HTTP: значення заголовків із Base64-сентиинелом ──────────────
SENTINEL_PREFIX, SENTINEL_SUFFIX = "=?base64?", "?="


def header_value(value: str) -> str:
    """Кодує значення для Mcp-Name / Mcp-Param-* за правилами Streamable HTTP."""
    safe = (
        value.isascii()
        and value.isprintable()
        and value == value.strip()
        and not (value.startswith(SENTINEL_PREFIX) and value.endswith(SENTINEL_SUFFIX))
    )
    if safe:
        return value
    encoded = base64.b64encode(value.encode("utf-8")).decode("ascii")
    return f"{SENTINEL_PREFIX}{encoded}{SENTINEL_SUFFIX}"


CASES = [
    ("us-west1", "простий ASCII"),
    ("Hello, 世界", "не-ASCII"),
    (" padded ", "пробіли по краях"),
    ("line1\nline2", "вбудований новий рядок"),
    ("=?base64?literal?=", "схоже на сам сентинел"),
]
for value, why in CASES:
    print(f"{value!r:24} {why:26} -> {header_value(value)}")
```

Фактичний вивід:

```
Усього рядків у кадрі: 1
{"jsonrpc":"2.0","id":7,"method":"tools/call","params":{"name":"add","arguments":{"a":1,"b":2}}}

Кадр із вбудованим \n: {"method": "notifications/message", "params": {"text": "line1\nline2"}}
Рядків усе одно: 1

'us-west1'               простий ASCII              -> us-west1
'Hello, 世界'              не-ASCII                   -> =?base64?SGVsbG8sIOS4lueVjA==?=
' padded '               пробіли по краях           -> =?base64?IHBhZGRlZCA=?=
'line1\nline2'           вбудований новий рядок     -> =?base64?bGluZTEKbGluZTI=?=
'=?base64?literal?='     схоже на сам сентинел      -> =?base64?PT9iYXNlNjQ/bGl0ZXJhbD89?=
```

Усі чотири закодовані значення **збігаються з таблицею в специфікації** — це найшвидший спосіб
переконатися, що ваша реалізація кодування правильна. Зверніть увагу на останній рядок: значення,
яке вже виглядає як сентинел, кодується повторно. Без цього правила сервер не зміг би відрізнити
закодоване значення від буквального.

**`x-mcp-header` — розширення схеми інструмента.** Сервер **MAY** позначити конкретні параметри
інструмента так, щоб клієнт дублював їх у HTTP-заголовки. Клієнти **MUST** підтримувати цю
можливість; клієнти на stdio **MAY** ігнорувати анотацію повністю. Обмеження на значення:

- **MUST NOT** бути порожнім;
- **MUST** відповідати синтаксису імені поля HTTP (`1*tchar`, RFC 9110 §5.1);
- **MUST NOT** містити керівних символів, зокрема CR і LF;
- **MUST** бути унікальним без урахування регістру серед усіх `x-mcp-header` у `inputSchema`;
- **MUST** застосовуватись лише до параметрів примітивних типів (`integer`, `string`, `boolean`);
  тип `number` **не дозволений**; цілі числа **MUST** бути в безпечному діапазоні JS
  (−2⁵³+1 … 2⁵³−1);
- **MUST** застосовуватись лише до властивостей, **статично досяжних** від кореня схеми ланцюжком,
  що складається виключно з ключів `properties` — не через `items`, композиційні (`oneOf`, `anyOf`,
  `allOf`, `not`), умовні (`if`/`then`/`else`) ключі або `$ref`.

Клієнт на Streamable HTTP **MUST** відкинути визначення інструмента, де хоч одне `x-mcp-header`
порушує ці обмеження, і **MUST** виключити такий інструмент із результату `tools/list` (а не
відкинути весь список). Специфікація також попереджає: не позначайте `x-mcp-header` чутливі
параметри (паролі, ключі, токени, PII) — значення заголовків видно проміжним вузлам.

**Типові помилки**

| Помилка | Що ламається |
|---|---|
| `print()` у stdio-сервері | `stdout` забруднюється; клієнт бачить невалідний JSON-RPC |
| Забути `Accept: application/json, text/event-stream` на HTTP | Сервер має право відповісти SSE, і клієнт, який уміє лише JSON, зламається |
| Надіслати `Mcp-Name`, який не збігається з `params.name` | `400` + `-32020 HeaderMismatch` |
| Не оновити `MCP-Protocol-Version` після відкату на іншу версію | Заголовок і тіло розійдуться → `-32020` |
| Чекати на відновлення SSE через `Last-Event-ID` | Механізм прибрано; потік не відновлюється, запит треба повторити |
| Надсилати GET, щоб відкрити окремий потік сповіщень | Ендпоінта немає; `405 Method Not Allowed`. Для сповіщень є `subscriptions/listen` |
| Покладатися на `Mcp-Session-Id` | Сесій більше немає; сервер його проігнорує |
| Виводити логи в `stdout` замість `stderr` | Те саме, що `print()`: псує дріт |

**Альтернативи.** Кастомні транспорти дозволені: протокол транспортно-агностичний. Вимоги до них —
зберегти формат JSON-RPC, патерни повідомлень і модель per-request метаданих, а також
задокументувати встановлення з'єднання, кадрування й скасування. Для потоків поверх Unix domain
socket або TCP специфікація прямо радить **перевикористати** кадрування stdio, а не вигадувати нове.
Окремо варто пам'ятати про застарілий транспорт **HTTP+SSE** з `2024-11-05`: він у стані
Deprecated, нові реалізації **SHOULD NOT** його брати.

### 14.4 Примітиви: tools, resources, prompts

**Що це.** Сервер надає рівно три роди примітивів. Розрізняє їх не форма, а **хто вирішує ними
скористатися**.

**Навіщо це знати.** Це найпрактичніше рішення при проєктуванні сервера. Специфікація формулює
правило прямо: інструменти **model-controlled**, ресурси **application-driven**, промпти
**user-controlled**. Помилка у виборі примітива дає не помилку в коді, а неправильний UX і
непередбачувану поведінку моделі.

**Як працює під капотом.**

| Примітив | Хто контролює | Що це | Приклад | Аналогія з HTTP |
|---|---|---|---|---|
| **Tools** | Модель | Функція, яку модель викликає, щоб виконати дію | Виклик API, запис у БД | POST |
| **Resources** | Застосунок | Дані, які host завантажує в контекст моделі | Вміст файлу, відповідь API | GET |
| **Prompts** | Користувач | Багаторазовий шаблон повідомлень, який користувач викликає за назвою | Slash-команда, пункт меню | — (немає аналога) |

**Tools.** Схема `Tool` вимагає рівно два поля: `name` і `inputSchema`. Решта — необов'язкові:
`title`, `description`, `icons`, `annotations`, `outputSchema`, `_meta`.

Правила імен (усе зі сторінки Tools):

- довжина **SHOULD** бути від 1 до 128 символів включно;
- імена **SHOULD** вважатися чутливими до регістру;
- дозволені символи **SHOULD** обмежуватись ASCII-літерами (`A-Z`, `a-z`), цифрами, `_`, `-`, `.`;
- пробіли, коми й інші спецсимволи **SHOULD NOT** використовуватись;
- імена **SHOULD** бути унікальними в межах сервера.

`inputSchema` — це JSON Schema (за замовчуванням діалект 2020-12), і корінь **MUST** мати
`type: "object"`, бо аргументи завжди об'єкт. Для інструмента без параметрів специфікація радить
`{ "type": "object", "additionalProperties": false }` — це явно приймає лише порожні об'єкти,
тоді як `{ "type": "object" }` приймає будь-який об'єкт.

`outputSchema` (необов'язкова) описує структуру `structuredContent`. Якщо вона є, сервер **MUST**
віддавати структурований результат, що їй відповідає, а клієнт **SHOULD** його валідувати.

`annotations` — підказки, і специфікація наголошує, що **всі** вони є підказками й не гарантують
достовірного опису поведінки:

| Поле | Значення за замовчуванням | Сенс |
|---|---|---|
| `readOnlyHint` | `false` | Інструмент не змінює середовище |
| `destructiveHint` | `true` | Може виконувати руйнівні оновлення. Має сенс лише коли `readOnlyHint == false` |
| `idempotentHint` | `false` | Повторний виклик із тими самими аргументами не дає додаткового ефекту. Лише коли `readOnlyHint == false` |
| `openWorldHint` | `true` | Взаємодіє з «відкритим світом» зовнішніх сутностей (веб-пошук — так, пам'ять — ні) |
| `title` | — | Людиночитана назва |

Результат виклику — `CallToolResult`. Обов'язкові поля: `content` і `resultType`. Найважливіше
семантичне поле — `isError`:

> Помилки, що походять **від самого інструмента**, **SHOULD** повідомлятися всередині результату з
> `isError: true`, а **не** як протокольна помилка MCP. Інакше LLM не побачить, що сталася помилка,
> і не зможе виправитися самостійно. Але помилки **пошуку** інструмента, відсутність підтримки
> викликів інструментів або інші виняткові умови **SHOULD** повідомлятися як помилка MCP.

Тобто «файл не знайдено» — це `isError: true` у результаті (модель прочитає й спробує інакше), а
«такого інструмента не існує» — це JSON-RPC-помилка (моделі нема чого виправляти).

`content` — масив `ContentBlock`: `text`, `image`, `audio`, `resource_link`, `resource`. Плюс
необов'язкове `structuredContent` — будь-яке JSON-значення (об'єкт, масив, рядок, число, булеве,
`null`). Для зворотної сумісності інструмент, який віддає структурований вміст, **SHOULD** також
повертати серіалізований JSON у блоці `TextContent`. Специфікація окремо застерігає, що
`structuredContent` — це **результат роботи сервера** і не має нічого спільного з «structured
outputs» моделі (див. розділ 11).

**Resources.** Схема `Resource` вимагає `name` і `uri`. Необов'язкові: `title`, `description`,
`mimeType`, `size` (у байтах, до base64-кодування), `annotations`, `icons`.

Ключова ідея — **шаблони**. Схема `ResourceTemplate` вимагає `name` і `uriTemplate`, де `uriTemplate`
це шаблон за [RFC 6570](https://datatracker.ietf.org/doc/html/rfc6570). Шаблон як `books://{title}`
не перелічується в `resources/list` (бо конкретного ресурсу ще немає) — він живе окремо, у
`resources/templates/list`. Читання виконується через `resources/read` із конкретним `uri`, а
результат — `ReadResourceResult` із масивом `contents`, кожен елемент це `TextResourceContents`
(`uri` + `text`) або `BlobResourceContents` (`uri` + `blob`, base64).

Правило стабільності: набір ресурсів **MAY** бути порожнім і **MAY** змінюватися з часом, але
**MUST NOT** залежати від з'єднання або бути побічним ефектом інших запитів. Він **MAY** залежати
від авторизації, наданої в запиті, — бо це per-request ввід, а не стан з'єднання. Те саме
сформульовано для `tools/list` і `prompts/list`.

Інструменти можуть посилатися на ресурси двома способами: `resource_link` (клієнт сам вирішить,
читати чи ні) і `resource` — вбудований ресурс із вмістом. Специфікація попереджає: посилання,
повернуті інструментом, **не гарантовано** з'являться в `resources/list`.

**Prompts.** Схема `Prompt` вимагає лише `name`. Необов'язкові: `title`, `description`, `arguments`
(масив `PromptArgument`, кожен із яких вимагає `name` і має `description` та `required`), `icons`.
Виклик — `prompts/get` з `name` та `arguments` (об'єкт рядкових значень), результат —
`GetPromptResult` з обов'язковим `messages` (масив `PromptMessage`, кожне з `role` і `content`).

Практичне застосування — slash-команди: користувач обирає промпт, клієнт викликає `prompts/get`,
отримує готові повідомлення й передає їх моделі. Сервер не «пише в чат» — він лише будує
повідомлення.

**Спільні утиліти.** Обидва списки й читання ресурсів підтримують:

- **Пагінацію**: `params.cursor` у запиті, `nextCursor` у результаті. Курсор — непрозорий рядок.
- **Кешування**: `ttlMs` (скільки мілісекунд результат вважається свіжим) і `cacheScope`
  (`"public"` або `"private"`). Ці поля **MUST** бути присутні в результатах `server/discover`,
  `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read`.
  Проміжні результати з `resultType: "input_required"` **не** кешуються.

`cacheScope` — це не дрібниця: `"public"` означає, що будь-який клієнт, спільний шлюз або кешувальний
проксі **MAY** віддати цю відповідь будь-якому користувачеві. `"private"` — що кеш не **MUST**
перевикористовуватись між контекстами авторизації. Помилка тут — це витік даних, а не зайвий запит.

**Сповіщення про зміни.** Замість старого `resources/subscribe` працює `subscriptions/listen`:
клієнт надсилає фільтр, сервер **MUST** першим повідомленням надіслати
`notifications/subscriptions/acknowledged` з `io.modelcontextprotocol/subscriptionId` у `_meta`, і
**MUST NOT** слати нічого раніше. Усі наступні сповіщення на цьому потоці несуть той самий
`subscriptionId`. Фільтр:

| Поле `notifications` | Тип | Що приходить |
|---|---|---|
| `toolsListChanged` | `boolean` | `notifications/tools/list_changed` |
| `promptsListChanged` | `boolean` | `notifications/prompts/list_changed` |
| `resourcesListChanged` | `boolean` | `notifications/resources/list_changed` |
| `resourceSubscriptions` | `string[]` | `notifications/resources/updated` для цих URI |

Усі поля необов'язкові; пропущене поле рівнозначне відмові від цього типу сповіщень. Сервер
**MUST NOT** слати типи, які клієнт явно не запросив.

**Робочий приклад.** Перевіримо власні результати саме тими `required`-полями, які оголошує схема.

```python
import json
import pathlib

RAW = pathlib.Path("research/07/mcp_schema.json.txt").read_text(encoding="utf-8")
DEFS = json.loads(RAW[RAW.index("{"):])["$defs"]


def missing_required(schema_name: str, payload: dict) -> list[str]:
    """Які обов'язкові поля цієї схеми відсутні у payload."""
    return [key for key in DEFS[schema_name].get("required", []) if key not in payload]


TOOLS_LIST = {
    "resultType": "complete",
    "tools": [
        {
            "name": "search_books",
            "title": "Пошук у каталозі",
            "description": "Шукає книги за назвою або автором.",
            "inputSchema": {
                "type": "object",
                "properties": {
                    "query": {"type": "string", "description": "Назва або автор."},
                    "limit": {"type": "integer", "default": 10, "minimum": 1, "maximum": 50},
                },
                "required": ["query"],
            },
            "annotations": {"readOnlyHint": True, "openWorldHint": False},
        }
    ],
    "ttlMs": 300_000,
    "cacheScope": "public",
}

RESOURCES_LIST = {
    "resultType": "complete",
    "resources": [
        {"uri": "file:///project/config.json", "name": "config.json",
         "title": "Конфігурація проєкту", "mimeType": "application/json", "size": 412}
    ],
    "ttlMs": 60_000,
    "cacheScope": "private",
}

RESOURCE_TEMPLATES_LIST = {
    "resultType": "complete",
    "resourceTemplates": [
        {"name": "book", "uriTemplate": "books://{title}",
         "description": "Запис каталогу за назвою книги.", "mimeType": "text/plain"}
    ],
    "ttlMs": 60_000,
    "cacheScope": "private",
}

PROMPTS_LIST = {
    "resultType": "complete",
    "prompts": [
        {"name": "code_review", "title": "Ревʼю коду",
         "description": "Просить модель оцінити якість коду.",
         "arguments": [{"name": "code", "description": "Код для ревʼю", "required": True}]}
    ],
    "ttlMs": 600_000,
    "cacheScope": "public",
}

for schema_name, payload in [
    ("ListToolsResult", TOOLS_LIST),
    ("ListResourcesResult", RESOURCES_LIST),
    ("ListResourceTemplatesResult", RESOURCE_TEMPLATES_LIST),
    ("ListPromptsResult", PROMPTS_LIST),
]:
    print(f"{schema_name:28} обов'язкові: {DEFS[schema_name]['required']}")
    print(f"{'':28} бракує      : {missing_required(schema_name, payload) or '—'}")
print()

print("Обов'язкові поля вкладених типів:")
for schema_name in ["Tool", "Resource", "ResourceTemplate", "Prompt", "PromptArgument",
                    "CallToolResult", "TextContent", "ResourceLink", "EmbeddedResource"]:
    print(f"  {schema_name:24} {DEFS[schema_name].get('required')}")
print()

print("Типи вмісту, які може повернути tool (ContentBlock.anyOf):")
print("  ", [n["$ref"].rsplit("/", 1)[-1] for n in DEFS["ContentBlock"]["anyOf"]])
print()
print("Успішний виклик і збій виконання розрізняються полем isError,")
print("а не окремим JSON-RPC error:")
print("  CallToolResult.required:", DEFS["CallToolResult"]["required"])
```

Фактичний вивід:

```

                             бракує      : —
ListResourcesResult          обов'язкові: ['cacheScope', 'resources', 'resultType', 'ttlMs']
                             бракує      : —
ListResourceTemplatesResult  обов'язкові: ['cacheScope', 'resourceTemplates', 'resultType', 'ttlMs']
                             бракує      : —

                             бракує      : —

Обов'язкові поля вкладених типів:
  Tool                     ['inputSchema', 'name']
  Resource                 ['name', 'uri']

  CallToolResult.required: ['content', 'resultType']
```

Найважливіший рядок тут — перший блок: `ttlMs` і `cacheScope` **обов'язкові** в усіх чотирьох
результатах списків. Сервер, написаний під `2025-11-25`, їх не шле — і це найпомітніша суміснісна
відмінність при переході на `2026-07-28`.

**Типові помилки**

- Повернути помилку пошуку інструмента як `isError: true`. Модель не має способу це виправити;
  специфікація вимагає тут протокольної помилки.
- Повернути помилку виконання як JSON-RPC-помилку. Модель не побачить її й не зможе виправитися.
- Забути `ttlMs` / `cacheScope` у результатах списків. Формально результат невалідний за схемою.
- Поставити `cacheScope: "public"` на результатах, які залежать від користувача. Кешувальний проксі
  має право віддати їх будь-кому.
- Вважати, що `resources/list` покаже ресурси, створені з шаблону. Шаблони живуть у
  `resources/templates/list`.
- Трактувати `annotations` із чужого сервера як факт. Специфікація прямо це забороняє.
- Використовувати промпт там, де потрібен інструмент (або навпаки). Промпт не виконує дій і не
  повертає результатів — він лише будує повідомлення.
- Позначити `number`-параметр через `x-mcp-header`. Тип `number` явно не дозволений.

**Альтернативи.** Розподіл примітивів не завжди очевидний. Практичні правила:

| Ситуація | Що брати | Чому |
|---|---|---|
| Модель має вирішити, коли це робити (пошук, обчислення, запис) | **Tool** | Рішення ухвалює модель під час генерації |
| Дані треба підкласти в контекст незалежно від рішення моделі | **Resource** | Рішення ухвалює застосунок; можна кешувати окремо від виклику |
| Користувач має явно обрати сценарій | **Prompt** | Користувач бачить назву й аргументи у своєму UI |
| Треба віддати великий документ, з якого модель прочитає частину | **Resource** + посилання з tool | Не тягнути весь вміст у кожен виклик |
| Треба автодоповнення аргументів | `completion/complete` | Оголошується через capability `completions` |
| Треба сповіщати про зміни | `subscriptions/listen` | Єдиний механізм змін у `2026-07-28` |

### 14.5 Версіонування й сумісність

**Що це.** Механізм, яким клієнт і сервер узгоджують, «якою мовою вони говорять»: версію протоколу,
необов'язкові розширення й сумісність зі старішими ревізіями, побудованими на рукопожатті.

**Навіщо це знати.** Тут найбільша практична різниця між 2025 і 2026 роком, і тут же найбільше
можливостей зробити тиху помилку. Ключове речення специфікації: **рукопожаття перемовин не існує**.
Кожен запит несе свою версію, і сервер приймає або відхиляє кожен запит незалежно.

**Як працює під капотом.** Специфікація вводить три терміни:

| Термін | Означення |
|---|---|
| **Modern** | Ревізії, де версія, ідентичність і можливості передаються як per-request метадані (`2026-07-28` і пізніші) |
| **Legacy** | Ревізії, де сесія встановлюється рукопожаттям `initialize` (`2025-11-25` і раніші) |
| **Dual-era** | Реалізація, що підтримує обидві ери |

**Узгодження версії.** Кожен запит оголошує версію в `_meta`; на HTTP вона ж їде в заголовку
`MCP-Protocol-Version`. Якщо сервер не реалізує запитану версію — неважливо, невідома вона йому чи
відома, але свідомо не підтримувана — він **MUST** відповісти `UnsupportedProtocolVersionError`
(`-32022`) зі **списком підтримуваних версій**. Клієнт **SHOULD** обрати спільну версію з цього
списку й повторити запит або показати помилку користувачеві, якщо спільної версії немає.

Сервери **MUST** реалізовувати `server/discover`. Клієнти **MAY** викликати його перед будь-якими
іншими запитами, щоб заздалегідь дізнатися підтримувані версії, — але не зобов'язані: клієнт має
право викликати будь-який RPC одразу й обробити `UnsupportedProtocolVersionError`.

**Узгодження розширень.** Розширення оголошуються в полі `extensions` усередині можливостей — це
карта «ідентифікатор розширення → об'єкт налаштувань». Ідентифікатори **MUST** відповідати правилам
іменування ключів `_meta`, з обов'язковим префіксом. Порожній об'єкт означає підтримку без
додаткових налаштувань. Якщо одна сторона підтримує розширення, а інша ні, підтримуюча **MUST** або
повернутися до поведінки ядра, або відхилити запит відповідною помилкою; розширення **SHOULD**
документувати очікувану поведінку відкату.

**Сумісність між ерами.** Сервер, який хоче обслуговувати і legacy-, і modern-клієнтів, **MAY**
реалізувати обидві поведінки. Клієнт визначає еру сервера транспортно-специфічним способом:

- **stdio**: проба через `server/discover` і відкат за будь-якої помилки, яка **не** є визнаною
  modern-помилкою;
- **Streamable HTTP**: спроба modern-запиту й аналіз тіла відповіді `400 Bad Request` перед відкатом.

В обох випадках визнана modern JSON-RPC-помилка (як-от `UnsupportedProtocolVersionError`) означає,
що сервер **modern**: клієнт повторює з підтримуваною версією, а **не** відкочується на `initialize`.
Будь-що інше означає legacy-сервер.

Тут є пастка, яку специфікація підкреслює окремо: **відкат MUST NOT бути прив'язаний до конкретного
коду помилки**. Legacy-сервери відповідають на невідомі запити до `initialize` власними кодами
(найчастіше `-32601` або `-32602`) або взагалі не відповідають. Тому єдине надійне правило —
«modern, якщо помилка *розпізнана як modern*, інакше legacy».

Визначення ери — це властивість **сервера**, а не окремого запиту. Клієнти **SHOULD** кешувати
результат на час життя процесу сервера (stdio) або origin (HTTP) і **MAY** зберігати його між
перезапусками тієї самої конфігурації, повторно пробуючи, якщо припущення згодом не справдилося.

Матриця сумісності зі специфікації:

| Клієнт | Сервер | Результат |
|---|---|---|
| Modern | Modern | Працює. `server/discover` необов'язковий; розбіжність версій дає `UnsupportedProtocolVersionError` і повтор із спільною версією |
| Modern | Legacy | **Не працює.** Сервер може відхилити запит власною помилкою, мовчати або навіть обробити ера-неоднозначний метод за legacy-семантикою. На stdio клієнтам **SHOULD** спершу надіслати `server/discover`, щоб провалитися детерміновано |
| Dual-era | Modern | Працює. Проба повертає `DiscoverResult` (або `UnsupportedProtocolVersionError`); на HTTP перший modern-запит успішний або дає modern-помилку |
| Dual-era | Legacy | Працює. stdio: проба дає не-modern помилку або таймаут, клієнт відкочується на `initialize`. HTTP: modern-запит дає `4xx` без розпізнаного modern-тіла, клієнт відкочується (за потреби — далі на застарілий HTTP+SSE) |
| Legacy | Modern | **Не працює.** stdio: сервер відхиляє `initialize` (код визначає реалізація). HTTP: запит без обов'язкових заголовків відхиляється з `400 Bad Request`. Legacy-клієнти не мають механізму руху вперед |
| Legacy | Dual-era | Працює. Сервер відповідає на `initialize` і обслуговує клієнта за узгодженою legacy-ревізією |
| Legacy | Legacy | Працює за legacy-ревізією; поза межами цього документа |

Окреме прохання до modern-серверів: сервер, який підтримує лише modern-версії, **SHOULD** назвати
підтримувані версії в **будь-якій** помилці, яку він повертає у відповідь на `initialize`, на
будь-якому транспорті. Причина практична: legacy-клієнти не мають механізму руху вперед, і це
повідомлення може бути єдиною діагностикою, яку вони здатні показати користувачеві.

**Робочий приклад.** Змоделюємо узгодження й визначення ери.

```python
import json

CLIENT_SUPPORTS = ["2026-07-28", "2025-11-25"]
SERVER_SUPPORTS = ["2026-07-28"]


def server_handle(version: str) -> dict:
    """Сервер або обслуговує версію, або перелічує ті, які підтримує."""
    if version in SERVER_SUPPORTS:
        return {"jsonrpc": "2.0", "id": 1, "result": {"resultType": "complete",
                                                     "supportedVersions": SERVER_SUPPORTS}}
    return {
        "jsonrpc": "2.0",
        "id": 1,
        "error": {
            "code": -32022,
            "message": "Unsupported protocol version",
            "data": {"supported": SERVER_SUPPORTS, "requested": version},
        },
    }


def negotiate(preferred: str) -> tuple[str, str]:
    """Один раунд: пробуємо улюблену версію, за відмови обираємо спільну."""
    reply = server_handle(preferred)
    if "error" not in reply:
        return preferred, "погоджено з першої спроби"
    advertised = reply["error"]["data"]["supported"]
    mutual = [v for v in advertised if v in CLIENT_SUPPORTS]
    if not mutual:
        raise RuntimeError("спільної версії немає — показуємо помилку користувачеві")
    return mutual[0], f"сервер відповів -32022, відкотились на {mutual[0]}"


for preferred in ("2026-07-28", "1900-01-01", "2025-11-25"):
    version, note = negotiate(preferred)
    print(f"клієнт просив {preferred:12} -> {version:12} ({note})")
print()

print("Тіло помилки, яке отримує клієнт:")
print(json.dumps(server_handle("1900-01-01")["error"], indent=2, ensure_ascii=False))
print()

# ── Визначення «ери» сервера на stdio ──────────────────────────────────────
def probe_stdio(server_kind: str) -> str:
    """server/discover як проба: три можливі результати (mcp_stdio.md)."""
    if server_kind == "modern":
        return "modern: DiscoverResult -> беремо версію з supportedVersions"
    if server_kind == "modern-old":
        return "modern: UnsupportedProtocolVersionError -> НЕ відкочуємось на initialize"
    return "legacy: будь-яка інша помилка або таймаут -> initialize-рукопожаття"


for kind in ("modern", "modern-old", "legacy"):
    print(f"{kind:12} -> {probe_stdio(kind)}")
print()
print("Правило: відкат заборонено прив'язувати до конкретного коду помилки —")
print("легасі-сервери відповідають на невідомий метод чим завгодно (-32601, -32602) або мовчать.")

# ── Перевірка ключів _meta на HTTP: заголовок мусить збігатися з тілом ──────
def validate_header(header: str | None, body_version: str) -> dict:
    if header is None:
        return {"code": -32020, "message": "Header mismatch: MCP-Protocol-Version missing"}
    if header != body_version:
        return {"code": -32020,
                "message": f"Header mismatch: MCP-Protocol-Version '{header}' does not match "
                           f"body value '{body_version}'"}
    return {}


print()
for header, body in [("2026-07-28", "2026-07-28"), ("2025-11-25", "2026-07-28"), (None, "2026-07-28")]:
    print(f"header={str(header):12} body={body:12} -> {validate_header(header, body) or 'OK'}")
```

Фактичний вивід:

```
клієнт просив 2026-07-28   -> 2026-07-28   (погоджено з першої спроби)
клієнт просив 1900-01-01   -> 2026-07-28   (сервер відповів -32022, відкотились на 2026-07-28)
клієнт просив 2025-11-25   -> 2026-07-28   (сервер відповів -32022, відкотились на 2026-07-28)

Тіло помилки, яке отримує клієнт:
{
  "code": -32022,
  "message": "Unsupported protocol version",
  "data": {
    "supported": [
      "2026-07-28"
    ],
    "requested": "1900-01-01"
  }
}

modern       -> modern: DiscoverResult -> беремо версію з supportedVersions
modern-old   -> modern: UnsupportedProtocolVersionError -> НЕ відкочуємось на initialize
legacy       -> legacy: будь-яка інша помилка або таймаут -> initialize-рукопожаття

Правило: відкат заборонено прив'язувати до конкретного коду помилки —
легасі-сервери відповідають на невідомий метод чим завгодно (-32601, -32602) або мовчать.

header=2026-07-28   body=2026-07-28   -> OK
header=2025-11-25   body=2026-07-28   -> {'code': -32020, 'message': "Header mismatch: MCP-Protocol-Version '2025-11-25' does not match body value '2026-07-28'"}
header=None         body=2026-07-28   -> {'code': -32020, 'message': 'Header mismatch: MCP-Protocol-Version missing'}
```

Зверніть увагу на третій рядок: клієнт **просив** `2025-11-25`, яку сам підтримує, але сервер її не
підтримує — і кінцевий результат усе одно `2026-07-28`. Узгодження вибирає **спільну** версію, а не
улюблену клієнтом.

**Типові помилки**

- Писати відкат як `if error.code == -32601: initialize()`. Специфікація прямо забороняє прив'язувати
  відкат до конкретного коду: legacy-сервери відповідають чим завгодно або мовчать.
- Відкочуватися на `initialize` після `UnsupportedProtocolVersionError`. Це modern-сервер; треба
  повторити з підтримуваною версією з `supported`.
- Зашивати версію протоколу в клієнті назавжди. Версія — це per-request метадані, і вона може
  відрізнятися між запитами.
- Оновлювати `_meta.protocolVersion` на HTTP, але забути заголовок `MCP-Protocol-Version` (або
  навпаки). Розбіжність — це `-32020`.
- Визначати еру сервера на кожен запит. Це властивість сервера; результат **SHOULD** кешуватися.
- Не вказати підтримувані версії в помилці на `initialize`. Legacy-клієнт не має іншого джерела
  діагностики.

**Альтернативи.** Є три стратегії підтримки клієнтів:

| Стратегія | Кому підходить | Ціна |
|---|---|---|
| Тільки modern | Новий сервер без спадщини | Не працює з клієнтами до 2026; у помилці на `initialize` треба назвати версії |
| Тільки legacy | Сервіс, який обслуговує старі хости, і ви не плануєте оновлюватись | Втрачаєте MRTR, `subscriptions/listen`, кеш-підказки. Самі застарілі механізми зникнуть |
| **Dual-era** | Продакшн під час переходу | Найбільше коду: дві поведінки на одному ендпоінті. Специфікація прямо дозволяє обслуговувати обидві ери одночасно |

Для SDK Python це вирішено окремим важелем: `Client(target)` за замовчуванням має `mode="auto"` —
надсилає одну пробу `server/discover` найновішою версією, яку знає SDK, і за потреби відкочується на
`initialize`. `mode="legacy"` завжди йде рукопожаттям. `mode="2026-07-28"` не надсилає нічого
(див. 14.7).

### 14.6 Скасування та MRTR (multi-round-trip requests)

**Що це.** Дві речі, які разом замінили стару модель «сервер посеред обробки кличе клієнта»:
**скасування** — як клієнт відмовляється від запиту, який уже в польоті; **MRTR** — як сервер
отримує від клієнта те, чого йому бракує, **не** ініціюючи власний запит.

**Навіщо це знати.** MRTR — це ламальна зміна з прямою позначкою в специфікації: «попередній патерн
ініційованих сервером запитів більше не підтримується». Якщо ваш сервер питав користувача через
`elicitation/create` як окремий запит — він зламається. Якщо ваш клієнт умів відповідати на
`sampling/createMessage` — він більше не отримає такого запиту. Замість цього обидві сторони
домовляються через результат запиту.

**Як працює під капотом.**

#### Скасування

Клієнт **SHOULD** надіслати сповіщення `notifications/cancelled`, щоб позначити, що раніше виданий
запит треба припинити. Параметри — `requestId` (обов'язковий) і необов'язковий рядок `reason`:

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": { "requestId": "123", "reason": "User requested cancellation" }
}
```

Транспорт визначає **спосіб** скасування:

| Транспорт | Як сигналізується |
|---|---|
| **Streamable HTTP** | Закриття SSE-потоку відповіді **і є** скасуванням. Сервер **MUST** трактувати розрив клієнта як скасування цього запиту. Сповіщення `notifications/cancelled` не потрібне й не очікується |
| **stdio** | Потоку на запит немає. Клієнт **MUST** надіслати `notifications/cancelled` із посиланням на `id` запиту |

Дзеркальний випадок: сервер **MUST** надіслати `notifications/cancelled`, посилаючись на `id` запиту
`subscriptions/listen`, коли він закриває цей потік підписки. І сервери **MUST NOT** слати
`notifications/cancelled` з будь-якої іншої причини.

Вимоги до поведінки:

1. Сповіщення про скасування **MUST** посилатися лише на запити, які клієнт раніше видав і які, як
   він вважає, ще виконуються.
2. Сервер, отримавши скасування, **SHOULD** припинити обробку, звільнити ресурси й **не** слати
   відповіді на скасований запит.
3. Сервер **MAY** проігнорувати скасування, якщо запит невідомий, уже завершений або не може бути
   скасований.
4. Клієнт **SHOULD** ігнорувати будь-яку відповідь на скасований запит, що прийде пізніше.

Специфікація окремо описує **гонки**: через затримку мережі скасування може прийти після того, як
обробка завершилася, і навіть після відправки відповіді. Обидві сторони **MUST** обробляти ці
ситуації коректно, а невідомі `id`, завершені запити й невалідні сповіщення **SHOULD** просто
ігноруватися — це зберігає природу «надіслав і забув».

Про таймаути: реалізації **SHOULD** встановлювати таймаут на всі надіслані запити, щоб не тримати
завислі з'єднання й не вичерпувати ресурси. SDK і проміжне ПЗ **SHOULD** дозволяти налаштовувати
таймаут **на кожен запит окремо**. Реалізації **MAY** скидати таймер при отриманні
`notifications/progress` (це означає, що робота справді йде), але **SHOULD** завжди застосовувати
максимальний таймаут незалежно від прогресу.

#### MRTR

Ідея проста й тому гарна: **сервер не кличе клієнта, а повертає йому питання у відповіді на його ж
запит**. Клієнт збирає відповіді й **повторює** той самий запит, доклавши їх.

Загальний потік:

1. Клієнт надсилає початковий запит із потрібними параметрами.
2. Сервер розуміє, що потрібна додаткова інформація, і відповідає запитом на неї.
3. Клієнт збирає інформацію в користувача або з інших джерел і **повторює** початковий запит,
   доклавши її.
4. Сервер бачить, що інформації достатньо, і повертає фінальний результат.

Три типи, на яких це тримається:

| Тип | Що це |
|---|---|
| `InputRequests` | Карта серверних запитів: ключ — призначений сервером рядковий ідентифікатор, значення — `ElicitRequest`, `CreateMessageRequest` або `ListRootsRequest` |
| `InputResponses` | Карта відповідей клієнта: ключі збігаються з ключами `InputRequests`, значення — `ElicitResult`, `CreateMessageResult` або `ListRootsResult` |
| `InputRequiredResult` | Результат із `resultType: "input_required"`, який несе `inputRequests`, `requestState` або обидва |

`requestState` — непрозорий рядок, змістовний лише для сервера. Клієнти **MUST NOT** його
переглядати, розбирати, змінювати або робити будь-які припущення про його вміст. Якщо поля немає —
клієнт **MUST NOT** додавати його у повтор. Якщо поле є — клієнт **MUST** повернути **точне**
значення.

Які запити можуть отримати `InputRequiredResult`:

| Запит клієнта | Підтримує `InputRequiredResult` |
|---|---|
| `prompts/get` | Так |
| `resources/read` | Так |
| `tools/call` | Так |

Сервери **MUST NOT** слати `InputRequiredResult` у відповідь на будь-які інші запити клієнта.

Вимоги до сервера (найважливіше):

- `inputRequests` — ключі призначає сервер, вони **MUST** бути унікальні в межах запиту; значення
  **MUST** бути одним із `ElicitRequest`, `CreateMessageRequest`, `ListRootsRequest`.
- Сервер **MUST** включити принаймні одне з полів `inputRequests` або `requestState`.
- Сервер **MUST NOT** слати `inputRequests` того типу, який клієнт не оголосив у можливостях.
  Наприклад, якщо клієнт не оголосив `elicitation`, у `inputRequests` не може бути
  `elicitation/create`.
- Сервер **MUST NOT** припускати, що клієнт виконає запити або повторить запит. Сервер **MAY**
  повертати `InputRequiredResult` кілька разів поспіль, поки не отримає потрібне.
- **Безпека `requestState`** — найважливіший пункт. Якщо запит клієнта містить `requestState`,
  сервер **MUST** трактувати його як **підконтрольний зловмиснику ввід**. Якщо `requestState` впливає
  на авторизацію, доступ до ресурсів або бізнес-логіку, сервер **MUST** захистити його цілісність
  (HMAC або AEAD) і **MUST** відхиляти стан, що не пройшов перевірку. Захист цілісності **MAY** бути
  відсутній лише тоді, коли підміна може спричинити не більше ніж збій запиту.
- Для захисту від повтору сервер **SHOULD** включати в захищений `requestState` і перевіряти при
  отриманні: (а) автентифікованого суб'єкта — відхиляючи стан, поданий іншим суб'єктом;
  (б) короткий TTL — відхиляючи прострочений стан; (в) ідентифікатор вихідного запиту (наприклад,
  назву методу й дайджест його значущих параметрів) — відхиляючи стан, поданий із невідповідним
  запитом. Специфікація попереджає окремо: ці заходи обмежують вікно повтору й запобігають
  міжкористувацькому та міжзапитному перевикористанню, але **самі по собі не гарантують
  одноразовості**. Сервери, для яких `requestState` має бути використаний не більше одного разу
  (наприклад, одноразові погашення), **MUST** забезпечувати цю інваріанту на своєму боці.

Вимоги до клієнта:

- Отримавши `InputRequiredResult` із `inputRequests`, клієнт **MUST** зібрати запитаний ввід перед
  повтором. Якщо поля `inputRequests` немає — клієнт **MAY** повторити запит негайно.
- Якщо є `requestState` — клієнт **MUST** повернути його точне значення; якщо немає — **MUST NOT**
  додавати.
- JSON-RPC `id` **MUST** відрізнятися між початковим запитом і повтором: це незалежні запити.
- Обидва поля впливають **лише** на повтор цього конкретного запиту; вони **MUST NOT**
  використовуватися для інших паралельних запитів.

Обробка помилок: сервер **SHOULD** валідувати, що дані клієнта — коректний `InputResponses`, а
протокольні помилки (невалідний JSON, невідповідність схемі, внутрішні збої) **SHOULD** повертати
як JSON-RPC-помилку. Невідомі зайві параметри в `InputResponses` сервер **SHOULD** ігнорувати. І
найкорисніше правило: якщо клієнт не надіслав частину раніше запитаної інформації, і вона потрібна,
сервер **SHOULD** відповісти **новим** `InputRequiredResult` із повторним запитом, **а не** помилкою.

**Робочий приклад.** Повний двораундовий обмін плюс демонстрація того, чому `requestState` не можна
лишати незахищеним.

```python
import hashlib
import hmac
import json
import time

SECRET = b"key-from-env-not-hardcoded-in-real-code"
TEMPERATURE_SAMPLE = 21.5          # «зовнішній» ресурс, який потрібен інструменту


# ── Серверна частина: requestState із захистом цілісності ───────────────────
def seal_state(payload: dict) -> str:
    """Підписуємо стан; клієнт його лише переносить і не має читати."""
    body = json.dumps({**payload, "exp": time.time() + 600}, sort_keys=True).encode()
    return f"{body.decode()}|{hmac.new(SECRET, body, hashlib.sha256).hexdigest()}"


def open_state(token: str) -> dict:
    """Будь-яка підміна або прострочення — відмова, а не тихе прийняття."""
    body, _, signature = token.rpartition("|")
    expected = hmac.new(SECRET, body.encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(signature, expected):
        raise ValueError("requestState не пройшов перевірку цілісності")
    payload = json.loads(body)
    if payload["exp"] < time.time():
        raise ValueError("requestState прострочений")
    return payload


def call_tool(params: dict) -> dict:
    """Обробник tools/call, який уміє відповісти InputRequiredResult."""
    answers = params.get("inputResponses") or {}
    if "city" not in answers:
        return {
            "resultType": "input_required",
            "inputRequests": {
                "city": {
                    "method": "elicitation/create",
                    "params": {
                        "mode": "form",
                        "message": "Для якого міста показати температуру?",
                        "requestedSchema": {
                            "type": "object",
                            "properties": {"name": {"type": "string"}},
                            "required": ["name"],
                        },
                    },
                }
            },
            "requestState": seal_state({"tool": "get_temperature", "args_digest": "d41d8cd9"}),
        }
    # Другий раунд: стан мусить повернутися незміненим.
    state = open_state(params["requestState"])
    assert state["tool"] == "get_temperature", "стан виданий для іншого інструмента"
    city = answers["city"]["content"]["name"]
    return {
        "resultType": "complete",
        "content": [{"type": "text", "text": f"{city}: {TEMPERATURE_SAMPLE} °C"}],
        "structuredContent": {"city": city, "celsius": TEMPERATURE_SAMPLE},
    }


# ── Клієнтська частина: цикл, який проганяє SDK за вас ─────────────────────
def drive(rounds_limit: int = 5) -> dict:
    params: dict = {"name": "get_temperature", "arguments": {"units": "celsius"}}
    for _ in range(rounds_limit):
        result = call_tool(params)
        print("  resultType:", result["resultType"])
        if result["resultType"] == "complete":
            return result
        params = {
            "name": params["name"],
            "arguments": params["arguments"],              # ті самі аргументи
            "inputResponses": {"city": {"action": "accept", "content": {"name": "Київ"}}},
            "requestState": result["requestState"],        # луна без змін
        }
    raise RuntimeError("перевищено ліміт раундів")


print("=== MRTR: два раунди одного tools/call")
final = drive()
print("  фінал     :", final["content"][0]["text"])
print()

print("=== той самий requestState, підмінений клієнтом")
sealed = call_tool({"name": "get_temperature", "arguments": {}})["requestState"]
tampered = sealed.replace('"get_temperature"', '"delete_database"')
try:
    call_tool({"name": "get_temperature", "arguments": {},
               "inputResponses": {"city": {"action": "accept", "content": {"name": "Київ"}}},
               "requestState": tampered})
except ValueError as exc:
    print("  відмова   :", exc)
print()

print("=== скасування запиту (stdio)")
cancel = {"jsonrpc": "2.0", "method": "notifications/cancelled",
          "params": {"requestId": "123", "reason": "User requested cancellation"}}
print(" ", json.dumps(cancel, ensure_ascii=False))
print("  id у сповіщенні:", "id" in cancel, "(сповіщення не має id)")
```

Фактичний вивід:

```
=== MRTR: два раунди одного tools/call
  resultType: input_required
  resultType: complete
  фінал     : Київ: 21.5 °C

=== той самий requestState, підмінений клієнтом
  відмова   : requestState не пройшов перевірку цілісності

=== скасування запиту (stdio)
  {"jsonrpc": "2.0", "method": "notifications/cancelled", "params": {"requestId": "123", "reason": "User requested cancellation"}}
  id у сповіщенні: False (сповіщення не має id)
```

Зверніть увагу: у другому раунді клієнт надсилає **ті самі** `name` та `arguments` — повтор це
буквально той самий виклик, а не новий метод. І `id` у справжньому обміні мусить відрізнятися, бо
це незалежні JSON-RPC-запити.

**Типові помилки**

- Розбирати або «виправляти» `requestState` на клієнті. Специфікація прямо забороняє його
  інспектувати, а сервер зобов'язаний вважати його підконтрольним зловмиснику.
- Приймати `requestState` без перевірки цілісності, коли він впливає на авторизацію або доступ до
  ресурсів. Це прямий шлях до обходу перевірок.
- Повторювати запит із **тим самим** JSON-RPC `id`. Це порушує вимогу про незалежність запитів.
- Слати `inputRequests` із `elicitation/create` клієнту, який не оголосив `elicitation`. Це
  порушення: сервер **MUST NOT** слати запити на неоголошені можливості.
- Відповідати помилкою, коли клієнт забув частину вводу. Специфікація радить повернути новий
  `InputRequiredResult` із повторним запитом.
- Обробити `InputRequiredResult` як `CallToolResult` і впасти на `result["content"]`. Перевіряйте
  `resultType` — або, ще краще, дайте SDK прогнати цикл за вас.
- Слати `notifications/cancelled` на Streamable HTTP. Там сигналом є закриття SSE-потоку, і
  сповіщення не очікується.
- Не ставити таймаут на запит. Специфікація радить завжди застосовувати максимальний таймаут,
  навіть якщо приходять сповіщення про прогрес.

**Альтернативи.** MRTR — не єдиний спосіб отримати від користувача потрібне:

| Ситуація | Підхід | Компроміс |
|---|---|---|
| Треба ввід під час виконання одного виклику | **MRTR** (`InputRequiredResult`) | Єдиний канал у `2026-07-28`; усі раунди — звичайні запити клієнта |
| Треба ввід, який не залежить від запиту | Параметр інструмента або `resources/read` | Простіше, але модель мусить знати значення заздалегідь |
| Треба LLM-компліт усередині сервера | `CreateMessageRequest` через MRTR | Sampling застарілий (14.8); специфікація радить інтегруватися з API провайдера напряму |
| Треба довготривала операція з полінгом | Розширення `io.modelcontextprotocol/tasks` | Поза ядром протоколу; замінює блокуючий `tasks/result` полінгом через `tasks/get` |
| Клієнт не вміє обробляти MRTR | Протокольна помилка з поясненням | Гірше, ніж MRTR, але чесніше, ніж тихо вгадувати |

### 14.7 Написання власного MCP-сервера

**Що це.** Практика: мінімальний сервер, який говорить справжнім MCP, і шлях від «три функції» до
продакшн-сервера на офіційному SDK.

**Навіщо це знати.** Найцінніше в MCP — те, що сервер справді малий. Специфікація формулює це як
принцип дизайну: **сервери мають бути надзвичайно простими в побудові**, а складна оркестрація — це
відповідальність host. Якщо ваш сервер виходить великим, ви, найімовірніше, поклали в нього логіку,
яка належить застосунку.

**Як працює під капотом.** Подивимось спершу, що саме сервер мусить зробити, без жодної бібліотеки.
Це корисно, бо знімає магію: SDK робить рівно це й нічого більше.

Мінімальний сервер мусить:

1. читати по одному JSON-RPC-повідомленню на рядок зі `stdin` (або з тіла POST);
2. перевіряти обов'язкові поля `_meta` у кожному запиті;
3. перевіряти версію протоколу й повертати `-32022` зі списком підтримуваних при невідповідності;
4. диспетчеризувати метод; невідомий метод — `-32601`;
5. класти в кожен `result` поля `resultType`, і для списків ще `ttlMs` і `cacheScope`;
6. відрізняти збій виконання інструмента (`isError: true`) від протокольної помилки;
7. писати логи у `stderr`, а у `stdout` — лише MCP-повідомлення.

Порядок кроків 2–4 важливий: перевірка `_meta` йде **перед** диспетчеризацією, бо запит без
обов'язкових полів невалідний незалежно від методу.

**Робочий приклад.** Нижче — повний сервер і клієнт на стандартній бібліотеці. Транспорт змодельовано
двома чертами замість `stdin`/`stdout` підпроцесу: семантика кадрування та сама, але приклад
детермінований і не потребує запуску процесу.

```python
import json

PROTOCOL_VERSION = "2026-07-28"
SERVER_INFO = {"name": "handbook-demo", "version": "0.1.0"}

# ── Примітиви, які оголошує сервер ──────────────────────────────────────────
TOOLS = {
    "add": {
        "name": "add",
        "title": "Додавання двох чисел",
        "description": "Повертає суму двох цілих чисел.",
        "inputSchema": {
            "type": "object",
            "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}},
            "required": ["a", "b"],
            "additionalProperties": False,
        },
        "annotations": {"readOnlyHint": True, "openWorldHint": False},
    }
}


def tool_add(arguments: dict) -> int:
    return arguments["a"] + arguments["b"]


TOOL_IMPLS = {"add": tool_add}


class RpcError(Exception):
    """Протокольна помилка: те, що модель не може виправити (на відміну від isError)."""

    def __init__(self, code: int, message: str, data: dict | None = None) -> None:
        super().__init__(message)
        self.code, self.message, self.data = code, message, data

    def to_response(self, request_id) -> dict:
        error = {"code": self.code, "message": self.message}
        if self.data is not None:
            error["data"] = self.data
        return {"jsonrpc": "2.0", "id": request_id, "error": error}


# ── Сервер ──────────────────────────────────────────────────────────────────
class DemoServer:
    """Найменший сервер, який усе ще говорить справжнім MCP."""

    def capabilities(self) -> dict:
        return {"tools": {"listChanged": False}}

    def handle(self, message: dict) -> dict | None:
        """Диспетчер: вхідне повідомлення -> вихідне (або None для сповіщення)."""
        method = message.get("method")
        if method is None:                     # це відповідь або сміття
            return None
        request_id = message.get("id")
        params = message.get("params") or {}

        # Кожен запит мусить нести обов'язкові поля _meta.
        meta = params.get("_meta") or {}
        for key in ("io.modelcontextprotocol/protocolVersion",
                    "io.modelcontextprotocol/clientCapabilities"):
            if key not in meta:
                return self._error(request_id, -32602, f"missing required _meta field: {key}")

        version = meta["io.modelcontextprotocol/protocolVersion"]
        if version != PROTOCOL_VERSION:
            return self._error(
                request_id, -32022, "Unsupported protocol version",
                {"requested": version, "supported": [PROTOCOL_VERSION]},
            )

        try:
            result = self._dispatch(method, params)
        except RpcError as exc:
            return exc.to_response(request_id)

        return {"jsonrpc": "2.0", "id": request_id,
                "result": {**result, "_meta": {"io.modelcontextprotocol/serverInfo": SERVER_INFO}}}

    def _dispatch(self, method: str, params: dict) -> dict:
        if method == "server/discover":
            result = {
                "resultType": "complete",
                "supportedVersions": [PROTOCOL_VERSION],
                "capabilities": self.capabilities(),
                "instructions": "Демонстраційний сервер довідника.",
                "ttlMs": 3_600_000,
                "cacheScope": "public",
            }
        elif method == "tools/list":
            result = {
                "resultType": "complete",
                "tools": list(TOOLS.values()),
                "ttlMs": 300_000,
                "cacheScope": "public",
            }
        elif method == "tools/call":
            result = self._call_tool(params)
        else:
            raise RpcError(-32601, f"Method not found: {method}")
        return result

    def _call_tool(self, params: dict) -> dict:
        name = params.get("name")
        tool = TOOLS.get(name)
        if tool is None:
            # Помилка ПОШУКУ інструмента — це протокольна помилка, а не isError.
            raise RpcError(-32602, f"Unknown tool: {name!r}")
        arguments = params.get("arguments") or {}
        missing = [k for k in tool["inputSchema"]["required"] if k not in arguments]
        if missing:
            return {
                "resultType": "complete",
                "content": [{"type": "text", "text": f"Invalid arguments, missing: {missing}"}],
                "isError": True,
            }
        try:
            value = TOOL_IMPLS[name](arguments)
        except Exception as exc:                       # збій виконання -> isError
            return {
                "resultType": "complete",
                "content": [{"type": "text", "text": f"Error executing tool {name}: {exc}"}],
                "isError": True,
            }
        return {"resultType": "complete",
                "content": [{"type": "text", "text": str(value)}],
                "structuredContent": {"result": value}}

    @staticmethod
    def _error(request_id, code: int, message: str, data: dict | None = None) -> dict:
        error = {"code": code, "message": message}
        if data is not None:
            error["data"] = data
        return {"jsonrpc": "2.0", "id": request_id, "error": error}


# ── Транспорт: дві черги замість stdin/stdout ────────────────────────────────
class Pipe:
    """Односпрямований канал newline-delimited JSON-RPC."""

    def __init__(self) -> None:
        self._frames: list[str] = []

    def write(self, message: dict) -> None:
        frame = json.dumps(message, separators=(",", ":"))
        assert "\n" not in frame, "кадр stdio не може містити вбудованих нових рядків"
        self._frames.append(frame)

    def read(self) -> dict | None:
        return json.loads(self._frames.pop(0)) if self._frames else None


to_server, to_client = Pipe(), Pipe()
server = DemoServer()


def rpc(method: str, params: dict | None = None, request_id: int = 1) -> dict:
    """Повний оберт: клієнт пише кадр, сервер обробляє, клієнт читає кадр."""
    params = dict(params or {})
    params["_meta"] = {
        "io.modelcontextprotocol/protocolVersion": PROTOCOL_VERSION,
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "HandbookClient", "version": "1.0.0"},
    }
    to_server.write({"jsonrpc": "2.0", "id": request_id, "method": method, "params": params})
    reply = server.handle(to_server.read())
    if reply is not None:
        to_client.write(reply)
    return to_client.read()


print("=== server/discover")
discover = rpc("server/discover")
print(json.dumps(discover, indent=2, ensure_ascii=False))
print()

print("=== tools/list")
listing = rpc("tools/list", request_id=2)
print("resultType      :", listing["result"]["resultType"])
print("ttlMs/cacheScope:", listing["result"]["ttlMs"], "/", listing["result"]["cacheScope"])
print("Інструменти     :", [t["name"] for t in listing["result"]["tools"]])
print()

print("=== tools/call (успіх)")
ok = rpc("tools/call", {"name": "add", "arguments": {"a": 2, "b": 3}}, request_id=3)
print(json.dumps(ok["result"], indent=2, ensure_ascii=False))
print()

print("=== tools/call (бракує аргументу)")
bad_args = rpc("tools/call", {"name": "add", "arguments": {"a": 2}}, request_id=4)
print("isError:", bad_args["result"]["isError"], "|", bad_args["result"]["content"][0]["text"])
print()

print("=== невідомий метод")
unknown = rpc("tools/nonexistent", request_id=5)
print(json.dumps(unknown, ensure_ascii=False))
print()

print("=== стара версія протоколу")
params = {"_meta": {"io.modelcontextprotocol/protocolVersion": "1900-01-01",
                    "io.modelcontextprotocol/clientCapabilities": {}}}
to_server.write({"jsonrpc": "2.0", "id": 6, "method": "tools/list", "params": params})
print(json.dumps(server.handle(to_server.read()), ensure_ascii=False))
print()

print("=== невідомий інструмент (протокольна помилка, не isError)")
unknown_tool = rpc("tools/call", {"name": "divide", "arguments": {}}, request_id=7)
print(json.dumps(unknown_tool, ensure_ascii=False))
```

#### Офіційний Python SDK

Станом на 09.2026 актуальна версія пакета `mcp` — **2.2.0**, опублікована **2026-09-07**; потрібен
Python **3.10+**. Це **v2** — велика переробка, яка підтримує ревізію `2026-07-28` (і всі попередні).
Версія 1.x продовжує отримувати критичні виправлення на гілці `v1.x`; у завантаженому описі PyPI
рекомендація закріпити конкретну версію 1.x **обрізана**, тому точний номер там не підтверджується.

Мінімальний сервер на SDK — це три декоратори:

```python
from mcp.server import MCPServer

mcp = MCPServer("Demo")


@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers."""
    return a + b


@mcp.resource("greeting://{name}")
def greeting(name: str) -> str:
    """Greet someone by name."""
    return f"Hello, {name}!"


@mcp.prompt()
def summarize(text: str) -> str:
    """Summarize a piece of text in one sentence."""
    return f"Summarize the following text in one sentence:\n\n{text}"


if __name__ == "__main__":
    mcp.run()          # без аргументу транспорт — stdio
```

Що тут важливо:

- **Імпорт саме такий**: `from mcp.server import MCPServer`. Клас клієнта живе в іншому місці —
  `from mcp import Client`; конструкції `from mcp import MCPServer` не існує.
- **Схема, назва й опис беруться з функції**: `a: int, b: int` перетворюється на JSON Schema, назва
  інструмента — це ім'я функції, опис — докстрінг. Аніякої окремої декларації писати не треба.
- **Ресурс із `{param}` у URI стає шаблоном** і потрапляє в `resources/templates/list`, а не в
  `resources/list`.
- **Можливості оголошуються автоматично**: зареєстрували примітив — з'явилася відповідна
  можливість. Це видно з боку клієнта:

```python
import anyio
from mcp import Client


async def main() -> None:
    async with Client("http://localhost:8000/mcp") as client:
        print(client.server_capabilities.model_dump(exclude_none=True))


if __name__ == "__main__":
    anyio.run(main)
```

Типовий вивід на сервері з трьома примітивами:

```
{'prompts': {'list_changed': True}, 'resources': {'subscribe': True, 'list_changed': True}, 'tools': {'list_changed': True}}
```

Зверніть увагу: `model_dump()` дає **snake_case** (`list_changed`), бо це Pydantic-модель. На дроті
поле називається `listChanged` — саме так, як вимагає схема. Не плутайте подання в Python із
форматом на дроті.

**Транспорти.** Вибір транспорту — це один аргумент `run()`:

```python
mcp.run()                                       # stdio (типово)
mcp.run(transport="streamable-http", port=3001) # HTTP на http://127.0.0.1:3001/mcp
```

Опції транспорту йдуть у `run()`, а не в конструктор: `MCPServer(...)` описує, **що** це за сервер
(назва, версія, інструкції), а `run()` — **як** його обслуговують. Серед корисних опцій:
`json_response=True` (відповідати одним JSON-об'єктом замість SSE; тіло вміщає лише
відповідь, тож `ctx.elicit()` на цій нозі дає `NoBackChannelError`, а сповіщення, прив'язані до
виклику — прогрес від `ctx.report_progress()` і логи цього виклику — просто відкидаються),
`stateless_http=True`, `max_request_body_size` (типово 4 MiB), `session_idle_timeout` (типово 1800 с,
для legacy-сесій), `max_sessions` (типово 10 000).

**Клієнт і тестування.** `Client` працює з трьома видами цілі: URL (Streamable HTTP), опис
підпроцесу (`StdioServerParameters`) і **сам об'єкт сервера** — у пам'яті, без процесу й порту:

```python
import pytest
from mcp import Client
from server import mcp


@pytest.mark.anyio
async def test_add() -> None:
    async with Client(mcp) as client:
        result = await client.call_tool("add", {"a": 1, "b": 2})
        assert result.structured_content == {"result": 3}
```

Для stdio-клієнта дитина **не** успадковує ваше середовище: їй дістається мінімальний список
(`HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, `USER` на POSIX), і потрібні змінні треба передавати
явно через `env=`.

**Помилки.** SDK розрізняє три класи, і це прямо відображає поділ зі специфікації:

| Що зробили | Що бачить модель | Що бачить застосунок |
|---|---|---|
| `raise ToolError(...)` | `is_error=True` і ваш текст у `content` — модель може виправитися | Нічого особливого; один рядок `INFO` у логах |
| `raise MCPError(code=..., message=...)` | Нічого | JSON-RPC-помилка; `code`, `message`, `data` доходять без змін |
| Будь-який інший виняток | `is_error=True` з текстом `Error executing tool <name>` **без** вашого повідомлення | `ERROR` із трейсбеком у логах сервера |

Правило вибору формулює документація SDK одним питанням: **чи міг би розумніший виклик цього
уникнути?** Якщо так — `ToolError` (модель побачить і виправиться). Якщо ні — `MCPError`.
Текст непередбаченого винятку навмисно не виходить за межі сервера: `KeyError` з вашого коду або
стек SQL-драйвера можуть описати внутрішній устрій сервера.

Для ресурсів є окремі винятки: `ResourceNotFoundError` перетворюється на `-32602` з `uri` у `data`,
`ResourceError` — на `-32603`.

**MRTR на SDK.** На високому рівні (`@mcp.tool()`) ви зазвичай оголошуєте залежність, яка просить
ввід, і SDK сам формує `InputRequiredResult`. Ручна форма — низькорівневий `Server`, де
`on_call_tool` має тип `-> CallToolResult | InputRequiredResult`. На боці клієнта цикл прогоняється
автоматично, якщо зареєструвати `elicitation_callback` (або `sampling_callback`, `list_roots_callback`).
Кількість раундів обмежена: `Client(..., input_required_max_rounds=10)` за замовчуванням.

Окремо про `requestState`: SDK захищає його **за замовчуванням**. Кожен вихідний стан шифрується й
підписується під ключем, згенерованим на старті процесу, а кожна луна перевіряється. Цей типовий
ключ живе й помирає разом із процесом — тому для кількох процесів (кілька воркерів uvicorn, кілька
інстансів за балансувальником) або для переживання перезапуску потрібно передати спільні ключі:

```python
from mcp.server.mcpserver import MCPServer, RequestStateSecurity

mcp = MCPServer("fleet", request_state_security=RequestStateSecurity(keys=[key]))
```

Запечатаний стан прив'язаний до часового вікна (типово 600 секунд на раунд, не на весь флоу), до
автентифікованого суб'єкта й до вихідного запиту — методу, назви інструмента й дайджесту
аргументів. Це рівно ті заходи, які вимагає специфікація в розділі MRTR.

**Типові помилки**

- `print()` у stdio-сервері. SDK відводить дріт на приватний дескриптор і перенаправляє вже
  скинутий у `stdout` вивід у `stderr`, але вивід, який лишився в буфері до початку обслуговування,
  усе одно потрапить у дріт. Використовуйте модуль `logging`.
- Передати опції транспорту в конструктор. `MCPServer("Bookshop", port=3001)` дає
  `TypeError: MCPServer.__init__() got an unexpected keyword argument 'port'`.
- Чекати, що stdio-дитина успадкує змінні середовища. Вона їх не успадковує — передавайте через `env=`.
- Повертати рядок із текстом помилки замість `raise`. Повернутий рядок має `is_error=False`:
  і для моделі, і для UI це виглядає як успішна відповідь, якою є текст помилки.
- Писати валідацію аргументів вручну. Невалідні аргументи відсікаються за схемою **до** виклику
  вашої функції й повертаються моделі як `is_error=True`.
- Використовувати `mode="2026-07-28"` і чекати на `server_info` / `server_capabilities`. Пін не
  надсилає нічого: `server_info` буде `None`, а всі можливості — `None`. Компроміс — `prior_discover=`
  із збереженим `DiscoverResult`.
- Будувати розрахунок на типовий ключ `RequestStateSecurity` у багатопроцесному розгортанні. Повтор,
  що приземлиться на інший воркер, буде відкинуто.

**Альтернативи.** Писати сервер на SDK чи вручну:

| Підхід | Коли брати | Ціна |
|---|---|---|
| **`MCPServer` зі SDK** | Майже завжди | Залежність на пакет `mcp`; натомість схема, диспетчеризація й можливості — автоматично |
| **Низькорівневий `Server` зі SDK** | Потрібен контроль над `inputSchema` вручну або повернення `InputRequiredResult` з `on_call_tool` | Більше коду, але точний контроль |
| **Свій код на stdlib** | Вбудовані обмеження, навчальні цілі, дуже вузький сервер | Уся сумісність, версіонування й кадрування — на вас |
| **Інші офіційні SDK** | Не-Python стек | Специфікація однакова; відрізняється лише рівень абстракції |

### 14.8 Що застаріло й чому

**Що це.** Реєстр того, що ревізія `2026-07-28` прибрала, замінила або позначила як Deprecated, із
причинами й шляхами міграції.

**Навіщо це знати.** Це найпрактичніший список розділу. Більшість наявного MCP-коду в інтернеті
написана під `2025-11-25` і раніші ревізії. Оновлення сервера без цього списку перетворюється на
вгадування.

**Як працює під капотом.**

**Що прибрано повністю (ламальні зміни).** Специфікація перелічує дев'ять великих змін:

| # | Що змінилося | Причина / заміна |
|---|---|---|
| 1 | Прибрано протокольні сесії та заголовок `Mcp-Session-Id` | Ендпоінти списків (`tools/list`, `resources/list`, `prompts/list`) більше не залежать від з'єднання. Для стану між викликами — явні серверні хендли, передані як звичайні аргументи інструмента (SEP-2567) |
| 2 | MCP став stateless: прибрано рукопожаття `initialize` / `notifications/initialized` | Версія й можливості їдуть у `_meta` кожного запиту; розбіжність версій дає `UnsupportedProtocolVersionError` (SEP-2575) |
| 3 | Додано `server/discover` | Сервери **MUST** його реалізувати: оголошує підтримувані версії, можливості й ідентичність (SEP-2575) |
| 4 | Прибрано GET-ендпоінт і `resources/subscribe`/`resources/unsubscribe` | Замінено на `subscriptions/listen` — один довгий POST-потік для обраних типів сповіщень (SEP-2575) |
| 5 | Прибрано `ping`, `logging/setLevel`, `notifications/roots/list_changed` | Рівень логування тепер per-request через `io.modelcontextprotocol/logLevel` у `_meta`; сервер **MUST NOT** слати `notifications/message`, якщо поле не передано (SEP-2575) |
| 6 | Експериментальні задачі винесено з ядра в розширення `io.modelcontextprotocol/tasks` | Блокуючий `tasks/result` замінено полінгом через `tasks/get` і новим `tasks/update`; `tasks/list` прибрано (SEP-2663) |
| 7 | Введено MRTR замість запитів, ініційованих сервером | `roots/list`, `sampling/createMessage`, `elicitation/create` більше не надсилаються як окремі запити; їхні payload-и їдуть у `InputRequiredResult.inputRequests` (SEP-2322) |
| 8 | Усі результати тепер несуть обов'язковий `resultType` | `"complete"` або `"input_required"`; відсутнє поле від старіших серверів клієнт **MUST** трактувати як `"complete"` (SEP-2322) |
| 9 | Прибрано відновлюваність SSE-потоків | `Last-Event-ID` і SSE event IDs зникли; розірваний потік означає втрачений запит, який клієнт **MUST** повторити з новим `id` (SEP-2575) |

Менші, але важливі:

- У `ClientCapabilities` і `ServerCapabilities` додано поле `extensions`.
- Сервери **SHOULD** повертати інструменти з `tools/list` у **детермінованому порядку** — це
  дозволяє клієнтам кешувати список і покращує влучання в prompt-кеш LLM (розділ 9).
- Додано обов'язкові заголовки `Mcp-Method` і `Mcp-Name` на Streamable HTTP POST і підтримку
  `x-mcp-header` (SEP-2243).
- `ttlMs` і `cacheScope` стали обов'язковими в результатах п'яти операцій (SEP-2549).
- Код «resource not found» змінено з `-32002` на `-32602` (Invalid Params).
- `inputSchema` і `outputSchema` розширено до будь-яких ключів JSON Schema 2020-12, а
  `structuredContent` — до будь-якого JSON-значення; додано вимоги до резолвінгу `$ref` (SEP-2106).
- Прибрано сповіщення `notifications/elicitation/complete` і поле `elicitationId` з URL-режиму
  elicitation (обидва з'являлися в `2025-11-25`). За MRTR клієнт дізнається про результат, повторивши
  вихідний запит, тож серверний сигнал завершення й ідентифікатор для його кореляції більше не
  вписуються в протокол. Серверам, яким треба кореляція між повторами, слід кодувати власний
  ідентифікатор у `requestState`.
- Введено політику виділення кодів помилок: `-32000…-32019` лишається застарілим, `-32020…-32099`
  зарезервовано за специфікацією. Коди в цьому чернетковому циклі перенумеровано:
  `HeaderMismatch` `-32001` → `-32020`, `MissingRequiredClientCapability` `-32003` → `-32021`,
  `UnsupportedProtocolVersion` `-32004` → `-32022`.

**Що позначено як Deprecated.** Ці можливості ще повністю працюють, але заплановані до видалення;
нові реалізації **SHOULD NOT** їх додавати:

| Можливість | SEP | Deprecated in | Шлях міграції | Найраніше видалення |
|---|---|---|---|---|
| **Roots** | SEP-2577 | `2026-07-28` | Передавати каталоги або файли як аргументи інструментів, URI ресурсів або конфігурацію сервера | Перша ревізія, випущена 2027-07-28 або пізніше |
| **Sampling** | SEP-2577 | `2026-07-28` | Інтегруватися з API провайдера LLM напряму | Перша ревізія, випущена 2027-07-28 або пізніше |
| **Logging** | SEP-2577 | `2026-07-28` | Логувати в `stderr` (stdio) або використовувати OpenTelemetry | Перша ревізія, випущена 2027-07-28 або пізніше |
| **Dynamic Client Registration** | PR #2858 | `2026-07-28` | Client ID Metadata Documents | Перша ревізія, випущена 2027-07-28 або пізніше |
| `includeContext: "thisServer"` / `"allServers"` | SEP-2596 | `2025-11-25` | Пропустити поле або використати `"none"` | Разом із Sampling |
| **HTTP+SSE транспорт** (`2024-11-05`) | SEP-2596 | `2025-03-26` | Streamable HTTP | Три місяці після того, як SEP-2596 набуде статусу Final |

Специфікація вводить загальну **політику життєвого циклу**: стани Active / Deprecated / Removed і
**мінімальне дванадцятимісячне вікно** депрекації. «Найраніше видалення» позначає момент, коли
можливість стає *придатною* до видалення; фактичне видалення — рішення Core Maintainer під час
підготовки релізу й може статися пізніше. Станом на `2026-07-28` **жодна** можливість ще не
видалена за цією політикою.

```
але їхні ТИПИ живуть усередині InputRequiredResult.inputRequests:
   InputRequest.anyOf: ['CreateMessageRequest', 'ListRootsRequest', 'ElicitRequest']
   InputResponse.anyOf: ['CreateMessageResult', 'ListRootsResult', 'ElicitResult']
   перевірка: 'sampling/createMessage' у ClientRequest? False
              'CreateMessageRequest' у InputRequest? True
```

Останні два рядки — найважливіший висновок розділу. `sampling/createMessage` як метод **зник** зі
списку запитів клієнта, але тип `CreateMessageRequest` **лишився** — він тепер їде всередині
`InputRequiredResult`. Тому фраза «sampling видалено» неточна: видалено *механізм доставки*, а не
сам запит. Це стосується і `roots/list`, і `elicitation/create`.

**Що робити з наявним кодом.** Міграційна таблиця:

| Було (до `2026-07-28`) | Стало | Що зробити в коді |
|---|---|---|
| `initialize` + `notifications/initialized` | `_meta` у кожному запиті | Прибрати рукопожаття; додати `protocolVersion` і `clientCapabilities` у кожен запит |
| `Mcp-Session-Id`, HTTP DELETE для завершення | Немає сесій | Прибрати роботу з сесіями; стан між викликами — явні хендли в аргументах |
| GET-потік + `resources/subscribe` | `subscriptions/listen` | Замінити підписку на один довгий POST; читати `_meta.subscriptionId` |
| `ping` | Нічого | Прибрати; на modern-з'єднанні метод дає «Method not found» |
| `logging/setLevel` + `notifications/message` | `io.modelcontextprotocol/logLevel` у `_meta` | Ставити рівень на кожен запит; без поля сервер **не має права** слати логи |
| `notifications/roots/list_changed` | Аргументи інструмента / URI ресурсів | Прибрати сповіщення; передавати шляхи явно |
| Запит сервера до клієнта (`sampling/createMessage`, `roots/list`, `elicitation/create`) | `InputRequiredResult.inputRequests` + повтор із `inputResponses` | Переписати зворотний канал на «повернути питання й дочекатися повтору» |
| `resultType` відсутній | Обов'язковий | Додати `"complete"` у кожен результат; `"input_required"` — у проміжні |
| `Last-Event-ID`, відновлення SSE | Немає | Повторювати запит як новий із новим `id` |
| `ttlMs`/`cacheScope` відсутні | Обов'язкові в п'яти операціях | Додати обидва поля в результати списків і `resources/read` |
| HTTP+SSE транспорт | Streamable HTTP | Перевести сервер; HTTP+SSE у стані Deprecated |
| `-32002` для resource not found | `-32602` | Оновити сервер; клієнт **SHOULD** досі приймати `-32002` від старих серверів |

**Типові помилки**

- Вважати, що «sampling видалено» означає «типів немає». Типи є, змінився спосіб доставки.
- Видаляти код для `roots`/`sampling`/`logging` одразу. Вони в стані Deprecated, а не Removed;
  вікно депрекації — мінімум 12 місяців. Але нові реалізації їх додавати не повинні.
- Оновлювати `initialize` замість того, щоб його прибрати. Це не «застарілий метод», а метод, якого
  в схемі `2026-07-28` немає.
- Залишити роботу з `Mcp-Session-Id`. Сесій немає; заголовок буде проігноровано.
- Продовжувати логувати через `notifications/message` без `io.modelcontextprotocol/logLevel` у
  запиті. Специфікація прямо забороняє це для ревізії `2026-07-28`.
- Чекати на `notifications/elicitation/complete`. Сповіщення прибрано; результат дізнаєтесь із
  повтору запиту.
- Орієнтуватися на `-32002`. Це застарілий код; новий — `-32602`.

**Альтернативи.** Якщо оновлення зараз неможливе, є три легальні стратегії, і всі вони описані в
специфікації:

| Стратегія | Як | Ризик |
|---|---|---|
| **Dual-era сервер** | Обслуговувати і modern-, і legacy-клієнтів на одному ендпоінті | Більше коду й тестів; але специфікація це прямо дозволяє |
| **Пін legacy-клієнта** | У SDK це `mode="legacy"`: рукопожаття, а не проба | Працює лише проти legacy-сесій; sampling і elicitation push доступні тільки там |
| **Прибрати залежність від застарілого** | Замінити Roots аргументами, Sampling — прямим API, Logging — `stderr`/OpenTelemetry | Це і є рекомендований специфікацією шлях |

Терміни для орієнтування: `-32000…-32019` ніколи не отримає нових кодів; `-32002` та `-32042`
лишаються зарезервованими, але видавати їх заборонено; перші видалення за політикою життєвого циклу
можливі не раніше ревізії, випущеної 2027-07-28 або пізніше.

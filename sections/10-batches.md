## 10. Масова обробка: Message Batches API

Батч-обробка — найпростіший спосіб зменшити рахунок удвічі. Документація формулює прямо: **усе
використання тарифікується за 50% стандартних цін API**. Плата за це — асинхронність: результат
приходить не одразу, а коли система завершить обробку.

Цей розділ про те, коли батч справді вигідний, як формувати запити, як читати чотири типи
результатів (і за які з них ви **не** платите), і чому батч і кешування — не альтернативи, а
множники.

### 10.1 Як працює батч і для чого він

**Що це.** Ви надсилаєте **один** HTTP-запит, який містить **багато** окремих запитів до Messages API.
Система створює Message Batch і обробляє його асинхронно, **кожен запит незалежно**. Ви опитуєте
статус і забираєте результати, коли обробка завершилася для всіх запитів.

**Навіщо це знати.** Документація перелічує типові задачі, для яких це призначено:

| Задача | Що робиться |
|---|---|
| **Масштабна евалюація** | Обробка тисяч тестових випадків |
| **Модерація контенту** | Асинхронний аналіз великих обсягів користувацького вмісту |
| **Аналіз даних** | Генерація висновків або резюме для великих наборів даних |
| **Масова генерація контенту** | Створення великих обсягів тексту — описи товарів, резюме статей |

Спільна властивість усіх чотирьох: **результат не потрібен негайно**. Якщо він потрібен негайно,
батч не підходить — і жодна знижка цього не компенсує.

**Як працює під капотом.** Три кроки з документації:

1. Система створює новий Message Batch із наданими замовленнями Messages.
2. Батч обробляється **асинхронно**, кожен запит **незалежно**.
3. Ви опитуєте статус батчу й забираєте результати, коли обробка завершилася для всіх запитів.

**Обмеження** — їх треба знати точно, бо кожне впливає на архітектуру:

| Обмеження | Значення |
|---|---|
| Розмір батчу | **100 000 запитів** або **256 МБ**, що буде досягнуто першим |
| Час обробки | Більшість батчів завершуються **протягом 1 години** |
| Коли доступні результати | Коли всі повідомлення завершено **або через 24 години**, що настане першим |
| Протермінування | Батчі **протерміновуються**, якщо обробка не завершилася за 24 години |
| Термін зберігання результатів | **29 днів** після створення. Далі батч видно, але результати завантажити не можна |
| Область видимості | Батчі обмежені **робочим простором** (Workspace) |
| Ліміти швидкості | Діють і на HTTP-запити Batches API, і на кількість запитів усередині батчу, що чекають обробки |
| Ліміт витрат | Через високу пропускну здатність і паралельну обробку батчі **можуть трохи перевищити** налаштований ліміт витрат простору |

Останній рядок — не дрібниця. Якщо ви покладаєтеся на ліміт витрат як на жорсткий запобіжник,
батчі можуть його перевищити. Документація також попереджає: обробка **може сповільнюватися залежно
від поточного попиту й вашого обсягу**, і тоді більше запитів протермінується після 24 годин.

**Що можна батчити.** Документація каже: **майже будь-який** запит до Messages API, зокрема vision,
tool use (включно з **усіма** серверними інструментами — web search, web fetch, code execution,
MCP-конектори, advisor і tool search), системні повідомлення, багатоходові розмови, extended
thinking і більшість бета-функцій.

І важлива властивість: **оскільки кожен запит обробляється незалежно, у межах одного батчу можна
змішувати різні типи запитів.**

**Що НЕ можна батчити.** Невелика кількість параметрів Messages API не підтримується в батч-запитах.
Їх включення повертає **помилку валідації**:

| Параметр | Чому |
|---|---|
| `stream: true` | Результати батчу повертаються **єдиним файлом**, а не потоком |
| `speed` (fast mode) | Fast mode налаштовує **синхронну** латентність, що не застосовна до асинхронної батч-обробки |
| `max_tokens: 0` | Попереднє прогрівання кешу в батчі не підтримується: ефемерний запис кешу, зроблений під час батч-обробки, імовірно протермінується |

**Типові помилки**

- Використовувати батч для інтерактивної задачі. Результат може прийти через годину, і клієнт цього
  не переживе.
- Передати `stream: true`, скопіювавши синхронний код. Отримаєте помилку валідації.
- Покладатися на ліміт витрат як на жорсткий бар'єр. Батчі можуть його перевищити.
- Не передбачити протермінування. Батч, що не завершився за 24 години, протерміновується — і частина
  запитів не буде оброблена взагалі (за них ви не платите, але й результату не отримаєте).
- Забути, що результати живуть 29 днів. Пайплайн, який «забере результати пізніше», може їх не знайти.

**Альтернативи.** Для задач, де потрібна швидкість, є синхронні паралельні запити — але без знижки.
Компроміс: розділити роботу на дві частини — термінову (синхронно) і фонову (батчем). Це типовий
продакшн-патерн.

### 10.2 Ціна: 50% і множники

**Що це.** Батч коштує рівно половину. Але справжня економія може бути більшою, бо знижки
**складаються**.

**Навіщо це знати.** Документація формулює ключову властивість прямо: **знижки від кешування промпту
й Message Batches можуть складатися, даючи ще більшу економію, коли обидві функції
використовуються разом.**

**Як працює під капотом.** Ось ціни батчів з документації (за мільйон токенів):

| Модель | Батч: вхід | Батч: вихід | Звичайна ціна (вхід / вихід) |
|---|---|---|---|
| Claude Fable 5.1 | $5 | $25 | $10 / $50 |
| Claude Opus 5 | $2.50 | $12.50 | $5 / $25 |
| Claude Sonnet 5 | $1 | $5 | $2 / $10 |

Тобто батч — це рівно 50% від базової ціни. Тепер додамо кешування: читання з кешу на Opus 5
коштує 10% базової ціни входу (розділ 9). Якщо батч і кеш діють одночасно, вхідні токени з кешу
коштують 10% × 50% = **5%** базової ціни.

```python
def cost_with_levers(
    input_tokens: int,
    output_tokens: int,
    *,
    price_in: float,
    price_out: float,
    cached_input_tokens: int = 0,
    cache_read_frac: float = 0.10,
    batch: bool = False,
) -> float:
    """Вартість із можливістю застосувати кеш і батч одночасно."""
    fresh = input_tokens - cached_input_tokens
    cost = (
        fresh / 1_000_000 * price_in
        + cached_input_tokens / 1_000_000 * price_in * cache_read_frac
        + output_tokens / 1_000_000 * price_out
    )
    return cost * 0.5 if batch else cost


# Приклад: масова евалюація, 50 000 запитів, у кожному 6000 кешованих
# токенів (промпт + інструменти) і 2000 змінних
PER_REQUEST_CACHED, PER_REQUEST_FRESH, PER_REQUEST_OUT = 6000, 2000, 300
N = 50_000
total_in = (PER_REQUEST_CACHED + PER_REQUEST_FRESH) * N
total_out = PER_REQUEST_OUT * N

print(f"{'конфігурація':34} {'вартість':>14} {'економія':>10}")
print("-" * 62)
base = None
for label, kwargs in (
    ("без оптимізацій", {}),
    ("+ батч", {"batch": True}),
    ("+ кеш", {"cached_input_tokens": PER_REQUEST_CACHED * N}),
    ("+ кеш і батч разом", {"cached_input_tokens": PER_REQUEST_CACHED * N, "batch": True}),
):
    c = cost_with_levers(total_in, total_out, price_in=5.0, price_out=25.0, **kwargs)
    base = base or c
    print(f"{label:34} ${c:>13.2f} {1 - c/base:>9.1%}")
```

Запустіть це — фактичний вивід для 50 000 запитів на Claude Opus 5:

```text
конфігурація                             вартість   економія
--------------------------------------------------------------
без оптимізацій                    $      2375.00      0.0%
+ батч                             $      1187.50     50.0%
+ кеш                              $      1025.00     56.8%
+ кеш і батч разом                 $       512.50     78.4%
```

Зверніть увагу на останній рядок. **Кеш і батч разом дають 78.4%, а не 60%** (50% + 10%).
Причина в тому, що множники застосовуються до різних частин рахунку: батч множить **усе** на 0.5, а
кеш зменшує **лише кешовану частину входу** — і вже після цього батч множить результат. Це
арифметика множників, а не додавання відсотків, і саме тому документація каже, що знижки
«складаються».

Різниця між «лише батч» і «батч плюс кеш» на цьому обсязі — **$675 за один прогін** із 50 000
запитів. Якщо такий прогін відбувається щотижня, це близько $2 900 на місяць лише на цьому
навантаженні.

**Але з кешем у батчі є принципове обмеження.** Документація попереджає: оскільки батч-запити
обробляються **асинхронно й паралельно**, влучання в кеш надаються **за принципом best-effort**.
Типові показники влучань — **від 30% до 98%**, залежно від характеру трафіку.

Це означає, що **кеш у батчі не гарантований**. Ви не можете розраховувати на 100% влучань, як у
синхронному режимі з контрольованим темпом.

**Три способи підвищити ймовірність влучань** (з документації):

1. **Включайте ідентичні блоки `cache_control`** у **кожен** запит батчу.
2. **Підтримуйте стабільний потік запитів**, щоб записи кешу не протерміновувалися після їхнього
   п'ятихвилинного терміну життя.
3. **Структуруйте запити так, щоб вони ділили якнайбільше кешованого вмісту.**

Другий пункт особливо важливий і неочевидний: кеш живе 5 хвилин (розділ 9), а батч обробляється
година. Якщо потік запитів нерівномірний, кеш встигає протермінуватися між пачками.

**Типові помилки**

- Вважати, що кеш у батчі працюватиме так само, як синхронно. Він best-effort, 30%–98%.
- Ставити різні `cache_control` у різних запитах батчу. Це прямо знижує влучання.
- Розраховувати бюджет на 100% влучань у кеш. Закладайте консервативну оцінку.
- Не враховувати, що знижки складаються. Можна недооцінити вигоду й не використати її.

**Альтернативи.** Якщо кеш у батчі працює погано через нерівномірний потік, розгляньте
**впорядкування запитів**: згрупуйте запити з однаковим префіксом поруч у батчі. Документація
прямо радить структурувати запити так, щоб вони ділили якнайбільше кешованого вмісту.

### 10.3 Результати: чотири типи й за що ви не платите

**Що це.** Коли обробка батчу завершилася, **кожен** запит має результат одного з чотирьох типів.

**Навіщо це знати.** Тут захована приємна властивість: за три з чотирьох типів ви **не платите**.
І ще одна: **збій одного запиту не впливає на обробку інших**.

**Як працює під капотом.** Чотири типи результатів з документації:

| Тип | Що означає | Чи платите |
|---|---|---|
| `succeeded` | Запит успішний. Містить результат повідомлення | **Так** |
| `errored` | Запит натрапив на помилку, повідомлення не створено. Можливі помилки: невалідні запити й внутрішні помилки сервера | **Ні** |
| `canceled` | Користувач скасував батч до того, як цей запит було надіслано моделі | **Ні** |
| `expired` | Батч досяг 24-годинного протермінування до того, як цей запит було надіслано моделі | **Ні** |

Поле `request_counts` батчу дає огляд розподілу за цими типами.

**Скасування.** Документація описує механіку: скасувати батч, що обробляється, можна через
ендпоінт скасування. Одразу після скасування `processing_status` батчу буде `canceling`. Той самий
метод опитування дозволяє дочекатися завершення скасування. **Скасовані батчі набувають статусу
`ended` і можуть містити часткові результати** для запитів, оброблених до скасування.

Останнє важливо практично: скасування не означає втрату всієї роботи.

**Порядок результатів не гарантований.** Документація радить використовувати **змістовні значення
`custom_id`**, щоб легко зіставляти результати із запитами, **оскільки порядок не гарантовано**.

Це прямий аналог пастки зіставлення за `id` у tool use (розділ 12): зіставляти треба за
ідентифікатором, а не за позицією.

**Типові помилки**

- Зіставляти результати з запитами за порядком. Порядок не гарантовано.
- Використовувати випадкові або незмістовні `custom_id`. Діагностика перетворюється на археологію.
- Вважати, що збій одного запиту зламає батч. Не зламає — документація підкреслює, що збій одного
  запиту не впливає на обробку інших.
- Не обробляти `expired` як окремий випадок. Це не помилка запиту — це протермінування батчу, і
  лікування інше: розбити роботу на менші батчі.

**Альтернативи.** Якщо вам потрібна гарантія обробки кожного запиту, розбийте велику роботу на
**менші батчі** — документація прямо радить це для кращої керованості. Менший батч має більше шансів
завершитися за 24 години.

### 10.4 Практика: формування, відстеження, діагностика

**Що це.** Робочий цикл батч-обробки: підготувати запити, створити батч, опитувати статус, забрати
результати, обробити збої.

**Навіщо це знати.** Батч — асинхронна операція, і весь продакшн-код навколо неї має бути
ідемпотентним і стійким до часткових збоїв.

**Як працює під капотом.** Документація дає чотири практичні правила:

1. **Регулярно відстежуйте статус обробки** й реалізуйте **відповідну логіку повторів** для невдалих
   запитів.
2. **Використовуйте змістовні `custom_id`** для зіставлення результатів із запитами, бо порядок не
   гарантовано.
3. **Розгляньте розбиття дуже великих наборів даних** на кілька батчів для кращої керованості.
4. **Зробіть пробний прогін однієї форми запиту** через Messages API, щоб уникнути помилок валідації.

Четверте правило економить найбільше часу. Помилка в схемі запиту, розмножена на 50 000 запитів,
означає 50 000 записів `errored` — і весь цикл очікування намарно. Один синхронний запит виявляє
проблему за секунди.

**Діагностика типових проблем.** Документація перелічує перевірки:

| Симптом | Що перевірити |
|---|---|
| Помилка `413 request_too_large` | Загальний розмір батч-запиту не перевищує **256 МБ** |
| Запити не обробляються | Усі запити використовують **підтримувані моделі** |
| Невалідні запити | Кожен запит має **унікальний** `custom_id` |
| Результати недоступні | Минуло **менше 29 днів** від `created_at` батчу (**не** від `ended_at`) |
| Батч не завершується | Батч **не скасовано** |

Зверніть увагу на нюанс у четвертому рядку: 29 днів рахуються від **`created_at`**, а не від
`ended_at`. Тобто тривалий батч має менший запас часу на забирання результатів, ніж здається.

**Серверні інструменти в батчі.** Документація описує важливу відмінність: усі серверні інструменти
працюють у батч-запитах, і батч-воркер запускає **той самий серверний агентний цикл**, що й
синхронний Messages API.

Але є нюанс: оскільки **немає відкритого з'єднання, яке треба підтримувати**, батч-цикл виконує
**більше ітерацій за хід**, ніж синхронний запит, перш ніж повернути `stop_reason: "pause_turn"`.

Практичний наслідок: якщо результат батчу приходить із `pause_turn`, **хід не завершено** — його
можна продовжити, надіславши призупинений вміст асистента в наступному запиті (батч або синхронному).
Це той самий патерн продовження `pause_turn`, що для синхронних запитів (розділ 12).

Документація також зазначає, що батч-воркер **додатково обмежує `web_search` на рівні організації**,
щоб високі навантаження не перевантажували сервіс.

**Типові помилки**

- Запустити 50 000 запитів без пробного прогону. Одна помилка схеми множиться на весь батч.
- Не обробляти `pause_turn` у результатах. Хід залишиться незавершеним без явної помилки.
- Перевіряти термін зберігання від `ended_at`. Рахувати треба від `created_at`.
- Дублювати `custom_id`. Отримаєте помилку валідації.
- Не мати логіки повторів для `errored`. За такі запити не стягнули плату, але й результату немає.

**Альтернативи.** Для дуже великих обсягів розгляньте **дворівневу схему**: батч робить чорнову
роботу (генерація, класифікація), а синхронні запити — фінальну перевірку тих випадків, де впевненість
низька. Це дає знижку батчу на більшості обсягу й гарантію якості там, де вона потрібна.

---

### 10.5 Коли батч НЕ потрібен

**Що це.** Чесна межа застосовності. Знижка 50% спокушає застосувати батч усюди.

**Навіщо це знати.** Батч вносить асинхронність, і це ускладнює систему: опитування, зберігання
стану, обробка часткових збоїв, ідемпотентність. Якщо обсяг малий, складність не окупається.

**Як ухвалювати рішення.**

| Ситуація | Батч? | Чому |
|---|---|---|
| Користувач чекає на відповідь | **Ні** | Результат може прийти за годину |
| Тисячі незалежних запитів, результат не терміновий | **Так** | Класичний випадок для батчу |
| Евалюація 500 тестових кейсів | **Так** | Документація називає це першим прикладом застосування |
| 20 запитів на день | **Ні** | Складність більша за економію |
| Модерація потоку користувацького контенту | **Так** | Асинхронність тут природна |
| Агент, що має відповісти за секунди | **Ні** | Агентний цикл вимагає синхронності (розділ 12) |
| Попередня обробка корпусу документів | **Так** | Ідеальний випадок: великий обсяг, без терміновості |
| Кеш-прогрів промпту | **Ні** | `max_tokens: 0` у батчі не підтримується |

**Три питання, які вирішують усе:**

1. **Чи може результат чекати годину?** Якщо ні — батч відпадає.
2. **Чи є обсяг, на якому 50% перекриває складність?** Для десятків запитів — ні.
3. **Чи можна розбити роботу на термінову й фонову частину?** Якщо так — синхронно робіть термінову,
   батчем — решту.

**Типові помилки**

- Застосувати батч до інтерактивної функції заради знижки.
- Будувати батч-інфраструктуру для обсягу, де ручний запуск простіший.
- Забути, що батч потребує зберігання стану. Хтось має пам'ятати `batch_id` і потім забрати
  результати — це робота, а не безкоштовний бонус.
- Не передбачити, що результати живуть 29 днів і потім зникають.

**Альтернативи.** Для середніх обсягів, де терміновість не критична, але година — забагато,
розгляньте **синхронні паралельні запити з обмеженням конкурентності**. Ви втратите знижку 50%,
але отримаєте передбачуваність і простішу архітектуру. Рішення залежить від того, що дорожче у
вашому випадку: гроші чи складність.

### 10.6 Зведення

| Питання | Відповідь |
|---|---|
| Знижка | **50%** на все використання |
| Ліміт батчу | 100 000 запитів **або** 256 МБ, що перше |
| Типовий час | Більшість завершуються за **1 годину** |
| Протермінування | **24 години**, далі батч протерміновується |
| Зберігання результатів | **29 днів** від `created_at` |
| За що не платите | `errored`, `canceled`, `expired` |
| Зіставлення результатів | За `custom_id` — **порядок не гарантовано** |
| Кеш у батчі | Працює, але **best-effort**: типово 30%–98% влучань |
| Знижки кешу й батчу | **Складаються** |
| Не підтримується | `stream: true`, `speed`, `max_tokens: 0` |
| Що робити перед запуском | Пробний прогін однієї форми запиту синхронно |

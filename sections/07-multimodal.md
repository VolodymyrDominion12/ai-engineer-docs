## 7. Мультимодальний ввід: зображення, PDF, цитати, Files API

Модель може отримувати не лише текст. Зображення, PDF-документи й цитати перетворюють LLM із
генератора тексту на інструмент аналізу документів — і водночас вносять власну механіку, яку треба
розуміти, щоб не втрачати гроші й не дивуватися результатам.

Цей розділ про те, як насправді рахуються токени зображень (формула проста, але її наслідки
неочевидні), що саме сервер робить із вашим PDF, як побудувати відповідь із посиланнями на джерела
й чому Files API має власну модель безпеки.

### 7.1 Зображення: формати, роздільність і справжня ціна

**Що це.** Модель не бачить пікселів. Вона бачить **патчі** — блоки 28×28 пікселя, які документація
називає **візуальними токенами** (visual tokens).

**Навіщо це знати.** Документація дає точну формулу, і з неї випливає практичний висновок: ціна
зображення залежить **не від розміру файлу**, а від кількості патчів. Скриншот 4K і фотографія 4K
однакового розміру коштуватимуть по-різному, якщо один із них буде зменшено на сервері.

**Як працює під капотом.** Формула з документації:

```
візуальні токени = ⌈ширина / 28⌉ × ⌈висота / 28⌉
```

Тобто зображення 200×200 дає `⌈200/28⌉ × ⌈200/28⌉ = 8 × 8 = 64` токени. Зображення 1000×1000 —
`36 × 36 = 1296`. Формула лінійна за площею, тож подвоєння обох сторін **учетверо** збільшує вартість.

**Два рівні роздільності.** Кожна модель має максимальну нативну роздільність, виражену двома
межами: довгою стороною й кількістю візуальних токенів. Зображення, більше за будь-яку з них,
**зменшується перед обробкою**:

| Рівень | Моделі | Макс. довга сторона | Макс. візуальних токенів |
|---|---|---|---|
| Висока роздільність | Claude 4.7 і пізніші | 2576 px | 4784 |
| Стандартний | Усі інші | 1568 px | 1568 |

Документація підкреслює: підтримка високої роздільності на зазначених моделях **автоматична й не
потребує ні бета-заголовка, ні opt-in на боці клієнта**.

**Таблиця з документації** — найкращий спосіб побачити різницю між рівнями:

| Розмір зображення | Стандартний: зменшено до | Стандартний: токенів | Висока розд.: зменшено до | Висока розд.: токенів |
|---|---|---|---|---|
| 200×200 px (0.04 Мп) | без зміни | 64 | без зміни | 64 |
| 1000×1000 px (1 Мп) | без зміни | 1296 | без зміни | 1296 |
| 1092×1092 px (1.19 Мп) | без зміни | 1521 | без зміни | 1521 |
| 1920×1080 px (2.07 Мп) | 1456×819 px | 1560 | **без зміни** | **2691** |
| 2000×1500 px (3 Мп) | 1269×952 px | 1564 | без зміни | 3888 |
| 3840×2160 px (8.29 Мп) | 1456×819 px | 1560 | 2576×1449 px | 4784 |

Прочитайте цю таблицю уважно — у ній захована важлива властивість. На **стандартному** рівні
зображення 1920×1080, 2000×1500 і 3840×2160 коштують **майже однаково** (1560, 1564, 1560 токенів),
бо всі вони зменшуються приблизно до однієї межі. На **високій роздільності** між ними вже є
різниця: 2691, 3888, 4784.

Практичний наслідок: на стандартному рівні **передавати велике зображення немає сенсу** — ви
заплатите стільки ж, скільки за зменшене, і втратите деталі через зменшення. На високій
роздільності велике зображення справді дає більше деталей — але й коштує пропорційно.

**Перевірка власної реалізації.** Формулу можна відтворити в кілька рядків і звірити з таблицею:

```python
import math


def visual_tokens(width: int, height: int) -> int:
    """Візуальні токени зображення: патчі 28x28 пікселя.

    Формула з документації: ceil(width / 28) * ceil(height / 28).
    Застосовна, коли зображення НЕ перевищує межі моделі.
    """
    return math.ceil(width / 28) * math.ceil(height / 28)


# Звірка з таблицею документації для розмірів, які не зменшуються
for w, h, expected in [(200, 200, 64), (1000, 1000, 1296), (1092, 1092, 1521),
                       (1920, 1080, 2691)]:
    got = visual_tokens(w, h)
    status = "OK" if got == expected else "РОЗБІЖНІСТЬ"
    print(f"{w}x{h}: {got:>5} токенів, у документації {expected:>5}  {status}")
```

Фактичний вивід:

```
200x200:    64 токенів, у документації    64  OK
1000x1000:  1296 токенів, у документації  1296  OK
1092x1092:  1521 токенів, у документації  1521  OK
1920x1080:  2691 токенів, у документації  2691  OK
```

Для 1920×1080 значення 2691 — це **високороздільний** рядок таблиці (без зменшення). Стандартний
рівень дає 1560, бо зображення спершу зменшується до 1456×819. Формула рахує токени **вже
зменшеного** зображення; сам алгоритм зменшення документація описує окремо.

**Що робити з цим числом.** Ось ціна одного зображення на Claude Opus 5 ($5 за мільйон вхідних
токенів, розділ 6). Усі значення — або з таблиці документації, або точний результат формули для
зображень, які **не** зменшуються:

| Зображення | Токенів | Джерело числа | Ціна на Opus 5 |
|---|---|---|---|
| 200×200 | 64 | таблиця документації | $0.00032 |
| 512×512 | 361 | формула (без зменшення) | $0.001805 |
| 1024×768 | 1036 | формула (без зменшення) | $0.00518 |
| 1920×1080 (висока розд.) | 2691 | таблиця документації | $0.013455 |
| 3840×2160 (висока розд.) | 4784 | таблиця документації | $0.02392 |

Одна фотографія з телефона коштує приблизно як 3 000 токенів тексту. Для тисячі документів на день
це стає основною статтею витрат — і саме тому кешування зображень (розділ 9) і попереднє
зменшення мають сенс.

> **Застереження про числа.** Документація описує сам **алгоритм зменшення** окремо (за посиланням
> «How Claude resizes and pads images»), і в збережених джерелах його точних правил немає. Тому для
> зображень, які **перевищують** межі моделі, точну кількість токенів наперед не порахувати —
> формула вище застосовна лише після зменшення. Для великих зображень користуйтеся ендпоінтом
> підрахунку токенів (розділ 3, підтема 3.5) або наведеною таблицею як орієнтиром.

**Формати й обмеження.** Документація перелічує підтримувані формати: **JPEG, PNG, GIF і WebP**
(`image/jpeg`, `image/png`, `image/gif`, `image/webp`). **Анімації не підтримуються** — документація
каже прямо: використовується лише перший кадр.

Обмеження на кількість:

| Обмеження | Значення |
|---|---|
| Зображень на повідомлення в claude.ai | 20 |
| Зображень на запит в API (моделі з вікном 200k) | 100 |
| Зображень на запит в API (усі інші моделі) | 600 |
| Максимальні розміри одного зображення | 8000×8000 px |

**Найпідступніше обмеження — «багато-зображувальні запити».** Якщо один запит містить **більше 20
зображень**, до **кожного** зображення в цьому запиті застосовується **суворіший ліміт розмірів**.
І — ось де легко помилитися — документація уточнює, що в цей поріг входять **усі** блоки `image`:
включно із зображеннями з попередніх ходів розмови, які ви надсилаєте повторно, і включно із
зображеннями **всередині вмісту `tool_result`** (наприклад, скриншотами, повернутими інструменту
computer use). На Amazon Bedrock і Google Cloud до цього порогу враховуються також блоки документів,
як-от PDF.

Зображення, що перевищують суворіший ліміт, **відхиляються** з `invalid_request_error`, у
повідомленні якого згадуються «many-image requests».

**Окремий випадок: computer use і browser use.** Документація описує виняток, який варто знати
точно: скриншоти й zoom-зображення, які ви повертаєте наборам інструментів computer use і browser
use, **не зменшуються**. API **відхиляє** `tool_result` із таким зображенням, якщо воно перевищує
межі моделі, з помилкою валідації. Тому такі зображення треба **зменшувати у своєму застосунку**
перед поверненням. Щоб і будь-яке інше завелике зображення відхилялося з помилкою замість
зменшення, документація радить установити поле `transformations` у блоці зображення.

**Типові помилки**

- Передавати оригінальні фотографії без зменшення. На стандартному рівні ви заплатите стільки ж,
  скільки за зменшене, але втратите контроль над тим, що саме побачить модель.
- Вважати, що розмір файлу визначає ціну. Ціну визначає кількість патчів 28×28.
- Забувати, що зображення з попередніх ходів і з `tool_result` враховуються в порозі 20 зображень.
  Довга розмова зі скриншотами може раптово почати відхиляти зображення.
- Повертати великі скриншоти в computer use без зменшення. Вони будуть **відхилені**, а не зменшені.
- Слати анімований GIF і очікувати анімацію. Обробляється лише перший кадр.
- Не знати, на якому рівні роздільності ваша модель. Різниця в 1.7 раза за той самий розмір.

**Альтернативи.** Якщо вам потрібен текст із зображення, а не розуміння візуального змісту —
розгляньте OCR або витягування тексту перед відправкою. Це дешевше: текст коштує за токенами
тексту, а не за патчами. Для діаграм, графіків і схем OCR не допоможе — там потрібне справжнє
розуміння зображення.

### 7.2 PDF: що сервер робить за вас

**Що це.** PDF не передається моделі «як файл». Документація описує трьохкроковий процес:
система **витягує вміст документа**, конвертуючи **кожну сторінку в зображення** й витягуючи текст
із кожної сторінки поряд із цим зображенням; модель аналізує **і текст, і зображення**; модель
відповідає, за потреби посилаючись на вміст.

**Навіщо це знати.** Два висновки одразу:

1. **Ви платите двічі за кожну сторінку** — за витягнутий текст і за зображення сторінки.
2. **Модель бачить візуальний вміст** — графіки, діаграми, складні таблиці. Саме тому PDF-підтримка
   працює там, де OCR безсилий.

**Як працює під капотом.** Документація розкладає ціну на дві складові:

| Складова | Вартість |
|---|---|
| Текст | **1 500 – 3 000 токенів на сторінку**, залежно від щільності вмісту. Стандартні ціни API, без додаткових PDF-зборів |
| Зображення | Оскільки кожна сторінка конвертується в зображення, застосовуються **ті самі розрахунки**, що для зображень (див. 7.1) |

Тобто сторінка A4 коштує приблизно **від 2 500 до 4 000 токенів** залежно від щільності тексту.
Порахуймо на Claude Opus 5 ($5/MTok), припустивши, що сторінка дає близько 1 036 візуальних токенів
(це відповідає зображенню 1024×768, яке не зменшується):

| Сторінок | Вартість на Opus 5 |
|---|---|
| 1 | $0.0127 – $0.0202 |
| 10 | $0.13 – $0.20 |
| 100 | $1.27 – $2.02 |
| 300 | $3.80 – $6.05 |

**Припущення тут — кількість візуальних токенів на сторінку.** Документація дає лише діапазон
текстових токенів (1 500–3 000) і посилається на «ті самі розрахунки, що для зображень»; точний
розмір зображення, у яке конвертується сторінка PDF, у збережених джерелах не вказано. Тож
наведені суми — оцінка порядку величини, а не точний прайс. Для реального бюджету міряйте
конкретні PDF через ендпоінт підрахунку токенів (розділ 3, підтема 3.5) — документація прямо радить
це робити.

Головний висновок від цього не змінюється: **триста сторінок — це одиниці доларів лише за читання.**
Саме тому для великих PDF варто спершу подумати, чи потрібен вам весь документ.

**Обмеження PDF** (з документації):

| Вимога | Межа |
|---|---|
| Максимальний розмір запиту | **32 МБ** (різниться за платформами) |
| Максимум сторінок на запит | **600** (100, якщо контекстне вікно запиту менше 1M токенів) |
| Формат | Стандартний PDF **без паролів і шифрування** |

Важлива деталь: **обидві межі стосуються всього корисного навантаження запиту**, включно з будь-яким
іншим вмістом, надісланим поряд із PDF. Для великих PDF документація радить завантажувати їх через
**Files API** і посилатися за `file_id`, щоб тримати розмір запиту малим.

**Щільні PDF дорожчі.** Документація окремо попереджає, що щільні PDF (багато сторінок із дрібним
шрифтом, складні таблиці, насичена графіка) можуть давати вищу витрату токенів — і верхня межа
діапазону 1 500–3 000 токенів на сторінку не є абсолютною стелею для екстремальних випадків.

**Як оптимізувати.** Документація називає три способи покращити ефективність PDF-обробки: **кешування
промпту** (для повторюваного аналізу того самого документа), **батч-обробку документів** (для
великого обсягу) і **tool use** (щоб витягувати конкретну інформацію з документів як вхідні дані
інструментів).

Комбінація «кеш + PDF» особливо вигідна: якщо ви аналізуєте той самий PDF багато разів із різними
питаннями, кеш прибирає повторну оплату за витягнутий текст і зображення сторінок (розділ 9). При
ціні PDF у тисячі токенів на сторінку це найбільша доступна економія.

**Типові помилки**

- Рахувати PDF як «текст». Ви платите ще й за зображення кожної сторінки.
- Слати 500-сторінковий PDF цілком, щоб поставити питання про одну сторінку. Спочатку відберіть
  сторінки — це прямо зменшує рахунок у сотні разів.
- Забувати про ліміт 32 МБ на **весь** запит. Великий PDF плюс історія розмови може перевищити його.
- Слати зашифрований або захищений паролем PDF. Він не обробляється.
- Не використовувати кеш для PDF, який аналізується повторно. Це найочевидніша втрата грошей у
  цьому розділі.
- Очікувати, що витягнутий текст буде ідеальним. Документація не гарантує якості витягування для
  складних макетів — саме тому додається зображення сторінки.

**Альтернативи.** Для документів, де потрібен лише текст, розгляньте витягування тексту **до**
відправки (бібліотеки на кшталт PDF-парсерів) і надсилання звичайного тексту або блоків `document`
типу plain text. Це прибирає витрати на зображення сторінок. Але ви втратите розуміння графіків і
складних таблиць — а саме заради них PDF-підтримка й існує. Для RAG-конвеєрів (розділ 16) часто
правильний шлях — витягнути текст один раз під час індексації й далі працювати лише з текстом.

### 7.3 Цитати: відповідь, яку можна перевірити

**Що це.** Механізм, за якого модель не просто відповідає на основі документа, а вказує **точне
місце** в документі, звідки взяла кожне твердження.

**Навіщо це знати.** Це спосіб перетворити «модель щось сказала» на «модель сказала, і ось джерело,
яке можна відкрити й перевірити». Для юридичних, медичних, фінансових і будь-яких внутрішніх
застосунків це не зручність, а вимога.

**Як працює під капотом.** Документація визначає, що саме може бути процитовано:

- **Текст усередині поля `source` документа** — саме звідси беруться цитати.
- **`title` і `context`** — необов'язкові поля, які передаються моделі, але **не використовуються
  як процитований вміст**.

Останнє має практичне застосування, яке документація підкреслює прямо: `title` **обмежений у
довжині**, тож поле `context` корисне для зберігання **метаданих документа** як тексту або
серіалізованого JSON. Тобто `context` — це місце для «звідки цей документ, яка в нього дата, який
відділ», а не для вмісту, який ви хочете цитувати.

**Три типи документів.** Документація описує три типи з різним поділом на фрагменти й різним
форматом цитат:

| Тип | Для чого найкраще | Поділ | Формат цитати |
|---|---|---|---|
| **Plain text** | Прості текстові документи, проза | За реченнями | Індекси символів (**з 0**) |
| **PDF** | PDF-файли з текстовим вмістом | За реченнями | Номери сторінок (**з 1**) |
| **Custom content** | Списки, транскрипти, особливе форматування, дрібніші цитати | Налаштовується | Залежить від структури |

Документи можна подавати безпосередньо в повідомленні (base64, текст або URL) або завантажувати
через Files API й посилатися за `file_id`.

Зверніть увагу на різницю індексації: **символьні індекси починаються з 0, номери сторінок — з 1.**
Це класичне джерело помилок «на одиницю» при підсвічуванні цитат в інтерфейсі.

**Ціна цитат — і чому вона несподівано вигідна.** Документація описує це так:

- Увімкнення цитат дає **невелике зростання вхідних токенів** через доповнення системного промпту й
  поділ документів на фрагменти.
- Але **з вихідними токенами цитати дуже ефективні**. Внутрішньо модель виводить цитати в
  стандартизованому форматі, який потім розбирається на процитований текст і індекси розташування
  в документі. Поле **`cited_text` надається для зручності й не зараховується до вихідних токенів**.
- При передаванні в наступних ходах розмови **`cited_text` також не зараховується до вхідних
  токенів**.

Це означає, що цитати вигідніші, ніж здається: ви отримуєте процитований текст практично
безкоштовно, бо платите лише за компактні індекси.

**Практичний патерн:**

```python
# Документ подається як plain text із метаданими в context.
# ВАЖЛИВО: цитуватися буде лише вміст source, не title і не context.
document_block = {
    "type": "document",
    "source": {
        "type": "text",
        "media_type": "text/plain",
        "data": "Повний текст документа, з якого беруться цитати...",
    },
    "title": "Назва для людини",        # обмежений у довжині
    "context": '{"dept": "legal", "date": "2026-09-01", "rev": 3}',  # метадані
    "citations": {"enabled": True},     # увімкнути цитати
}

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": [
            document_block,
            {"type": "text", "text": "Які умови розірвання договору?"},
        ],
    }],
)
```

У відповіді текстові блоки міститимуть цитати з полем `cited_text` (процитований фрагмент) і
індексами розташування. Документація зазначає, що цитати підтримуються й у стрімінгу.

**Типові помилки**

- Покласти вміст, який треба цитувати, у `context` замість `source`. Він не буде процитований.
- Використовувати `title` для довгих метаданих. Поле обмежене в довжині — для метаданих є `context`.
- Плутати індексацію: символи з 0, сторінки з 1. Підсвічування «на одиницю» зсунуте.
- Рахувати цитати дорогими. Вони дорогі на вході (незначно) і дешеві на виході.
- Використовувати plain text для таблиць зі складною структурою. Для них документація радить
  тип custom content.

**Альтернативи.** Якщо вам потрібні цитати, але документ великий, комбінуйте: RAG-конвеєр відбирає
релевантні фрагменти (розділ 16), а цитати вказують на джерело вже всередині відібраного. Це дешевше
за передавання всього документа й дає перевірюваність. Для повної прозорості додавайте власні
ідентифікатори джерел у блоки й повертайте їх у відповіді — цитати дають місце в документі, а
ідентифікатор — посилання на документ у вашій системі.

### 7.4 Files API і життєвий цикл файлів

**Що це.** Сховище файлів на боці Anthropic: ви завантажуєте файл один раз і посилаєтеся на нього за
`file_id` у багатьох запитах, замість того щоб передавати вміст у кожному запиті.

**Навіщо це знати.** Це розв'язує дві проблеми одночасно: зменшує розмір запиту (важливо для PDF із
лімітом 32 МБ) і позбавляє від повторного передавання того самого вмісту.

**Як працює під капотом — модель безпеки.** Документація описує життєвий цикл файлів так, і кожен
пункт має практичні наслідки:

| Властивість | Наслідок для застосунку |
|---|---|
| Файли **обмежені робочим простором** (workspace), у якому завантажені | Будь-який запит у тому самому просторі може на них посилатися |
| **Ніколи не приймайте file ID із недовірених джерел** | Пряме попередження документації про доступ у межах простору |
| Файли **не можна змінювати чи перейменовувати** після завантаження | Щоб змінити вміст — завантажте новий і видаліть старий |
| Файли зберігаються, доки ви їх не видалите через `DELETE /v1/files/{file_id}`, або доки не настане `expires_at` | Потрібне власне керування життєвим циклом |
| **Видалені файли відновити неможливо** | Видалення — незворотна операція |
| Одразу після видалення файли недоступні через API, але можуть зберігатися в **активних** викликах Messages API та пов'язаних використаннях інструментів | Видалення не миттєве для вже запущених запитів |

**Обмеження сховища** (з документації):

| Обмеження | Значення |
|---|---|
| Максимальний розмір файлу | **500 МБ** на файл |
| Загальне сховище | **1 ТБ** на організацію |

**Найважливіше з цього розділу — рядок про недовірені джерела.** Документація прямо попереджає:
оскільки будь-який запит у тому самому робочому просторі може посилатися на файл, **ніколи не
приймайте file ID із недовірених джерел**.

Чому це критично: `file_id` — це фактично **можливість** (capability), а не просто ідентифікатор.
Якщо ваш застосунок приймає від користувача `file_id` і підставляє його в запит, користувач може
вказати ID файлу, завантаженого **іншим** користувачем у тому самому просторі, — і модель прочитає
його. Це не ескалація привілеїв у класичному сенсі, це прямий обхід контролю доступу.

Практичне правило: зберігайте відповідність «користувач → його file_id» у своїй базі й підставляйте
ID лише з неї. Ніколи не беріть `file_id` із тіла запиту клієнта.

**Типові помилки**

- Приймати `file_id` від клієнта. Це прямий обхід контролю доступу в межах робочого простору.
- Очікувати, що файл можна оновити. Оновлення немає — є нове завантаження плюс видалення старого.
- Не керувати терміном життя. Файли накопичуються до ліміту 1 ТБ на організацію.
- Вважати видалення миттєвим. Активні запити можуть ще використовувати файл.
- Передавати вміст замість `file_id` для великих PDF і впиратися в ліміт 32 МБ запиту.

**Альтернативи.** Якщо файли невеликі й використовуються одноразово, простіше передавати їх
безпосередньо в запиті — це не потребує керування життєвим циклом. Files API виправданий, коли файл
використовується **багаторазово** (тоді виграш і в розмірі запиту, і в можливості кешування) або
коли він завеликий для запиту.

### 7.5 Коли попередня обробка краща за пряму передачу

**Що це.** Рішення про те, чи віддавати документ моделі «як є», чи обробити його заздалегідь.

**Навіщо це знати.** Пряма передача найпростіша в реалізації й найдорожча в експлуатації. Для
великих обсягів попередня обробка зменшує рахунок у рази.

**Як ухвалювати рішення.** Ось зведення за типами задач:

| Задача | Пряма передача | Попередня обробка |
|---|---|---|
| Витягнути текст із PDF | Дорого: $0.02+ за сторінку (текст + зображення) | **Витягти текст парсером один раз** і надсилати текст |
| Питання про конкретні сторінки великого PDF | Дуже дорого: платите за всі сторінки | **Відібрати сторінки** — рахунок пропорційний |
| Розуміння графіків і діаграм | Пряма передача — єдиний спосіб | OCR не допоможе |
| Складні таблиці з макетами | Добре працює (модель бачить зображення) | Можливе витягування структури спеціалізованими парсерами |
| Той самий документ, багато питань | Пряма передача **з кешем** (розділ 9) | Індексація в RAG (розділ 16) |
| Тисячі документів щодня | Найгірший варіант: платите за кожен | **Обов'язково**: батч + витягування + RAG |

**Три конкретні важелі:**

1. **Витягування тексту замість зображень.** Для PDF, де потрібен лише текст, попереднє витягування
   прибирає витрати на зображення сторінок. З урахуванням того, що текстова складова — 1 500–3 000
   токенів на сторінку, а зображувальна додає ще стільки ж, це **приблизно двократна** економія.

2. **Відбір сторінок.** Питання про одну сторінку 500-сторінкового документа не має коштувати як
   весь документ. Спочатку визначте потрібні сторінки (метадані, зміст, пошук), потім надсилайте їх.

3. **Кешування для повторного аналізу.** Якщо документ аналізується повторно тим самим префіксом,
   кеш прибирає повторну оплату (розділ 9). Документація прямо радить кешування промпту як перший
   спосіб покращити ефективність PDF-обробки.

**Порядок діагностики витрат на документи:**

| Крок | Що перевірити |
|---|---|
| 1 | Чи потрібен вам увесь документ? Відберіть сторінки |
| 2 | Чи потрібне вам зображення сторінки, чи досить тексту? Витягніть текст |
| 3 | Чи аналізується документ повторно? Увімкніть кеш |
| 4 | Чи багато документів? Використайте батч-обробку (розділ 10) |
| 5 | Чи потрібна перевірюваність? Увімкніть цитати — `cited_text` не коштує вихідних токенів |
| 6 | Чи потрібна вибірка замість повного документа? Побудуйте RAG (розділ 16) |
| 7 | Чи можна зменшити зображення без втрати потрібних деталей? Зменште — ціна лінійна за площею |

**Типові помилки**

- Оптимізувати промпт, коли 90% рахунку — це документи. Спершу подивіться, що ви передаєте.
- Витягувати текст там, де потрібне розуміння зображення. Отримаєте неповну відповідь без помилки.
- Будувати RAG для одного документа. Для п'яти сторінок кеш простіший і дешевший.
- Не використовувати батч для масової обробки документів. Знижка 50% (розділ 10) тут найдоречніша.

**Альтернативи.** Для великого стабільного корпусу документів найефективніший шлях — **індексація
один раз, запити за потребою**: витягнути текст, порізати на фрагменти, побудувати векторний індекс
і надсилати моделі лише відібрані фрагменти (розділи 15 і 16). Це найдорожчий в реалізації шлях і
найдешевший в експлуатації.
